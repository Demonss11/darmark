### 1. Архитектурные принципы: Document / View / Pane

Текущая связка «файл ↔ редактор ↔ предпросмотр» должна быть заменена на три независимых слоя. Это фундамент, без которого плагины превратятся в хаос.

**Document** — данные файла: содержимое, история undo/redo, грязный флаг, путь. Не знает, как его отображают. Один на файл.

**View** — способ отображения документа. Editor, preview, outline, diff, inspector — всё это виды. На один Document может быть несколько View, каждый со своим состоянием (позиция курсора, скролл).

**Pane** — слот в layout. Содержит стек вкладок (как в VS Code), активный View, историю фокуса.

**Layout** — бинарное дерево разбиений (как i3/tmux). Пресеты «1/2/4 экрана» — это просто готовые структуры дерева, а не жёстко зашитые режимы. Пользователь может двигать разделители, перетаскивать панели, открывать один Document в двух Pane одновременно.

Как только это разделение появится:
- Preview становится обычным View, регистрируемым плагином.
- «Открыть рядом» — тривиальная операция создания нового Leaf в дереве.
- Sync-scroll — плагин, подписывающийся на события скролла двух View одного Document.
- Inspector — оверлей или отдельный View, работающий с парой других View.

### 2. Плагинная система: Wasmi + JSON-RPC over stdio

Для проекта, борющегося за каждый мегабайт, **Wasmi** (интерпретатор WASM) — правильный выбор. Он добавляет всего ~0.5–1 МБ к бинарнику против +5–10 МБ у Wasmtime, при этом остаётся полноценным WASM-рантаймом с песочницей.

#### 2.1. Сравнение рантаймов

| Рантайм | Размер (+к 3.6 МБ) | Скорость | Песочница | Cold start |
|---|---|---|---|---|
| **Wasmi** (интерпретатор) | ~0.5–1 МБ | В 5–10× медленнее JIT | Да | ~5 мс |
| Wasmtime (JIT) | +5–10 МБ | Эталонная | Да | 10–50 мс |
| mlua (LuaJIT) | ~0.3–0.5 МБ | Хорошая | Слабая | ~1 мс |
| Rhai | ~0.4–0.7 МБ | Средняя | Да | <1 мс |
| Нативные DLL | ~0 | Максимум | Нет | ~0.1 мс |

Wasmi v2.0 (вышел в сентябре 2026) примерно в 2.2 раза быстрее Wasmi 1.0 и обгоняет Wasmtime Pulley (интерпретаторный режим) в бенчмарках. Против JIT-компиляторов он в 5.3–10.7× медленнее на вычислительно тяжёлых задачах, но для плагинов, которые не занимаются рендерингом видео, этого достаточно.

#### 2.2. Почему не WIT / Component Model

Хотя WIT — стандарт Bytecode Alliance для типизированных интерфейсов, для MVP он создаёт лишнюю сложность. Как отмечает автор `wasmi-plugin-framework`: изменение сигнатуры функции в WIT — это **breaking change**, требующий версионирования всего интерфейса. Для простого хоста с JSON-RPC по stdio это оверкилл.

**Рекомендация**: начать с **JSON-RPC over stdio**. Хост и плагин общаются через stdin/stdout JSON-сообщениями, stderr — для логов. Это:
- Не требует ручного управления линейной памятью WASM.
- Работает на всех платформах (включая iOS).
- Даёт асинхронность «бесплатно».
- Позволяет плагинам быть stateless — состояние хранит хост.

Когда экосистема вырастет и понадобится строгая типизация — можно мигрировать на WIT.

#### 2.3. Структура крейтов

```
crates/
  md-core/          # Парсинг Markdown (уже есть)
  plugin-api/       # Общие типы для хоста и плагинов (Request, Response, Error)
  plugin-host/      # Wasmi-хост: загрузка, маршрутизация, permissions
  app/              # Tauri-шелл + фронтенд
```

`plugin-api` компилируется и в хост, и в плагины (как `wasm32-unknown-unknown`). В нём — только `serde`-структуры, никаких зависимостей на Wasmi или Tauri. Это позволяет разработчикам плагинов подключать лёгкий крейт и не тянуть editor целиком.

### 3. API плагинов: минимальный, но расширяемый

Начать стоит с 6–8 host-функций. Этого хватит для preview, inspector и sync-scroll.

**Document API** (хост → плагин, плагин → хост):
- `get_document_text(doc_id) -> String` — текущий текст.
- `get_document_version(doc_id) -> u64` — версия для кэширования.
- `apply_edit(doc_id, range, text)` — применить правку.

**View API**:
- `get_view_state(view_id) -> ViewState` — позиция курсора, скролл.
- `set_view_content(view_id, html)` — отрендерить HTML.
- `on_event(view_id, event)` — уведомить View о событии (фокус, скролл).

**Host API**:
- `log(level, message)` — логирование в stderr хоста.
- `show_message(text)` — уведомление пользователя.

**Событийная шина** — плагины подписываются на события хоста: `document:changed`, `view:scroll`, `view:focus`, `pane:resized`. Это делает sync-scroll и inspector тривиальными.

Важно: **никакого прямого доступа к файловой системе**. Если плагину нужно прочитать файл, он вызывает `host::read_file(path)`, и хост проверяет разрешение. Это соответствует capability-модели WASI: «модуль стартует без прав, получает только явно выданные».

### 4. Модель разрешений (Permissions)

По аналогии с Tauri ACL: по умолчанию **все команды заблокированы**, плагин должен декларировать, что ему нужно.

**Типы разрешений**:
- `document:read`, `document:write` — доступ к содержимому.
- `view:create`, `view:modify` — создание и изменение View.
- `filesystem:read` — чтение файлов (с scope: какие пути).
- `network` — сетевые запросы (по умолчанию запрещено).
- `ui:menu`, `ui:statusbar`, `ui:sidebar` — точки расширения UI.

Пользователь видит список разрешений при установке плагина и может отозвать их. Это критично для доверия к экосистеме.

### 5. Языки плагинов: стратегия двух уровней

**Уровень 1: WASM (Rust)** — основной. Плагины компилируются в `wasm32-unknown-unknown`, подключают `plugin-api` и общаются с хостом через JSON-RPC. Подходит для preview, inspector, сложной аналитики, LSP.

**Уровень 2: Rhai (позже)** — для простых скриптовых плагинов. Rhai — чистый Rust, без C-зависимостей, инициализируется за <1 мс, песочница по умолчанию. Подходит для «показать статистику документа», «отформатировать выделение», «экспортировать в PDF». Пользователь редактирует `.rhai` файл без пересборки.

**Почему не Lua**: `mlua` тянет C-зависимость (LuaJIT), что усложняет cross-compilation. Rhai проще встраивается и ближе к Rust по синтаксису.

**Почему не TS**: TypeScript-плагины имели бы доступ к DOM и UI, но лишались бы системных API и производительности. Для UI-расширений можно позже добавить **UI-плагины** (чистый TS/HTML, загружаемые в iframe или Web Component), но ядро системы — WASM/Rhai.

### 6. Тестирование плагинов

**Юнит-тесты**: плагин тестируется как обычный Rust-крейт. Host-функции мокаются через trait, в тестах подставляется `MockHost`. Это позволяет запускать `cargo test` без реального редактора.

**Интеграционные тесты**: `plugin-host` тестируется с реальным `.wasm` файлом. Загружаем простой плагин, вызываем методы, проверяем ответы. Это проверяет сериализацию JSON, маршрутизацию, обработку ошибок.

**E2E-тесты**: запускаем `darmark` в headless-режиме, загружаем тестовый плагин, эмулируем действия пользователя (открыть файл, нажать кнопку), проверяем DOM/состояние. У вас уже есть Cucumber + WebdriverIO — используйте их.

**Дифференциальные тесты**: если плагин делает то же, что встроенная функция (например, preview), сравнивайте результаты. Это ловит регрессии при рефакторинге.

**CI для плагинов**: предоставьте `darmark plugin test <path>` — команду, которая поднимает изолированный хост, загружает плагин и прогоняет его тесты. Разработчики плагинов смогут включить это в свой CI.

### 7. Управление размером бинарника

Базовая сборка (без плагинов) должна оставаться ~3.6–4 МБ. Это значит:

- Wasmi **всегда** в бинарнике (он лёгкий, ~0.5–1 МБ).
- Встроенные плагины (preview, inspector) компилируются в WASM и **вшиваются** в бинарник как ресурсы. Они не увеличивают размер Rust-кода, только добавляют байты `.wasm` файлов (по ~50–200 КБ каждый).
- Пользовательские плагины загружаются из `%APPDATA%/darmark/plugins/` и не входят в дистрибутив.
- Тяжёлые зависимости (например, парсер LaTeX) живут только в плагинах, а не в ядре.

### 8. Дорожная карта: от MVP к платформе

**Фаза 1: Рефакторинг Document/View/Pane (2–4 недели)**
Выделить `DocumentStore` в Rust и TS. Ввести `PaneId`, `DocumentId`, `ViewId`. Layout сделать деревом, но сначала поддержать только 1 и 2 панели. Preview пока остаётся встроенным, но вызывается через интерфейс `ViewProvider`. Это обкатает контракт без WASM.

**Фаза 2: Wasmi-хост и первый плагин (3–4 недели)**
Создать `plugin-host` и `plugin-api`. Реализовать JSON-RPC over stdio. Написать простейший плагин «Hello, darmark» на Rust/WASM. Загрузить его, вызвать, получить ответ. Убедиться, что всё работает.

**Фаза 3: Preview как плагин (2–3 недели)**
Перенести логику предпросмотра в WASM-плагин `md-preview`. Он получает текст документа, вызывает `md-core::to_html_mapped` (тоже скомпилированный в WASM), возвращает HTML. Хост рендерит его. Это докажет жизнеспособность архитектуры.

**Фаза 4: Разрешения и события (2–3 недели)**
Добавить модель разрешений. Реализовать событийную шину. Sync-scroll и inspector становятся плагинами, подписанными на события. Написать UI для управления плагинами (список, включение/отключение, разрешения).

**Фаза 5: Rhai-плагины (2 недели)**
Добавить `mlua` или `rhai` как второй рантайм. Простые плагины пишутся на Rhai, сложные — на WASM. Оба рантайма используют один и тот же `plugin-api` (через JSON-RPC).

**Фаза 6: Маркетплейс (4+ недели)**
Реестр плагинов на Git-репозитории с `index.json`. Подпись артефактов Ed25519 (как в `tauron`). Установка плагинов из UI редактора.

### 9. Подводные камни

**Фокус при нескольких панелях**: глобальный фокус → активная Pane → активный View. Без чёткой модели будет хаос с клавиатурными сокращениями.

**Производительность при 4 панелях**: если 4 preview одновременно рендерят Markdown, парсинг должен кэшироваться на уровне Document (по версии). Плагин `md-preview` запрашивает `get_document_version` и, если версия не изменилась, возвращает кэш.

**Stateless-плагины**: wasmi-plugin-framework делает плагины stateless — каждый вызов создаёт новый инстанс. Это упрощает изоляцию, но требует, чтобы хост хранил состояние. Для preview это идеально: плагин — чистая функция «текст → HTML».

**Обратная совместимость API**: как только `plugin-api` опубликован, его изменения болезненны. Используйте семантическое версионирование. Для JSON-RPC можно добавить поле `api_version` в каждый запрос и отклонять несовместимые.

**Отладка плагинов**: предоставьте режим `darmark --debug-plugin <path>`, который логирует все JSON-RPC сообщения. Без этого разработка плагинов превратится в боль.

Эта стратегия позволяет развивать `darmark` итеративно: каждая фаза даёт работающий результат, а не требует «большого взрыва». Начать стоит с рефакторинга Document/View/Pane — это самое важное и самое сложное. Всё остальное вырастет из него.
