## 2. Общая оценка

Направление выбрано верно и точно соответствует цели «лёгкий бинарник + функционал в плагины + база/адаптер
под плагины». Уровень проработки заметно выше среднего: двухтировый ViewProvider, ревизионный кэш рендера,
инвентаризация e2e-контрактов как «нельзя ломать», явные списки «НЕ делаем». Выбор wasmi обоснован и
фактически точен (wasmi 2.0.0 реально вышел 01.09.2026; crate ~300 КБ исходников; существует
Wasmi Plugin Framework / `wasmi-plugin-rt`).

Главные проблемы не в направлении, а в:
1. **Стыках между двумя планами** (Pane с вкладками vs без; undo в Rust vs нативный undo textarea; preview
   как wasm-плагин vs рендер на хосте).
2. **Честной арифметике размера** (встроенные wasm-плагины НЕ уменьшают бинарник — они его увеличат).
3. **Пробелах, без которых DESIGN_DOC не написать**: спецификация манифеста плагина, события→плагин и
   обратная маршрутизация DOM-событий, лимиты ресурсов плагина, политика санитайзера по SVG/`data-*`,
   жизненный цикл плагинов, настройки/персистентность, CI и бюджет размера.
4. **Рассинхроне с активной задачей** `TZ-excel-tables.md` — ни один документ ideas/ её не упоминает,
   хотя фазы 4–5 рефакторинга перекраивают ровно тот код (`tables.ts`), который эта задача сейчас дорабатывает.

## 3. Сильные стороны (сохранить и перенести в будущие CONCEPT/VISION/DESIGN_DOC)

1. **Двухтировый ViewProvider — центральная удачная идея.** Тир 1 (`HtmlViewProvider`: только JSON на входе,
   HTML-строка на выходе, `dispose()`) — это ровно тот контракт, который сможет выполнить wasmi-плагин;
   тир 2 (`DomViewProvider`) — для встроенных view с полным DOM (редактор, таблицы, инспектор). Контракт
   обкатывается сегодня без WASM, завтра миграция = замена транспорта, а не перераздел ответственности.
2. **Владение состоянием: текст/rev/кэш — в Rust `DocumentStore`; dirty/selection/scroll/layout — в TS.**
   Обоснование точное: плагин никогда не увидит DOM, единственный общий знаменатель для контента — Rust-ядро;
   TS-стор — проекция, а не второй источник истины. Это же фундамент для «плагины говорят с ядром, а не с UI».
3. **Команды Tauri спроектированы 1:1 к будущим JSON-RPC-методам** (`update_document`, `render_document`,
   `close_document`…) — рефакторинг не придётся переделывать под плагины.
4. **Фазовый план с гейтами**: каждая фаза — работающее приложение + проверяемый гейт (cargo test / build /
   e2e-сценарии). Оценка дельт строк (+220/−60 и т.п.) полезна для ревью. «Большого взрыва» нет.
5. **Инвентаризация e2e-контрактов** (id, классы, 120 мс debounce, ECHO_MS=100, стартовый текст,
   `window.__errors`) как замороженного API — редкая дисциплина; решение «id остаются на элементах первичной
   панели + новые data-pane/data-view» — правильный приём совместимости.
6. **Ревизионная корректность**: `RenderIndex` несёт `rev`, inspector/scrollsync отбрасывают индекс при
   несовпадении rev; кэш рендера ключуется (mapped, rev) на Rust-стороне; `changed:false` при том же rev.
   Это закрывает класс гонок, который в текущем `main.ts` латается `renderSeq`/`lastRenderedHtml`.
7. **Permissions-модель** по образцу Tauri ACL (всё запрещено по умолчанию, декларация в манифесте,
   показ пользователю при установке, отзыв) — согласуется с философией проекта и даёт доверие к экосистеме.
8. **Стратегия тестирования плагинов** (MockHost-юниты, интеграция с реальным .wasm, e2e через существующий
   Cucumber-стенд, дифференциальные тесты «плагин vs встроенная функция», `darmark plugin test`,
   `--debug-plugin`) — полноценный DX, о котором большинство планов забывает.
9. **Отказ от WIT/Component Model для MVP** в пользу JSON-конверта — прагматично (breaking-change-цена WIT
   на старте API реальна); отказ от Lua в пользу Rhai (чистый Rust, без C-зависимостей) — тоже.
10. **Раздел «Подводные камни»** (фокус при N панелях, кэш рендера по версиям, stateless-инстансы,
    семвер plugin-api, отладка) — правильно названные места, где обычно ломаются такие системы.

## 4. Противоречия между документами (разрешить до DESIGN_DOC)

### 4.1. Preview: wasm-плагин или встроенный view на хосте? ⚠️ главное архитектурное решение
- `БАЗОВЫЙ_ПЛАН` фаза 3: preview становится WASM-плагином `md-preview` с md-core, скомпилированным в wasm;
  встроенные плагины «вшиваются в бинарник».
- `ОПИСАНИЕ_ПЛАН`: `update_document`/`render_document` — команды хоста, рендер остаётся в Rust-шелле;
  PreviewView — тир-1 провайдер **на хосте**.
- Проблема фазы 3: (а) самый горячий путь (каждый дебаунс нажатия) уходит в интерпретируемый WASM
  (wasmi в 5–10× медленнее JIT по собственным данным плана); (б) md-core придётся поддерживать в двух
  ипостасях — native (санитайзер на хосте нужен в любом случае) и wasm; (в) бинарник **вырастет**
  (wasmi + wasm-блобы), а не похудеет.
- **Рекомендация**: встроенный preview оставить на хосте за тир-1 контрактом (это и есть «обкатка»).
  Плагинную систему доказывать на **холодных** плагинах (статистика документа, экспорт, mermaid,
  word-count в статусбаре). Миграцию preview в wasm — делать только за бенч-гейтом
  (например, рендер 500 КБ документа ≤ +20% к native) и рассматривать как опциональный dogfooding,
  а не как обязательную фазу. Перед решением — замерный спайк (1–2 дня): собрать md-core под
  wasm32-unknown-unknown, померить реальный размер .wasm и скорость рендера в wasmi. Заявленные
  «50–200 КБ на плагин» для md-core+pulldown-cmark оптимистичны — скорее 300–700 КБ; это надо измерить,
  а не предполагать.

### 4.2. Pane: стек вкладок или один view?
- `БАЗОВЫЙ_ПЛАН` §1: Pane «содержит стек вкладок (как в VS Code)».
- `ОПИСАНИЕ_ПЛАН`: `Pane = { doc, view }`, вкладки — в «сознательно НЕ делаем», MAX_PANES=2.
- Фазирование нормальное, но **модель данных надо заложить сейчас**: `Pane = { views: ViewId[], active }`
  даже если в v1 всегда `views.length === 1`. Иначе дерево layout и все e2e-контракты придётся
  перекраивать второй раз при появлении вкладок.

### 4.3. Undo/redo: кто владеет?
- `БАЗОВЫЙ_ПЛАН` §1: Document содержит «историю undo/redo» (т.е. Rust).
- `ОПИСАНИЕ_ПЛАН` (риски): нативный undo textarea сохраняется, свой undo-стек — «отдельная задача».
- Конфликт станет острым, как только появится плагинный `apply_edit(doc_id, range, text)`: правка плагина
  обязана попадать в undo-историю, иначе первые же плагины-форматтеры сломают базовое ожидание пользователя.
- **Рекомендация**: признать Document (Rust) владельцем текста **и** undo-стека уже на уровне концепции;
  в v1 можно жить с нативным undo textarea как «временной аномалией», но в DESIGN_DOC зафиксировать
  целевую модель: операции `{rev, range, text}` (кстати, тот же формат, что diff-пayload события
  document:changed и apply_edit плагинов — одна структура на три用途).

### 4.4. Транспорт: «JSON-RPC over stdio» в wasmi буквально невозможен
- `БАЗОВЫЙ_ПЛАН` §2.2 описывает общение «через stdin/stdout» — но у `wasm32-unknown-unknown` нет stdio
  (WASI по умолчанию нет). Реальный транспорт in-process WASM — host-функции импорта, читающие/пишущие
  линейную память (именно так устроен упомянутый в плане wasmi-plugin-framework).
- «Асинхронность бесплатно» — преувеличение: wasmi синхронен; асинхронность достигается воркер-тредом +
  каналами, а таймауты — fuel-метрингом (в wasmi есть) или ручной yields-проверкой.
- **Рекомендация**: в DESIGN_DOC разделить **протокол** (JSON-RPC-конверт, единый для всех) и
  **транспорты**: (1) in-process wasmi через host-функции — основной; (2) внешний процесс по настоящему
  stdio — только режим разработчика/доверенные плагины (публиковать установку сторонних нативных exe
  через маркетплейс нельзя — это разрушит модель безопасности).

### 4.5. Мелочи
- §5 «Почему не Lua: mlua тянет C-зависимость» против фазы 5 «Добавить mlua или rhai» — оставить только Rhai.
- `БАЗОВЫЙ_ПЛАН` §7: «базовая сборка должна оставаться ~3.6–4 МБ» и там же «Wasmi всегда в бинарнике
  (~0.5–1 МБ) + вшитые .wasm по 50–200 КБ» — арифметика не сходится с собственным лимитом. Бюджет надо
  пересчитать честно (см. §7 этого ревью).
- Нейминг: продукт/идентификатор/окно — `mdedit` (`dev.mdedit.app`), а план оперирует `darmark`
  (`darmark plugin test`, `%APPDATA%/darmark/plugins`). **Решить до CONCEPT**: смена identifier,
  appdata-каталога и имени установщика после релизов — болезненная миграция.

## 5. Технические пробелы (без них DESIGN_DOC неполон)

### 5.1. Санитайзер блокирует классы плагинов — проверить и решить
Факты из кода (`md-core/src/lib.rs`): `DROP_CONTENT_TAGS` включает **`svg`** (вырезается вместе с
содержимым), `GLOBAL_ATTRS = class/id/title/lang/dir/role` — **все `data-*` срезаются** (mapped-конвейер
инжектит `data-md` строго после санитайзера, см. L63, L150).
Следствия для плагинов:
- Диаграммные/chart-плагины (mermaid и т.п.) с SVG-выводом **невозможны** при текущем санитайзере.
- Интерактивный HTML плагина (клики по элементам) требует стабильных атрибутов для маршрутизации событий
  обратно в плагин — `data-*` сейчас не выживают.
**Решения для DESIGN_DOC**: (а) единая точка санитизации — хост санитизирует любой HTML, входящий в webview
(плагинная санитизация — опциональная избыточность); (б) политика по SVG: либо allowlist-подмножество
(как DOMPurify), либо растровый fallback (`<img src="data:image/png…">` — CSP уже разрешает `img-src data:`);
(в) разрешить `data-*` c плагиновым префиксом (например `data-p-<pluginid>-*`) **после** санитайзера —
тем же приёмом, каким инжектится `data-md`.

### 5.2. Обратная маршрутизация событий в тир-1 view не специфицирована
В API-наброске есть `on_event(view_id, event)`, но не описано, как клики/изменения внутри HTML плагина
попадают обратно: делегированный слушатель хоста на контейнере view → сериализация
`{type, target: data-атрибуты, позиция}` → плагин → патч/новый HTML. Это надо зафиксировать вместе с 5.1(в).

### 5.3. Лимиты ресурсов и отказоустойчивость плагинов — отсутствует entirely
Нужно: fuel-метринг или таймаут запроса (бесконечный цикл в плагине не должен вешать приложение);
лимит линейной памяти (Store limiter, например 64–128 МБ на плагин); обработка trap → «плагин упал,
отключён, ошибка видна пользователю», а не crash приложения; карантин/автоотключение после N падений.

### 5.4. Модель событий и backpressure
Событийная шина набросана (`document:changed`, `view:scroll`, …), но не определены: доставка
«notify-only + pull» (событие несёт `doc_id, rev`, текст плагин тянет сам через `get_document_text` —
иначе при быстром наборе N плагинов получат N полных текстов до 10 МБ); коалесинг событий по rev;
порядок доставки и отписка при `dispose()`; адресация view-событий.

### 5.5. Жизненный цикл инстансов плагинов
§9 «Подводные камни» говорит про stateless-инстансы (каждый вызов — новый), но API (`on_event(view_id)`,
подписки) подразумевает долгоживущее состояние. Развести явно: **плагин = код** (манифест + wasm),
**инстанс = привязка к view/подписке** с собственным слотом состояния, который хранит хост.
Для preview-подобных чистых функций stateless ок, для sync-scroll/inspector — нет.

### 5.6. Манифест плагина и точки расширения — не описаны
Минимально нужно: `id, name, version, api_version, entry (.wasm), permissions[], contributes{views[],
commands[], toolbar[], statusbar[], settings-schema, keybindings}`. Permissions в плане есть,
contribution points упомянуты одной строкой (`ui:menu/statusbar/sidebar`) — для DESIGN_DOC это
полноценный раздел (реестр вкладов, как их рендерит хост, как плагин узнаёт о вызове команды).

### 5.7. Настройки, состояние окна, recent files
Нигде не упомянуты: где живёт конфигурация приложения (разумно: Rust-side store + JSON в appdata),
как плагины читают/пишут свои настройки (settings-schema в манифесте + host-API `get/set_setting`),
восстановление layout/открытых документов между сессиями. Это всплывёт сразу после появления
DocumentStore и 2 панелей.

### 5.8. Редактор и его отношение к плагинам
Roadmap README обещает подсветку синтаксиса (CodeMirror 6 или свой overlay), но ideas/ молчат о том,
чем является редактор в плагинной архитектуре: тир-2 встроенный view — очевидно; а вот **расширяемость
редактирования плагинами** (форматтеры, линтеры, сниппеты через `apply_edit`) — не описана. Плюс
CodeMirror — это +сотни КБ во встроенный фронтенд (т.е. в exe) и собственная extension-модель,
конкурирующая с плагинной. Решение «textarea ещё на N фаз / CodeMirror потом / своё» должно быть ADR.

### 5.9. CI и бюджет размера — отсутствуют полностью
`.github/` нет; фронтенд-юнит-тестов нет (TZ-excel-tables AC-20 уже требует `npm run test` + CI — тоже
не создано). Для проекта, где размер бинарника — продуктовая метрика, а plugin-api — публичный контракт:
CI (cargo test + tsc/build + e2e-смоук) и **size-gate** (проверка размера exe/установщика в каждом PR,
например порог «base ≤ X МБ, +warning на рост > N КБ») — обязательны. Без size-gate «лёгкий бинарник»
ержится только на дисциплине, а плагины начнут его разъедать незаметно.

### 5.10. Синхронизация с активной задачей TZ-excel-tables ⚠️ организационный риск
`tasks/TZ-excel-tables.md` (v1.0, активна; последние коммиты «доработка таблиц», «подготовка к правкам
визуализации») перекраивает `tables.ts`: стабильный ключ таблицы, sessionStorage-персистентность,
точечный diff вместо innerHTML, `tables-core.ts` + юнит-тесты, мультисортировка, предикатные фильтры, i18n.
Фазы 4–5 `ОПИСАНИЕ_ПЛАН` перемещают `enhanceTables` внутрь previewView и переводят tables.ts на
экземпляр-контроллеры. Это **одна и та же территория**, но документы друг друга не упоминают.
Более того — рефакторинг даёт таблицам то, что им нужно: OQ-1/OQ-2 TZ-excel-tables (ключ таблицы,
неймспейс хранилища при вкладках) естественно решаются через `docId + rev` из DocumentStore.
**Рекомендация**: явно состыковать последовательность — либо заморозить/завершить P0-P1 таблиц до старта
Document/View/Pane, либо встроить требования TZ-excel-tables (стабильный ключ, персистентность) в фазы 3–5
рефакторинга как часть контракта. Иначе две параллельные перестройки `tables.ts` гарантированно конфликтуют.

### 5.11. Дифференциальные тесты preview — поддержать и усилить
Идея §6 (сравнивать вывод плагина со встроенной функцией) — правильная; добавить: прогон корпусов
CommonMark/GFM spec через harness (уже в roadmap README) как общий фундамент и для native, и для wasm-сборки
md-core — это же ловит расхождения «native vs wasm» до миграции.

1. `ОПИСАНИЕ_BACK.md` §0 утверждает: «`tasks/**` → нет каталога», «TZ-*.md → нет файлов»,

   на которые план рефакторинга не ссылается.
2. Мелкий дрейф строковых счётчиков: `main.ts` в аудите 318 строк, в HEAD 325 (коммиты «доработка таблиц»

5. `БАЗОВЫЙ_ПЛАН` §2.2 «JSON-RPC over stdio» для wasm32-unknown-unknown — технически некорректная

## 7. «Лёгкий бинарник» и плагины: честная арифметика

Текущий ориентир: ~3.6 МБ exe. Что реально произойдёт при выполнении БАЗОВОГО_ПЛАНА:

| Статья | Эффект |
|---|---|
| wasmi 2.x в хосте | **+0.5–1 МБ** (оценка плана; проверить замером) |
| Вшитые wasm-плагины (preview 50–200 КБ каждый — оптимистично; md-core+wasm скорее 300–700 КБ) | **+0.3–1.5 МБ** |
| Дублирование md-core (native для санитайзера + wasm в плагине) | +wasm-копия |
| JSON-RPC-слой, permissions, менеджер плагинов (Rust + TS UI) | +100–300 КБ |
| Вынос тяжёлого (LaTeX, PDF, mermaid) в скачиваемые плагины | **экономия только относительно гипотетического «всё в exe»** |

Вывод, который надо честно записать в CONCEPT: **плагинная система не уменьшает базовый бинарник — она
ограничивает его будущий рост** и изолирует сторонний код. База вырастет примерно до 4.5–5.5 МБ
(оценка, требует замер-спайка). Легковесность как продуктовая метрика формулируется так:
- жёсткий бюджет базы (например «exe ≤ 6 МБ, установщик ≤ 8 МБ») + size-gate в CI;
- любая тяжёлая фича по умолчанию вне базы (только скачиваемый плагин);
- бюджет на каждый встроенный wasm-плагин (например ≤ 300 КБ);
- сравнение с альтернативой (Electron-редакторы 150–300 МБ) — это и есть ценностное предложение.

Если цель «остаться ~3.6 МБ» важнее dogfooding — отказ от фазы 3 (preview как wasm) и встроенных
wasm-плагинов вообще даёт экономию ~1–2 МБ: wasmi + менеджер плагинов остаются, но экосистемные плагины
ставятся пользователем, а в базе нет ни одного .wasm. Это валидный вариант концепции
(«нулевая база, всё опционально»), его стоит явно рассмотреть как ADR.

## 8. Куда должен идти проект — рекомендуемый каркас

### Продуктовый стержень (для CONCEPT)
«Лёгкая верстак-платформа для Markdown»: ядро = документы + layout + безопасный рендер + плагин-хост;
всё остальное — плагины. Ценности: размер как фича (анти-Electron), безопасность (sandbox + явные
permissions), скорость старта и отклика, расширяемость без форков. Не-цели v1: вкладки-в-UI, мобильные
платформы, совместное редактирование, собственный редакторский движок.

### Горизонты (для VISION)
- **H1 (сейчас, 1–2 месяца)**: Document/View/Pane по `ОПИСАНИЕ_ПЛАН` (фазы 1–6) + состыковка с
  TZ-excel-tables + CI и size-gate. Плагинного кода ещё нет, но контракты (тир-1) обкатаны.
- **H2**: `plugin-api` + `plugin-host` (wasmi, JSON-конверт, host-функции), hello-плагин, первые
  холодные плагины (статусбар-word-count, экспорт HTML/PDF, mermaid после решения по SVG), permissions UI,
  менеджер плагинов, событийная шина. Sync-scroll и inspector — кандидаты в плагины (подписки на события).
- **H3**: Rhai-тир для скриптов, реестр плагинов (git + index.json + Ed25519), template-репозиторий,
  `darmark plugin test`, документация для авторов. Опционально: миграция preview в wasm за бенч-гейтом.

### Слои контрактов (для DESIGN_DOC)
1. **Rust-ядро**: md-core (чистое) → DocumentStore/ошибки/команды (src-tauri) → plugin-host (wasmi,
   лимиты, permissions, шина) → plugin-api (общие serde-типы, компилируется и в хост, и в wasm).
2. **TS-оболочка**: layout-дерево, PaneHost, viewRegistry, тир-1/тир-2 провайдеры, ViewContext-фасад.
3. **Протокол**: JSON-RPC-конверт + api_version; транспорт 1 — host-функции wasmi; транспорт 2 (dev) —
   stdio внешнего процесса. События — notify+pull (rev), данные — по запросу.

### ADR-список (решения, которые надо принять ПЕРЕД написанием трёх документов)
1. Имя продукта: mdedit vs darmark (identifier, appdata, CLI, домен дока).
2. Preview: встроенный тир-1 на хосте (рекомендуется) vs wasm-плагин (только за бенч-гейтом).
3. База «нулевая» (ни одного встроенного wasm) vs «встроенные плагины вшиты» (бюджет ≤300 КБ/шт).
4. Панель: модель данных сразу под вкладки (`views[] + active`), даже если UI v1 одно-вью (рекомендуется).
5. Undo: целевой владелец — Rust Document (текст + операции `{rev, range, text}`); textarea-undo — временное.
6. Редактор: остаётся textarea до H2; CodeMirror — отдельный ADR с size-анализом; расширяемость
   редактирования плагинами (apply_edit + команды) — часть plugin-api.
7. Санитайзер: единая точка на хосте; политика SVG (allowlist-подмножество vs raster-fallback);
   `data-p-*` переживают санитизацию.
8. Транспорт: host-функции — основной; stdio — только dev-режим доверенных плагинов.
9. Лимиты: fuel/таймаут, память ≤64–128 МБ, карантин после N trap.
10. События: notify+pull, коалесинг по rev, backpressure.
11. Настройки: Rust-store + JSON в appdata; settings-schema плагинов; восстановление layout/документов.
12. Размер: бюджет базы ≤6 МБ (уточнить замером) + size-gate в CI (CI — создать, его нет).
13. Последовательность с TZ-excel-tables: завершить/заморозить P0-P1 или слить стабильный ключ
    и персистентность в фазы 3–5 рефакторинга на базе docId/rev (рекомендуется второе).
14. Языки экосистемы: UI/доки приложения — ru; plugin-api доки и манифесты — en (или ru+en) — решить.
15. Платформы: Windows — продукт; Linux — dev; мобильные — вне vision (или явно «когда-нибудь»).

## 9. Предлагаемая структура документации (следующий шаг, когда скажешь «пишем»)

```
docs/
  CONCEPT.md        # что за продукт, ценности, границы, не-цели, бюджет размера как метрика
  VISION.md         # горизонты H1–H3, образ экосистемы, метрики успеха (размер, скорость, # плагинов)
  DESIGN_DOC.md     # слои, контракты, протокол, permissions, события, лимиты, lifecycle, DX
  adr/              # 15 решений из §8 — по одному ADR на каждое (контекст/варианты/решение/следствия)
ideas/              # оставить как историю; аудиты помечаются «as of a76acc4» и после старта уходят в архив
tasks/              # TZ-doc-view-pane-v1.md (фаза 0 плана) — уже предусмотрен ОПИСАНИЕ_ПЛАН
```

CONCEPT отвечает на «зачем/что», VISION — «куда за 3 горизонта», DESIGN_DOC — «как устроены контракты»;
ADR — единственное место, где живут спорные решения, чтобы идеи-документы не переписывались задним числом.
