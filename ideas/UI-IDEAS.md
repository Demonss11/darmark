# UI-IDEAS — бэклог идей интерфейса

> **Статус:** non-normative, живой бэклог. Нормативная спецификация — `docs/DESIGN_DOC.md` (+ ADR в `docs/adr/`).
> **Как идея продвигается:** идея → research/спайк (`crates/*-spike`, замеры в `docs/proto/FINDINGS.md`) → ADR + `DESIGN_DOC` → TZ (`tasks/`) → код.
> Принятое решение **уходит** отсюда в `DESIGN_DOC`/ADR; в этом файле остаётся ссылка и статус. Описание реализованного UI — `ideas/UI_CONCEPT.md`.

## Статусы

- `идея` — сырое, не оценено;
- `research` — нужен спайк/замер;
- `adr` — нужно архитектурное решение;
- `tz` — готово к реализации (есть/нужен ТЗ);
- `done` — реализовано (ссылка на TZ);
- `dropped` — отклонено (кратко почему).

## Бэклог

### IDEA-001 — Панель меню (Файл, Вид, Помощь…)

- **Статус:** идея
- **Зачем:** разгрузить icon-toolbar и дать привычную навигацию/discoverability; задел под пункты меню от плагинов (H2).
- **Суть:** полоса меню (`Файл · Правка? · Вид · Формат? · Плагины (H2) · Помощь`) с выпадающими списками; часть функционала перенести из тулбара (файловые команды, тумблеры панелей/синхронизации), самые частые действия оставить в тулбаре.
- **Затрагивает:** `DESIGN_DOC` §5 (UI-слой); §13.2 — id `btn-new/open/save/save-as`, `toggle-sync/preview` должны выжить (кнопки могут стать пунктами меню, но контракт e2e обязан остаться рабочим).
- **Артефакты:** возможно ADR (модель меню + нативное/HTML), затем TZ (`tasks/TZ-UI-menu.md`).
- **Открытые вопросы:**
  1. Нативное меню Tauri (`Menu`/`MenuItem`) vs HTML-меню в DOM. Нативное — вне DOM, e2e по id не кликается (помечать `@manual`), но привычнее для Windows; HTML-меню остаётся под e2e и CSP `'self'`.
  2. Что именно уходит из тулбара, что остаётся.
  3. Акселераторы и дублирование с уже существующими хоткеями.
- **Критерий успеха:** файл-команды и тумблеры доступны из меню; все e2e-контракты §13.2 зелёные.

### IDEA-002 — Разделение Host / Engine (универсальный редактор)

- **Статус:** research (спайки) → adr
- **Зачем:** продуктовый pivot — от «Markdown-редактора» к универсальному редактору с подключаемыми движками. Host работает с файлом, **не зная**, что это Markdown.
- **Суть:**
  - **Host** — оболочка/окно/файлы/UI: открывает файл, отдаёт текст движку, получает «данные для отрисовки».
  - **Engine** — абстракция `text → данные отрисовки`; реализации: встроенный `md-core`, WASM-движок, внешний процесс (IPC), движок плагина.
  - Целевая проверка: можно ли превратить md-редактор в универсальный редактор с системой **Engine + WASM + IPC + Плагины**.
- **Затрагивает:** `DESIGN_DOC` §2 (слои), §3 (контракт ядра), §5.3/§5.4 (тир-1 ViewProvider как «движок-представление»), §6–§12 (плагины), §13.2 (id/селекторы), §14 (бюджет). **Нужен отдельный ADR.**
- **Артефакты:**
  - спайки: `crates/*-spike` + замеры в `docs/proto/FINDINGS.md` (латентность IPC, размер/запуск WASM, стоимость сериализации render-data);
  - ADR с границей Host/Engine и формальным контрактом;
  - обновление `DESIGN_DOC` §2/§3.
- **Открытые вопросы (гипотезы для спайков):**
  1. Что именно отдаёт Engine: HTML (как сейчас `preview.innerHTML`) или структурные данные (AST/токены/патч)? Инкрементальность?
  2. Выдержит ли дебаунс рендера 120 мс (§13.2) проход через WASM/IPC?
  3. Где живёт mapping байты↔UTF-16 и `data-md` — в Engine или Host? Инспектор/scrollsync завязаны на это.
  4. WASM: движок (Rust→`wasm32`), размер, бюджет §14 (GUI ≤ 6 МБ).
  5. Плагины H2 и «плагины-движки» — общий механизм или разные?
  6. Совместимость: `md-core` остаётся эталонным Engine.
- **Критерий успеха спайка:** Host, не знающий про Markdown, отображает Markdown через Engine-абстракцию; замеры IPC/WASM приемлемы; замороженные e2e §13.2 не сломаны (либо есть явный план их миграции).
