# UI-IDEAS — бэклог идей интерфейса

> **Статус:** non-normative, живой бэклог. Нормативная спецификация — `docs/DESIGN_DOC.md` (+ ADR в `docs/adr/`).
> **Как идея продвигается:** идея → research/спайк (`crates/*-spike`, замеры в `docs/proto/FINDINGS.md`) → ADR + `DESIGN_DOC` → TZ (`tasks/`) → код.
> Принятое решение **уходит** отсюда в `DESIGN_DOC`/ADR; в этом файле остаётся ссылка и статус. Описание реализованного UI — `ideas/UI_CONCEPT.md`.

## Статусы

- `идея` — сырое, не оценено;
- `research` — нужен спайк/замер;
- `adr` — нужно архитектурное решение;
- `tz` — готово к реализации (есть/нужен ТЗ);
- `done` — реализовано (ссылка на TZ);
- `dropped` — отклонено (кратко почему).

## Шаблон идеи

```
### IDEA-NNN — <название>
- **Статус:** идея | research | adr | tz | done | dropped
- **Зачем:** <продуктовая ценность>
- **Суть:** <что делаем>
- **Затрагивает:** DESIGN_DOC §…, ADR-…, замороженные контракты §13.2 (да/нет)
- **Артефакты:** спайк / ADR / TZ
- **Открытые вопросы:** …
- **Критерий успеха:** …
```

## Бэклог

### IDEA-001 — Панель меню (Файл, Вид, Помощь…)

- **Статус:** идея
- **Зачем:** разгрузить icon-toolbar и дать привычную навигацию/discoverability; задел под пункты меню от плагинов (H2).
- **Суть:** полоса меню (`Файл · Правка? · Вид · Формат? · Плагины (H2) · Помощь`) с выпадающими списками; часть функционала перенести из тулбара (файловые команды, тумблеры панелей/синхронизации), самые частые действия оставить в тулбаре.
- **Затрагивает:** `DESIGN_DOC` §5 (UI-слой); §13.2 — id `btn-new/open/save/save-as`, `toggle-sync/preview` должны выжить (кнопки могут стать пунктами меню, но контракт e2e обязан остаться рабочим).
- **Артефакты:** возможно ADR (модель меню + нативное/HTML), затем TZ (`tasks/TZ-UI-menu.md`).
- **Открытые вопросы:**
  1. Нативное меню Tauri (`Menu`/`MenuItem`) vs HTML-меню в DOM. Нативное — вне DOM, e2e по id не кликается (помечать `@manual`), но привычнее для Windows; HTML-меню остаётся под e2e и CSP `'self'`.
  2. Что именно уходит из тулбара, что остаётся.
  3. Акселераторы и дублирование с уже существующими хоткеями.
- **Критерий успеха:** файл-команды и тумблеры доступны из меню; все e2e-контракты §13.2 зелёные.

### IDEA-002 — Разделение Host / Engine (универсальный редактор)

- **Статус:** research (спайки) → adr
- **Зачем:** продуктовый pivot — от «Markdown-редактора» к универсальному редактору с подключаемыми движками. Host работает с файлом, **не зная**, что это Markdown.
- **Суть:**
  - **Host** — оболочка/окно/файлы/UI: открывает файл, отдаёт текст движку, получает «данные для отрисовки».
  - **Engine** — абстракция `text → данные отрисовки`; реализации: встроенный `md-core`, WASM-движок, внешний процесс (IPC), движок плагина.
  - Целевая проверка: можно ли превратить md-редактор в универсальный редактор с системой **Engine + WASM + IPC + Плагины**.
- **Затрагивает:** `DESIGN_DOC` §2 (слои), §3 (контракт ядра), §5.3/§5.4 (тир-1 ViewProvider как «движок-представление»), §6–§12 (плагины), §13.2 (id/селекторы), §14 (бюджет). **Нужен отдельный ADR.**
- **Артефакты:**
  - спайки: `crates/*-spike` + замеры в `docs/proto/FINDINGS.md` (латентность IPC, размер/запуск WASM, стоимость сериализации render-data);
  - ADR с границей Host/Engine и формальным контрактом;
  - обновление `DESIGN_DOC` §2/§3.
- **Открытые вопросы (гипотезы для спайков):**
  1. Что именно отдаёт Engine: HTML (как сейчас `preview.innerHTML`) или структурные данные (AST/токены/патч)? Инкрементальность?
  2. Выдержит ли дебаунс рендера 120 мс (§13.2) проход через WASM/IPC?
  3. Где живёт mapping байты↔UTF-16 и `data-md` — в Engine или Host? Инспектор/scrollsync завязаны на это.
  4. WASM: движок (Rust→`wasm32`), размер, бюджет §14 (GUI ≤ 6 МБ).
  5. Плагины H2 и «плагины-движки» — общий механизм или разные?
  6. Совместимость: `md-core` остаётся эталонным Engine.
- **Критерий успеха спайка:** Host, не знающий про Markdown, отображает Markdown через Engine-абстракцию; замеры IPC/WASM приемлемы; замороженные e2e §13.2 не сломаны (либо есть явный план их миграции).

### IDEA-003 — Пользовательские превью через плагинные view-провайдеры

- **Статус:** done (ядро реализовано в H2) → research (латентность/уточнение ADR)
- **Зачем:** дать пользователю создавать **свои представления/превью** на Lua (свой рендер, статистика,
  альтернативная разметка), не переписывая UI приложения. Lua **не заменяет** UI, а поставляет
  провайдеры представлений; нативные редактор/инспектор/панели остаются на хосте.
- **Суть:** плагин объявляет `contributes.views[{kind,title,tier:1}]` (permissions `view:create`/
  `view:modify`) и становится ещё одним `HtmlViewProvider` в `viewRegistry.ts`. Пользователь выбирает
  вид в панели (`pane-head`/`view-switch`); нативный Markdown-предпросмотр остаётся **дефолтным**
  провайдером. Протокол: хост шлёт `document:changed{doc_id,rev}` (notify-only), плагин тянет окно
  `get_document_range`, строит HTML и зовёт `host.set_view_content(view_id, html)`; хост санитизирует
  публичным входом `md-core` (`data-p-*` allowlist) и вставляет в контейнер. Клики — `data-p-<id>-action`
  → хендлер плагина. Это логика **H2 (фазы 4/5)**; TZ при этом **не меняем**.
- **Уточнение нормы (важно):** ADR-0022 §5/D2 отклонял «preview как плагин» как **обязательный горячий
  путь** (каждый debounce через интерпретатор). Это не запрет на *пользовательский* preview: любой
  тир-1 провайдер (встроенный **или** плагинный) может быть помещён в панель по явному выбору
  пользователя — тогда цена IPC — осознанное решение. Формулировку ADR-0022/§5.3 нужно уточнить.
- **Реализация (H2, Фаза 4):** ядро сделано. Каждое плагинное view регистрируется как настоящий
  `HtmlViewProvider` в `viewRegistry.ts` (kind = `view_id = <plugin_id>:<kind>`, есть
  `unregisterHtml`), `#plugin-view` — его контейнер; нативный preview остаётся **дефолтной** вкладкой
  `.view-switch`. HTML приходит `host.set_view_content` → санитизация `md-core::sanitize_fragment`
  (`data-p-*`) → событие `plugin-views-changed` → `HtmlView` пишет innerHTML; клики
  `data-p-<id>-action/-payload` возвращаются через `plugin_view_action` → Lua `on_action`. События
  (`document:changed` notify-only) и обратная маршрутизация — в проде. Остаётся research: замер
  латентности opt-in превью против D2, форма привязки `view ↔ doc_id`, при необходимости — уточнение
  ADR-0022/§5.3 и reference-плагин `preview-*` с e2e.
- **Затрагивает:** `DESIGN_DOC` §5.3/§5.4 (тир-1 ViewProvider, `ViewContext`), §9.2–§9.4 (события,
  обратная маршрутизация), §11 (санитизация фрагмента + `data-p-*`), §6–§8 (плагины/permissions),
  ADR-0022, D2; замороженные контракты §13.2 — да (панели/`view-switch`, id `preview`).
- **Артефакты:** спайк (плагин-`HtmlViewProvider` на реальном debounce; замер латентности IPC против
  D2), решение по UI выбора превью, при необходимости ADR; далее — доработка ТЗ (Фаза 4/5).
- **Открытые вопросы:**
  1. **Форма выбора:** переключатель в `view-switch` существующей правой панели (нативный preview ↔
     плагинные) или плагин добавляет **новую** панель/вкладку? Второе задевает `MAX_PANES=2` и layout.
  2. **Привязка view ↔ документ:** как view узнаёт `doc_id` — в событии, в `opts` при `create_view`,
     или через отдельное `view:bound{doc_id}`?
  3. **Интерактивность:** достаточно ли в H2 пассивного HTML-превью на `document:changed`, или нужен
     полноценный back-channel кликов (`data-p-*`)?
  4. **Границы:** пользовательское превью **не** поддерживает scrollsync/inspector (нужен двусторонний
     контроль редактора: `host.reveal_range`/`scroll_editor`, `view:scroll/focus`). Подтвердить как
     ограничение H2, расширение — H3.
  5. **Горячий путь:** дефолтный preview остаётся нативным (D2) — ок? Плагинное превью выбирают явно.
  6. **Эталон:** добавить reference-плагин `preview-*` (сейчас reference — `word-count`/`export-html`/
     `format-selection`, не превью) + e2e-спек.
- **Критерий успеха:** плагин отдаёт пользовательское превью в панели, выбранное в `view-switch`;
  HTML санитизирован; `document:changed` перерисовывает; нативный preview и e2e §13.2 не сломаны;
  замер спайка показывает приемлемую латентность для opt-in сценария.

### IDEA-004 — Тонкий host + набор адаптеров/провайдеров (богатый плагинный API)

- **Статус:** research (спайки) → adr
- **Порядок:** начинать **после закрытия вехи H2** (сделана Фаза 4; остаются фазы 5–6 плагинной системы) —
  не раньше, чтобы спайк опирался на готовый плагинный UX (эталонные плагины + менеджер UI).
- **Зачем:** довести плагинную систему от «Lua + узкий host-API» до платформы, где host максимально
  тонкий, а функциональность плагинам дают подключаемые **адаптеры** (мосты к хостовым подсистемам:
  документ, файлы, диалоги, статусбар, события, экспорт) и **провайдеры** (тир-1
  `HtmlViewProvider`, команды/меню, будущие engines). Цель — богатый плагинный API без раздувания
  базы (D6) и без утечки `mlua` в GUI-хост (D16/ADR-0021).
- **Суть:** вынести из `Supervisor`/`plugin-host` минимум «несущего» (транспорт, Job/watchdog,
  permissions, dispatch) и оформить расширения как реестр адаптеров/провайдеров, декларативно
  включаемых хостом. Спайками измерить, насколько тонким может быть host и как навешивать
  permission-модель на адаптер, а не на хардкод host-функции. Продолжение IDEA-002 (Host/Engine) и
  IDEA-003 (плагинные view-провайдеры).
- **Затрагивает:** `DESIGN_DOC` §2 (слои), §5.3/§5.4 (ViewProvider/`ViewContext`), §6–§9 (Lua,
  host-функции, permissions, события), §10/§14 (лимиты/бюджет), §16 (реестр ADR), ADR-0021,
  ADR-0022; D6, D8. **Нужен отдельный ADR** (граница host ↔ адаптеры/провайдеры).
- **Артефакты:** спайк(и) `crates/*-spike` + замеры в `docs/proto/FINDINGS.md` (цена адаптеров:
  число host-call'ов, латентность, размер child/GUI); черновик ADR; обновление `DESIGN_DOC` §2/§5/§6;
  далее — TZ.
- **Открытые вопросы (гипотезы для спайков):**
  1. Что остаётся в «ядре host» (транспорт, Job/watchdog, permissions, dispatch), что уходит в
     адаптеры? Как формально мерить «тонкость»?
  2. Форма описания адаптеров/провайдеров: Rust-трейты на хосте, Lua-таблицы, манифест
     (`contributes`)? Где проходит граница «декларация vs код»?
  3. Как permission-модель навешивается на адаптер (ACL-подобно, §8) вместо хардкода host-fn?
  4. Остаётся ли `plugin-core` единственным общим крейтом, или появляется `plugin-api`-крейт для
     адаптеров (упомянут в `docs/ROADMAP.md` H2 п.1)?
  5. Влияние на бюджет: адаптеры живут в child, host держит только метаданные/диспетчер — удержать
     GUI ≤ 6 МБ (D6).
  6. Совместимость с `HOST_API_VERSION`: расширение новыми адаптерами/host-fn без мажора.
- **Критерий успеха:** спайк демонстрирует тонкий host с ≥2 подключаемыми адаптерами/провайдерами,
  где новый плагинный функционал добавляется без правок ядра; замеры размер/латентность приемлемы;
  замороженные контракты §13.2 и e2e зелёные.

### IDEA-005 — Ограниченный доступ к плагинам в тулбаре (триггер + меню)

- **Статус:** идея
- **Зачем:** вернуть идентичность плагина (`--pc`) и быстрый доступ в тулбар, **не** возвращая O(N)-разрастание полосы (`BUG-004`; снято в H2).
- **Суть:** один компактный контрол «Плагины» (иконка + счётчик активных, точка `--pc`) открывает попап-меню со списком плагинов: монограмма `--pc`, имя, слово состояния, действия (открыть первое представление, выполнить команду). Тулбар остаётся O(1) при любом числе плагинов.
- **Затрагивает:** `DESIGN_DOC` §5 (UI-слой), §7 (menu: `role`, клавиатура, Escape, возврат фокуса); замороженные контракты §13.2 — нет. Пересекается с шагами dialog-инфраструктуры в H2.
- **Артефакты:** опирается на `dialog.ts`/`#modal-root` из шага 3; при необходимости ADR, затем TZ.
- **Открытые вопросы:** переполнение меню (скролл/поиск/группировка); связь с палитрой команд;
  показывать только активные плагины или все; не дублировать панель «Плагины».
- **Критерий успеха:** число контролов в тулбаре не зависит от числа плагинов; действия доступны
  с клавиатуры; e2e §13.2 зелёные.

### IDEA-011 — Мультивкладки документов (§11.1.1)

- **Статус:** tz (прототип готов, хендофф готов)
- **Зачем:** открытие нескольких документов одновременно, переключение между вкладками, закрытие, индикаторы изменений (dirty)
- **Суть:** панель вкладок под тулбаром; каждая вкладка содержит иконку типа файла, имя, dirty-точку, кнопку закрытия; переключение кликом / Ctrl+Tab / Ctrl+Shift+Tab; закрытие кнопкой / Ctrl+W / контекстным меню; подтверждение при несохранённых изменениях; drag-and-drop для изменения порядка; контекстное меню (закрыть, закрыть остальные, закрыть справа, копировать путь)
- **Затрагивает:** `DESIGN_DOC` §5.2 (Pane/View), §13.2 (id `tab-strip`, `tab-name`, `tab-dirty` — де-факто контракты)
- **Артефакты:** прототип `ideas/front_idea11.html` (интерактивный, CSP-safe, токены = продуктовые)
- **Открытые вопросы:**
  1. Подтверждение закрытия при dirty — диалог с тремя кнопками (отмена / сохранить / закрыть без сохранения) или упрощённый вариант?
  2. Поведение при закрытии всех вкладок — пустое состояние или автоматическое создание нового документа?
  3. Нужна ли кнопка «Новый документ» на панели вкладок (как в Notepad++) или только через тулбар?
  4. Drag-and-drop — оставить как есть или добавить визуальный индикатор вставки в виде вертикальной линии?
- **Критерий успеха:** пользователь может открыть несколько документов, переключаться между ними, закрывать с подтверждением при несохранённых изменениях; dirty-индикаторы видны; горячие клавиши работают; e2e-контракты §13.2 не сломаны

### IDEA-012 — Мониторинг ресурсов (ОЗУ) в панели «Журнал»

- **Статус:** реализовано (ADR-0031; спайк F49–F54; Фазы 2–4 ✅)
- **Зачем:** видеть, сколько ресурсов потребляет приложение и плагины; ловить утечки и «болтливые»/зависшие child-процессы до релиза; дать пользователю прозрачность по нагрузке (мониторинг потребления программы, плагинов и связанных процессов).
- **Суть:** в панели «Журнал» (H3, слот `#sb-logs`) добавить секцию мониторинга ресурсов: потребление ОЗУ (обязательно) и, опционально, CPU/хендлов — суммарно и в разрезе: главный процесс + каждый активный `darmark-plugin-host.exe` (child) с привязкой к `plugin_id`. Обновление по таймеру, числа + при необходимости спарклайн, подсветка при превышении порога. Источник данных — Rust-хост: child-процессы уже управляются через Job Object в `supervisor.rs`, там же известны PID.
- **Затрагивает:** `DESIGN_DOC` §5 (UI-слой, статусбар/журнал), H3 (журнал), плагинную подсистему (`supervisor.rs` — PID child'ов, Job Object), §10/§14 (лимиты/бюджет — мониторинг не должен раздувать GUI). Замороженные контракты §13.2 — нет (кроме слота `#sb-logs`).
- **Артефакты:** спайк (платформенный API: Windows `K32GetProcessMemoryInfo`/`PROCESS_MEMORY_COUNTERS` через `windows`-crate vs всеядный `sysinfo` — сверить с бюджетом D6), замеры в `docs/proto/FINDINGS.md`; затем TZ.
- **Открытые вопросы:**
  1. Источник данных: WinAPI через `windows`-crate или `sysinfo` (размер/зависимости, D6); нужна ли кроссплатформенность или Windows-only.
  2. Что мониторим: только ОЗУ или ещё CPU/потоки/хендлы; частота опроса и влияние самого опроса.
  3. Что считать «связанными процессами»: только child'ы из Job Object или все подпроцессы.
  4. Формат UI: числа + sparkline; пороги и реакция при превышении (подсветка, запись в журнал, автоматический kill?).
  5. Поведение при crash/kill child (карантин N=3) — как показывать «осиротевшие» метрики.
- **Критерий успеха:** в журнале видно потребление ОЗУ приложения и по каждому активному плагину; обновляется без заметной нагрузки; корректно переживает crash/kill child; бюджет размера и e2e не нарушены.

### IDEA-013 — Кнопка AI: чат с готовыми промтами и harness для документов и Lua-плагинов

- **Статус:** tz (ТЗ готово — `tasks/TZ-AI-ASSISTANT.md`; крупная, затрагивает безопасность/сеть). **Размещение пересмотрено (11.10.2026):** чат с AI — не правый дровер 480px, а **режим нижней панели-дока** (прототип `ideas/front_idea-ai-assistant.html`, редакция 2). ТЗ §8 ждёт правки: дровер → режим нижнего дока; принят **ADR-0030** (док на два режима «Журнал»/«AI»; исключение из ADR-0024). **Провайдер пересмотрен (11.10.2026):** OpenAI-совместимый API (облако, точка `routerai.ru`, модель `deepseek/deepseek-v4.1-flash`), локальная LLM (Ollama) отложена на неопределённый срок — **ADR-0032**.
- **Зачем:** снизить порог входа в расширение редактора и работу с Markdown: AI-ассистент, который умеет править текущий документ и создавать/сопровождать Lua-плагины по заранее подготовленным «скиллам» (промт-шаблонам), не заставляя пользователя писать с нуля.
- **Суть:**
  - **Кнопка «AI»** в тулбаре (и `#sb-ai` в статусбаре) открывает **режим «AI-ассистент» нижнего дока** — того же, где панель «Журнал» (ADR-0029); переключение режима — тихий сегмент в шапке панели.
  - **Библиотека готовых промтов («скиллов»):** например «переструктурировать документ», «сделать конспект», «сгенерировать Lua-плагин», «отладить/дополнить плагин», «добавить команду представления».
  - **Harness (инструменты ассистента):**
    1. редактирование текущего документа — через существующий IPC/`apply_edit`/`docStore` (диффы + ревью перед применением, отмена);
    2. полный цикл Lua-плагинов — создание/редактирование/удаление `main.lua` + `plugin.json`, с валидацией манифеста и прогоном в песочнице (`plugin-host --self-test`).
  - **Провайдер LLM (11.10.2026):** **OpenAI-совместимый API** (облако, `base_url` `https://routerai.ru/api/v1`, модель `deepseek/deepseek-v4.1-flash`, `POST /chat/completions`) — единственный реализуемый в MVP; ключ — в Windows Credential Manager. Локальная LLM (Ollama/llama.cpp) **отложена на неопределённый срок** (ADR-0032). Важно: CSP `default-src 'self'` запрещает внешние вызовы из WebView — сеть/ключи только на Rust-стороне, с согласием пользователя на отправку содержимого (данные идут через сторонний роутер `routerai.ru`).
- **Затрагивает:** `DESIGN_DOC` §5 (UI), §6–§9 (host-API, permissions, sandbox), безопасность (CSP, внешние данные, ключи, consent), §14 (бюджет), новый слой «AI». **ADR оформлены:** ADR-0030 (режим AI дока), **ADR-0032** (провайдер OpenAI-совместимый API/routerai.ru; границы ассистента: доступ к документу/ФС/сети/плагинам).
- **Артефакты:** спайк (провайдер LLM, канал стриминга, tool-calling/harness), ADR, затем TZ.
- **Открытые вопросы:**
  1. ~~Провайдер: локальная модель vs облачный API vs оформление как плагин; где хранятся/вводятся ключи; приватность~~ — **решено (ADR-0032): OpenAI-совместимый API (routerai.ru, `deepseek/deepseek-v4.1-flash`); ключ в Windows Credential Manager; локальная LLM отложена на неопределённый срок.** Остаётся: стоимость/лимиты, поведение при недоступности роутера.
  2. Сеть/безопасность: только Rust-сторона (CSP), явное согласие на отправку текста документа; лимиты и логирование запросов.

  6. UX: чат — режим нижней панели-дока (решено, см. прототип редакции 2); открытыми остаются история диалога и отмена правок.
- **Критерий успеха:** из чата можно (а) применить предложенную правку к документу с предпросмотром и отменой и (б) сгенерировать/отредактировать/удалить Lua-плагин, проходящий валидацию песочницы; секреты и содержимое обрабатываются с согласием, CSP не нарушен.

### IDEA-014 — Подсветка синтаксиса редактора

- **Статус:** идея (отложено на неопределённый срок — «когда-нибудь»)
- **Зачем:** читаемость Markdown-исходника (заголовки, списки, код, ссылки); задел под «универсальный редактор» (IDEA-002: движки/Host–Engine).
- **Суть:** подсветка синтаксиса в области редактирования. Возможные пути: (а) overlay-слой подсветки поверх `<textarea>` (без смены контракта `#editor`); (б) переход на полноценный редактор (CodeMirror/аналог); (в) подсветка данными из ядра/движка (Rust) с рендером токенов.
- **Затрагивает:** `DESIGN_DOC` §5.3 (editor — тир-2 view, `textarea`), §15; ADR «Редактор: textarea; CodeMirror — отдельный ADR» (§16 п.6). **Замороженный контракт §13.2 — id `#editor`** (e2e) обязан выжить либо получить явный план миграции. Пересекается с IDEA-002 (Host/Engine) и inspector/scrollsync (mapping байты↔UTF-16, `data-md`).
- **Артефакты:** ADR (механизм + влияние на инспектор/scrollsync/размер), при необходимости спайк (вес CodeMirror vs overlay; производительность на больших файлах D6).
- **Открытые вопросы:**
  1. Механизм: overlay поверх `textarea`, CodeMirror/аналог или подсветка данными движка (Rust)?
  2. Совместимость: сохранять ли `#editor` (textarea) как замороженный e2e-контракт — overlay это позволяет; смена на CodeMirror требует миграции e2e.
  3. Влияние на inspector/scrollsync (mapping) и производительность больших документов (лимит 10 МБ).
  4. Размер: бюджет GUI ≤ 6 МБ (D6) — вес редактора с подсветкой.
  5. Область подсветки: только Markdown или по языку в fenced-блоках; тема оформления.
- **Критерий успеха:** исходник читается с подсветкой без регрессий inspector/scrollsync и при сохранении (или явной миграции) замороженного контракта `#editor`; бюджет размера не превышен.

### IDEA-015 — Нижний док: вкладка «Мониторинг» и полное скрытие (× / прогрессивный Esc)

- **Статус:** реализовано (вкладка «Мониторинг» + скрытие дока; ADR-0030 дополнен 11.10.2026)
- **Зачем:** (1) **баг** — док `#logs-panel` после открытия можно только свернуть до полосы, вернуть в
  `hidden` нечем; (2) **UX** — мониторинг ресурсов (IDEA-012) зажат в тесную строку `#logs-resources`
  в шапке дока (10.5px, переносится), нужна полноценная вкладка.
- **Суть:** вынести весь мониторинг из шапки в **отдельную вкладку-режим** дока
  «Журнал | Мониторинг | AI-ассистент»; в шапке оставить тихую сводку. Добавить явное **скрытие**
  дока: кнопка `#logs-close` (×, скрыть в `hidden`) при сохранении шеврона (свернуть до полосы) и
  прогрессивного `Esc` (развёрнут → свернуть, свёрнут → скрыть). Тело вкладки: строка главного
  процесса + строки плагинов (имя · `24 / 64 МБ` · прогресс-бар · CPU · возраст), пороги
  `.warn`/`.crit`, `orphan` («завершён»), «нет данных», пустое состояние («Плагины не запущены»).
- **Затрагивает:** `docs/adr/0030-bottom-dock-two-modes.md` (режимы дока + состояние `hidden`),
  `docs/adr/0029-journal-bottom-panel.md` (место `#logs-resources`),
  `docs/adr/0031-resource-monitoring-source.md` (§1.2 — перенос строки в вкладку),
  замороженные контракты §13.2 — да: `#logs-panel`, `#logs-resize`,
  `#logs-collapse`, `#logs-body`, `#logs-list`, `#logs-clear`, `#logs-resources` **сохраняются**;
  новые id — аддитивны (`#logs-close`, `#mode-mon-btn`, `#mon-body`, `#mon-summary`, `#sb-mon`).
- **Артефакты:** расширение ADR-0030 (режимы дока + состояние `hidden`) и реализация
  (`frontend-developer`); прототип дока удалён после реализации.
- **Открытые вопросы:**
  1. Порядок вкладок: «Журнал | Мониторинг | AI-ассистент» (мониторинг рядом с журналом как
     диагностика) или «Журнал | AI-ассистент | Мониторинг»?
  2. Триггер статусбара `#sb-mon` — нужен ли отдельный, или «Мониторинг» остаётся вкладкой внутри
     уже открытого дока (без своего триггера)?
  3. Шеврон vs ×: оставить оба (шеврон = полоса, × = скрыть) или свести к одному контролу?
  4. `role` региона: `#logs-resources` сохраняет `role="note"` внутри `#mon-body[role=tabpanel]`?
- **Критерий успеха:** док полностью скрывается в `hidden` (× / Esc) и возвращается триггером;
  мониторинг читается как полноценная вкладка с порогами/orphan/«нет данных»; замороженные id и
  e2e `logs.feature`/`a11y.feature` зелёные.
