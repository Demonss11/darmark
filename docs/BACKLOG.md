# Бэклог идей

> **Статус:** non-normative, живой бэклог идей проекта (не только UI).
> **Нормативно:** `docs/DESIGN_DOC.md` (layout/контракты, + ADR в `docs/adr/`); визуальная идентичность и дизайн-концепции — `DESIGN.md`.
> **Как идея продвигается:** идея → спайк → ADR → TZ → код.

## Статусы

- `идея` — сырое, не оценено;
- `research` — нужен спайк;
- `adr` — нужно архитектурное решение;
- `tz` — готово к реализации;
- `done` — реализовано (ссылка на TZ);
- `dropped` — отклонено (кратко почему).

## Шаблон идеи

```
### IDEA-NNN — <название>
- **Статус:** идея | research | adr | tz | done | dropped
- **Зачем:** <продуктовая ценность>
- **Суть:** <что делаем>
- **Затрагивает:** DESIGN_DOC §…, ADR-…, замороженные контракты §13.2 (да/нет)
- **Артефакты:** спайк / ADR / TZ
- **Открытые вопросы:** …
- **Критерий успеха:** …
```

## Бэклог

### IDEA-002 — Разделение Host / Engine (универсальный редактор)

- **Статус:** research (спайки) → adr
- **Зачем:** продуктовый pivot — от «Markdown-редактора» к универсальному редактору с подключаемыми движками. Host работает с файлом, не зная про Markdown.
- **Суть:**
  - **Host** — оболочка/файлы/UI: открывает файл, отдаёт текст движку.
  - **Engine** — абстракция `text → данные отрисовки`; реализации: `md-core`, WASM, IPC, плагин.
- **Затрагивает:** `DESIGN_DOC` §2 (слои), §3 (контракт ядра), §5.3/§5.4 (тир-1 ViewProvider как «движок-представление»), §6–§12 (плагины), §13.2 (id/селекторы) (бюджет). **Нужен отдельный ADR.**
- **Артефакты:**
  - спайки: `crates/*-spike` + замеры в `docs/FINDINGS.md` (латентность IPC, размер/запуск WASM, стоимость сериализации render-data);
  - ADR с границей Host/Engine и формальным контрактом;
  - обновление `DESIGN_DOC` §2/§3.
- **Открытые вопросы (гипотезы для спайков):**
  1. Что отдаёт Engine: HTML или структурные данные (AST/токены/патч)? Инкрементальность?
  2. Выдержит ли дебаунс рендера 120 мс (§13.2) проход через WASM/IPC?
  3. Где живёт mapping байты↔UTF-16 и `data-md` — в Engine или Host?
  4. WASM: размер, бюджет (GUI ≤ 6 МБ).
  5. Плагины H2 и «плагины-движки» — общий механизм или разные?
  6. Совместимость: `md-core` остаётся эталонным Engine.
- **Критерий успеха спайка:** Host отображает Markdown через Engine; замеры IPC/WASM приемлемы; e2e §13.2 не сломаны.

### IDEA-017 — AI Ф3: дополнительные встроенные скиллы (перечень кандидатов)

- **Статус:** идея (**отложено**; часть Ф3 — `tasks/TZ-AI-PHASE3.md` §2.1/§7 п.1, AC-P3-1)
- **Зачем:** расширить набор скиллов сверх MVP-двух (`explain`, `create-plugin`) — снизить порог для типовых задач.
- **Суть (кандидаты, требуют решения по составу перед реализацией):**
  - **документные:**
    - `explain-syntax` — разбор разметки Markdown (в отличие от `explain`); read-only.
    - `restructure` — привести структуру документа к порядку; правка через `ai_diff`/`ai_apply_edit`.
    - `summarize` — сжатое изложение; развилка: правка или показ.
  - **плагинные:**
    - `debug-plugin` — диагностика ошибок песочницы (`on_activate`, host-API, permissions).
    - `add-view` — генерация view-плагина (`contributes.views`, `view:create`/`view:modify`, `host.set_view_content`), поверх `create-plugin`.
- **Затрагивает:** `skills.rs`, `FALLBACK_SKILLS` в `aiPanel.ts`, UI; harness `ai_diff`/`ai_apply_edit` (ADR-0034/ADR-0026). Тест `mvp_has_exactly_two_skills` и упоминания «2 скилла» обновить. Промты — через цикл `skill-creator`. §13.2 — нет.
- **Открытые вопросы:**
  1. **Доступ к коду плагина** для `debug-plugin`/`add-view`: сейчас уходит только `{{doc}}`. Варианты: менеджер плагинов, чтение по id, вставка вручную.
  2. **Конспект/переструктурировать** — правка или показ.
  3. Не дублирует ли `explain-syntax` имеющийся `explain` — возможно, уточнить `explain`, а не плодить скилл.
  4. **Стоимость/латентность:** reasoning-модель дорога (§2.3/§2.4) — промты держать лёгкими, мерить живьём.
  5. **Порядок:** сначала документные (Этап A), затем плагинные (Этап B — см. п.1).
- **Критерий успеха:** скиллы добавлены как промты + карточки UI, проходят ассерты `skill-creator`, покрыты E2E; §13.2 не сломаны.

### IDEA-018 — Tool-calling у провайдера без поддержки: детект, авто-ретрай или локальный разбор вызова

- **Статус:** идея (**вне Фазы 3**; tool-loop в объёме `tasks/PLAN-AI-PHASE3-MCP-v2.md` Epic 6, OQ-3)
- **Зачем:** не оставлять пользователя с голым «Некорректный запрос к провайдеру», когда его
  OpenAI-совместимый шлюз просто не умеет `tools`/function-calling — ассистент должен деградировать
  до обычного чата сам.
- **Суть:** определить поведение цикла, когда провайдер (а) отвечает 400 на поле `tools`,
  (б) молча игнорирует его, (в) возвращает `finish_reason`/`tool_calls` в нестандартной форме.
  Варианты: детект по 400 → один автоматический повтор без `tools` с явной записью в журнал;
  «локальный разбор вызова» из текста ответа (как предлагает TZ-MCP R6) — отдельный дизайн
  с отдельным парсером и рисками prompt-injection.
- **Затрагивает:** `crates/app/src-tauri/src/ai/{transport,backend/reqwest,tool_loop}.rs`,
  `crates/app/src/aiPanel.ts`, `docs/FINDINGS.md` §2.5 (п.1 «Tool-loop не реализован»);
  ADR-0027 (аддитивные события — только при появлении), ADR-0035 §2.10 (сеть/протокол без изменений).
  §13.2 — нет. **Нужен отдельный ADR**, если выбран локальный разбор вызова.
- **Открытые вопросы:** 1. Повтор без `tools` — молчаливый (лог `warn`) или с карточкой в чате?
  2. Кэшировать ли «этот провайдер не умеет tools» на сессию? 3. Что считать «нестандартной формой»
  `tool_calls` и где её терпеть (SSE-парсер)? 4. Как отличить 400 «из-за `tools`» от прочих 400?
- **Критерий успеха:** зафиксировано поведение для (а)/(б)/(в); при выборе локального разбора —
  ADR + тест на разбор вызова и на изоляцию результата (R7: «данные, не инструкции»).
