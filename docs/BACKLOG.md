# Бэклог идей

> **Статус:** non-normative, живой бэклог идей проекта (не только UI).
> **Нормативно:** `docs/DESIGN_DOC.md` (layout/контракты, + ADR в `docs/adr/`); визуальная идентичность и дизайн-концепции — `DESIGN.md`.
> **Как идея продвигается:** идея → research/спайк (`crates/*-spike`, замеры в `docs/FINDINGS.md`) → ADR + `DESIGN_DOC` → TZ (`tasks/`) → код.
> Принятое решение **уходит** отсюда в `DESIGN_DOC`/ADR; в этом файле остаётся ссылка и статус.

## Статусы

- `идея` — сырое, не оценено;
- `research` — нужен спайк/замер;
- `adr` — нужно архитектурное решение;
- `tz` — готово к реализации (есть/нужен ТЗ);
- `done` — реализовано (ссылка на TZ);
- `dropped` — отклонено (кратко почему).

## Шаблон идеи

```
### IDEA-NNN — <название>
- **Статус:** идея | research | adr | tz | done | dropped
- **Зачем:** <продуктовая ценность>
- **Суть:** <что делаем>
- **Затрагивает:** DESIGN_DOC §…, ADR-…, замороженные контракты §13.2 (да/нет)
- **Артефакты:** спайк / ADR / TZ
- **Открытые вопросы:** …
- **Критерий успеха:** …
```

## Бэклог

### IDEA-001 — Панель меню (Файл, Вид, Помощь…)

- **Статус:** идея
- **Зачем:** разгрузить icon-toolbar и дать привычную навигацию/discoverability; задел под пункты меню от плагинов (H2).
- **Суть:** полоса меню (`Файл · Правка? · Вид · Формат? · Плагины (H2) · Помощь`) с выпадающими списками; часть функционала перенести из тулбара (файловые команды, тумблеры панелей/синхронизации), самые частые действия оставить в тулбаре.
- **Затрагивает:** `DESIGN_DOC` §5 (UI-слой); §13.2 — id `btn-new/open/save/save-as`, `toggle-sync/preview` должны выжить (кнопки могут стать пунктами меню, но контракт e2e обязан остаться рабочим).
- **Артефакты:** возможно ADR (модель меню + нативное/HTML), затем TZ (`tasks/TZ-UI-menu.md`).
- **Открытые вопросы:**
  1. Нативное меню Tauri (`Menu`/`MenuItem`) vs HTML-меню в DOM. Нативное — вне DOM, e2e по id не кликается (помечать `@manual`), но привычнее для Windows; HTML-меню остаётся под e2e и CSP `'self'`.
  2. Что именно уходит из тулбара, что остаётся.
  3. Акселераторы и дублирование с уже существующими хоткеями.
- **Критерий успеха:** файл-команды и тумблеры доступны из меню; все e2e-контракты §13.2 зелёные.

### IDEA-002 — Разделение Host / Engine (универсальный редактор)

- **Статус:** research (спайки) → adr
- **Зачем:** продуктовый pivot — от «Markdown-редактора» к универсальному редактору с подключаемыми движками. Host работает с файлом, **не зная**, что это Markdown.
- **Суть:**
  - **Host** — оболочка/окно/файлы/UI: открывает файл, отдаёт текст движку, получает «данные для отрисовки».
  - **Engine** — абстракция `text → данные отрисовки`; реализации: встроенный `md-core`, WASM-движок, внешний процесс (IPC), движок плагина.
  - Целевая проверка: можно ли превратить md-редактор в универсальный редактор с системой **Engine + WASM + IPC + Плагины**.
- **Затрагивает:** `DESIGN_DOC` §2 (слои), §3 (контракт ядра), §5.3/§5.4 (тир-1 ViewProvider как «движок-представление»), §6–§12 (плагины), §13.2 (id/селекторы), §14 (бюджет). **Нужен отдельный ADR.**
- **Артефакты:**
  - спайки: `crates/*-spike` + замеры в `docs/FINDINGS.md` (латентность IPC, размер/запуск WASM, стоимость сериализации render-data);
  - ADR с границей Host/Engine и формальным контрактом;
  - обновление `DESIGN_DOC` §2/§3.
- **Открытые вопросы (гипотезы для спайков):**
  1. Что именно отдаёт Engine: HTML (как сейчас `preview.innerHTML`) или структурные данные (AST/токены/патч)? Инкрементальность?
  2. Выдержит ли дебаунс рендера 120 мс (§13.2) проход через WASM/IPC?
  3. Где живёт mapping байты↔UTF-16 и `data-md` — в Engine или Host? Инспектор/scrollsync завязаны на это.
  4. WASM: движок (Rust→`wasm32`), размер, бюджет §14 (GUI ≤ 6 МБ).
  5. Плагины H2 и «плагины-движки» — общий механизм или разные?
  6. Совместимость: `md-core` остаётся эталонным Engine.
- **Критерий успеха спайка:** Host, не знающий про Markdown, отображает Markdown через Engine-абстракцию; замеры IPC/WASM приемлемы; замороженные e2e §13.2 не сломаны (либо есть явный план их миграции).

### IDEA-004 — Тонкий host + набор адаптеров/провайдеров (богатый плагинный API)

- **Статус:** research (спайки) → adr
- **Порядок:** начинать **после закрытия вехи H2** (сделана Фаза 4; остаются фазы 5–6 плагинной системы) —
  не раньше, чтобы спайк опирался на готовый плагинный UX (эталонные плагины + менеджер UI).
- **Зачем:** довести плагинную систему от «Lua + узкий host-API» до платформы, где host максимально
  тонкий, а функциональность плагинам дают подключаемые **адаптеры** (мосты к хостовым подсистемам:
  документ, файлы, диалоги, статусбар, события, экспорт) и **провайдеры** (тир-1
  `HtmlViewProvider`, команды/меню, будущие engines). Цель — богатый плагинный API без раздувания
  базы (D6) и без утечки `mlua` в GUI-хост (D16/ADR-0021).
- **Суть:** вынести из `Supervisor`/`plugin-host` минимум «несущего» (транспорт, Job/watchdog,
  permissions, dispatch) и оформить расширения как реестр адаптеров/провайдеров, декларативно
  включаемых хостом. Спайками измерить, насколько тонким может быть host и как навешивать
  permission-модель на адаптер, а не на хардкод host-функции. Продолжение IDEA-002 (Host/Engine);
  опирается на реализованные плагинные view-провайдеры (H2).
- **Затрагивает:** `DESIGN_DOC` §2 (слои), §5.3/§5.4 (ViewProvider/`ViewContext`), §6–§9 (Lua,
  host-функции, permissions, события), §10/§14 (лимиты/бюджет), §16 (реестр ADR), ADR-0021,
  ADR-0022; D6, D8. **Нужен отдельный ADR** (граница host ↔ адаптеры/провайдеры).
- **Артефакты:** спайк(и) `crates/*-spike` + замеры в `docs/FINDINGS.md` (цена адаптеров:
  число host-call'ов, латентность, размер child/GUI); черновик ADR; обновление `DESIGN_DOC` §2/§5/§6;
  далее — TZ.
- **Открытые вопросы (гипотезы для спайков):**
  1. Что остаётся в «ядре host» (транспорт, Job/watchdog, permissions, dispatch), что уходит в
     адаптеры? Как формально мерить «тонкость»?
  2. Форма описания адаптеров/провайдеров: Rust-трейты на хосте, Lua-таблицы, манифест
     (`contributes`)? Где проходит граница «декларация vs код»?
  3. Как permission-модель навешивается на адаптер (ACL-подобно, §8) вместо хардкода host-fn?
  4. Остаётся ли `plugin-core` единственным общим крейтом, или появляется `plugin-api`-крейт для
     адаптеров (адаптеры/host — см. IDEA-002/IDEA-004 в этом бэклоге)?
  5. Влияние на бюджет: адаптеры живут в child, host держит только метаданные/диспетчер — удержать
     GUI ≤ 6 МБ (D6).
  6. Совместимость с `HOST_API_VERSION`: расширение новыми адаптерами/host-fn без мажора.
- **Критерий успеха:** спайк демонстрирует тонкий host с ≥2 подключаемыми адаптерами/провайдерами,
  где новый плагинный функционал добавляется без правок ядра; замеры размер/латентность приемлемы;
  замороженные контракты §13.2 и e2e зелёные.

### IDEA-005 — Ограниченный доступ к плагинам в тулбаре (триггер + меню)

- **Статус:** идея
- **Зачем:** вернуть идентичность плагина (`--pc`) и быстрый доступ в тулбар, **не** возвращая O(N)-разрастание полосы (`BUG-004`; снято в H2).
- **Суть:** один компактный контрол «Плагины» (иконка + счётчик активных, точка `--pc`) открывает попап-меню со списком плагинов: монограмма `--pc`, имя, слово состояния, действия (открыть первое представление, выполнить команду). Тулбар остаётся O(1) при любом числе плагинов.
- **Затрагивает:** `DESIGN_DOC` §5 (UI-слой), §7 (menu: `role`, клавиатура, Escape, возврат фокуса); замороженные контракты §13.2 — нет. Пересекается с шагами dialog-инфраструктуры в H2.
- **Артефакты:** опирается на `dialog.ts`/`#modal-root` из шага 3; при необходимости ADR, затем TZ.
- **Открытые вопросы:** переполнение меню (скролл/поиск/группировка); связь с палитрой команд;
  показывать только активные плагины или все; не дублировать панель «Плагины».
- **Критерий успеха:** число контролов в тулбаре не зависит от числа плагинов; действия доступны
  с клавиатуры; e2e §13.2 зелёные.

### IDEA-014 — Подсветка синтаксиса редактора

- **Статус:** идея (отложено на неопределённый срок — «когда-нибудь»)
- **Зачем:** читаемость Markdown-исходника (заголовки, списки, код, ссылки); задел под «универсальный редактор» (IDEA-002: движки/Host–Engine).
- **Суть:** подсветка синтаксиса в области редактирования. Возможные пути: (а) overlay-слой подсветки поверх `<textarea>` (без смены контракта `#editor`); (б) переход на полноценный редактор (CodeMirror/аналог); (в) подсветка данными из ядра/движка (Rust) с рендером токенов.
- **Затрагивает:** `DESIGN_DOC` §5.3 (editor — тир-2 view, `textarea`), §15; ADR «Редактор: textarea; CodeMirror — отдельный ADR» (§16 п.6). **Замороженный контракт §13.2 — id `#editor`** (e2e) обязан выжить либо получить явный план миграции. Пересекается с IDEA-002 (Host/Engine) и inspector/scrollsync (mapping байты↔UTF-16, `data-md`).
- **Артефакты:** ADR (механизм + влияние на инспектор/scrollsync/размер), при необходимости спайк (вес CodeMirror vs overlay; производительность на больших файлах D6).
- **Открытые вопросы:**
  1. Механизм: overlay поверх `textarea`, CodeMirror/аналог или подсветка данными движка (Rust)?
  2. Совместимость: сохранять ли `#editor` (textarea) как замороженный e2e-контракт — overlay это позволяет; смена на CodeMirror требует миграции e2e.
  3. Влияние на inspector/scrollsync (mapping) и производительность больших документов (лимит 10 МБ).
  4. Размер: бюджет GUI ≤ 6 МБ (D6) — вес редактора с подсветкой.
  5. Область подсветки: только Markdown или по языку в fenced-блоках; тема оформления.
- **Критерий успеха:** исходник читается с подсветкой без регрессий inspector/scrollsync и при сохранении (или явной миграции) замороженного контракта `#editor`; бюджет размера не превышен.

### IDEA-016 — MCP-сервер (inbound): внешние клиенты и границы доверия

- **Статус:** **трек выделен** — `tasks/TZ-MCP.md`; рамка пересмотрена **ADR-0036** (внутренний клиент, in-memory транспорт, контрактный tool-слой). Прежняя рамка (inbound, вне MVP) — ADR-0034 §2.5 (**замещён**)
- **Зачем:** дать внешним клиентам (другие AI-агенты/редакторы) доступ к возможностям darmark
  (документ, плагины) по открытому протоколу — расширить экосистему за пределы встроенного ассистента.
- **Суть:** darmark выступает **MCP-сервером** (inbound): внешний клиент вызывает наши
  инструменты/ресурсы. Это **качественно иная граница доверия**, чем outbound-запрос AI к провайдеру
  (ADR-0034 §2.5): входящие вызовы, аутентификация/авторизация клиента, ограничение набора доступных
  инструментов, аудит. В MVP **не входит**; при появлении кейса внешних клиентов — отдельный ADR.
- **Затрагивает:** безопасность (новая **inbound**-поверхность), `DESIGN_DOC` §… (слои/безопасность);
  замороженные контракты §13.2 — нет. **Нужен отдельный ADR** (граница доверия, список инструментов,
  auth). Пересекается с IDEA-013 (встроенный ассистент) — но роль иная.
- **Артефакты:** раздел MCP в `tasks/TZ-AI-PHASE3.md` (внесено, вне MVP); отдельный ADR (граница
  доверия, инструменты/ресурсы, аутентификация) + при необходимости спайк; в MVP — не реализуется.
- **Открытые вопросы:**
  1. Что открывать: только чтение документа, плагины, файлы? Каков минимальный набор инструментов?
  2. Транспорт MCP (stdio / HTTP+SSE) и аутентификация внешних клиентов.
  3. Граница доверия и аудит: что считается доверенным клиентом; как не повторить «инверсию
     привилегий» (ср. разбор сайдкара в ADR-0034 §4).

  не реализуется (не раздувает MVP).

### IDEA-017 — AI Ф3: дополнительные встроенные скиллы (перечень кандидатов)

### IDEA-018 — Шрифты редактора/предпросмотра и светлая тема (направление A)

- **Статус:** adr (нужен ADR: направление противоречит `DESIGN.md` «одна тёмная тема»; прототип готов)
- **Зачем:** читаемость кириллицы в редакторе и предпросмотре (моно с нормальной кириллицей,
  тело под длинное чтение, заголовки документа отдельным голосом) и вторая, светлая тема
  для работы при дневном свете — сейчас продукт умеет только тёмную.
- **Суть:** ролевые гарнитуры `--font-mono` (JetBrains Mono, встроенный), `--font-body` (Inter),
  `--font-heading` (Source Serif 4, засечки) + новая светлая палитра на тех же семантических
  токенах; оболочка остаётся системным sans. Прототип-референс — `docs/proto/front_idea1.html`
  (переключатели «Было/Стало» и «Тёмная/Светлая», таблица контрастов с фактическими замерами).
- **Затрагивает:** `DESIGN.md` (Typography, Colors, «Don't вводить вторую тему»), `docs/DESIGN_DOC.md`
  §5 (UI-слой), `crates/app/src/style.css` (`:root`, `@font-face`, `.markdown-body h1..h3`) —
  состав шрифтов и бюджет размера (§14, D6: только нужные веса, доставка `.woff2` как same-origin,
  а не `data:` — CSP `font-src`); замороженные контракты §13.2 — не ломаются, но затрагиваются
  доступные имена/id, выявленные при разборе (`#stat-msg` как live region, `chk-sync`/`chk-preview`).
- **Артефакты:** ADR (вторая тема + ролевые гарнитуры + доставка шрифтов, OFL-лицензии в дистрибутив);
  обновление `DESIGN.md`; прототип `docs/proto/front_idea1.html` (готов).
- **Открытые вопросы (из разбора прототипа, редакция 2):**
  1. `--disabled` используется как цвет **текста** легенды «выключено» в тёмной теме (3,64:1 — FAIL),
     в светлой та же роль проходит (5,16:1) — расхождение одной роли между темами;
     предложение: `.sem.off { color: var(--fg-mute) }` + точка `--disabled` (правится в продукте, меняет «Было»).
  2. Тональная лестница светлой темы (`--bg-0..--bg-3`, шаг 2–3 %) — предлагается развести слои
     до `#eef0f4`/`#e5e8ee`/`#d9dde6` с пересчётом контрастов.
  3. `--gutter` в светлой теме: «светлее `--bg-0`» из брифа даёт `#ffffff` (инверсия роли) —
     в прототипе сохранена роль тёмной темы (gutter темнее рабочей области), брифинг нужно поправить.
  4. Метрики Inter: тело 13px даёт +1 строку на абзац против Segoe UI 13px (+12 % высоты текста);
     уменьшение до 12,5px переносы не меняет — решение: оставить 13px и принять плотность.
  5. Засечки у **всех** h1/h2/h3 или только h1/h2 (h3 ближе к UI); в прототипе — все три, кегли 30/21/17.
- **Критерий успеха:** ADR принят, `DESIGN.md` обновлён, шрифты поставляются как same-origin `.woff2`
  с OFL-текстами, бюджет GUI (§14) не превышен, обе темы проходят AA на фактически отрендеренных парах.
