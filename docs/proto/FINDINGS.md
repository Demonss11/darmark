# FINDINGS — прототип Lua-плагинного хоста

> **Ветка:** `proto/lua-plugin-host`. **Код в `main` не мёржится** — переносятся выводы.
> **Основание:** `tasks/TZ-proto-lua-host.md`, `docs/DESIGN_DOC.md` (D11, §0).
> **Форма:** таблица «гипотеза → замер → вывод» (D15).
> **Дата:** 06.10.2026. **Статус:** P1 закрыт; ранние замеры P2/P3/P4 + спайки panic-стратегии
> (in-process B) и выноса Lua в процесс (C). F21–F25 — ревизия выводов C: stdio проверен не в
> GUI-конфигурации, N1 переоценён, модель процессов и RSS не измерены (закрыто в P9, F30–F31).
> **P9/M10 (GUI stdio) — закрыт** (F26–F27): round-trip и обрывы проверены в GUI-конфигурации
> (`crates/lua-rpc-spike/gui-parent`, subsystem 2) без консоли. **P9/M11 (Job Object) — закрыт**
> (F28–F29): память — жёстко и точно; CPU/время — ОС-лимит с грубой периодической проверкой.
> **P9/M12 (модель процессов, RSS) — закрыт** (F30–F31): измерены память/активация; «общий child»
> теряет/блокирует все плагины при одном сбое. P9 (M10–M12) полностью пройден.
> **Новое следствие P9 — F32:** Job CPU-лимит грубый (секунды), поэтому host зависает на время
> срабатывания → обязателен per-call watchdog/async host-вызовов.
> **D16-пробелы (ADR-0021 §3) закрыты кодом:** per-call watchdog (**F33**) и range/delta host-API
> (**F34**); прогон — `crates/lua-rpc-spike/run-d16.ps1` (exit 0 = гейт).
> **Уточнения F33/F34, закрытые тем же прогоном:** абсолютный дедлайн invocation (**F35** —
> прогресс-таймаут не ловит chatty-плагин) и устойчивость протокола (**F36** — кадры child'а
> трактуются как hostile: лимит размера, fallible-парсер, без panic).
> **ADR-0021 §3 закрыт полностью:** добавлены карантин N=3 (**F37**) и канонические строки
> границы изоляции для UI/магазина (**F38**); прогон — тот же `run-d16.ps1` (exit 0 = гейт).
> **Решение D16 принято: вариант C** (`docs/adr/0021-plugin-isolation-process.md`).

Замеры выполнены на Windows x86_64-msvc, rustc 1.99, mlua 0.12.2, vendored Lua 5.5.1
(`lua-src 551.0.2`). Релизный профиль — `[profile.release]` (`opt-level="s"`, LTO, strip,
`panic="abort"`). Где нужен `unwind` — профиль `[profile.proto]`.

Job'а на документе 10 МБ.
**Реализация F37 (карантин):** `Quarantine` в `lib.rs` (порог, серия, сброс, ручное включение),
`src/bin/quarantine_parent.rs` (+ `[[bin]] quarantine-parent`), фикстуры `crash.lua`/`hello.lua`.
**Реализация F38 (граница изоляции):** `ISOLATION_NOTICE`/`DOCUMENT_ACCESS_NOTICE` и
`permission_notices` в `lib.rs`; печатаются `quarantine-parent --permissions <csv>`.
Грабли реализации: `std::process::Child::wait()` закрывает собственный `stdin`, поэтому запись
«в мёртвого child» надо вести через **заранее взятый** `ChildStdin`, иначе `.unwrap()` паникует
(под `panic="abort"` — fail-fast `0xC0000409`).

Дополнительно (для API-референса плагинов под 5.5): `LUA_REGISTRYINDEX` в Lua 5.5 равен
`-(INT_MAX/2 + 1000)` = **−1073742823**, а не старое `−1001000`. Наш C-модуль сначала падал
с `0xC0000005` из-за захардкоженного старого значения.

## 2. Критическая находка: `panic="abort"` и ошибки из Rust-callback (F9)

- **Симптом:** под релизным `panic="abort"` любой плагин, чья ошибка приходит из
  Rust-зарегистрированной функции, убивает процесс. Чистый Lua `error()` — ловится.
- **Механизм:** mlua объявляет hook как `unsafe extern "C-unwind" fn hook_proc`
  (`mlua-0.12.2/src/state/raw.rs:466`) и при `Err` вызывает `ffi::lua_error` (`raw.rs:174`).
  На MSVC `lua_error` разворачивает стек через SEH (`luaD_throw` → `RtlUnwindEx`); если
  ошибка родилась **внутри** Rust-фрейма, разворачивание обязано пройти сквозь него, а под
  `panic="abort"` фрейм помечен non-unwind → `panic_cannot_unwind` → abort.
- **Широта:** бьёт и по hook, и по host-функциям (H2/P5): `apply_edit` без права должен
  вернуть `permission_denied`, а в релизе уронит приложение.
- **Статус:** исправлено для лимита инструкций (C-hook, §3); для host-функций — **открыто**
  (нужен возврат ошибки Lua-значением, не `Err`).

## 3. Спайк C-hook + RAII-гвард

Реализовано в прототипе (`crates/lua-proto`):

- `src/proto_hook.c` — нативный C-hook (`lua_sethook` + `luaL_error`) и scoped safe-`pcall`/`xpcall`;
- `build.rs` + `[build-dependencies] cc` — сборка C;
- `limits.rs` — `InstructionLimitGuard` (RAII): взводит hook на время работы плагина, снимает
  в `Drop`; счётчик лимита сбрасывается на каждый вызов; safe-`pcall` устанавливается/снимается
  тем же гвардом;
- `main.rs` — флаги `--c-hook`, `--hook-step`.

Проверки (release, `panic="abort"`): `hello` → `exit=0`; `spin` + C-hook → `exit=1`, жив;
`spin` + mlua-hook → abort (контроль); обычные `pcall`/`xpcall` → корректны; `pcall`-обход
(в т.ч. вложенный) → лимит не проглочен.

**Остаточные риски/ограничения спайка:**
1. Состояние C глобальное (одно `lua_State` на процесс) — для нескольких инстансов нужен
   per-state счётчик (реестр Lua), P3/P5.
2. Host-функции с `Err` под `abort` всё ещё абортят (F9) — вне C-hook.
3. Оверхед hook ~×2, пока взведён (F14). `Drop` восстанавливает `pcall` через Lua API: на пути
   лимита под C-hook он выполняется (F15), а при настоящем abort (Rust-паника) — нет.

## 4. Спайк варианта C: Lua в отдельном процессе

len+payload). Child держит Lua 5.5, host-функции ходят **честный round-trip** в parent.
Детали и таблица узких мест — `reviews/TZ-proto-lua-host-P1-review-v1.4.md`.

Замеры (release, Windows/msvc): F16–F20.

**Что C снимает разом:** узкие места W1–W7, W12–W14 пути B (panic-стратегия, hook-оверхед,

## 5. Развилка для ADR (вход)

| Вариант | Lua-ошибки | Лимит инструкций | Изоляция плагина | Размер базы | Вердикт |
|---|---|---|---|---|---|
| A. `unwind` + `catch_unwind` | да | есть | нет | ~7.2 МБ | **закрыт**: D6 |
| B. `abort` + C-hook + safe-pcall + Lua-ошибки значениями | да (возвратом) | есть (C-hook + safe-pcall) | нет | ~4.0 МБ | жизнеспособен, но хрупок; остаётся host-`Err`/паника |
| **C. `abort` + Lua в отдельном процессе** | да | есть (kill / Job Object) | **отказов: жёсткая** (F25) | ~4.3 МБ | **выбран** (ADR-0021) |

**Решение принято (06.10.2026):** вариант **C** — `docs/adr/0021-plugin-isolation-process.md`.
Обязательны до H2: per-call wall-clock watchdog (F32) и range/delta-API (F22/F30).

**Решение по модели процессов (F23) — измерено в P9/M12 (F30/F31):**
Цена процесса ≈0.6 МиБ commit и ~2 мс spawn. «Общий child» почти константен по памяти/времени
(N плагинов в одном процессе), но **аннулирует изоляцию**: один `crash` → `Disconnected` и все
плагины теряются; один `spin` → весь child блокируется, поздние плагины не стартуют. «На плагин»
даёт заявленную в C жёсткую изоляцию (при `crash`/`spin` выживают остальные), платя N×~0.6 МиБ и
N×spawn (~2 мс).

**Рекомендация для ADR (D16):** выбрать **«child на плагин»** — иначе C теряет своё главное
преимущество (F25), и весь смысл варианта C пропадает. «Общий child» допустим только как явный
режим с отказом от обещания изоляции (экономия памяти на десятки–сотни плагинов); на масштабе
«лёгкого редактора» (единицы плагинов) выигрыш не оправдывает потерю изоляции.

**Обязательные следствия для D16 (синхронизировано с P9-review):**
- **Watchdog** (F32/F33/F35): прогресс-таймаут **и** абсолютный дедлайн invocation реализованы;
  «кооперирующийся» плагин ограничен дедлайном, `while true do end` — прогресс-таймаутом;
- **range/delta-API** при «child на плагин» + крупный документ — по **памяти** (F22/F30), а не
  только ради латентности;
- **устойчивость протокола** (F36): host трактует кадры child'а как hostile (лимит размера,
  fallible-парсер) — закрыто.
