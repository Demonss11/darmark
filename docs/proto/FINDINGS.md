# FINDINGS — прототип Lua-плагинного хоста

> **Ветка:** `proto/lua-plugin-host`. **Код в `main` не мёржится** — переносятся выводы.
> **Основание:** `tasks/TZ-proto-lua-host.md`, `docs/DESIGN_DOC.md` (D11, §15.0).
> **Форма:** таблица «гипотеза → замер → вывод» (D15).
> **Дата:** 06.10.2026. **Статус:** P1 закрыт; ранние замеры P2/P3/P4 + спайки panic-стратегии
> (in-process B) и выноса Lua в процесс (C). F21–F25 — ревизия выводов C: stdio проверен не в
> GUI-конфигурации, N1 переоценён, модель процессов и RSS не измерены.

Замеры выполнены на Windows x86_64-msvc, rustc 1.99, mlua 0.12.2, vendored Lua 5.5.1
(`lua-src 551.0.2`). Релизный профиль — `[profile.release]` (`opt-level="s"`, LTO, strip,
`panic="abort"`). Где нужен `unwind` — профиль `[profile.proto]`.

## 2. Критическая находка: `panic="abort"` и ошибки из Rust-callback (F9)

- **Симптом:** под релизным `panic="abort"` любой плагин, чья ошибка приходит из
  Rust-зарегистрированной функции, убивает процесс. Чистый Lua `error()` — ловится.
- **Механизм:** mlua объявляет hook как `unsafe extern "C-unwind" fn hook_proc`
  (`mlua-0.12.2/src/state/raw.rs:466`) и при `Err` вызывает `ffi::lua_error` (`raw.rs:174`).
  На MSVC `lua_error` разворачивает стек через SEH (`luaD_throw` → `RtlUnwindEx`); если
  ошибка родилась **внутри** Rust-фрейма, разворачивание обязано пройти сквозь него, а под
  `panic="abort"` фрейм помечен non-unwind → `panic_cannot_unwind` → abort.
- **Широта:** бьёт и по hook, и по host-функциям (H2/P5): `apply_edit` без права должен
  вернуть `permission_denied`, а в релизе уронит приложение.
- **Статус:** исправлено для лимита инструкций (C-hook, §3); для host-функций — **открыто**
  (нужен возврат ошибки Lua-значением, не `Err`).

## 3. Спайк C-hook + RAII-гвард

Реализовано в прототипе (`crates/lua-proto`):

- `src/proto_hook.c` — нативный C-hook (`lua_sethook` + `luaL_error`) и scoped safe-`pcall`/`xpcall`;
- `build.rs` + `[build-dependencies] cc` — сборка C;
- `limits.rs` — `InstructionLimitGuard` (RAII): взводит hook на время работы плагина, снимает
  в `Drop`; счётчик лимита сбрасывается на каждый вызов; safe-`pcall` устанавливается/снимается
  тем же гвардом;
- `main.rs` — флаги `--c-hook`, `--hook-step`.

Проверки (release, `panic="abort"`): `hello` → `exit=0`; `spin` + C-hook → `exit=1`, жив;
`spin` + mlua-hook → abort (контроль); обычные `pcall`/`xpcall` → корректны; `pcall`-обход
(в т.ч. вложенный) → лимит не проглочен.

**Остаточные риски/ограничения спайка:**
1. Состояние C глобальное (одно `lua_State` на процесс) — для нескольких инстансов нужен
   per-state счётчик (реестр Lua), P3/P5.
2. Host-функции с `Err` под `abort` всё ещё абортят (F9) — вне C-hook.
3. Оверхед hook ~×2, пока взведён (F14). `Drop` восстанавливает `pcall` через Lua API: на пути
   лимита под C-hook он выполняется (F15), а при настоящем abort (Rust-паника) — нет.

## 4. Спайк варианта C: Lua в отдельном процессе

Реализовано в `crates/lua-rpc-spike` (`rpc-parent` + `rpc-child`, stdio-RPC, ручная кодировка
len+payload). Child держит Lua 5.5, host-функции ходят **честный round-trip** в parent.
Детали и таблица узких мест — `reviews/TZ-proto-lua-host-P1-review-v1.4.md`.

Замеры (release, Windows/msvc): F16–F20.

**Что C снимает разом:** узкие места W1–W7, W12–W14 пути B (panic-стратегия, hook-оверхед,
`pcall`-патч, C-ABI, per-state счётчик, Windows-специфика) — перечень W в v1.4 §4,
подтверждено F18.

**Новые узкие места C:**

| # | Узкое место | Комментарий |
|---|---|---|
| N1 | Передача документа ~12 мс/10 МБ | **переоценено (F22):** 1.2 мкс/КБ → на 50–200 КБ это 0.06–0.24 мс; не доминирует, range/delta-API — аккуратность, а не необходимость |

## 5. Развилка для ADR (вход)

| Вариант | Lua-ошибки | Лимит инструкций | Изоляция плагина | Размер базы | Вердикт |
|---|---|---|---|---|---|
| A. `unwind` + `catch_unwind` | да | есть | нет | ~7.2 МБ | **закрыт**: D6 |
| B. `abort` + C-hook + safe-pcall + Lua-ошибки значениями | да (возвратом) | есть (C-hook + safe-pcall) | нет | ~4.0 МБ | жизнеспособен, но хрупок; остаётся host-`Err`/паника |
| **C. `abort` + Lua в отдельном процессе** | да | есть (kill / Job Object) | **отказов: жёсткая** (F25) | ~4.3 МБ | **приоритетный кандидат** (F16–F20, F22) |

**Открытое решение по модели процессов (F23):**
«процесс на плагин» vs «один child на все плагины». От этого зависят:
- масштабируемость (N × spawn / N × RSS) при первом варианте,
- «жёсткая изоляция» при втором — иллюзорна (один `spin`/`crash` блокирует/убивает всех).
Решение — в ADR, после замеров RSS (F24).

## 6. Что не проверено (очередь)

- C: **stdio в GUI-приложении (subsystem 2)** — блокер, без этого C не проверялся в конфигурации продукта (§3.3 parent — console, §F21). Честный тест: GUI-хост + child + большой кадр + обрыв.
- **RSS child**: пустой и с 10 МБ документом (F24).
- **Один child на все плагины vs процесс на плагин** (F23): заодно даст RSS-множитель и ответ на вопрос о блокировке.
- **Job Object** (RSS/CPU/time) — v1.4 сам ставит это следующим.
- **Деградация при зависании child на большом кадре** — §6, риск блокировки записи; это же проверит и пункт «stdio в GUI».
- range/delta-API против N1.
- Решение **B vs C** и запись в ADR.
- P3: `MemoryError` на `hog.lua`; `spin.lua` под лимитом; M6 на `count.lua`; M7 (два инстанса в одном процессе).
- P5: host-функции на заглушке + permissions; возврат ошибок Lua-значением.
- P6: внешние строки 5.5 (M9).
- P2: полный M1 (`strip`, baseline именно прототипа).
- API-референс 5.5: `global`, `table.create`, отличия C API (в т.ч. `LUA_REGISTRYINDEX`).
