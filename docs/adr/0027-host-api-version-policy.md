# ADR-0027. Политика совместимости `HOST_API_VERSION`

- **Статус:** **Принят**
- **Дата:** 10.10.2026
- **Основание:** gate перед распространением плагинов (S15); веха H3 «экосистема»,
  Фаза 3 «Расширение API — итеративно» (историческая дорожная карта H3 удалена; политика
  версий — этот ADR + `HOST_API_VERSION`); существующий контракт — `crates/plugin-core`
  (`HOST_API_VERSION`, `Manifest::validate`), `docs/DESIGN_DOC.md` §7.2
- **Связанные:** `docs/DESIGN_DOC.md` §7.2, §8, §16; `docs/PLUGIN_API.md` §1–§4;
  `docs/adr/0021-plugin-isolation-process.md`, `docs/adr/0023-plugin-runtime.md`,
  `docs/adr/0026-local-plugin-catalog.md`; `crates/plugin-core`, `crates/plugin-cli`

---

## 1. Контекст

H2/H3 зафиксировали контракт host ↔ плагин: единственная версия `HOST_API_VERSION = 1`
(`crates/plugin-core/src/lib.rs`). Плагин объявляет `api_version` в `plugin.json`; хост
отвергает `api_version == 0` и `api_version > HOST_API_VERSION` (`Manifest::validate`), проверка
идёт при разборе манифеста (`Manifest::from_json`) — в GUI-скане (`crates/app/src-tauri/src/plugins/scan.rs`)
и в CLI `darmark-plugin` (`crates/plugin-cli`). В `docs/DESIGN_DOC.md` §7.2 уже объявлен принцип
(«обратная совместимость — семантическое версионирование, удаление функций запрещено без мажора»),
но конкретных правил нет: что именно поднимает мажор, сколько длится депрекация, как вводится
новая версия.

Фаза 3 H3 (расширение API) идёт **итеративно, по потребностям реальных плагинов**.
Без политики каждая итерация рискует сломать уже написанные
плагины — риск, который «дёшево закрыть сейчас и дорого после публикации». S15 —
**gate перед публичным распространением плагинов**.

Версия в коде **однокомпонентная** (целое ≥ 1), а не `major.minor.patch`; политика должна
соответствовать этой форме.

---

## 2. Решение

**Фиксируется политика совместимости контракта host ↔ плагин на базе единственного целочисленного
`HOST_API_VERSION`: мажор — только несовместимые изменения, аддитивные расширения мажор не
поднимают, депрекация — двухступенчатая (deprecated → removed через мажор).**

### 2.1. Семантика версии

1. `HOST_API_VERSION` — **единственное целое ≥ 1**, обозначающее **мажор контракта** host ↔ плагин
   (не `major.minor.patch`). Ноль недопустим (`ManifestError::ApiVersionZero`).
2. Мажор поднимается **только** при **несовместимом** изменении: удаление, переименование или
   смена контракта (сигнатуры, семантики, типа результата) существующей host-функции, точки
   входа, события или поля конверта; сужение допустимых значений, из-за которого ранее валидный
   вызов становится невалидным.
3. **Аддитивные** изменения мажор **не поднимают** (перечень — §2.4).

### 2.2. Контракт плагина

4. Плагин **обязан** объявлять `api_version` в `plugin.json` — целое ≥ 1; это версия, на которую
   плагин написан.
5. Хост **принимает** `api_version ≤ HOST_API_VERSION` и **отвергает** `api_version > HOST_API_VERSION`
   ошибкой `ManifestError::ApiVersionTooNew { found, host }` с сообщением
   `api_version {found} новее поддерживаемого хостом {host}`. Отдельно отвергается `api_version == 0`
   ошибкой `ManifestError::ApiVersionZero` («api_version должен быть ≥ 1»).
6. Проверка — **на хосте при разборе манифеста** (`Manifest::from_json` → `validate`), **до** spawn
   child-процесса; одинакова для GUI-скана и CLI. Отвергнутый плагин **не запускается**; ошибка
   попадает в отчёт скана/вывод CLI с путём к `plugin.json`.

### 2.3. Депрекация — двухступенчатая

7. **Ступень 1 — deprecated.** Функция/точка входа/событие остаётся полностью работоспособной и
   помечается в `docs/PLUGIN_API.md` как устаревшая, с указанием замены и мажора, в котором будет
   удалена.
8. Плагин, использующий deprecated-функцию, **продолжает работать без ошибки** в течение всего
   окна; хост **должен** логировать предупреждение при обслуживании такого вызова.
9. **Окно депрекации — не менее одного полного мажорного цикла:** минимум один принятый
   ADR/релиз с пометкой «deprecated» до момента удаления.
10. **Ступень 2 — removed.** Удаление допускается **только** вместе с подъёмом `HOST_API_VERSION`
    (несовместимое изменение, §2.1). До этого удаление запрещено.

### 2.4. Что НЕ поднимает мажор (аддитивные изменения)

11. Мажор **не поднимают**: новые host-функции; новые поля/варианты конверта (обратно совместимые,
    с `#[serde(default)]`); новые события; новые permissions; новые точки входа; новые поля
    `contributes`.
12. **Инвариант совместимости:** плагин с `api_version = N` продолжает корректно работать на хосте
    того же мажора `N` после любого аддитивного расширения. Проверяется тестами (§2.5).

### 2.5. Обязанности

13. Любая **смена контракта обязана** сопровождаться обновлением `docs/PLUGIN_API.md` в том же
    изменении (§1 манифест, §2 точки входа, §3 host-функции, §4 события).
14. Несовместимое изменение и смена `HOST_API_VERSION` **обязаны** фиксироваться в реестре ADR
    (`docs/DESIGN_DOC.md` §16) — новым ADR или записью; deprecated-пометка — в `PLUGIN_API.md`.
15. **Тесты совместимости.** При аддитивном расширении — тест, что манифест/плагин с меньшим
    `api_version` валиден и работает; при несовместимом — тест, что `api_version > HOST_API_VERSION`
    отвергается. База уже есть: `crates/plugin-core/src/manifest.rs` (`accepts_reference_manifest`,
    `rejects_api_version_too_new`, `rejects_api_version_zero`),
    `crates/app/src-tauri/src/plugins/tests.rs`, `crates/plugin-cli/src/catalog.rs`.

### 2.6. Процедура

16. Проверка версии — **на хосте при загрузке манифеста** (`Manifest::from_json`/`validate`), до
    старта child; не в плагине и не в рантайме Lua.
17. **Ввод новой версии:** поднять `HOST_API_VERSION` в `crates/plugin-core/src/lib.rs`; обновить
    `docs/PLUGIN_API.md` и (при необходимости) §7.2 `DESIGN_DOC.md`; оформить ADR (§2.5); расширить
    тесты (§2.5).
18. Понижение версии или удаление версии/функции без ADR **запрещено**.

### 2.7. Минимальная принимаемая версия — не вводится

19. Хост **не** отвергает плагины по нижней границе версии: принимается любой `api_version` в
    диапазоне `1..=HOST_API_VERSION`. Причина — сохранить аддитивную совместимость (депрекация,
    §2.3, даёт авторам полный мажорный цикл на миграцию); отвергать плагины, которые не используют
    удалённое, было бы вредно.
20. Плагин с `api_version < HOST_API_VERSION` загружается; хост **должен** логировать предупреждение.
21. Введение минимальной версии (`MIN_SUPPORTED_API_VERSION`) возможно **только** вместе с
    breaking-major **без** предшествующей депрекации — отдельным ADR; по умолчанию запрещено.

## 3. Последствия

**Положительные:**

- Итерации Фазы 3 не ломают существующие плагины: аддитивные изменения гарантированно совместимы.
- Единая точка проверки (`plugin-core`) — GUI-скан и CLI ведут себя одинаково, до spawn child.
- Депрекация даёт авторам окно миграции; мажор — явный, документируемый сигнал о несовместимости.

**Отрицательные / ограничения:**

- Хост принимает `api_version ≤ HOST_API_VERSION`, поэтому при подъёме мажора плагины **прежнего
  мажора не отвергаются автоматически** (§2.7 — так и задумано). Вызов удалённой/недоступной функции
  возвращает **явную** ошибку контракта (`unknown method`/`not_implemented`), а не тихий сбой; плюс
  предупреждение в логе при `api_version < HOST_API_VERSION`.
- Однокомпонентная версия не выражает «минимальную версию хоста» для плагина, использующего новую
  аддитивную функцию (аддитивное изменение мажор не поднимает). Плагин должен сам обрабатывать
  отсутствие функции (feature-detect / обработка ошибки).
- Политика — **соглашение**: контроль — тестами и ревью, а не отдельным механизмом рантайма.

---

## 4. Отклонённые альтернативы

- **Semver `major.minor.patch` для `HOST_API_VERSION`.** Отклонено: у контракта нет «патч»-измерения,
  аддитивные изменения не требуют новой версии, а код уже использует одно целое ≥ 1.
- **Поднимать мажор на любое изменение (включая аддитивное).** Отклонено: заставляло бы переписывать
  `api_version` у всех плагинов и обесценивало версию; противоречит обещанию «аддитивно — совместимо».
- **Одноступенчатое удаление (сразу removed).** Отклонено: не оставляет авторам окна миграции;
  после публичного распространения недопустимо.
- **Не версионировать контракт (всегда `1`).** Отклонено: нельзя отвергнуть плагин, требующий более
  новый хост, и нет сигнала о несовместимом изменении.
- **Проверять версию в рантайме/child.** Отклонено: поздно и дорого (spawn уже случился);
  валидация манифеста — первый барьер жизненного цикла (`scan → validate → load`).
