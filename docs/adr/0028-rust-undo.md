# ADR-0028. Rust-undo: модель diff-undo и единый стек правок (D5)

- **Статус:** **Принят**
- **Дата:** 11.10.2026
- **Основание:** D5 (`docs/DESIGN_DOC.md` §4.1/§4.2/§4.3); S16 (gate перед реализацией)

---

## 1. Контекст

D5 принят: владелец текста и undo-стека — Rust `Document` (§4.1/§4.2).
Правки текста идут через Rust: ввод редактора (`update_document`) и программные
правки (`apply_edit` — `formatActions`, плагины).

**Нативный undo `<textarea>` непригоден:** программная смена `value` сбрасывает
историю браузера (§13 DESIGN_DOC). Нужна единая история для ввода и правок плагинов.

S16 — gate перед реализацией: зафиксировать rev-семантику и контракт undo до кодинга.

---

## 2. Решение

**Diff-модель undo в Rust: единый стек для ввода и `apply_edit`, операция — замена
байтового диапазона, отдельные `undo`/`redo`, лимит по числу операций, только в памяти.**

### 2.1. Модель

1. Единица истории — **операция замены диапазона** (байтовые смещения, UTF-8).
2. Поле `rev` из операции уходит: отмена — операция над текстом, а не над ревизией.
3. `undo` применяет обратную замену, `redo` — прямую.

### 2.2. Единый стек

4. Все правки идут через **один** стек: ввод редактора (`update_document`) и
   программные правки (`apply_edit`).
5. `update_document` фиксирует **минимальный** diff-оп (общий префикс/суффикс);
   `apply_edit` — **точную** оп по заданному диапазону.
6. Сигнатуры `update_document`/`apply_edit` **не меняются** — фронт и плагины работают
   без правок транспорта.
7. Правка без смены текста оп не пишет и `redo` не очищает (эхо-защита).

### 2.3. undo / redo

8. Новые операции стора: `undo`/`redo` возвращают текст **после** операции и диапазон
   результата (байты UTF-8) для восстановления выделения во фронте.
9. Пустой стек → no-op.

### 2.4. Команды IPC

10. Новые команды: `undo_document(id)`, `redo_document(id)`; обёртки — в `tauri.ts`.

### 2.5. rev, кэш, события

11. `rev` растёт на **любой** реальной смене текста, включая undo/redo → инвалидация
    кэша рендера и событие `document:changed` для плагинов.

### 2.6. Лимит и персистентность

12. Стек ограничен по числу операций (константа в коде); при переполнении отбрасываются
    **самые старые** оп-ы.
13. Стек — **только в памяти**, на диск не персистится (§4.2).
14. Фронт перехватывает `Ctrl+Z`/`Ctrl+Y`/`Ctrl+Shift+Z` и `beforeinput` с `inputType`
    `historyUndo`/`historyRedo`, вызывает команды и применяет результат.

## 3. Последствия

**Положительные:**

- Единая точка правок (D5): ввод и `apply_edit` отменяются одним стеком.
- Нативный undo заменяется предсказуемым: программные правки не рвут историю.
- Транспорт не меняется: diff считается на Rust из уже отправленного текста.
- `rev`/кэш/события переиспользуются.

**Отрицательные / ограничения:**

- **Coalescing грубый:** границей оп-а служит дебаунс ввода — тонкой группировки нет.
- **Память:** каждая оп держит две строки; при лимите и крупных вставках объём заметен.
- **`dirty` остаётся на TS** (§4.2): undo к сохранённому тексту корректно сбрасывает флаг.
- **Выделение возвращается во фронт** байтовым диапазоном (Rust не владеет выделением).
- **Стек не персистится:** перезапуск приложения историю теряет.

---

## 4. Отклонённые альтернативы

- **Delta-транспорт.** Отклонён: дороже, ломает текущий конвейер (весь текст через IPC).
- **Нативный undo `<textarea>`.** Отклонён: программная смена `value` рвёт историю (§13).
- **Персистентный undo.** Отклонён: история эфемерна, перезапуск её потеряет.
- **`rev` в `EditOp`.** Отклонён: усложняет без пользы — отмена работает с текстом.
