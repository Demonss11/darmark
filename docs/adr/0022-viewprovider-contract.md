# ADR-0022. Контракт ViewProvider: два тира представлений

- **Статус:** **Принят**
- **Дата:** 07.10.2026
- **Основание:** реализация H1 (Фазы 3–5): `crates/app/src/viewRegistry.ts`, `previewView.ts`,
  `editorView.ts`, `layout.ts`, `paneHost.ts`
- **Связанные:** `docs/DESIGN_DOC.md` §2, §5.2–§5.4, §9.4, §11.2, §16;
  `tasks/TZ-H1.md` §2 (Фазы 4–6), `tasks/TZ-H1-F4.md`, `tasks/TZ-H1-F5.md`

## 1. Контекст

Продукт расширяется пользовательскими Lua-плагинами (H2) без пересборки (§1.2). Плагину нужно
**показывать разметку** в панели, но плагин исполняется в отдельном процессе и **не видит DOM**
(§2, §11.4). Нужен контракт представления, который:

- одинаково работает для встроенных view и для будущих плагинных;
- не пропускает произвольный доступ к хосту (`document`/`window`/`fetch`/ФС);
- не гонит горячий путь предпросмотра (каждый debounce) через интерпретатор (D2).

## 2. Решение

Вводится **два тира** провайдеров представлений (§5.3):

1. **Тир 1 — plugin-safe** (`HtmlViewProvider`): JSON на входе, HTML на выходе.
   ```ts
   interface HtmlView { render(doc: DocumentSnapshot): Promise<void>; dispose(): void }
   interface HtmlViewProvider { kind; title; createView(ctx: ViewContext, opts: Json): HtmlView }
   ```
   Ровно то, что сможет отдать Lua-плагин: строка HTML + JSON, без DOM.

2. **Тир 2 — built-in only** (`DomViewProvider`): полный DOM.
   ```ts
   interface DomView { activate(); deactivate(); dispose() }
   interface DomViewProvider { kind; title; createView(ctx: ViewContext, host: HTMLElement, opts: Json): DomView }
   ```
   Для встроенных контроллеров, которым нужен DOM (редактор; в будущем — инспектор панели).

**Единственная «песочница» — `ViewContext` (§5.4):** `document()`, `edit()`, `render()`,
`status()`, `openExternal()`, `onDocument()`. Никакого доступа к `document`/`window`/`fetch`/ФС.
Контекст передаётся в `createView`; тир-1 его использует, но `innerHTML` пишет только реализация view.

**Реализация H1:**

- `previewView` — **тир-1** (`HtmlView`), но **встроен на хосте** (D2): `createView` получает живые
  DOM-зависимости (`previewEl`, `RenderIndex`, колбэк), потому что хост-провайдер вправе; плагин
  получит строгий `Json`. Это единственное место, где выполняется `preview.innerHTML = html`.
- `editorView` — **тир-2** по природе (textarea, полный DOM); в H1 создаётся напрямую, регистрация
  `DomViewProvider` — H2.
- Контракт `HtmlView`/`DomView` уже сейчас использует `dispose()`/unsubscribe (§5.6) — готовность
  к нескольким панелям.
- Обратная маршрутизация (H2, §9.4): клики внутри HTML-плагина идут через делегированный слушатель
  контейнера view и `data-p-<pluginid>-*` — **единственный** класс атрибутов, переживающий
  санитизацию (D7, §11.2).

## 3. Почему два тира, а не один

Единый контракт «дай DOM» невозможен для плагина (кросс-процессный, без DOM), а единый контракт
«только HTML» делает редактор невозможным (нужен textarea/selection). Два тира честно разделяют
**plugin-safe** и **host-only** поверхности, поэтому миграция на Lua — замена транспорта, а не
перераздел модели (§5.3).

## 4. Последствия

**Положительные:**

- Плагинные view (H2) подключаются через тот же `createView`/`render` — интерфейс не меняется.
- Горячий путь предпросмотра остаётся на хосте (D2), не через интерпретатор.
- Единая точка санитизации: HTML плагина идёт через тот же `sanitize_html`, что и `render_markdown`
  (§11.1–§11.2).
- `ViewContext` заведомо уже, чем доступный из `main.ts` — плагину нельзя отдать «лишнее».

**Отрицательные / цена:**

- Две поверхности вместо одной: провайдер должен выбрать тир (или реализовать оба).
- Встроенному тир-1 провайдеру (`previewView`) приходится расширять `opts` за пределы `Json`
  (живые зависимости); это компенсируется generic-параметром `opts` в реестре и кастом в провайдере.

## 5. Отклонённые альтернативы

- **Один тир (только DOM).** Невозможен для плагина: кросс-процессный, без DOM (§2, §11.4).
- **Один тир (только HTML).** Делает редактор невозможным (textarea, selection).
- **Preview как плагин.** Отклонён решением D2: горячий путь (каждый debounce) недопустимо гнать
  через интерпретатор.
