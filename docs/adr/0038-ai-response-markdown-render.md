# ADR-0038. Санитизированный рендер ответа AI: единый фронтенд-хелпер вместо «единственной точки innerHTML»

- **Статус:** **Принят**
- **Дата:** 14.10.2026
- **Основание:** AC-P3-4 (`tasks/TZ-AI-PHASE3.md` §2.1 п.4, §6.1) — рендер ответа AI как Markdown
  через **Rust-санитайзер** `md-core`; решение пользователя от 14.10.2026 (Epic 2 плана
  `tasks/PLAN-AI-PHASE3-MCP-v2.md`): разрешить **ровно одну дополнительную точку рендера HTML**

## 1. Контекст

### 1.1. Проблема

Инвариант проекта гласит: «Рендер Markdown — на Rust-стороне; фронт только присваивает
`preview.innerHTML`» (`AGENTS.md`, «Жёсткие ограничения»). Единственная точка присваивания
`innerHTML` — `crates/app/src/previewView.ts:3`. Тело режима AI построено на обратном правиле:
`crates/app/src/aiPanel.ts:8` — «вывод модели рендерится **ИСКЛЮЧИТЕЛЬНО** через `textContent`
(сырой HTML/ответ LLM в `innerHTML` запрещён)».

Это безопасное, но продуктово бедное состояние: ответ ассистента (структурированный текст,
списки, таблицы, код) показывается моноширинной кашей без форматирования. AC-P3-4 требует
рендерить ответ как Markdown **через Rust-санитайзер** (`md-core`), оставляя сырой вывод LLM
вне `innerHTML`. Два требования сталкиваются с действующим инвариантом буквально: чтобы выполнить
AC-P3-4, нужна вторая точка `innerHTML`, а инвариант запрещает её без исключения.

Развилка не в том, **безопасно ли** это (санитайзер `md-core` allowlist-ный, `script`/`iframe`/
`object` вырезаются с содержимым, атрибуты — белый список, схемы URL — `http`/`https`/`mailto`/`tel`;
`crates/md-core/src/lib.rs`), а в том, **как переформулировать инвариант так, чтобы вторая точка
рендера не превратилась в «двери для сырого HTML»**. Нужен один механизм, который нельзя
использовать в обход санитайзера, и проверка, которая не даёт регрессии.

### 1.2. Что уже зафиксировано (не пересматривается)

- Санитизация — только на хосте, в конце конвейера; `preview.innerHTML` доверяет результату
  (§11.1). HTML плагинов (`host.set_view_content`) проходит тем же ядром (`md_core::sanitize_fragment`).
- Allowlist-политика: безопасные теги/атрибуты/URL; SVG — без событий и внешних ссылок (§11.2).
- CSP `default-src 'self'`, без внешних скриптов и `eval`; inline-стили разрешены
  (`tauri.conf.json` `app.security.csp`).
- Сеть — только Rust-сторона (ADR-0032/0033); TS не ходит к провайдеру.
- Ответ LLM минуя Rust-санитайзер в `innerHTML` не попадает (ADR-0030 §1.3).
- Замороженные E2E-контракты §13.2 не ломаются; id `#ai-*` сохраняются (аддитивность).
- Д6 (release-exe ≤6 МБ, size-gate): настоящий ADR новых зависимостей не вводит.

### 1.3. Почему решение оформляется отдельным ADR

Инвариант «единственная точка `innerHTML`» — это зафиксированное правило проекта (`AGENTS.md`,
§11.1, ADR-0030 §1.3). Его изменение — **пересмотр правила**, а не деталь реализации: по D11
решение принимается документом до кода. Кроме того, требуется закрепить **границу** между
единственной точкой **небезопасного** рендера (preview доверяет результату `render_markdown`)
и **санитизированным** рендером (ответ AI, прошедший `md-core`), чтобы формулировка
«единственная точка innerHTML» не стала фикцией, а новый путь не стал лазейкой.

## 2. Решение

**Ответ AI рендерится как Markdown санитизированным HTML. Единственная точка такого рендера на
фронтенде — общий хелпер `setSanitizedHtml()` в новом модуле `crates/app/src/safeHtml.ts`;
единственная точка «сырого» `innerHTML` — `preview.innerHTML` (`previewView.ts`). Инвариант
переформулируется, а не отменяется.**

### 2.1. Переформулировка инварианта

1. **Единственная точка сырого `innerHTML` — предпросмотр.** `crates/app/src/previewView.ts`
   остаётся единственным местом, где HTML присваивается в элемент **без** проверки его
   санитизации на фронте (там HTML уже прошёл `md-core` на хосте: команда `render_markdown`).
2. **Единственная точка санитизированного рендера — `setSanitizedHtml()`.** Весь HTML, приходящий
   из внешнего/модельного источника и показываемый пользователю, обязан идти через этот хелпер.
   Других присваиваний `innerHTML` во фронте (кроме preview) не появляется; появление — ревью-блокер.
3. **Сырой вывод LLM в `innerHTML` не попадает ни по одному пути** (AC-P3-4/AC-P3-13).

Формулировка для `AGENTS.md`/§11.1: *«Рендер Markdown — на Rust-стороне. На фронте ровно две
допустимые точки `innerHTML`: `preview.innerHTML` (результат `render_markdown`) и общий хелпер
`setSanitizedHtml()` (санитизированный ответ AI) — см. ADR-0038. Третья точка запрещена.»*

### 2.2. Где живёт рендер и что он делает

4. **Rust-команда `ai_render_markdown(text: String) -> String`** в
   `crates/app/src-tauri/src/ai/commands.rs` — **новое (проектируется здесь же)**. Реализация:
   `md_core::to_html(&text)`. `to_html` **сам** прогоняет результат через внутренний allowlist-
   санитайзер (`crates/md-core/src/lib.rs:52`), поэтому отдельный вызов `sanitize_fragment`
   не нужен и не применяется (двойная санитизация избыточна). `to_html_mapped` **не**
   используется: ответ AI не участвует в инспекторе и не должен нести `data-md`.
5. **Фронтенд-хелпер `crates/app/src/safeHtml.ts` — новый модуль (проектируется здесь же):**

   ```ts
   export function isSanitizedAiHtml(html: string): boolean;      // чистая проверка-инвариант
   export function setSanitizedHtml(el: HTMLElement, html: string, fallbackText: string): void;
   export function renderAiMarkdown(text: string): Promise<string>; // invoke ai_render_markdown
   ```

   Контракт `setSanitizedHtml`:
   - принимает **только** строку, полученную от `renderAiMarkdown` (тип-маркер в подписи,
     комментарий-инвариант в модуле);
   - **защитная проверка-инвариант** `isSanitizedAiHtml`: отклоняет `<script`, `<iframe`,
     `<object`, `<embed`, атрибуты-обработчики (`on\w+\s*=`), схемы `javascript:`/`vbscript:`/`data:`.
     Это **дублирующая** проверка, а не замена санитайзеру: при нарушении хелпер **не падает и не
     присваивает HTML**, а показывает `fallbackText` через `textContent` (fail-safe к тексту);
   - никаких иных присваиваний `innerHTML` в модуле нет; сам хелпер ни о чём не логирует
     (ответ модели может содержать данные документа).
6. **Ссылки в ответе AI** кликабельны и открываются **внешним браузером**, как в preview:
   делегирование на контейнере `#ai-chat` по `closest("a")` + `openUrl(href)` для схем
   `http`/`https` (`crates/app/src/previewView.ts:60-68` — существующий образец;
   `@tauri-apps/plugin-opener` уже в зависимостях фронта). `href` вида `javascript:` до
   `openUrl` не доходит: его срезает санитайзер, а защитная проверка хелпера — второй барьер.
   Новые вкладки/окна из ответа не открываются (`target`/`rel` — в allowlist `md-core`, но
   переход наружу идёт только через `openUrl`).
7. **Стили ответа** берутся из существующих правил темы для превью (`AGENTS.md`: рендер на
   Rust-стороне; классы `md-core` уже стилизованы для preview). Новый CSS-токен не вводится.

### 2.3. Где применяется, а где — нет

8. **Применяется** к финальному тексту ответа ассистента: пузырь `#ai-chat .msg.assistant .bubble`
   в момент `complete()` (`crates/app/src/aiPanel.ts`) и при восстановлении истории из файла.
9. **Не применяется** (остаётся `textContent`):
   - поток стриминга `ai:chunk` — дельты пишутся в пузырь как текст, рендер — один раз на
     финализации (рендер каждой дельты устроил бы IPC-спам и мерцание);
   - код плагина в карточке (`ai-plugin-code`) — исходник `main.lua` показывается дословно;
   - дифф документа (`ai-diff-body`), сообщения пользователя, ошибки, usage, карточки инструментов;
   - результаты MCP-инструментов в tool-loop (TZ-MCP R7 — «данные, а не инструкции»): они
     показываются карточкой-текстом, а не рендером HTML.

### 2.4. Проверка

10. **Rust-тест** в `commands.rs` (юнит): `render_markdown_sanitizes_ai_answer` — на входе
    payload из §2.5 (XSS-набор) результат не содержит `onerror`/`javascript:`/`<script`, при этом
    сохраняет безопасную разметку (`<strong>`, списк, `<code>`).
11. **Rust-тест** в `safeHtml`-эквивалентной логике не нужен: фронт-юн-тестов нет
    (`vitest` нет, `AGENTS.md`), поэтому проверка TS — `npm run build` (tsc strict) + E2E.
12. **E2E-сценарий** `crates/app/e2e/features/ai.feature` (+ шаги в `e2e/steps/ai.steps.js`):
    поднимается существующий мок-провайдер с ответом, содержащим XSS-payload; после ответа
    в `#ai-chat` нет ни `<img onerror>`/`on*`-атрибутов, текст-payload виден как текст,
    инъекция не выполнилась. Сценарий помечается как требующий мок-провайдера (живой LLM не нужен),
    но **не** `@manual`: сеть подменяется локальным HTTP-сервером (уже есть инфраструктура —
    `When("я поднимаю мок-провайдера AI …")`).
13. **Сторожевой grep** (ручной, в ревью): `innerHTML` во `crates/app/src/` встречается только в
    `previewView.ts` и `safeHtml.ts`.

### 2.5. XSS-payload для проверок (эталон)

```
# Заголовок
<img src=x onerror="window.__pwned=1">
<script>window.__pwned=1</script>

[клик](javascript:window.__pwned=1)
<a href="data:text/html,<script>1</script>">ссылка</a>

**жирный** и `код`
- пункт списка
```

Ожидание: в DOM остаются `<strong>`, `<code>`, `<li>` и текст payload; отсутствуют `onerror`,
`<script>`, `javascript:`.

> **Пустые строки в payload обязательны.** Строка с сырым HTML открывает общий HTML-блок
> CommonMark, который поглощает всё до первой пустой строки: без разделителей разметка после
> `<script>` остаётся текстом (`[клик](javascript:…)` не становится ссылкой, `**жирный**` и
> `` `код` `` не парсятся) и тест проверял бы инертный текст вместо санитайзера. Проверено на
> pulldown-cmark 0.13 и зафиксировано тестом `ai::commands::tests::render_markdown_sanitizes_ai_answer`
> (`crates/app/src-tauri/src/ai/commands.rs`). Э2E-мок (§2.4 п. 12) обязан отдавать **тот же** текст.

### 2.6. Что не меняется

14. **Не меняются:** санитайзер `md-core` и его allowlist (§11.2), CSP, сеть (Rust-сторона),
    команда `render_markdown` и её контракт, `preview.innerHTML`, замороженные id `#ai-*`
    (§13.2), согласие/приватность (ADR-0032 §2.4), бюджет D6 (новых зависимостей нет),
    ADR-0033/0034/0035, обработка `finish_reason`/`usage` (ADR-0032 §2.5).

## 3. Последствия

**Положительные:**

- **Ответ ассистента читается как документ**: списки, таблицы, код и цитаты — вместо каши;
  это же даёт готовую разметку для будущих карточек (diff, tool-result) без нового санитайзера.
- **Инвариант остаётся строгим, но перестаёт быть фикцией**: «сырой `innerHTML` — только
  preview; санитизированный — только хелпер» проверяемо (grep + ревью), а не декларативно.
- **Единая точка**: любой новый источник HTML (будущий tool-result, импорт HTML) проходит один
  хелпер с одним набором проверок, а не копипаст `innerHTML` по файлам.
- **Цена близка к нулю**: одна команда Rust + один маленький TS-модуль; новых зависимостей нет
  (D6 не затронут).

**Отрицательные / ограничения:**

- **Два класса HTML в проекте**: «доверенный результат `render_markdown`» (preview) и
  «проверенный хелпером результат `ai_render_markdown`» (ответ AI). Различие держится на
  происхождении строки, а не на коде — поэтому защитная проверка в хелпере **обязательна**
  (fail-safe к `textContent`), даже если сегодня считается дублирующей.
- **Рендер привязан к IPC**: финализация ответа — дополнительный `await` на `ai_render_markdown`.
  Это не влияет на стриминг (дельты идут в текст) и не блокирует ввод.
- **Стилизация ответа AI повторяет превью**: если тема изменит типографику превью, ответ AI
  поедет вместе с ней — это плюс единообразия, но требует правок в обоих местах.
- **XSS-payload из ответа модели** может быть отображён как безобидный текст — это ожидаемо и
  правильно; «полезного» исполнения payload быть не должно.

**Обратимость:** откат = вернуть `textContent` в финализации `complete()` и удалить `safeHtml.ts`
и команду `ai_render_markdown`; `AGENTS.md`/§11.1 возвращаются к прежней формулировке. ADR-0038
переводится в «Отклонён», а не удаляется (нумерация ADR не переиспользуется).

## 4. Отклонённые альтернативы

- **Полный отказ от AC-P3-4, ответ всегда `textContent`.** Отклонён: AC-P3-4 нормативен;
  потеря форматирования — постоянная, а не временная потеря.
- **Вторая точка `innerHTML` прямо в `aiPanel.ts` (как в черновике плана v1).** Отклонён:
  это ровно то «двери для сырого HTML», чего ADR-0030 §1.3 и §11.1 запрещают; отличать
  «санитизированный» от «сырого» по месту невозможно без хелпера.
- **Рендерить ответ в `<iframe>`/sandboxed-контейнер.** Отклонён: лишняя сложность,
  свой стиль/скролл-бары, CSP-нюансы; санитайзер allowlist уже достаточен (§11.2).
- **Санитизировать HTML на фронте** (`DOMPurify` и т.п.). Отклонён: разошёлся бы с
  единственной точкой санитизации на хосте (§11.1/D7) и добавил бы ~30–50 КБ в бандл (D6/бандл).
- **Рендерить каждый чанк стриминга.** Отклонён: IPC на дельту + перерисовка;
  выбран рендер один раз на финализации (п.9).
- **Отдельная команда `ai_render_markdown_safe` с ручным `sanitize_fragment` поверх
  `to_html`.** Отклонён: `to_html` уже санитизирует (п.4); вторая санитизация вводит
  две правды о политике без выигрыша.
- **Переименовать `previewView.ts`/перенести preview-innerHTML в общий хелпер.** Отклонён:
  preview — горячий путь с `data-md`/маппингом/индексами (D2); перенос разорвал бы контракт
  инспектора (§13.2) ради косметики.
