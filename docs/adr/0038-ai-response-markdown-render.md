# ADR-0038. Санитизированный рендер ответа AI: единый фронтенд-хелпер вместо «единственной точки innerHTML»

- **Статус:** **Принят**
- **Дата:** 14.10.2026
- **Основание:** AC-P3-4 (`tasks/TZ-AI-PHASE3.md` §2.1 п.4, §6.1) — рендер ответа AI как Markdown
  через **Rust-санитайзер** `md-core`; Epic 2 плана `tasks/PLAN-AI-PHASE3-MCP-v2.md`; текущее
  состояние — `textContent`, форматирования нет; ограничения: §1.2.

  `docs/adr/0030-bottom-dock-two-modes.md` (§1.3 — уточняется п.1 настоящего ADR);
  `docs/adr/0032-ai-provider-openai.md` §2.5 (согласие/приватность),
  `docs/adr/0033-ai-http-client-streaming.md` (сеть — Rust-сторона),
  `docs/adr/0034-ai-runtime-placement.md` (AI в процессе GUI),

## 1. Контекст

### 1.1. Проблема

Инвариант проекта: `preview.innerHTML` — единственная точка (`AGENTS.md`); режим AI сегодня
рендерит через `textContent` (`aiPanel.ts:8`). AC-P3-4 требует рендерить ответ как Markdown
**через Rust-санитайзер** (`md-core`), оставляя сырой вывод LLM вне `innerHTML` — это нужна
вторая точка `innerHTML`, а инвариант запрещает её без исключения.

Развилка не в безопасности (санитайзер allowlist-ный, `DESIGN_DOC` §11.2), а в том, **как
переформулировать инвариант так, чтобы вторая точка рендера не превратилась в «двери для сырого
HTML»**. Нужен один механизм, который нельзя использовать в обход санитайзера, и проверка,
которая не даёт регрессии.

### 1.2. Что уже зафиксировано (не пересматривается)

- Хост-санитификация и allowlist (§11.1–11.2), CSP, сеть (ADR-0032/0033) — без изменений.
- Замороженные E2E-контракты §13.2: id `#ai-*` сохраняются (аддитивность).
- D6 (size-gate): новых зависимостей не вводится.

### 1.3. Почему решение оформляется отдельным ADR

Пересмотр инварианта `AGENTS.md`/§11.1 (ADR-0030 §1.3) оформляется документом по D11; закрепляется граница между небезопасным рендером preview и санитизированным ответом AI.

---

## 2. Решение

**Ответ AI рендерится как Markdown санитизированным HTML. Единственная точка такого рендера на
фронтенде — общий хелпер `setSanitizedHtml()` в новом модуле `crates/app/src/safeHtml.ts`;
единственная точка «сырого» `innerHTML` — `preview.innerHTML` (`previewView.ts`). Инвариант
переформулируется, а не отменяется.**

### 2.1. Переформулировка инварианта

1. **Все точки `innerHTML` во фронте перечислены явно, и список исчерпывающий:**

   | Файл | Что присваивает | Чем санитизировано |
   |---|---|---|
   | `crates/app/src/previewView.ts` | результат команды `render_markdown` | `md-core` на хосте (allowlist) |
   | `crates/app/src/safeHtml.ts` (**новый**, §2.2) | ответ модели через `ai_render_markdown` | `md-core::to_html` на хосте + проверка-инвариант в хелпере |
   | `crates/app/src/pluginViews.ts` | HTML вкладки плагина (`applyHtml`/`setActive`) | хост: `md_core::sanitize_fragment` |

   Точка плагинов существовала до ADR — она перечисленная, не разрешённая: правило «ни одной новой точки» применяется к ней так же.
2. **Новые точки `innerHTML` не появляются** — появление новой точки ревью-блокер.
3. **Сырой вывод LLM в `innerHTML` не попадает** ни по одному пути (AC-P3-4/AC-P3-13).

Формулировка для `AGENTS.md`/§11.1: *«Рендер Markdown — на Rust-стороне. На фронте `innerHTML`
допустим ровно в трёх перечисленных местах: `previewView.ts` (результат `render_markdown`),
`safeHtml.ts` → `setSanitizedHtml()` (санитизированный ответ AI, ADR-0038), `pluginViews.ts`
(HTML вкладки плагина, санитизирован хостом). Четвёртая точка запрещена.»*

### 2.2. Где живёт рендер и что он делает

4. **Rust-команда `ai_render_markdown(text: String) -> String`** в
   `crates/app/src-tauri/src/ai/commands.rs` — **новое (проектируется здесь же)**. Тонкая
   обёртка над `md_core::to_html` (встроенный allowlist-санитайзер); `to_html_mapped` не
   используется — ответ AI не участвует в инспекторе и не должен нести `data-md`.
5. **Фронтенд-хелпер `crates/app/src/safeHtml.ts` — новый модуль (проектируется здесь же).**
   Экспортирует `setSanitizedHtml` (рендер + инвариант), `isSanitizedAiHtml` (чистая
   проверка), `renderAiMarkdown` (обёртка `invoke`). Контракт `setSanitizedHtml`:
   - принимает строку, полученную от `renderAiMarkdown`/`ai_render_markdown`; происхождение
     фиксируется **комментарием-инвариантом** в модуле (брендированный тип сознательно не вводится:
     он не даёт гарантий на границе IPC, где строка приходит из команды);
   - **защитная проверка-инвариант** `isSanitizedAiHtml` отклоняет известные XSS-паттерны
     (скрипты, обработчики, `javascript:`-схемы) и при нарушении показывает `fallbackText`
     через `textContent` (fail-safe к тексту);
   - никаких иных присваиваний `innerHTML` в модуле нет; сам хелпер ни о чём не логирует
     (ответ модели может содержать данные документа).
6. **Ссылки в ответе AI** открываются внешним браузером через `openUrl` — как в preview
   (`previewView.ts:60-68`); `href="javascript:"` срезается санитайзером + проверкой хелпера.
   Новые вкладки/окна из ответа не открываются.
7. **Стили ответа** — существующие правила темы для превью; новый CSS-токен не вводится.

### 2.3. Где применяется, а где — нет

8. **Применяется** к финальному тексту ответа ассистента: пузырь `#ai-chat .msg.assistant .bubble`
   в момент `complete()` (`crates/app/src/aiPanel.ts`) и при восстановлении истории из файла.
9. **Не применяется** (остаётся `textContent`): поток стриминга `ai:chunk` (рендер один раз
   на финализации — иначе IPC-спам и мерцание); код плагина в карточке (`ai-plugin-code`);
   дифф документа (`ai-diff-body`), сообщения пользователя, ошибки, usage, карточки инструментов;
   результаты MCP-инструментов в tool-loop (TZ-MCP R7 — «данные, а не инструкции»).

### 2.4. Проверка

10. **Rust-тест** `render_markdown_sanitizes_ai_answer` в `ai/commands.rs`: XSS-payload
    из §2.5 не выполняется, безопасная разметка сохраняется.
11. **Фронт-юнит-тестов нет** (`AGENTS.md`) — проверка TS через `npm run build` + E2E.
12. **E2E-сценарий** `ai.feature`: мок-провайдер отдаёт XSS-payload; в `#ai-chat` нет `on*`-
    атрибутов, payload виден как текст. Не `@manual` — сеть подменяется локальным сервером.
13. **Сторожевой grep** (ручной, в ревю): `innerHTML` присваивается только в `previewView.ts`,
    `safeHtml.ts` и `pluginViews.ts` (§2.1); любое новое присваивание — блокер.


### 2.5. XSS-payload для проверок (эталон)
Эталонный payload (заголовок, `<img onerror>`, `<script>`, `javascript:`-ссылка,
`data:text/html`, безопасная разметка) зафиксирован в юнит-тесте
`ai::commands::tests::render_markdown_sanitizes_ai_answer` (`crates/app/src-tauri/src/ai/commands.rs`).
Э2E-мок обязан отдавать **тот же** текст.

> **Пустые строки в payload обязательны:** без них сырой HTML открывает общий CommonMark-блок
> и тест проверял бы инертный текст вместо санитайзера.


### 2.6. Что не меняется

14. **Аддитивность:** замороженные id `#ai-*` (§13.2), согласие/приватность (ADR-0032 §2.4),
    `finish_reason`/`usage` (ADR-0032 §2.5), ADR-0033/0034/0035 — без изменений.

## 3. Последствия

**Положительные:**

- **Единая точка**: любой новый источник HTML проходит один хелпер с одним набором проверок.
- **Цена близка к нулю**: одна команда Rust + один TS-модуль; новых зависимостей нет (D6).

**Отрицательные / ограничения:**

- **Два класса HTML**: «доверенный результат `render_markdown`» (preview) и «проверенный
  хелпером результат `ai_render_markdown`» (ответ AI). Защитная проверка в хелпере
  **обязательна** (fail-safe к `textContent`), даже если сегодня считается дублирующей.
- **Рендер привязан к IPC**: финализация — дополнительный `await` на `ai_render_markdown`.
  Не влияет на стриминг и не блокирует ввод.
- **Стилизация ответа AI повторяет превью**: плюс единообразия, но требует правок в обоих местах.
- **XSS-payload отображается как безобидный текст** — ожидаемо и правильно.

**Обратимость:** вернуть `textContent` в `complete()`, удалить `safeHtml.ts` и команду;
`AGENTS.md`/§11.1 возвращается к прежней формулировке. ADR переводится в «Отклонён», нумерация
не переиспользуется.

## 4. Отклонённые альтернативы

- **Отказ от AC-P3-4 (всегда `textContent`):** AC нормативен; потеря форматирования постоянная.
- **Вторая точка `innerHTML` в `aiPanel.ts`:** «двери для сырого HTML» (ADR-0030 §1.3, §11.1).
- **`<iframe>`/sandbox:** лишняя сложность; allowlist санитайзера достаточен (§11.2).
- **Фронт-санитация (`DOMPurify`):** расходится с хост-санитизацией (§11.1) + ~30–50 КБ (D6).
- **Рендер каждого чанк:** IPC-спам + мерцание; выбран рендер один раз (п.9).
- **Отдельная команда с ручным `sanitize_fragment`:** `to_html` уже санитизирует (п.4).
- **Перенос preview-innerHTML в общий хелпер:** preview — горячий путь с `data-md` (D2);
  перенос разорвал бы контракт инспектора (§13.2).
