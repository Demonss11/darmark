## 1. Контекст

### 1.1. Проблема

ADR-0034 §2.5 фиксировал MCP как **inbound** (внешние клиенты вызывают нас, отделённая граница
доверия, auth/consent/аудит) и выводил его из MVP. Продуктовое решение 12.10.2026 пересматривает рамку:
MCP-сервер — **внутренний контрактный tool-слой** для встроенного AI-ассистента (IDEA-016). Клиент —
только внутренний (встроенный AI darmark); внешних клиентов, inbound-auth и аудита внешних вызовов —
нет. Это качественно иная модель доверия, чем inbound-сервер внешних клиентов.

Нужно зафиксировать **транспорт/размещение** MCP-сервера и его контрактные рамки: что сервер
реализует (протокол по букве), где он исполняется (в процессе GUI), как связан с существующими
командами и песочницей, и что именно он даёт агенту (R1/R2 из ТЗ).

### 1.2. Что уже зафиксировано (не пересматривается)

- **AI-рантайм — в процессе GUI** (`crates/app/src-tauri/src/ai/`), сеть — на Rust-стороне
  (ADR-0034 §2.1, ADR-0032/0033). Сайдкар `darmark-ai.exe` отложен; фича включается конфигом
  `ai.enabled` (ADR-0034 §2.3).
- **Сеть — только Rust-сторона**; CSP `default-src 'self'` не ослабляется (ADR-0032 §2.5 п. 11,
  ADR-0033).
- **Согласие обязательно**: содержимое документа уходит в облако только после явного согласия
  (ADR-0030 §2.4, ADR-0032 §2.3); ответ рендерится через Rust-санитайзер (D7/§11).
- **Провайдеры LLM** — map в `config.json`, пользовательская конфигурация (ADR-0035).
- **Плагинная система** — child-per-plugin, `mlua` вне GUI, Supervisor/Job Object/watchdog/карантин
  (ADR-0021/0023); контракт `HOST_API_VERSION`, аддитивность (ADR-0027).
- **D6 (release-exe ≤6 МБ, size-gate §14)**; ориентир AI-клиента — маргинальный прирост ≤1.0 МиБ
  (ADR-0033).
- **Замороженные контракты** §13.2 (DOM id, селекторы, плагинные контракты) — не меняются.

### 1.3. Почему решение пересматривается

TZ-MCP §2 фиксирует пересмотр рамки ADR-0034 §2.5: MCP — не inbound для внешних клиентов, а
**внутренний tool-слой** для встроенного ассистента. Модель доверия простая: единственный клиент,
доверенный, в процессе. Это снимает требования auth/consent/аудита внешних вызовов, но сохраняет
главную цель MCP — **контракт для агента**: чёткий перечень команд (что вызвать, что передать,
что ждать) + наблюдаемость потока данных через журнал.

## 2. Решение

**MCP-сервер реализуется как встроенная подсистема хоста (in-memory транспорт): протокол MCP по букве
(JSON-RPC 2.0 + семантика MCP) поверх внутрипроцессного канала. Сервер исполняется в процессе GUI
(`crates/app/src-tauri/src/mcp/`), состояние документов/плагинов живёт там же. Клиент — только
внутренний (встроенный AI-ассистент). MCP — контракт и сужение поверхности, не механизм принуждения.**

### 2.1. Транспорт и размещение

1. **Транспорт — in-memory (embedded):** JSON-RPC 2.0 + семантика MCP поверх внутрипроцессного
   канала (channel/pipeline в рамках одного процесса). Нулевая OS-поверхность: не слушается порт,
   не создаётся child, не вводится новый бинарник. MCP-спека отделяет транспорт от протокола —
   протокол остаётся «настоящим» (initialize / tools.list / tools.call / resources.list /
   resources.read).
2. **Размещение — в процессе GUI:** MCP-сервер — модуль `crates/app/src-tauri/src/mcp/`, как
   `DocumentStore` или `RenderCache`. Состояние документов, плагинов, настроек — общее с хостом;
   IPC-прокси не требуется.
3. **Клиент — только внутренний:** встроенный AI-ассистент (`aiPanel.ts` + `crates/app/src-tauri/src/ai/`)
   вызывает MCP-инструменты через tool-loop. Внешних клиентов, inbound-auth и аудита внешних
   вызовов — нет. MCP-клиент darmark к чужим MCP-серверам (outbound) — **не входит** (ср. ADR-0034 §4.3).
4. **Сетевые вызовы из TS запрещены:** CSP `default-src 'self'`; всё — на Rust-стороне. MCP-транспорт
   не исключение: in-memory канал не покидает процесс.

### 2.2. Контракт и сужение поверхности

5. **Протокол — по букве:** сервер реализует `initialize`, `tools/list`, `tools/call`,
   `resources/list`, `resources/read`. Ответы — по спецификации MCP (JSON-RPC 2.0 envelope).
6. **Первый срез — read-only контракты плагинов** (§3): 6 resources + 4 tools. Мутаций нет.
7. **MCP — контракт, не принуждение:** права/rev-guard/безопасность путей остаются в существующих
   командах (permissions, `Manifest::validate`, белый список директорий). MCP не создаёт второго
   источника истины для безопасности (та же развилка «объявляет — принуждает», что у манифеста
   плагина и хоста, ADR-0023/0027, §11.4).
8. **Tool = тонкая обёртка** над существующей командой/CLI; никакой бизнес-логики в MCP (R4).
   Результат совпадает с прямым вызовом `plugin-cli`/`md-core` (AC-MCP-6).

### 2.3. Цель: результат, а не сервер

9. **Контрактная ясность для агента (R1):** у каждого tool/resources есть описание и схема
   (вход/выход); перечень доступен агенту для чтения (`tools.list`/`resources.list`). Имена,
   параметры и формат результата — детерминированные.
10. **Наблюдаемость (R2):** каждый вызов инструмента и его результат логируются в журнал
    (`#logs-panel`): инструмент, параметры (в допустимом объёме), длительность, итог/ошибка.
   Приватность: без секретов; для файлов — имя, не полный путь (§4.6 DESIGN_DOC); содержимое
    документа не логируется.
11. **Tool-loop:** встроенный ассистент вызывает инструменты в цикле (R6). Зависимость: поддержка
    tool-calling (tools/function-calling) провайдером; при отсутствии — локальный разбор вызова
    отдельным дизайном.

### 2.4. Что не меняется

12. **Сеть/HTTP-клиент/SSE/провайдеры** — без изменений (ADR-0032/0033/0035). MCP не вводит
    сетевого слоя.
13. **CSP** `default-src 'self'` и инвариант «сеть — только Rust» — без изменений.
14. **D6** — без изменений: ориентир MCP-сервера — маргинальный прирост ≤0.1 МиБ (оценка:
    модуль `mcp/` — ~50–80 КБ, без новых зависимостей; при необходимости — отдельный крейт
    `mcp-core` без Tauri).
15. **Инварианты ADR-0027:** контракты §13.2 сохранены (аддитивность); `HOST_API_VERSION` не
    поднимается; `mlua` вне GUI.
16. **Триггеры пересмотра ADR-0034 §2.6** сохранены: сайдкар AI, «поставка без AI», тяжёлый AI,
    гейт `reqwest` в `cargo tree -p darmark`. MCP-сервер не создаёт новых триггеров; при наступлении
    триггеров MCP выделяется в child по тому же шву, что и AI-рантайм.

## 4. Отклонённые альтернативы

- **Внутренний tool-слой без сервера («MCP-подобный» слой, YAGNI).** Отклонён **заказчиком**:
  продуктовое решение 12.10.2026 требует **настоящий MCP-сервер** (протокол по букве), а не
  внутренний слой с похожим API. MCP — открытый стандарт; реализация «по букве» даёт совместимость
  с экосистемой инструментов и честную границу: клиент может быть заменён на внешний (при
  появлении кейса) без переписывания сервера. YAGNI-аргумент («клиент один, сервер не нужен»)
  отклонён как ограничивающий обратимость.
- **Loopback Streamable HTTP (сервер слушает `127.0.0.1`).** Отклонён: вводит OS-поверхность
  (открытый порт, хотя loopback), новый inbound-listener в процессе GUI, риск конфликта портов
  и вопросы firewall/антивируса на Windows. При этом состояние документов/плагинов всё равно
  живёт в GUI-процессе (TZ-MCP §1, п.6), поэтому транспорт не даёт реального преимущества
  размещения — только усложнение. Внутренний клиент не требует HTTP-рукопожатия.
- **stdio/headless (отдельный процесс без GUI, состояние через IPC-прокси).** Отклонён: тяжёл
  (второй процесс, прокси состояния, синхронизация), не нужен при единственном внутреннем клиенте
  и состоянии в GUI. Выделение в child — только по триггерам ADR-0034 §2.6 (тяжёлый AI, бюджет,
  «поставка без AI»).
- **Внешние клиенты / inbound (сервер для внешних клиентов, auth/consent/аудит).** Отклонён
  **рамкой 12.10.2026**: клиент — только внутренний. Внешние клиенты — отделённая граница
  доверия, качественно иная, чем outbound-запрос к провайдеру; при появлении кейса — отдельный
  ADR (ср. ADR-0034 §2.5, §4). Настоящий ADR не вводит inbound-auth, аудита и согласия внешних
  вызовов.

## 5. Последствия

**Положительные:**

- **Нулевая OS-поверхность:** нет порта, нет child, нет нового бинарника; минимальный прирост
  размера (≤0.1 МиБ, §2.4 п. 14).
- **Состояние общее с хостом:** MCP-сервер в процессе GUI — нет IPC-прокси, синхронизации,
  дублирования состояния документов/плагинов.
- **Протокол остаётся «настоящим»:** MCP-спека отделяет транспорт от протокола; при появлении
  внешних клиентов (или выделения в child) сервер переносится на loopback/stdio **без
  переписывания протокольного слоя**.
- **Обратимость:** выделение MCP в child — по триггерам ADR-0034 §2.6, отдельным ADR; in-memory
  транспорт не блокирует этот путь.
- **Контрактная ясность:** агент получает чёткий перечень команд (что вызвать, что передать, что
  ждать) — главная цель (R1/R2, §2.3).
- **Наблюдаемость:** каждый вызов логируется в журнал (`#logs-panel`) с соблюдением приватности
  (§4.6 DESIGN_DOC).
- **CSP/D6/санитайзер/плагинные контракты — без изменений:** MCP не ослабляет границы.

**Отрицательные / ограничения:**

- **MCP-код остаётся в дереве `darmark`:** `cargo tree -p darmark` содержит MCP-модуль; CI-инвариант
  «без MCP» не достигается (аналогично `reqwest`, ADR-0034 §3).
- **Внутрипроцессный канал — не граница доверия:** MCP-сервер не изолирован от GUI-хоста; при
  компрометации MCP-модуля (или клиента) злоумышленник получает доступ к состоянию хоста. Это
  осознанно: клиент внутренний и доверенный; граница доверия — на уровне процесса, а не модуля.
- **Инвариант «сервер в процессе GUI» держит обратимость:** при выделении в child появится
  прокси состояния — цена, зафиксированная как триггер ADR-0034 §2.6.
- **Инструменты — тонкие обёртки:** при ошибке адаптер (например, `plugin_test`) результат должен
  совпадать с прямым вызовом CLI (AC-MCP-6); дрейф схем и сигнатур контролируется контракт-тестом.

**Обратимость:** MCP-модуль локализован (`crates/app/src-tauri/src/mcp/`) и не создаёт новых
замороженных контрактов. Перенос транспорта (loopback/stdio) или выделение в child — рефактор
модуля, не ломающий протокольный слой и замороженные контракты §13.2.
