## 1. Контекст

### 1.1. Проблема

`ai_chat` объявляет провайдеру инструменты всегда, когда реестр MCP непуст
(`ai/commands/mod.rs::provider_tools` → `ChatRequest.tools`). Часть OpenAI-совместимых шлюзов
поле `tools` не принимает и отвечает `400`. Сейчас такой ответ уходит в
`ai/errors.rs::map_status` → `ErrorCode::AiBadRequest` → `ai:error` в чат: для пользователя это
та же поломка, что была до tool-loop. IDEA-003 фиксирует это как регрессию.

Вторая, менее заметная половина проблемы: `map_status` схлопывает статус в код, поэтому по
`CommandError` **нельзя отличить** три разные ситуации, которые сейчас несут один код
`AiBadRequest`:

- провайдер отверг `tools` (нужен повтор без него);
- провайдер отверг что-то другое (`temperature`, неизвестная модель — повтор не поможет);
- ошибка **локальная**, ответа провайдера не было вовсе: «ответ превысил допустимый размер»
  (`backend/reqwest.rs::ensure_within_response_limit`), ошибки `tools/call` MCP-протокола
  (`tool_loop.rs::call_mcp_tool`).

Пока это не различено, любая политика деградации будет либо слепой, либо ошибочной.

### 1.2. Что уже зафиксировано (не пересматривается)

- Маппинг ошибок провайдера с ключевыми кейсами `401`/`429`/`5xx` и ретрай `5xx` с backoff —
  ADR-0032 §2.5 п.13, ADR-0033; логирование только метаданных — ADR-0032 §2.5 п.14.
- Одна пауза rate limit и **один** `message_id` на весь цикл (`ai/commands/mod.rs::run_chat`),
  лимит `MAX_TOOL_ITERATIONS = 4` и обрезка результата `MAX_TOOL_RESULT_CHARS` — ADR-0036.
- Клиентская сборка `tools` из реестра MCP по `tools/list`; MCP — контракт, а не принуждение
  (ADR-0036 §2.2).
- Сеть только Rust-сторона, CSP `default-src 'self'`, D6 без новых зависимостей (ADR-0032/0033).
- События AI аддитивны, `HOST_API_VERSION` не поднимается, §13.2 не затрагивается
  (ADR-0034 §2.7, ADR-0027 §2.4).
- Структуры с полями объявляются в модуле-родителе, тесты домена — отдельным деревом
  (ADR-0039 §2.1, §2.3).

### 1.3. Почему решение оформляется отдельным ADR (дополнением к ADR-0036)

ADR-0036 **не противоречит** задаче: он фиксировал транспорт и контракт tool-слоя, а поведение
провайдера, отвергающего `tools`, оставил открытым (§3.3 ТЗ трека). Настоящий ADR это
открытое место **дополняет**, не пересматривая §2.4 ADR-0036 («сеть/HTTP-клиент/провайдеры — без
изменений»): клиент и протокол те же, меняются маппинг ошибки и одна ветка цикла.

Отдельный документ (а не правка ТЗ) нужен потому, что решение меняет **общий для крейта тип
ошибки IPC** (`CommandError` — общий словарь ошибок приложения, §2.1) и **поведение цикла**, а
D11 требует оформлять такие решения документом.

Отдельный пункт контекста — **расхождение ТЗ и кода по сценарию (б)**: ТЗ требует «повтор без
`tools` при 200 с пустыми `tool_calls`», код этого не делает и не должен (§2.4). Это
расхождение закрывается здесь, формулировка §3.3 ТЗ исправляется.

## 2. Решение

**Провайдер, отвергающий поле `tools`, не ломает чат: ошибка провайдера сохраняет HTTP-статус,
tool-loop делает ровно один авто-повтор без `tools` в том же `run`, вердикт «провайдер не умеет
tools» кэшируется в памяти `AiState` по `(base_url, model)`, а сама деградация наблюдается тихим
`warn` на stderr. Сценарий «200 без `tool_calls`» повтором не сопровождается — это уже штатный
финальный ответ цикла.**

### 2.1. Статус в ошибке провайдера

1. `CommandError` получает **одно** поле — `http_status: Option<u16>`: HTTP-статус ответа
   провайдера. `None` означает «ответа провайдера по HTTP не было» (локальные проверки, ошибки
   MCP-протокола, сеть без ответа). Сериализация — с `#[serde(skip_serializing_if = "Option::is_none")]`,
   поэтому payload всех остальных команд остаётся `{ code, message }` без изменений.
2. **Писатель поля ровно один** — `ai::errors::map_status` (ADR-0032 §2.5 п.13). Он вызывает
   новый конструктор `CommandError::provider(status, code, message)`; остальные конструкторы
   (`new`, `not_found`, `io`, `too_large`, `not_utf8`, `unknown_document`, `nothing_to_*`) дают
   `None`.
3. `map_status` **не меняет** ни коды, ни тексты, ни `CONTEXT_MARKERS`: добавляется только
   проброс статуса в уже существующие ветки (`401`, `429`, `400` ×2, `5xx`, прочие).
4. Поле — **внутренняя диагностика, не контракт для фронтенда**: TS читает только `code`/`message`
   (`crates/app/src/panels/aiPanel/index.ts`), а событие `ai:error` собирается вручную
   (`ai/commands/mod.rs::emit_error`) и от `CommandError` не зависит. Замороженные контракты
   §13.2 не задеты.
5. **Риск расширения типа оценён и низок:** литерал `CommandError { .. }` существует только в
   `error.rs`; все места крейта (документы, плагины, AI, harness-и) используют конструкторы,
   поэтому изменение компилируется без правок на их стороне и не меняет их поведение. Тот же
   статус уже читается в `backend/reqwest.rs` и теряется единственный раз — на маппинге.

### 2.2. Сценарий (а): один авто-повтор без `tools`

6. Условие повтора — **все** пункты одновременно:
   - в текущем `run` повтор ещё не применялся;
   - `request.tools` — `Some` **с непустым массивом** (инструменты действительно объявлялись;
     пустой реестр MCP даёт `None`, а объявлять нечего — §2.2 п.10);
   - `err.http_status == Some(400)` (это ответ провайдера, а не локальная ошибка);
   - `err.code != ErrorCode::AiContextLength` (причина уже распознана как превышение контекста);
   - **следующий слот итерации свободен**: повтор делается `continue`, то есть следующей
     итерацией, а на последнем слоте следующей итерации нет — деградация молча проглотила бы
     ошибку (пользователь получил бы `ai:done` с пустым ответом вместо `ai:error`). На последнем
     слоте отказ доходит до пользователя как есть.
7. Повтор выполняется **в том же `run`**: `request.tools = None`, счётчик деградаций — 1, цикл
   продолжается. Следствие: **одна** пауза rate limit и **один** `message_id` (уже обеспечены
   `run_chat`, ADR-0036/ТЗ) — фронт не видит второго сообщения и не получает задвоенных дельт.
8. **Бюджет запросов не растёт:** число запросов в одном `run` остаётся ≤ `MAX_TOOL_ITERATIONS`.
   Повтор занимает слот итерации, а не добавляет новый, поэтому верхняя граница не меняется; в
   вырожденном случае у запроса без `tools` `tool_calls` не бывает, и цикл завершается на
   ветке пустых вызовов сразу после повтора. Из этого же следует запрет на повтор на последнем
   слоте (п.6): продолжить цикл нечем, и «повтор» без запроса вернул бы пустой ответ.
9. Если повтор тоже падает — ошибка возвращается пользователю как есть (с исходным текстом
   провайдера в сообщении). Дальнейших попыток нет.
10. Повтор не выполняется, если `tools` не объявлялись (пустой реестр MCP, §3.3 ТЗ «минимум»):
    деградировать нечего.

### 2.3. Эвристика отличия 400 «из-за `tools`» (Q3)

11. **Решение: повтор при любом 400 с непустым `tools`, кроме уже распознанного
    `AiContextLength`.** Новых маркеров не вводится; `CONTEXT_MARKERS` (`ai/errors.rs`)
    остаётся единственным местом, где решается «это превышение контекста».
12. Обоснование — **асимметрия цены ошибки.** Ложное срабатывание стоит одного лишнего запроса
    в том же `run` (тот же слот rate limit, тот же `message_id`), после которого пользователь
    видит ту же исходную ошибку; ложное отсутствие срабатывания означает, что у этого
    провайдера чат не работает **никогда** — ровно та регрессия, которую устраняем. Ставка на
    «повторить» строго дешевле ставки на «угадать».
13. **Разбор тела на слово «tools» не нужен и не должен вводиться:** у OpenAI-совместимых
    шлюзов текст отказа не стандартизован — `tools is not supported`,
    `Unrecognized request argument supplied: tools`, `invalid_request_error`, пустое тело. Любой
    список слов превращается в погоню за шлюзами, а **промах** этой эвристики означает вечную
    поломку чата: цена ошибки несопоставима с ценой одного лишнего запроса. Тело ответа
    используется там, где диагноз из него надёжен, — только для `AiContextLength`.
14. Исключение `AiContextLength` — не «уточнение эвристики», а **уже вычисленный диагноз**:
    маркер найден, причина известна, а повтор без `tools` превышение контекста не устраняет
    (убирая объявление инструментов, мы шлём тот же по объёму диалог и получаем тот же ответ).
    Пользователь вместо внятной ошибки получил бы вдвое больший расход и ту же ошибку с
    задержкой.
15. Ошибки **без статуса** (локальные `AiBadRequest`: превышение размера ответа, ошибки
    `tools/call`) повтором не ловятся — в этом и состоит польза поля §2.1 п.1.

**Правило границы бюджета.** Отказ, пришедший на **последнем слоте итерации**, повтором не
сопровождается (п.6): следующего слота нет, а деградация без запроса вернула бы пользователю пустой
финальный ответ вместо его ошибки. Такой отказ доходит до пользователя как есть, вердикт в кэш не
пишется. Нумерация пунктов §2.3 не сдвигается — правило дополняет п.6 и п.8, а не добавляет
новый пункт.

### 2.4. Сценарий (б): повтор **не** делается — ТЗ и код расходились

16. Текущий код уже покрывает сценарий по сути: `tool_loop::run` при пустых `tool_calls`
    **возвращает финальный ответ** (`ai/tool_loop.rs`, ветка `outcome.tool_calls.is_empty()`).
    Чат не ломается, ошибка пользователю не показывается.
17. «Повтор без `tools`» в формулировке ТЗ **не выполняется**, потому что:
    - первый запрос уже отправил дельты в `ai:chunk` под тем же `message_id`, а фронт дописывает
      дельты в тот же пузырь — пользователь увидел бы текст ответа **дважды**;
    - пустые `tool_calls` — **штатное конечное состояние здорового цикла** (модель просто
      ответила текстом и не стала звать инструменты); отличить «провайдер проигнорировал `tools`»
      от «инструменты не понадобились» по данным ответа невозможно в принципе;
    - правило «повтор при пустых вызовах» срабатывало бы на **каждом нормальном ходу** и
      удвоило бы задержку и расход каждого запроса; чтобы это ограничить, пришлось бы ввести
      счётчик — то есть угадывать.
18. Сценарий (в) закрыт существующим кодом и новых действий не требует: нестандартная форма
    `tool_calls` не парсится и даёт пустой список (`ai/tool_calls.rs::tool_calls_from_payload`,
    `ToolCallAccumulator::finish`), что попадает в ту же ветку §2.4 и даёт обычный ответ.
19. Формулировка §3.3 ТЗ по сценарию (б) исправлена: «200 с пустыми `tool_calls` → обычный
    финальный ответ, повтор не выполняется», с указанием причины (п.17).

### 2.5. Кэш «провайдер не умеет `tools`» (Q2)

20. Ключ — `(base_url, model)` **как есть, без нормализации**: склейка по хосту склеила бы разные
    эндпоинты одного шлюза и дала ложный вердикт, а лишний ключ стоит одного лишнего запроса.
21. Хранилище — **`AiState`** (поле `tools_unsupported: Mutex<HashSet<(String, String)>>`),
    **не статика**: процесс-глобальное состояние протекает между тестами и живёт дольше сессии;
    `AiState` уже владеет `settings` и `rate_limit` (ADR-0034 §2.3, ADR-0039 §2.1).
22. Запись ставится **только после успешного повтора**: 400 — это вердикт по одному ответу;
    кэшировать его до успешного повтора — значит запомнить недоказанное и не дать пользователю
    увидеть исходную ошибку. Если повтор упал, вердикт не кэшируется: пользователь видит ошибку,
    следующий запрос проверяет заново.
23. Кэш **очищается целиком** при любом успешном `ai_set_settings`
    (`ai/state.rs::update_settings`, рядом с persist-first присваиванием `*settings = next`):
    конфигурация провайдеров могла измениться, а устаревший вердикт хуже отсутствия вердикта
    (одна лишняя попытка дешевле вечной деградации). `ai_set_api_key` кэш не трогает — адрес и
    модель те же.
24. Кэш **не персистится** в `config.json`: это свойство окружения, а не пользовательская
    настройка; переживание перезапуска не даёт выигрыша (не больше одного лишнего запроса за
    сессию), а персистентность расширила бы `AiSettingsView` и схему конфига без нужды.
25. Перед первым запросом `run` снимает `tools`, если пара `(base_url, model)` **уже есть** в
    кэше («кэш-хит → ни одного отвергнутого запроса»): смысл кэша — не тратить запрос и не
    получать ошибку в лог.

### 2.6. Наблюдаемость (Q1)

26. Деградация логируется **тихим `warn` на stderr** (`eprintln!` с префиксом `darmark: ai:`) —
    конвенция проекта (`ai/commands/mod.rs::emit_event`, `setup/plugins.rs`). В записи только
    метаданные (ADR-0035 §2.6 п.16, ADR-0032 §2.5 п.14) — без ключа, без содержимого запроса и без
    текста документа. Две санитарные детали, обязательные по той же причине:
    - печатается **хост** (`ai::state::host_of_url`), а не `base_url` целиком: адрес шлюза
      допускает userinfo и query (`ai::state::validate_base_url`, H4), а там может лежать секрет;
    - **модель** — свободный пользовательский текст, поэтому переводы строк заменяются пробелом:
      иначе ими подделывается строка лога.
27. Запись — **одна на факт деградации** (успешный повтор). Кэш-хит молчит: повторов нет, нет и
    записей.
28. **Карточка в чате не вводится**, потому что: (i) деградация — не проблема пользователя, а
    диагностика: ответ получен, чат работает, ассистент просто не позвал инструменты; (ii)
    карточка создала бы новый видимый артефакт в чате, которого нет ни в перечне ADR-0038 §2.3,
    ни в замороженных контрактах §13.2, — то есть задеть контур рендера и панели ради одной
    служебной строки; (iii) вердикт кэшируется, а сообщение осталось бы в истории навсегда и со
    временем **врало бы** о следующих ходах.
29. Запись в журнал MCP (`#logs-panel`) **не делается**: там фиксируются вызовы инструментов
    (TZ-MCP R2, AC-MCP-4), а при деградации вызова не было — запись «MCP …» без вызова была бы
    ложью. Если видимость в журнале понадобится, это **отдельное решение** о пробросе `LogSink`
    (`setup/plugins.rs`) в `AiState` — триггер для нового ADR, а не расширение настоящего.
30. Требование ТЗ «запись в журнал» трактуется как запись в диагностический stderr; формулировка
    §3.3 ТЗ поправлена.

### 2.7. Места по модулям (ADR-0039 §2.1–§2.3)

31. `ai/tool_loop.rs`: трейт **`ToolsCapability`** с двумя операциями — «инструменты разрешены
    для `(base_url, model)`» и «пометить пару как не поддерживаемую»; в `run` — логика §2.2/§2.5 и
    `warn`. Трейт, а не прямая зависимость от `AiState`: `tool_loop` остаётся независимым от
    состояния и проверяется фейком (образец шва — `AiEmitter`). Единственная точечная связь с
    `ai::state` — чистая функция `host_of_url` для `warn` (§2.6 п.26), без типа `AiState` и без
    блокировок.
32. `ai/state.rs`: поле кэша, инициализация в конструкторе, `impl ToolsCapability for AiState`
    (чтение и запись) и очистка в `update_settings`. Поле объявлено здесь — оно читается из
    `tool_loop`, значит объявление обязано быть в модуле-владельце структуры (ADR-0039 §2.1).
33. `ai/commands/mod.rs`: `run_chat` передаёт `&state` как `&dyn ToolsCapability` в `tool_loop::run`;
    doc-комментарии `run_chat` и `provider_tools` обновляются — сейчас они объявляют деградацию
    открытым вопросом ТЗ.
34. `error.rs`: поле `http_status` и конструктор `provider`.
35. Тесты — **отдельным деревом `ai/tests/`** (ADR-0039 §2.3); приватные детали расширяются до
    `pub(super)`, не до `pub(crate)`. Двойник `ToolsCapability` и «транспорт, умеющий отдавать
    `Err`» живут в `ai/tests/support.rs`.

### 2.8. Что не меняется (Q4 и границы)

36. **Ничего из следующего не меняется:** набор и payload событий `ai:*` (нового события
    деградации нет), `ai:error`, замороженные контракты §13.2, `HOST_API_VERSION` (ADR-0027,
    ADR-0034 §2.7 п.18), шов `AiTransport` — тип ошибки остаётся `CommandError`, поэтому будущий
    сайдкар остаётся drop-in (ADR-0034 §2.2), сеть, CSP, D6 (зависимостей не добавлено),
    поведение сценария (в).
37. **Q4 (локальный разбор вызова из текста ответа) закрыт как «не вводим»:** превращение текста
    ответа модели в вызов инструмента противоречит R7 «данные, не инструкции» и открывает
    prompt-injection (враждебный вывод инструмента сам попадает в контекст). При появлении
    продуктового кейса — **отдельный ADR**.

## 3. Последствия

**Положительные:**

- Чат у провайдера без `tools` работает: вместо `ai:error` пользователь получает обычный ответ.
  Это и есть критерий успеха IDEA-003.
- Различение «ответ провайдера» / «локальная ошибка» по полю `http_status` полезно и за пределами
  деградации (диагностика, будущая политика ретраев).
- Решение (б) снимает риск задвоения текста в чате и удвоения расхода каждого хода.
- Бюджет запросов на `run` не растёт (п.8), новая сетевая политика не вводится.
- Кэш убирает повторную «проверку способности» у каждого запроса в сессии.

**Отрицательные / ограничения:**

- `CommandError` получает поле, относящееся к одному домену (AI). Цена сведена к нулю
  конструктором с единственным писателем и `skip_serializing_if`, но тип перестаёт быть
  полностью «нейтральным» — это осознанно (§2.1 п.5).
- Возможен один лишний запрос у провайдера, который отвергает `tools` (и повторно — пока не
  зафиксирован вердикт кэша). Плата — единичный round-trip, а не поломка чата.
- Между «провайдер отверг `tools`» и «провайдер отверг что-то другое» эвристика не различает:
  пользователь в редком случае увидит ту же ошибку после лишнего запроса.
- **Деградация срабатывает только на `400`.** Эвристика построена на статусе, а не на теле
  отказа (§2.3 п.13), поэтому шлюз, отвечающий на неприемлемое `tools` статусом `422`
  (RFC 4918, «необрабатываемый тип носителя») или `501` («не реализовано»), деградацией **не**
  покрывается: чат у него продолжит падать с `ai:error`. Осознанный размен — п.13 объясняет,
  почему разбор тела не вводится; для покрытия таких шлюзов понадобилась бы настройка
  «провайдер не поддерживает tools» (отклонённая альтернатива §4, её триггер — этот кейс).
- **`CONTEXT_MARKERS` неполны.** Превышение контекста распознаётся по шести маркерам тела; если
  провайдер формулирует отказ иначе, код остаётся `AiBadRequest`, и пользователь получит один
  лишний повтор без `tools` на том же по объёму диалоге — с той же ошибкой и с задержкой. Это
  плата за п.12, а не отдельный механизм; расширение списка маркеров — самостоятельная правка
  `ai/errors.rs`.
- Кэш сбрасывается на каждом сохранении настроек; при частом переключении настроек платим лишними
  запросами — приемлемо.
- Кэш в памяти: после перезапуска приложения первая проверка повторится.

**Обратимость:** решение локализовано в `error.rs`, `ai/errors.rs`, `ai/tool_loop.rs`,
`ai/state.rs`, `ai/commands/mod.rs`. Откат — удаление поля и ветки повтора; контракты IPC,
фронтенд и E2E при откате не меняются. Ручной флаг «провайдер не умеет tools» в настройках, если
автоопределение окажется недостаточным, — **отдельное решение**, а не часть настоящего.

## 4. Отклонённые альтернативы

- **Разбор тела ответа на «tools»/маркеры отказа.** Отклонено: текст отказа не стандартизован,
  список слов бесконечен, а промах означает вечную поломку чата (§2.3 п.13). Диагноз по телу
  остаётся только там, где он надёжен, — `AiContextLength`.
- **Повтор без `tools` при 200 с пустыми `tool_calls` (сценарий (б) по ТЗ).** Отклонено: задвоение
  дельт в чате, срабатывание на каждом нормальном ходе, необходимость угадывать счётчик (§2.4).
- **Карточка в чате о деградации.** Отклонено: не пользовательская проблема, новый артефакт в чате
  вне перечня ADR-0038 §2.3 и §13.2, «залипающая» правда в истории (§2.6 п.28).
- **Запись деградации в журнал MCP.** Отклонено: журнал фиксирует вызовы инструментов, которых
  при деградации не было (§2.6 п.29).
- **Кэш в статике (`static` + `OnceLock`).** Отклонено: утечка между тестами и между сессиями;
  состояние AI уже живёт в `AiState` (ADR-0034 §2.3).
- **Персистентность кэша в `config.json`.** Отклонено: свойство окружения, а не настройка;
  расширяет контракт настроек без выигрыша (§2.5 п.24).
- **Ручной флаг «провайдер не поддерживает tools» в настройках провайдера.** Отклонено сейчас:
  пользователь не обязан знать возможности шлюза, а вывод автоматический. Триггер пересмотра —
  кейс, когда автоопределение ошибается (тогда флаг станет точкой выхода).
- **Отдельный тип `ProviderError` вместо поля в `CommandError`.** Отклонено: меняет тип ошибки
  шва `AiTransport` (ADR-0034 §2.2), а значит — `transport.rs`, `backend/reqwest.rs`, все двойники
  в `ai/tests/` и конверсию на границе команды; при этом `CommandError` уже несёт 18
  AI-специфичных кодов, то есть по устройству является общим словарём ошибок приложения, а
  добавление `Option`-поля с одним писателем и `skip_serializing_if` не меняет контракт ни одной
  другой команды (§2.1 п.5).
- **Повтор внутри `backend/reqwest.rs` рядом с ретраем 5xx.** Отклонено: политика деградации —
  свойство цикла, а транспорт ничего не знает ни про MCP, ни про кэш возможностей; решение
  размножилось бы по будущим реализациям `AiTransport`.
- **Жёсткий лимит «один деградирующий запрос на сессию» вместо кэша по паре.** Отклонено: кэш по
  `(base_url, model)` решает ту же задачу точнее и переживает смену провайдера без лишних
  проверок.
