# ADR-0021. Изоляция плагинов: Lua в отдельном процессе (D16)

- **Статус:** **Принят**
- **Дата:** 06.10.2026
- **Основание:** прототип `proto/lua-plugin-host`; факты — `docs/proto/FINDINGS.md` (F1–F36)
- **Связанные:** `docs/DESIGN_DOC.md` §7.1, §10, §11.4, §14, §16;
  `reviews/TZ-proto-lua-host-P1-review-v1.4.md` (C-спайк), `reviews/TZ-proto-lua-host-P9-review-v1.0.md` (M10–M12)

---

## 1. Контекст

Прототип измерил in-process хостинг Lua под релизным `panic="abort"` и показал критическую
проблему: **любая ошибка, поднятая из Rust-зарегистрированной функции (hook или host-функция),
не ловится и абортит процесс** (F9: `panic_cannot_unwind` через SEH). Утверждение о
неуязвимости к Lua-ошибкам в in-process модели под `abort` ложно. Обходы in-process
(нативный C-hook F11, safe-`pcall` F13) работают, но: панику host-кода в принципе не поймать,
а hook даёт оверхед ~×2 (F14). Вариант `unwind` стоит +3.2 МБ и ломает D6 (F10).

Отдельно измерен вынос Lua в дочерний процесс (C, F16–F32): жёсткая изоляция отказов,
приемлемая латентность, подтверждённый транспорт в GUI-конфигурации и управляемые лимиты.

---

## 2. Решение

**Выбирается вариант C — Lua-плагин исполняется в отдельном дочернем процессе; GUI-хост не
линкует `mlua` и может оставаться на `panic="abort"`.**

1. **Рантайм.** Отдельный процесс (`child`) на Lua 5.5 (mlua `lua55`+`vendored`). Host и Lua
   разделены границей процесса. В базе GUI-хоста `mlua` отсутствует (F20).
2. **Транспорт.** stdio (явные пайпы, `bInheritHandles`), подтверждён в GUI-конфигурации
   (`windows_subsystem="windows"`, subsystem 2) без консоли; кадр 10 МБ, обрывы
   детектируются без блокировки (F26/F27). Смена транспорта не требуется.
3. **Модель процессов — «child на плагин»** (по одному процессу на плагин). Даёт заявленную
   изоляцию отказов; цена ≈0.6 МиБ commit и ≈2 мс spawn на плагин (F30). «Общий child»
   отвергнут: один `crash`/`spin` валит/блокирует все плагины (F31).
4. **Лимиты — Job Object.** Память (RSS) — жёсткий детерминированный лимит (F28). CPU/время —
   грубый ОС-backstop (секунды, F29), поэтому обязателен watchdog (`TerminateJobObject`):
   это **прогресс-таймаут** (F33) **плюс абсолютный дедлайн на invocation** (F35) — оба
   реализованы в прототипе.
5. **API host-функций — range/delta.** Передача документа целиком заменяется диапазонами/
   дельтами: при модели «child на плагин» каждый процесс держит копию документа
   (10 МБ → 20.7 МиБ ×N, F22/F30). Это **обязательное по памяти**, а не оптимизация.
6. **Изоляция — только изоляция отказов.** Краш/зависание/перерасход плагина не трогают
   GUI-хост (F18/F25). Это **не** защита от намеренного обхода Lua VM: скомпрометированный
   плагин получает процесс с правами пользователя (§11.4, F25).

## 3. Обязательные требования до H2

- [x] **Прогресс-таймаут (watchdog).** Нет события от child'а дольше бюджета → `TerminateJobObject`;
      отказ возвращается как отказ плагина. **Проверено в прототипе (F33):** `hang.lua` снят за
      ≈311–316 мс при бюджете 300 мс против 2034–5671 мс у чистого Job CPU-лимита 1000 мс.
- [x] **Абсолютный дедлайн на invocation (F35).** Общий wall-clock вызова, **не сбрасываемый**
      событиями: прогресс-таймаут не ограничивает плагин, бесконечно дёргающий быстрые host-вызовы.
      **Проверено в прототипе (F35):** `chatty.lua` при прогрессе-таймауте 500 мс не снимается вовсе
      (ждёт `--overall-ms` 3000 мс), а с `--deadline-ms 1500` снят за 1500.06 мс.
- [x] **Range/delta host-API.** `get_document_text(whole)` не является основным путём; вводятся
      диапазоны/дельты + версии (`rev`). Обязательно по памяти при «child на плагин» (F22/F30).
      **Проверено в прототипе (F34):** `get_document_len` + `get_document_range` + `apply_edit` на
      документе 10 МБ — ≈0.7 МиБ commit против ≈20.7 МиБ у полной передачи (~28×).
- [x] **Устойчивость протокола к данным child'а (F36).** Host трактует вывод child'а как hostile:
      лимит размера кадра (`read_frame`), `Cur`/`parse_*` → `io::Error` без паники, при нарушении
      протокола — отказ плагина. **Проверено в прототипе (F36):** кадр события ≤ 1 МиБ, кадр
      host → child ≤ 16 МиБ (документ), `bad-child` с неполным кадром даёт `PROTOCOL_ERROR`, а не
      abort; 8 юнит-тестов.
- [x] **Job Object лимиты** (память/CPU/time) и `KILL_ON_JOB_CLOSE`; уборка child'ов при
      смерти host. **Проверено в P9 (F28/F29).**
- [ ] **Карантин:** N=3 падений подряд → авто-отключение плагина.
- [ ] **Изоляция отказов, не защита данных** — формулировка в UI/магазине (§11.4).

## 4. Отклонённые альтернативы

- **A — `unwind` + `catch_unwind` (in-process).** Технически доказан, но +3.2 МБ ломает D6 (F10);
  кросс-платформенного сценария, оправдывающего цену, нет.
- **B — `abort` + C-hook + safe-`pcall` (in-process).** Работает для ошибок (F11/F13), но не
  ловит панику host-кода под `abort`, добавляет C-модуль/ABI-хрупкость (W5), глобальное
  per-state состояние (W6) и оверхед ×2 (F14). Сохраняется только как fallback, если
  процессная модель почему-либо окажется неприемлемой.

---

## 5. Последствия

**Положительные:**
- Снимается класс рисков F9 (ошибки/паники плагина не роняют редактор).
- GUI-хост остаётся без `mlua`; `panic="abort"` не требуется менять (D6 не под угрозой).
- Лимиты делегированы ОС (Job Object): память — точно, CPU/время — backstop.
- Транспорт stdio совпадает с уже задуманным dev-режимом (§7.1).

**Отрицательные / цена:**
- RPC-модель: host-вызовы становятся асинхронными/таймаутными; нужен watchdog.
- N процессов при N плагинах (≈0.6 МиБ и ≈2 мс каждый).
- Сложность жизненного цикла процесса (перезапуск, зомби, версионирование двух бинарей).

**Правки DESIGN_DOC по этому ADR:** §7.1 (stdio — основной), §10.1/§10.2 (Job Object + watchdog
и граница процесса), §14 (RSS child — измерено в P9).
