## 1. Контекст

### 1.1. Проблема

Плагинная подсистема использует модель «child на плагин» (ADR-0021, FINDINGS F30/F31): на каждый
активный плагин существует отдельный процесс `darmark-plugin-host.exe` с бюджетом Job Object.
Ресурсы этих процессов **не видны** в UI: утечка памяти одного плагина конкурирует с главным
процессом и обнаруживается только по замедлению/падению редактора; о срабатывании лимита Job Object
пользователь узнаёт по факту. Диагностика требует стороннего монитора и ручного сопоставления PID.

### 1.2. Что уже зафиксировано (не пересматривается)

`TZ-RESOURCE-MON` (§1, §4, §6) закрыл **продуктовые** границы: место — слот `#logs-resources` в
шапке панели «Журнал» (logs-режимный слот нижнего дока, ADR-0030); сбор — на **Rust-стороне**
(фронт не читает процессы/ФС); рендер — **только `textContent`** (CSP/XSS); **best-effort**
(потеря семпла некритична); **без авто-kill** (реакция — подсветка + запись в журнал); Windows-only.

Этот ADR фиксирует только то, что ТЗ оставило спайку: **источник данных, границы мониторинга,
частоту, технику и стоимость**.

### 1.3. Спайк (F49–F54)

Стенд `crates/resource-spike/` (в продукт не линкуется) измерил WinAPI-путь против `sysinfo`:

- **F49** — WinAPI (`K32GetProcessMemoryInfo`+`GetProcessTimes`) на наборе из 5 PID: **µs**, `sysinfo`
  refresh: **мс** (≈ ×375 в исходном прогоне, ≥ ×100 в независимой проверке). `sysinfo` медленный
  даже при обновлении конкретных PID.
- **F50** — CPU самого опроса (тик 2 с) у WinAPI с большим запасом проходит AC-17 (≤0.5% ядра);
  прямой замер квантован (~15.6 мс), рабочая оценка — производная от F49.
- **F51** — мёртвый/невалидный PID (`0`, `u32::MAX`), системный `4`: WinAPI возвращает **ошибку**
  (не панику и не «0»), `sysinfo` подставляет «0 байт».
- **F52** — PID reuse подтверждён (best-effort): открытие по «голому» PID может вернуть **чужой**
  процесс; риск снимается владением процессом (`Supervisor::Child`), окно «снимок PID → замер» —
  микросекунды.
- **F53** — `windows` уже в дереве `darmark` → маргинальная цена по размеру ≈0; `sysinfo` — новая
  зависимость (+57 КиБ standalone, +21 КиБ сверх winapi).
- **F54** — семантика совпадает: «RSS» == `WorkingSetSize`, «virtual» == `PrivateUsage`.

**Оговорки спайка** (учитывать при реализации): числа WinAPI — «порядок величины» (разброс ~×2);
WebView2/event-loop напрямую не тестировался (AC-19 — ручной GUI-прогон); замеры — на idle child'ах;
`GetProcessHandleCount` требует `PROCESS_QUERY_INFORMATION`.

## 2. Решение

**Источник метрик — WinAPI через крейт `windows` (Windows-only). Мониторятся только главный процесс
и активные child'ы `darmark-plugin-host.exe` из Job Object (привязка к `plugin_id`), период — 2 с,
в отдельном потоке; реакция — подсветка и журнал, без авто-kill. `sysinfo` отклонён как база.**

### 2.1. Источник данных

1. Источник — **WinAPI** через крейт `windows` (уже в дереве `darmark`, `windows 0.62.2`):
   `OpenProcess`/`CloseHandle`, `K32GetProcessMemoryInfo` (`PROCESS_MEMORY_COUNTERS_EX`),
   `GetProcessTimes`, `GetProcessHandleCount`. Хост **не добавляет новых крейтов** (D6/§14).
2. `windows` подключается **прямой зависимостью** `crates/app/src-tauri/Cargo.toml` с **минимальным**
   набором фич (`Win32_Foundation`, `Win32_System_ProcessStatus`, `Win32_System_Threading`), только
   под `#[cfg(windows)]`. Рост `cargo tree -p darmark` и размера release-exe не допускается
   (F53; size-gate §14).
3. Основная метрика ОЗУ — **рабочий набор** (`WorkingSetSize`) — «ОЗУ» в UI. `PrivateUsage`
   (private/commit) и `PeakWorkingSetSize` — опционально в детали. CPU % — производная
   `GetProcessTimes` (kernel+user) между тиками по wall-clock; хендлы — `GetProcessHandleCount`.
4. `sysinfo` **отклонён как база** (см. §4) и в продукт (хост и child) **не вводится**.

### 2.2. Мониторируемые процессы и границы

5. Мониторятся **только**: (а) главный процесс `darmark.exe` (`std::process::id()`) — всегда;
   (б) активные child'ы `darmark-plugin-host.exe`, принадлежащие живому `Supervisor` и назначенные
   Job Object, с привязкой к `plugin_id` (`PluginStatus::Active`).
6. **Не мониторятся**: внуки плагинов, процессы CLI `darmark-plugin.exe`, любые сторонние/чужие
   процессы. Причина — они вне runtime-инвариантов изоляции и Job Object, привязка к `plugin_id`
   для них не определена, а «голый PID» чужого процесса уязвим к reuse (F52).
7. Плагины в `failed`/`quarantined`/`stopped` живого child'а не имеют → строки ресурсов нет
   (только запись в журнал о завершении).
8. Мониторинг — **Windows-only**; вне Windows модуль не компилируется (`#[cfg(windows)]`, как весь
   `plugins/`), строка ресурсов остаётся пустой; сборка на прочих платформах проходит (AC-14).

### 2.3. Частота, поток, стоимость, устойчивость FFI

9. Период опроса — **2 с**, отдельный `std::thread` с флагом остановки (`Arc<AtomicBool>`), корректно
   завершающийся при закрытии/остановке приложения; **не** на event-loop и **не** в async-рантайме.
10. **Инвариант дедлок-безопасности:** снимок списка `(plugin_id, pid)` берётся под **коротким**
    локом `PluginManager`; вызовы WinAPI и эмит события идут **вне** любых блокировок
    `PluginManager`/`DocumentStore`. Снимок не должен блокироваться на время удержания лока
    менеджера watchdog'ом; допустимо **пропустить тик**, если лок занят (best-effort).
11. **Устойчивость к ошибкам (F51):** недоступный/мёртвый/невалидный (`0`, `u32::MAX`, системный `4`)
    PID → метрика **пропускается**, не паника. В FFI-пути запрещены `unwrap`/`expect`/`panic!`
    (профиль `panic="abort"`, ADR-0021). Метрика не отображается как «0».
12. **PID reuse (F52):** корректность обеспечивается **владением процессом** — PID берётся из живого
    `Supervisor::Child`, окно «снимок PID → замер» — микросекунды, смерть child → метрика
    пропускается (п. 11). Отдельный guard (`start_time`) для наших child'ов **не вводится**; для
    произвольных/чужих PID он был бы нужен, но они вне scope (п. 6).
13. Стоимость опроса — **в пределах AC-17** (≤0.5% одного ядра). F49 читается как «**порядок
    величины**» (µs против мс, ≥ ×100), а не как точный p50 (разброс ~×2, п. 24).
14. Поток опроса **не ухудшает отзывчивость UI** (AC-19). Проверка AC-19 — **ручная в GUI**, т.к.
    спайк WebView2/event-loop напрямую не тестировал (п. 25).

### 2.4. События и контракт

15. Канал — **только host → front** (push, Tauri `emit`). События: `resource-metrics` (текущий снимок
    каждый тик, если есть что показать) и `plugin-process-exited` (`{plugin_id, pid, reason?}`).
16. Контракт `resource-metrics`:
    `{ ts, main: { mem_bytes, cpu_percent?, handles? },
       children: [ { plugin_id, pid, mem_bytes, cpu_percent?, handles? } ] }`.
    `ts` — `Date.now()` на Rust-стороне; `mem_bytes` — рабочий набор (байты); формат «N МБ» — на
    фронте; `cpu_percent`/`handles` опциональны (фронт рендерит, если есть).
17. Изменения **аддитивны**: мажор `HOST_API_VERSION` **не поднимается**; контракт host↔child, набор
    host-функций, permissions и конверт **не меняются** (ADR-0027 §2.4). `resource-metrics`/
    `plugin-process-exited` — события фронт-шины (как `log-entry`), **не** часть контракта плагина;
    `docs/PLUGIN_API.md` не правится.
18. Рендер слота — **только `textContent`**; `innerHTML` для строк ресурсов запрещён; CSP
    `default-src 'self'` сохраняется.
19. **Обнаружение завершения child'а** (`plugin-process-exited`) производится **по владению
    процессом** (живой `Supervisor`/его хендл/переход статуса из `active`), а **не** пробой «голого
    PID»: `OpenProcess` по переиспользованному PID «успешно» вернул бы чужой процесс (F52). Порядок
    `plugin-process-exited` относительно `resource-metrics` **не гарантирован**; фронт идемпотентен
    (`orphan` → удаление по отсутствию `plugin_id` в свежем снимке).

### 2.5. Границы реакции

20. **Без авто-kill.** Мониторинг только наблюдает и подсвечивает; снятие child'а по ресурсам —
    исключительно Job Object/watchdog (`DESIGN_DOC §10`, ADR-0021). Мониторингу запрещено вызывать
    `TerminateJobObject`/`kill`/`Supervisor::terminate`.
21. Пороги `.warn`/`.crit` и запись в журнал (через существующий `log-entry`, с дедупликацией по
    переходу через порог) — продуктовое значение `TZ-RESOURCE-MON §6.5`. Хендлы показываются
    **только при превышении порога**. Примечание: пороги ТЗ заданы для **рабочего набора**, тогда как
    лимит Job Object — **committed**-память (64 МБ по умолчанию, ADR-0021); для плагинов с лимитом
    по умолчанию ОС снимет child раньше срабатывания `.warn` — пороги информативны для плагинов с
    увеличенным лимитом. Согласование порогов/единиц — продуктовое уточнение (§3).

### 2.6. Обязательные предусловия кода

22. `supervisor.rs` → `Supervisor::pid()` (`Child::id()`); `manager.rs` → `PluginRuntime::pid()`
    (PID только для `Active` с живым `Supervisor`) и `PluginManager::active_pids()` (или эквивалент).
    Сейчас PID наружу не выходят — это часть решения, а не деталь реализации.
23. Сбор — `crates/app/src-tauri/src/plugins/resource.rs` (Windows-only); эмиттеры — по образцу
    `services.rs`/`lib.rs` (канал `ResourceSink`, подключаемый в `setup_plugins`); модуль не знает про
    Tauri напрямую. TS-модуль — `crates/app/src/resourceMonitor.ts` (в §5.5).

### 2.7. Оговорки спайка (учитывать при реализации)

24. Числа WinAPI — «**порядок величины**»: разброс ~×2 между прогонами; «×375» — оптимистичная
    граница, типично ≈ ×100–×290.
25. **WebView2/event-loop напрямую не тестировался** → AC-19 — **ручной GUI-прогон** при реализации.
26. Замеры — на **idle** child'ах: стоимость вызова переносима, абсолютные значения метрик реальных
    плагинов — нет.
27. `GetProcessHandleCount` требует `PROCESS_QUERY_INFORMATION` (для наших child'ов доступно; для
    чужих процессов могло бы потребовать повышения прав) — дополнительная причина не трогать чужие
    PID.

## 3. Последствия

**Положительные:**

- **D6/§14 не под угрозой:** `windows` уже в дереве → маргинальная цена по размеру ≈0; size-gate без
  изменений.
- **Дешёвый горячий путь:** µs против мс, большой запас по AC-17.
- **Честная семантика ошибок:** мёртвый/недоступный PID → пропуск, а не «0» (F51).
- **Границы совпадают с моделью изоляции** (child-per-plugin + Job Object, ADR-0021), привязка к
  `plugin_id`; чужие процессы не задеваются.
- **Аддитивные события:** контракт плагинов и `HOST_API_VERSION` не затронуты (ADR-0027 §2.4).

**Отрицательные / ограничения:**

- **Windows-only + `unsafe` FFI:** код под `#[cfg(windows)]` требует аккуратности — никаких panic в
  FFI-пути (профиль `panic="abort"`).
- **Новая прямая зависимость `windows`** в `darmark` (не новый крейт в дереве): манифест и фичи надо
  держать минимальными; контроль — `cargo tree` + size-gate.
- **Поток опроса и снапшот PID под локом менеджера:** нужно не ухудшить watchdog-тайминги и не
  создать дедлок (инвариант п. 10).
- **Правки `supervisor.rs`/`manager.rs`** (PID-геттеры) — необходимы, т.к. PID наружу не выходят.
- **Пороги ТЗ не согласованы с committed-лимитом Job Object** (п. 21) — требует продуктового
  уточнения (пороги/единицы) при реализации.
- **Оговорки спайка:** AC-19 — только ручная проверка; абсолютные числа — порядок величины.

**Обратимость:** мониторинг — отдельный модуль (`resource.rs` + `resourceMonitor.ts`) и два
аддитивных события; удаляется без правок Job Object/watchdog, контрактов §13.2 и `HOST_API_VERSION`.

## 4. Отклонённые альтернативы

- **`sysinfo` как база.** Отклонён: новая зависимость (+57 КиБ standalone, +21 КиБ сверх winapi —
  F53) при D6; ~×100–×375 медленнее (F49); даёт RSS, а не рабочий набор на уровне API; рабочего
  преимущества нет — продукт Windows-only (§5). Оставлен только как возможный кроссплатформенный
  fallback — **не требуется** и в продуктовый код не вводится.
- **Pull с фронта** (`setInterval` + Tauri-команда). Отклонён: у фронта нет доступа к процессам,
  каждый тик — лишний IPC-раунд-трип; противоречит принципу «источник данных — Rust-хост».
- **Опрос на event-loop / в async-задаче Tauri.** Отклонён: риск для отзывчивости UI (AC-19) без
  выгоды.
- **`tokio::time::interval` / async-задача.** Отклонён: async-рантайм для таймера 2 с не нужен;
  `std::thread` даёт то же при нулевых новых зависимостях и явном управлении остановкой.
- **ETW / PDH (performance counters).** Отклонён: тяжёлый, запаздывающий, сложный, местами требует
  прав; избыточен против прямого WinAPI по известным PID.
- **Job Object completion port (`JOBOBJECT_ASSOCIATE_COMPLETION_PORT`) как основа.** Отклонён: даёт
  уведомление о завершении/лимите, но не метрики; как дополнение к обнаружению завершения допустим,
  базой быть не может.
- **Мониторинг «всех потомков»/сторонних процессов.** Отклонён: размывает привязку к `plugin_id`,
  выходит за Job Object, делает PID reuse реальным риском (F52).
- **Свои счётчики/аллокатор внутри child'а для точного RSS.** Отклонён: правки child и протокола
  (мажор контракта), дороже и не нужно для best-effort наблюдаемости.
