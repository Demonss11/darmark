# ADR-0031. Источник данных и границы мониторинга ресурсов приложения и плагинов

## 1. Контекст

### 1.1. Проблема

Плагинная подсистема использует модель «child на плагин» (ADR-0021, FINDINGS F30/F31): на каждый
активный плагин существует отдельный процесс `darmark-plugin-host.exe` с бюджетом Job Object.
Ресурсы этих процессов **не видны** в UI: утечка памяти одного плагина конкурирует с главным
процессом и обнаруживается только по замедлению/падению редактора; о срабатывании лимита Job Object
пользователь узнаёт по факту. Диагностика требует стороннего монитора и ручного сопоставления PID.

### 1.2. Что уже зафиксировано (не пересматривается)

Продуктовые границы **зафиксированы** (не пересматриваются): место — вкладка-режим
«Мониторинг» нижнего дока (ADR-0030 + дополнение 11.10.2026); сбор — на **Rust-стороне**;
рендер — **только `textContent`**; **best-effort**; **без авто-kill**; Windows-only.

Этот ADR фиксирует только то, что ТЗ оставило спайку: **источник данных, границы мониторинга,
частоту, технику и стоимость**.

### 1.3. Спайк (F49–F54)

Стенд `crates/resource-spike/` (в продукт не линкуется) зафиксировал (`docs/FINDINGS.md §2.1`):

- **F49** — WinAPI быстрее `sysinfo` на порядки (µs против мс).
- **F50** — CPU опроса в пределах AC-17.
- **F51** — WinAPI возвращает ошибку на мёртвый/невалидный PID (не «0», не панику).
- **F52** — PID reuse подтверждён; риск снимается владением процессом.
- **F53** — `windows` уже в дереве; `sysinfo` — новая зависимость.
- **F54** — семантика метрик прояснена (см. §2.1 п. 3).

Оговорки спайка (числа — порядок величины; WebView2/event-loop не тестировался; idle child'ы) — см. §2.6.

## 2. Решение

**Источник метрик — WinAPI через крейт `windows` (Windows-only). Мониторятся только главный процесс
и активные child'ы `darmark-plugin-host.exe` из Job Object (привязка к `plugin_id`), период — 2 с,
в отдельном потоке; реакция — подсветка и журнал, без авто-kill. `sysinfo` отклонён как база.**

### 2.1. Источник данных

1. Источник — **WinAPI** через крейт `windows` (уже в дереве `darmark`). Хост **не добавляет
   новых крейтов** (D6).
2. `windows` подключается **прямой зависимостью** с **минимальным** набором фич, только
   под `#[cfg(windows)]`. Рост `cargo tree -p darmark` и размера release-exe не допускается
   (F53; size-gate).
3. Основная метрика ОЗУ **зависит от класса процесса** (уточнение п. 17; правка 11.10.2026): для
   child'а плагина — **private/commit** — та же величина, которую ограничивает Job Object; для
   главного процесса — **приватный рабочий набор** (как в Диспетчере задач; лимита Job Object
   у него нет). Полный рабочий набор включает разделяемые страницы DLL и завышает цифру,
   поэтому служит только **фолбэком**, если приватный набор недоступен (старая ОС / неизвестный
   размер структуры → берём полный, а не лживый ноль — F51). CPU % — производная времени
   процесса между тиками; хендлы — отдельный вызов. Все метрики — из **одного** вызова
   получения памяти, стоимость не растёт (F54).
4. `sysinfo` **отклонён как база** (см. §4) и в продукт (хост и child) **не вводится**.

### 2.2. Мониторируемые процессы и границы

5. Мониторятся **только**: (а) главный процесс `darmark.exe` (`std::process::id()`) — всегда;
   (б) активные child'ы `darmark-plugin-host.exe`, принадлежащие живому `Supervisor` и назначенные
   Job Object, с привязкой к `plugin_id` (`PluginStatus::Active`).
6. **Не мониторятся**: внуки плагинов, процессы CLI `darmark-plugin.exe`, любые сторонние/чужие
   процессы. Причина — они вне runtime-инвариантов изоляции и Job Object, привязка к `plugin_id`
   для них не определена, а «голый PID» чужого процесса уязвим к reuse (F52).
7. Плагины в `failed`/`quarantined`/`stopped` живого child'а не имеют → строки ресурсов нет
   (только запись в журнал о завершении).
8. Мониторинг — **Windows-only**; вне Windows модуль не компилируется (`#[cfg(windows)]`, как весь
   `plugins/`), строка ресурсов остаётся пустой; сборка на прочих платформах проходит (AC-14).

### 2.3. Частота, поток, стоимость, устойчивость FFI

9. Период опроса — **2 с**, отдельный `std::thread` с флагом остановки, корректно
   завершающийся при закрытии/остановке приложения; **не** на event-loop и **не** в async-рантайме.
10. **Инвариант дедлок-безопасности:** снимок списка `(plugin_id, pid)` берётся под **коротким**
    локом `PluginManager`; вызовы WinAPI и эмит события идут **вне** любых блокировок
    `PluginManager`/`DocumentStore`. Допустимо **пропустить тик**, если лок занят (best-effort).
11. **Устойчивость к ошибкам (F51):** недоступный/мёртвый/невалидный PID → метрика
    **пропускается**, не паника. В FFI-пути запрещены `unwrap`/`expect`/`panic!`
    (профиль `panic="abort"`, ADR-0021). Метрика не отображается как «0».
12. **PID reuse (F52):** корректность обеспечивается **владением процессом** — PID берётся из живого
    `Supervisor::Child`, окно «снимок PID → замер» — микросекунды, смерть child → метрика
    пропускается (п. 11).
13. Стоимость опроса — **в пределах AC-17** (≤0.5% одного ядра).

### 2.4. События и контракт

14. Канал — **только host → front** (push, Tauri `emit`). События: `resource-metrics` (текущий снимок
    каждый тик, если есть что показать) и `plugin-process-exited` (`{plugin_id, pid, reason?}`).
15. Контракт `resource-metrics`:
    `{ ts, main: { mem_bytes, cpu_percent?, handles? },
       children: [ { plugin_id, pid, mem_bytes, mem_limit_bytes, cpu_percent?, handles? } ] }`.
    `ts` — `Date.now()` на Rust-стороне; `mem_bytes` — приватный рабочий набор
    (как в Диспетчере задач; фолбэк на полный) для **главного**, private/commit для **child'а**
    (п. 3, п. 17); `mem_limit_bytes` — лимит Job Object плагина, у главного отсутствует;
    формат «N МБ» — на фронте; `cpu_percent`/`handles` опциональны (фронт рендерит, если есть).
14. Изменения **аддитивны**: мажор `HOST_API_VERSION` **не поднимается**; контракт host↔child, набор
    host-функций, permissions и конверт **не меняются** (ADR-0027 §2.4). `resource-metrics`/
    `plugin-process-exited` — события фронт-шины (как `log-entry`), **не** часть контракта плагина.
15. **Обнаружение завершения child'а** (`plugin-process-exited`) производится **по владению
    процессом** (живой `Supervisor`/его хендл/переход статуса из `active`), а **не** пробой «голого
    PID»: `OpenProcess` по переиспользованному PID «успешно» вернул бы чужой процесс (F52). Порядок
    `plugin-process-exited` относительно `resource-metrics` **не гарантирован**; фронт идемпотентен
    (`orphan` → удаление по отсутствию `plugin_id` в свежем снимке).

### 2.5. Границы реакции

16. **Без авто-kill.** Мониторинг только наблюдает и подсвечивает; снятие child'а по ресурсам —
    исключительно Job Object/watchdog (`DESIGN_DOC §10`, ADR-0021). Мониторингу запрещено вызывать
    `TerminateJobObject`/`kill`/`Supervisor::terminate`.
17. Пороги `.warn`/`.crit` и запись в журнал (через существующий `log-entry`, с дедупликацией по
    переходу) — продуктовое значение, фиксируется в ТЗ/бэклоге. Хендлы показываются
    **только при превышении порога**. **Уточнение (11.10.2026):** метрика порога зависит от класса
    процесса, т.к. лимит Job Object ограничивает **committed**-память, а не рабочий набор:
    - **плагин** — пороги задаются **долями лимита Job Object** (private/commit);
    - **главный процесс** (Job Object нет) — абсолютные значения (приватный рабочий набор).
    Согласование «пороги по рабочему набору vs committed-лимит» снято. **Бюджет Job Object
    не пересматривается**; замер фактического commit-базлайна плагинов — открытая задача
    реализации (см. §3).

### 2.6. Оговорки спайка (учитывать при реализации)

18. Числа WinAPI — «**порядок величины**»: разброс ~×2 между прогонами; «×375» — оптимистична
    граница, типично ≈ ×100–×290.
19. **WebView2/event-loop напрямую не тестировался** → AC-19 — **ручной GUI-прогон** при реализации.
20. Замеры — на **idle** child'ах: стоимость вызова переносима, абсолютные значения метрик реальных
    плагинов — нет.

## 3. Последствия

**Положительные:**

- **Границы совпадают с моделью изоляции** (child-per-plugin + Job Object, ADR-0021), привязка к
  `plugin_id`; чужие процессы не задеваются.
- **Аддитивные события:** контракт плагинов и `HOST_API_VERSION` не затронуты (ADR-0027 §2.4).

**Отрицательные / ограничения:**

- **Windows-only + `unsafe` FFI:** код под `#[cfg(windows)]` требует аккуратности — никаких panic в
  FFI-пути (профиль `panic="abort"`).
- **Новая прямая зависимость `windows`** в `darmark` (не новый крейт в дереве): манифест и фичи надо
  держать минимальными; контроль — `cargo tree` + size-gate.
- **Поток опроса и снапшот PID под локом менеджера:** нужно не ухудшить watchdog-тайминги и не
  создать дедлок (инвариант п. 10).
- **Пороги/единицы согласованы** (п. 17, уточнение 11.10.2026): для плагина пороги —
  доли лимита Job Object, для главного процесса — приватный рабочий набор.
  Остаётся **замер** фактического commit-базлайна штатных плагинов —
  подтвердить, что warn 75% не горит постоянно.
- **Оговорки спайка:** AC-19 — только ручная проверка; абсолютные числа — порядок величины.

**Обратимость:** мониторинг — отдельный модуль (`resource.rs` + `resourceMonitor.ts`) и два
аддитивных события; удаляется без правок Job Object/watchdog, контрактов §13.2 и `HOST_API_VERSION`.

## 4. Отклонённые альтернативы

- **`sysinfo` как база.** Отклонён: новая зависимость при D6 (F53); на порядки медленнее (F49);
  даёт RSS, а не рабочий набор на уровне API; рабочего преимущества нет — продукт Windows-only (§5).
  Оставлен только как возможный кроссплатформенный fallback — **не требуется** и в продуктовый код
  не вводится.
- **Pull с фронта** (`setInterval` + Tauri-команда). Отклонён: у фронта нет доступа к процессам,
  каждый тик — лишний IPC-раунд-трип; противоречит принципу «источник данных — Rust-хост».
- **Опрос на event-loop / в async-задаче Tauri.** Отклонён: риск для отзывчивости UI (AC-19) без
  выгоды.
- **`tokio::time::interval` / async-задача.** Отклонён: async-рантайм для таймера 2 с не нужен;
  `std::thread` даёт то же при нулевых новых зависимостях и явном управлении остановкой.
- **ETW / PDH (performance counters).** Отклонён: тяжёлый, запаздывающий, сложный, местами требует
  прав; избыточен против прямого WinAPI по известным PID.
- **Job Object completion port (`JOBOBJECT_ASSOCIATE_COMPLETION_PORT`) как основа.** Отклонён: даёт
  уведомление о завершении/лимите, но не метрики; как дополнение к обнаружению завершения допустим,
  базой быть не может.
- **Мониторинг «всех потомков»/сторонних процессов.** Отклонён: размывает привязку к `plugin_id`,
  выходит за Job Object, делает PID reuse реальным риском (F52).
- **Свои счётчики/аллокатор внутри child'а для точного RSS.** Отклонён: правки child и протокола
  (мажор контракта), дороже и не нужно для best-effort наблюдаемости.
