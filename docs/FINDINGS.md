# FINDINGS — замеры прототипов и спайков darmark

> **Назначение.** Источник чисел (размеры, память, латентность, стоимость) для решений проекта.
> Нормативная спецификация чисел не содержит: трассировка решений — `docs/DESIGN_DOC.md` §16 и
> ADR в `docs/adr/`; **источник чисел — этот файл** (D15).
> **Происхождение замеров.** Windows x86_64-msvc, rustc 1.99, релизный профиль
> `[profile.release]` (`opt-level="s"`, LTO, strip, `panic="abort"`); где нужен `unwind` —
> `[profile.proto]`. Стенды (`crates/*-spike`) и прототип `proto/lua-plugin-host` в продукт не
> входили и **удалены после реализации**; их блоки перенесены в продуктовые `plugin-host`/
> `plugin-core`, упоминания их файлов ниже — исторические.
> **Форма записей.** «гипотеза → замер → вывод» (D15); нумерация фактов `F1–F58` сквозная.
> **Статус.** Реализованные замеры свёрнуты в «Индекс закрытых фактов» (для трассируемости
> `F`-номеров); открытые оговорки — ниже.

## 1. Что не проверено (предел прототипа)

Пункты прототипной очереди, оставшиеся непроверенными (на принятые решения не влияют):

- range/delta-API против N1 (латентность) — проверено только по **памяти** (F34), не по латентности.
- P3: `MemoryError` на `hog.lua`; `spin.lua` под лимитом; M6 на `count.lua`; M7 (два инстанса в одном процессе).
- P5: host-функции на заглушке + permissions; возврат ошибок Lua-значением.
- P6: внешние строки 5.5 (M9).
- P2: полный M1 (`strip`, baseline именно прототипа).
- API-референс 5.5: `global`, `table.create`, отличия C API (в т.ч. `LUA_REGISTRYINDEX`).

## 2. Открытые вопросы и ограничения

### 2.1. Источник метрик ОЗУ/CPU (спайк, ADR-0031)

**Что не проверено стендом (оговорки):**

1. **WebView2/event-loop** напрямую не тестировался — стенд мерил только стоимость WinAPI/`sysinfo`,
   а не влияние на отзывчивость UI главного процесса (AC-19 остаётся на ручную проверку в GUI
   при реализации).
2. Замеры — на **idle** child'ах: реальные плагины с активным RSS/Lua дадут другие значения самих
   метрик, но не стоимости вызова.
3. CPU-время процесса **квантуется планировщиком** (~15.6 мс), поэтому прямой `[POLL]` — верхняя
   граница, а рабочая оценка — производная от F49.
4. `GetProcessHandleCount` требует `PROCESS_QUERY_INFORMATION` (для наших child'ов доступно; для
   чужих процессов может потребоваться повышенное право) — в UI хендлы только при превышении порога.

**Независимая проверка стенда (оговорки, 11.10.2026):**

- **F49 — «порядок величины», не точный p50.** Числа WinAPI нестабильны от прогона к прогону
  (разброс ~×2); подтверждён порядок «µs против мс» (≥×100), абсолют «×375» — оптимистичная граница.
- **F50 завышено для `sysinfo`.** Прямой квантованный замер для `sysinfo` даёт 0.31–1.09% (на n=5
  в 5 из 6 прогонов > AC-17 0.5%); производная от F49 указывает, что реальный CPU, вероятно, всё же
  проходит AC-17, но **прямой замер этого не доказывает**. Для WinAPI AC-17 — с большим запасом.
- **F52 усилена оговорка (PID reuse).** Открытие по «голому» PID может **молча** вернуть метрики
  **чужого** процесса (не `Err`, значит обработка ошибок F51 не спасает). Риск снят владением
  процессом (PID из живого `Supervisor`) и низкой частотой спавнов; для произвольных чужих PID
  нужен `start_time`/guard.

### 2.2. AI-клиент (спайк, ADR-0032/ADR-0033)

**Что не проверено стендом (оговорки):**

1. **Живой запрос к `routerai.ru`** — при спайке не выполнялся (нет `ROUTERAI_API_KEY`); проверялись
   парсер и mock-сервер. Разовая живая проверка выполнена позже (12.10.2026 — см. §2.3): HTTP 200,
   обычный OpenAI-формат (`choices[0].message.content`, `usage`), плюс `usage.completion_tokens_details.reasoning_tokens`
   и `usage.cost`, верхнеуровневые `system_fingerprint`/`provider`; модель — reasoning-вариант.
   Стриминг чанков (`ai:chunk`) на живом провайдере по-прежнему не проверен (только парсер+mock).
2. **Маргинальный размер в продукте** — не измерен: замеры standalone; в `darmark` уже присутствуют
   `tokio`, `url`, `http`, `serde_json`, поэтому реальный прирост `reqwest` **меньше** дельты стенда,
   а вклад `rustls`-стека (новый целиком) — близок к дельте. Точный размер требует сборки `darmark`
   с AI-модулем (отдельная задача).
3. **30-секундный таймаут / rate-limit / маппинг ошибок** — заданы номинально; поведение под
   `429`/`5xx`/офлайн не измерялось.
4. **Интеграция с UI Tauri** — не проверялась: blocking-`ureq` требует выноса с UI-потока
   (`async_runtime::spawn_blocking`) и доставки чанков событиями; `reqwest` — async-нативно.

### 2.3. AI-генерация плагинов: reasoning-бюджет (живая проверка, 12.10.2026)

**Контекст.** Разбор отчётов «Создать плагин» падал (`on_activate не найдена`, затем
`host.document == nil`): модель генерировала модуль-таблицу (`local M … return M`) и выдуманный API.
Причина — промт `create-plugin` не задавал контракт точки входа и перечень host-функций; исправлено
(промт + проброс `contributes` в манифест, покрыто тестами).

**Гипотеза → замер → вывод.**

- **Гипотеза:** живой провайдер даёт обычный поток; дефолтных `max_tokens` хватает на генерацию кода.
- **Замер** (`deepseek/deepseek-v4.1-flash`, изолированный профиль):
  - модель — **reasoning-вариант**: `completion_tokens_details.reasoning_tokens` уже на тривиальном
    запросе ≈75–128;
  - при `max_tokens = 4096` (прежний дефолт, `ai/types.rs`) сложная генерация тратит **весь бюджет на
    reasoning** и возвращает **пустой `content`** с `finish_reason: "length"`; **воспроизводится и со
    старым коротким промтом** → не регрессия промта, а свойство связки «reasoning-модель + лимит»;
  - живая перепроверка v4 (12.10.2026, §2.4): view-кейс при `max_tokens = 16384` **упирается в reasoning**
    (`reasoning_tokens = 16384`, пустой ответ), а при `32768` доходит (`reasoning ≈15.5k` + ответ ≈4.5k).
    И 4096, и 8192 — мало; разброс reasoning по кейсам/прогонам велик.
- **Вывод:** обрыв по лимиту неотличим от «пустого ответа» — нужен запас токенов и/или явная ошибка.

**Задачи:**

1. ~~**Обрыв по `max_tokens` ≠ «пустой ответ».**~~ *Закрыто:* дефолт `max_tokens` поднят
   `4096 → 32768` (`ai/types.rs`); `finish_reason` проведён сквозняком (SSE → `ChatOutcome` →
   `AiResponse` и в payload `ai:done`), UI при `"length"` показывает заметку об обрыве, а не «Пустой
   ответ» (пустой/частичный ответ не плодит карточек).
2. ~~**`has_on_activate` (plugin-cli) — узкая эвристика.**~~ *Закрыто:* распознаёт любые whitespace
   между `function` и `on_activate` и перед `=` (`function␣␣on_activate`, таб, перенос), при этом
   признаёт только **глобальную** точку входа — отвергает `M.on_activate =`/`M:on_activate`/
   `function M.on_activate` и `local function on_activate`/`local on_activate =` (тесты на полевую форму
   найдены `rust-tester` как падающие и исправлены).

**Что не проверено.** UI-путь стриминга чанков на живом провайдере (SSE парсили, но панель на живом
роутере не гоняли).

### 2.4. Промты встроенных скиллов: цикл оценки (12.10.2026)

**Контекст.** Промты `explain`/`create-plugin` (`ai/skills.rs`, дубль в `aiPanel.ts`) доработаны по
приёмам `skill-creator`: явный **формат вывода**, разбор «похожих» механизмов, правило «не выдумывай»,
пример-каркас. Оценка — сабагентами-«исполнителями» (baseline-снимок vs новая версия) и **живым
`deepseek`** (12.10.2026, стриминг SSE, запас `max_tokens = 32768`).

**Гипотеза → замер → вывод.**

- **Гипотеза:** явный формат и разведение API поднимут корректность генерации.
- **Замер (прокси, сабагенты):**
  - `explain`: без формата ответ непредсказуем (0/1 по критерию «4 секции»); с 4 секциями — pass.
  - create-plugin, статусбар: и baseline, и первая версия **путали** `host.set_view_content` со
    статусбаром (5/6 → после правила `host.show_message` 6/6).
  - create-plugin, view: `view_id` собирали из id view, а не плагина (`frontmatter:table` вместо
    `<plugin_id>:<kind>`) → рантайм `unknown_view`; явный состав `view_id` это снимает.
- **Замер (живой `deepseek`, `max_tokens = 32768`):** v4 проходит все ассерты — view `7/7`, статусбар
  `6/6`, explain `4/4` (baseline explain `3/4`). Цена: v4 тратит **в 2–4 раза больше reasoning-токенов**
  (view ≈15.5k, статусбар ≈2.6k, explain ≈3.3k против ≈0.9–11.7k у baseline).
- **Вывод:** промты улучшают результат (подтверждено живым прогоном), но раздувают reasoning — держать
  их **лёгкими**; без запаса `max_tokens` (§2.3) ответ обречён на пустоту.

**Задачи:**

1. **Прогнать цикл на Ф3-скиллах** (переструктурировать, конспект, отладить плагин, добавить view) —
   сейчас ADR-0032 держит ровно 2 скилла, это расширение MVP.
2. **Лёгкость промтов — гипотеза опровергнута (данные).** Живая выборка (view n≈37, статусбар n≈42,
   `max_tokens=32768`) показала: лёгкие кандидаты держат ассерты (view `7/7`, статусбар `6/6`,
   explain `4/4`), снижают reasoning на view (−25% у `c1`), но **повышают** его на статусбаре
   (+20…24%; в парных батчах — +42…56%). Вывод: явное разведение view/статусбар в v4 и есть то, что
   снижает рассуждения; сжатие его убирает и добавляет reasoning. Промт оставлен без изменений
   (v4 — оптимум из проверенных; baseline-статусбар дешевле, но менее точен).

Закрыто здесь: живая перепроверка v4 и просмотрщик эвалов (`skill-creator/eval-viewer/generate_review.py`).

### 2.5. MCP-сервер (трек `TZ-MCP`, План 1; 12.10.2026)

**Контекст.** MCP переосмыслен из inbound-сервера внешних клиентов (ADR-0034 §2.5) во **внутренний
контрактный tool-слой** (ADR-0036: in-memory транспорт, клиент — встроенный AI). Реализован **План 1**
(`tasks/TZ-MCP.md`, `tasks/PLAN-MCP.md`): крейт `mcp-core` (JSON-RPC 2.0 + семантика MCP), чистый крейт
`plugin-catalog`, модуль `mcp` в `src-tauri` (4 tools + 6 resources, журнал вызовов, белый список
путей). Tool-loop ассистента — **План 2** (зависит от поддержки tool-calling провайдером).

**Подтверждённые структурные факты (без `F`-номеров — это не замеры):**

- **`mlua` вне GUI сохранён:** `cargo tree -p darmark | Select-String mlua` пусто и после подключения
  MCP. Каталог плагинов вынесен из `plugin-cli` в чистый крейт `plugin-catalog` (deps: `plugin-core`,
  `serde_json`), т.к. **lib-таргет `plugin-cli` наследует `[dependencies]` пакета** → `plugin-host` →
  `mlua` и сломал бы guard ADR-0021/D6.
- **Тесты после Плана 1:** `md-core`, `mcp-core` (26), `plugin-catalog` (21), `darmark` (268 lib +
  13 контрактных `mcp_contract`, 1 `debug_plugin`); `cargo fmt --check` и `clippy -D warnings` — чисто;
  `npm run build` (tsc strict) — зелено.

**Открытые оговорки и не-блокеры (заведены; для MVP не критичны):**

1. **Tool-loop не реализован (План 2).** AC-MCP-5/14 (ассистент сам вызывает tools; результат —
   «данные, не инструкции») не закрыты: зависят от tools/function-calling провайдера, которого
   `ChatRequest` (`ai/transport.rs`) сейчас не несёт.
2. **`plugin_test` через MCP покрыт только схемой.** Прогон песочницы через MCP Rust-тестом не
   проверяется (сайдкар → E2E). Остаточный риск паритета с CLI.
3. **`app_log_sink` (prod-only) не покрыт.** Конверт `log-entry {level,category,message}` проверяется
   лишь до границы стока; `LogSink = Fn(&str)` не несёт уровень/категорию. MCP-записи идут уровнем
   `info` — при дефолтном фильтре журнала наблюдаемость R2 зависит от фильтра.
4. **Белый список путей: разрешён весь системный temp** (решение зафиксировано в TZ-MCP R3) — сужение
   до `darmark-ai-validate-*` сломало бы валидацию плагинов из произвольных temp-каталогов. FS-поверхность
   чтения шире буквы R3; клиент доверенный, изоляция (`canonicalize` + `starts_with` + отказ на reparse)
   сохранена.
5. **`catalog_repo()` зависит от CWD.** В упакованном приложении каталога может не быть → tool/resource
   вернут ошибку (открытый вопрос TZ-MCP §8).
6. **JSON-RPC-упрощения:** поле `jsonrpc` не валидируется; notification (без `id`) получает ответ с
   `id: null`; `"arguments": null` не нормализуется в `{}`. Для внутреннего клиента не критично.
7. **Шаблонный ресурс `darmark://plugins/{id}/manifest`** читается через `resources/read` (сегментный
   матч в `mcp-core::registry`); отдельный `resources/templates/list` (есть в спеке MCP) не вводится.
8. **Гигиена/мелочи:** `manifest_errors` стал `#[cfg(test)]` (консолидировать с `validate_plugin_static`);
   `sanitize_text` — prefix-replace без границ пути (best-effort); тесты мутируют глобальные env
   (`DARMARK_PLUGIN_REPO`/`DARMARK_PLUGINS_DIR`) без лока; цикл `AppHandle` в managed state (осознан,
   нужен комментарий); дублирование `ToolError`/`ResourceError`; часть тестов `mcp-core` тавтологичны.
9. **Не-Windows не собирался** (цель — Windows): cfg-ветки MCP (`plugin_validate`/`plugin_test` — только
   Windows) проверены чтением; CI — `windows-latest`.

## 3. Индекс закрытых фактов

Свёрнутые (реализованные) замеры — по диапазонам, чтобы любой цитируемый `F`-номер оставался
разрешимым. Границы уточнены по фактическому составу файла.

- **F1–F15** — прототип Lua-хоста, in-process (`panic="abort"`/`unwind`, C-hook, safe-`pcall`,
  транспорт) → ADR-0021 (изоляция процесса).
- **F16–F38** — вынос Lua в процесс: C-транспорт, P9 (M10–M12), закрытие D16 (per-call watchdog,
  range/delta, устойчивость протокола, карантин, граница изоляции) → ADR-0021/0023.
- **F39–F44** — продуктовая плагинная система H2 (рантайм, permissions, события, настройки,
  `view:create`, мёртвый код) → ADR-0022/0023.
- **F45–F48** — локальный каталог плагинов H3, Фаза 2a (`--repo`, `remove`, `link`, целостность/
  подпись отложена в Фазу 2b) → ADR-0026.
- **F49–F54** — источник метрик ОЗУ/CPU → ADR-0031 (WinAPI, `windows`-crate).
- **F55–F58** — AI-клиент (HTTP+TLS, SSE) → ADR-0032/0033 (`reqwest`+SChannel, SSE).
