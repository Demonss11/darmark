# Отчёт по C-спайку (Lua в отдельном процессе) и ревизия развилки B vs C

**Дата:** 06.10.2026
**Ветка:** `proto/lua-plugin-host`
**Повод:** по итогам v1.3 поднят вопрос «тестировали ли вынос Lua из процесса». Не тестировали.
Проведён C-спайк с честным bidirectional round-trip.
**Проверяемые документы:** `reviews/TZ-proto-lua-host-P1-review-v1.2.md` (спайк B),
`reviews/TZ-proto-lua-host-P1-review-v1.3.md` (разбор + Windows-only), `docs/proto/FINDINGS.md`.
**Артефакты:** `crates/lua-rpc-spike/` (`rpc-parent`, `rpc-child`).

---

## 1. Вердикт

**Вариант C измерен и из «аварийного люка» стал полноценным кандидатом.** Он снимает всю стопку
митигаций B (panic-стратегия, C-hook, safe-`pcall`, per-state счётчик, value-returns) и даёт
жёсткую изоляцию. Единственная существенная цена — **сериализация при передаче документа**
(~12 мс на 10 МБ), и она предсказуема и адресуема дизайном API (дельтами/диапазонами).

Мелкие host-вызовы дешёвы (18 µs), поэтому fine-grained API в C не проблема. Крах и зависание
плагина не трогают host — проверено.

**Рекомендация:** C — приоритетный кандидат для H2; B остаётся как более простой вариант, если
плагинам действительно нужен доступ ко всему тексту на каждое событие без задержек.

---

## 2. Что построено

Новый крейт `crates/lua-rpc-spike`:

- `src/lib.rs` — бинарный протокол (u32-длина + payload), кодирование вручную, без serde;
- `src/bin/parent.rs` — host-заглушка (документ `String` в памяти), обслуживает запросы child,
  меряет spawn/init/run, держит таймаут и убивает child;
- `src/bin/child.rs` — отдельный процесс с Lua 5.5 (mlua `lua55`+`vendored`), host-функции
  (`get_document_text`, `get_document_version`, `apply_edit`, `log`, `crash`) реально ходят
  **round-trip** в parent;
- фикстуры: `hello`, `ping` (2000 вызовов), `large` (10 МБ), `fetch10`, `edit`, `spin`, `crash`.

Транспорт — stdio. Никакого C-hook/`panic=abort`-трюка: в C он не нужен по построению.

## 3. Метрики (release, Windows/msvc)

### 3.1. Латентность и пропускная способность

| Метрика | Значение |
|---|---|
| spawn child (warm) | 2.8–5.0 мс (холодный первый — 75 мс) |
| init (CMD_RUN → READY: Lua state + host reg) | 2.2–4.4 мс |
| мелкий round-trip, 2000× `get_document_version` | **avg 18 µs**, max 162 µs |
| передача 10 МБ, один round-trip | **11.6 мс** (~900 МБ/с) |
| 10 × 10 МБ (устойчиво) | avg **12.1 мс**, ~652 МБ/с |
| `apply_edit` round-trip (мелкий payload) | 88 µs |

### 3.2. Изоляция

| Сценарий | Результат |
|---|---|
| `spin.lua` (`while true do end`) | parent убил child по таймауту 1500 мс, **host жив**, exit 0 |
| `crash.lua` (child `abort()`) | parent увидел закрытие потока, **host жив**, exit 0 |

### 3.3. Размеры

| Артефакт | Размер |
|---|---|
| пустой exe | 112 КБ |
| `rpc-parent` (host, фактически без mlua) | 257 КБ |
| `rpc-child` (mlua + Lua 5.5) | 433 КБ |
| `lua-proto` (in-process + C-hook), для сравнения | 441 КБ |

Оценка суммарно: **B** ≈ `mdedit` 3.69 + mlua 0.33 ≈ **4.0 МБ**; **C** ≈ 3.69 + parent ~0.15 +
отдельный child 0.43 ≈ **4.3 МБ**; **A** ≈ 7.2 МБ. B и C оба в рамках D6.

## 4. Влияние на узкие места (W1–W15 из обсуждения)

| # | Узкое место B | C |
|---|---|---|
| W1 | `panic=abort` убивает процесс на любой Rust-панике | **снято**: плагин в отдельном процессе; host может остаться на `abort` без mlua |
| W2 | host-код обязан быть panic-free и Err-free | **снято для plugin-host**; остаётся как общая дисциплина Rust-кода продукта |
| W3 | оверхед hook ×2 | **снято** (нет hook; лимит = kill); вместо этого transfer-cost (§3.1) |
| W4 | monkey-patch `pcall`/`xpcall` | **не нужен** |
| W5 | ручной C ABI без заголовков | **не нужен** (обычный mlua) |
| W6 | глобальные C-статики / per-state | **не нужен** (процесс = состояние) |
| W7 | состояние после лимита | **неактуально** (процесс пересоздаётся) |
| W8 | `MemoryError` перехватываем | заменяется на Job Object (RSS-лимит) — **не реализовано в спайке** |
| W9 | value-returns вместо `Err` | заменяется протоколом; но API становится RPC |
| W10 | атомарность частичного изменения | **остаётся** (свойство операции, не транспорта) |
| W11 | паника host-функции | в child = краш child (изолирован); в parent — общая проблема приложения |
| W12 | `cc` + C-объект в size-билде | `cc` не нужен; появился отдельный бинарь child (433 КБ) + plumbing (~145 КБ) |
| W13 | механизм завязан на MSVC | **переносимый** stdio; Windows-специфика только в Job Object (опционально) |
| W14 | dev на Linux vs рантайм Windows | **переносимо**, dev-тесты воспроизводимы |
| W15 | стопка митигаций | **заменяется одним архитектурным швом** (граница процесса) |

### 4.1. Новые узкие места, которые вносит C

| # | Узкое место | Комментарий |
|---|---|---|
| N1 | Передача документа ~12 мс/10 МБ | главная цена; лечится API (диапазоны/дельты), а не механизмом |
| N2 | Жизненный цикл процесса | spawn 3–5 мс, перезапуск, зомби, зависший child, риск блокировки записи на больших кадрах |
| N3 | RPC-протокол и совместимость | но §7 DESIGN_DOC уже планирует stdio-dev-транспорт — работа не впустую |
| N4 | Асинхронность/порядок вызовов | host-вызовы становятся RPC; shared memory не используется |
| N5 | Job Object для лимитов | Windows-специфичен; в спайке только kill по таймауту |
| N6 | Два бинаря | версионирование и синхронность host/child |

## 5. Обновлённая развилка

| Вариант | Лимиты | Изоляция | Паника плагина | Размер | Статус |
|---|---|---|---|---|---|
| A. `unwind` + `catch_unwind` | есть | нет | поймана | ~7.2 МБ | **закрыт** (D6) |
| B. `abort` + C-hook + safe-pcall + value-returns | есть, ценой ×2 CPU | нет | host обязан быть panic-free | ~4.0 МБ | рабочий, но хрупкий |
| **C. `abort` + Lua в процессе** | есть (kill / Job Object) | **жёсткая** | **host не трогает** | ~4.3 МБ | **приоритетный кандидат** |

## 6. Что спайк НЕ покрыл

- **Job Object**: RSS/CPU-лимиты не реализованы — только kill по таймауту.
- **Реальный DocumentStore**: правки/версии — заглушки.
- **Деградация при зависании child посреди большого ответа**: риск блокировки записи не провоцировался.
- **Перезагрузка плагина, состояние инстанса, карантин** (P7).
- **Shared memory / range-API** как способ снять N1 — не проверялось.
- Замеры — на спайк-харнессе (одноразовые процессы, холодный кэш), не на боевой нагрузке.

---

## 7. Вход в ADR

1. **Основной кандидат — C.** Паника/лимиты/`pcall`/C-ABI — не проблемы host'а.
2. **API плагинов проектировать под C**: предпочтение диапазонам/дельтам над полным `get_document_text`,
   иначе N1 (12 мс/10 МБ) станет доминировать на горячем пути.
3. **Лимиты — через Job Object** (память/CPU/время), а не `set_memory_limit`/hook.
4. **Базовый host остаётся на `abort`** и без mlua — D6 не трогаем.
5. §7 DESIGN_DOC: stdio-транспорт повышается из dev-режима в основной; формулировку
   «основной — in-process без сериализации» пересмотреть.
6. §10.2 DESIGN_DOC: поправка из v1.3 остаётся в силе (для B); для C — ограничение снимается
   границей процесса.

## 10. Итог

C-спайк закрывает главный незамеренный пробел развилки. Картина: **C даёт жёсткую изоляцию и
убирает всю хрупкость B почти без роста размера**, платя предсказуемой сериализацией на полном
доступе к документу. B остаётся проще в реализации, но несёт неустранимые риски (паника host =
смерть редактора, оверхед ×2). До решения B vs C осталось измерить Job Object и деградацию на
больших кадрах.
