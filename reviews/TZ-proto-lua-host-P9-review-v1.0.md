## 1. Вердикт (M10–M12)

**Гейт M10 пройден.** stdio-round-trip работает в GUI-конфигурации (parent — subsystem 2, без
консоли), включая кадр 10 МБ; при обрыве child parent детектирует закрытие границы и не виснет,
в т.ч. когда он заблокирован посреди крупной записи.

**Смена транспорта (named pipes / loopback-сокет) не требуется. Эскалации в ADR по транспорту
нет: C остаётся приоритетным кандидатом.**

**M11:** лимиты child'а перенесены в Job Object (без ручного kill). **Память** — жёсткий, точный,
детерминированный лимит. **CPU/время** — ОС завершает процесс, но проверка лимита «периодическая»
(док. формулировка), и на практике латентность — секунды: это **не точная граница**. Вывод для D16:
memory-лимит — основной; CPU/время — грубый backstop, при необходимости жёсткого CPU-бюджета
добавляется watchdog (`TerminateJobObject` по wall-clock).

**M12:** модель процессов измерена. «Общий child» экономит память/время (почти константен по N),
но **аннулирует изоляцию** — один `crash`/`spin` убивает/блокирует все плагины. «Child на плагин»
даёт заявленную в C жёсткую изоляцию ценой N×~0.6 МиБ и N×~2 мс spawn. **Рекомендация для ADR (D16):
«child на плагин»** — иначе C теряет своё главное преимущество (F25).

## 2. Что построено

Новый бинарь `gui-parent` (тот же протокол, что `rpc-parent`):

- сам parent собран как GUI-приложение (`#![cfg_attr(windows, windows_subsystem = "windows")]`,
  subsystem 2) — как `mdedit.exe`;
- child (`rpc-child`, subsystem 3) запускается с `CREATE_NO_WINDOW`: консоли нет и у child;
- пайпы — `Stdio::piped()` (std: `CreatePipe` + `STARTUPINFO.hStd*` + `bInheritHandles=TRUE`),

- у GUI-процесса нет stdout — результат пишется в `--report <path>`, паника — в `<report>.panic`,
  итог — в код выхода;

Прогон: `pwsh -File crates/lua-rpc-spike/run-m10.ps1` (exit 0 = гейт пройден).

## 3. Метрика M10 (release, Windows/msvc)

Фикстура `large.lua` (один `get_document_text` на документ 10 МБ), `doc-size` = 10 485 760.

| Сценарий | Наблюдение | Вывод |
|---|---|---|
| **roundtrip**: GUI-parent ↔ child, кадр 10 МБ | exit 0; init 11.9 мс; round-trip **11.9 мс**; `doc_bytes=10485760`; child-лог доставлен | stdio работает без консоли, 10 МБ проходят |
| **break**: child убит → parent пишет 10 МБ | запись `BrokenPipe` за **0.0 мс**; reader `Disconnected` за **0.0 мс**; `hang=0`; exit 0 | обрыв виден сразу, вечной блокировки нет |
| **break-write**: child жив, но не читает (`spin.lua`); parent блокируется в записи 10 МБ, watchdog убивает child | запись разблокирована через **151 мс** (`BrokenPipe`); дисконнект **0.0 мс**; `hang=0`; exit 0 | блокировка на заполненном пайпе снимается смертью child; N2 при обрыве не критичен |

События, приводящие к снятию блокировки, исчерпываются гибелью child. Отдельный таймаут
записи нужен только для «живого, но зависшего» child — снят Job Object'ом (M11, §3.1).

## 3.1. Метрика M11 (release, Windows/msvc)

Job Object (FFI kernel32, без внешних крейтов): `crates/lua-rpc-spike/src/job.rs`,
harness `src/bin/job_parent.rs`, фикстура `plugins/hog.lua`, прогон `run-m11.ps1`.
Никакого ручного `kill()`/таймаута в сценарии — лимит срабатывает на стороне ОС.

Контекст: harness сам запущен внутри чужого Job (`parent_in_job=1`), поэтому наш Job — **вложенный**.
По документации для вложенных Job эффективный per-process time-limit — «самый строгий в цепочке»
(наш), т.е. вложенность не мешает.

| Сценарий | Лимит | Наблюдение | Вывод |
|---|---|---|---|
| **hog** (аллокация 1 МиБ в цикле) | mem = 64 МиБ | `PeakProcessMemoryUsed` = 66.1 МБ (≈63.0 МиБ ≤ 64 МиБ); child снят за **153–206 мс**; `exit=0xC0000409`; parent жив | **память: жёстко, точно, детерминированно** |
| **spin** (`while true do end`) | cpu = 500 мс | снятие за **4.2–6.9 с** (разброс), процесс завершает ОС, parent жив | CPU/время: ОС-лимит есть, но **грубый** (периодическая проверка) |
| **spin** | cpu = 1 / 3 / 30 с | ~6.9 с / ~9.0 с / ~33.6 с | латентность растёт с лимитом, но не точная |
| **hello** (контроль) | cpu=500, mem=64 | `status=0`, штатное завершение за ~3 мс | лимиты не мешают нормальному плагину |
| **KILL_ON_JOB_CLOSE** | — | убийство parent → rpc-child мёртв за <500 мс | уборка при смерти host работает |

Почему CPU «грубый»: Microsoft формулирует так — *«The system **periodically** checks to determine
whether each process … has accumulated more user-mode time than the set limit»*. Период не
специфицирован; в этом окружении это секунды. Значит, CPU/время-лимит Job'а **нельзя**
использовать как точную границу (например, «не больше 200 мс на вызов плагина»).

**Интерпретация для D16/N5:** memory-лимит решает исходную задачу (защита от утечки/разбухания —
детерминированно). CPU/время-лимит годится как аварийный backstop. Если продукту нужен жёсткий
бюджет CPU/времени, к нему добавляется watchdog, который по wall-clock вызывает
`TerminateJobObject` (по-прежнему Job-уборка, но точность задаёт watchdog). Это не отменяет
выигрыша C: host не участвует в обработке ошибок плагина и не может быть уронен.

Уточнение по `hog`: child уходит в `abort` (`0xC0000409`) — не потому, что лимит «убивает», а
потому что под `panic="abort"` Rust-аллокатор не может выделить память под обработку `MemoryError`.
Результат тот же и приемлемый для C: плагин снят, host жив.

## 3.2. Метрика M12 (release, Windows/msvc)

Модель «общий child» реализована командой `CMD_RUN_N` (N плагинов в один процесс); «child на плагин» —
N процессов по `CMD_RUN`. Память — `PeakJobMemoryUsed` Job'а, в который назначены child'ы прогона
(aggregate-пик совпадает с суммой при одновременной жизни). Прогон `run-m12.ps1`.

### Память и активация

| Конфигурация | commit-пик | активация |
|---|---|---|
| пустой child (1 процесс) | **0.62 МиБ** | ~8 мс (одиночный) |
| child с 10 МБ документом | **20.7 МиБ** | ~24 мс (вкл. round-trip 10 МБ) |
| N=5, **общий child** | **0.64 МиБ** | **6.9–9.7 мс** |
| N=5, **child на плагин** | **3.12–3.17 МиБ** | **9.7–12.4 мс** |

Цена процесса ≈0.6 МиБ commit и ~2 мс spawn. «Общий child» почти не растёт с N; «на плагин» — ×N
(≈0.62 МиБ и ≈2 мс на плагин). С 10 МБ документом разрыв больше: каждый процесс держит свою копию
(20.7 МиБ), если API отдаёт документ целиком — аргумент за range/delta-API (F22) независимо от модели.

### Изоляция отказа (ключевое)

| Сбой | Общий child | Child на плагин |
|---|---|---|
| `crash` одного плагина | `Disconnected`, выживших **0** — теряются **все** N | гибнет только свой child, выживают **2/3** |
| `spin` одного плагина | `Timeout`, весь child заблокирован, поздние плагины не стартуют | таймаут только у своего child, выживают **2/3** |

### Вывод для D16

«Жёсткая изоляция» (F18/F25) реализуется **только** моделью **«child на плагин»**. «Общий child»
превращает C в «один плохой плагин роняет/вешает все» — то же, что и B, но с RPC-ценой. Поэтому:
**выбор — «child на плагин»**. «Общий child» допустим лишь как явный режим с отказом от обещания
изоляции (экономия на десятках–сотнях плагинов); на масштабе лёгкого редактора выигрыш не оправдан.

## 4. Грабли реализации

1. **M10:** `std::process::Child::wait()` закрывает собственный `stdin`: после `wait()` поле
   `child.stdin` становится `None`, и попытка писать «в мёртвого child» через
   `child.stdin.as_mut().unwrap()` паникует. Под релизным `panic="abort"` это fail-fast
   `0xC0000409` без сообщения (GUI-процесс — ещё и без консоли, поэтому причина не видна;
   добавлен panic-hook в файл). Правильно — забрать `ChildStdin` заранее (`child.stdin.take()`)
   и писать через него; хэндл остаётся открыт после гибели child, поэтому ошибка приходит как
   `BrokenPipe`, а не `None`.
2. **M11:** порядок `child.wait()` и `job.terminate()`. Если сначала ждать `wait()`, а child жив
   (лимит не сработал / выключен), parent виснет навсегда — `terminate` до `wait` обязателен.
   Пойман на сценарии `--cpu-ms 0`.
3. **M11:** `JOB_OBJECT_LIMIT_PROCESS_TIME` не даёт точного срабатывания (см. §3.1). Проверено,
   что ОС хранит выставленное значение (`stored_limits`) и не игнорирует из-за вложенности.

## 11. Синхронизация (06.10.2026)

По итогам внешней проверки отчёта (воспроизведение M10–M12 + разбор) внесено в `FINDINGS.md`
и `tasks/TZ-proto-lua-host.md`:

1. **F32 (новое) — UI-freeze.** Зацикленный внутри host-вызова плагин блокирует host на `read`
   до срабатывания Job CPU-лимита, а он грубый (F29, секунды). Изоляция отказов это не ломает,
   но ограничивает UI. Обязателен **per-call wall-clock watchdog** (`TerminateJobObject`) и/или
   async host-вызовы. В §3.1 это упомянуто как «жёсткий бюджет CPU» — но это не опция, а
   условие UX.
2. **F22 пересмотрена для модели «child на плагин».** При полном документе каждый процесс держит
   копию (F30: 10 МБ → 20.7 МиБ ×N) → **range/delta-API обязателен по памяти**, а не «аккуратность».
3. **Гейт M11** в ТЗ уточнён: «память — детерминированно (F28); CPU/время — грубый ОС-backstop
   (F29)». В §4.1 ТЗ добавлен блок «Что P9 вскрыл дополнительно»; в §10 — решения по модели
   процессов и лимитам.

Существо P9 не меняется: транспорт подтверждён, Job Object принят, модель — «child на плагин»,
C остаётся приоритетным кандидатом.
