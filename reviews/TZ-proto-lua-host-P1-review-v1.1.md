## 1. Вердикт

Функционально P1 сделан, гейт на `hello.lua` проходит. **Вывод v1.0 о закрытии фазы
некорректен:** гейт проверялся только в debug-профиле, а релизная конфигурация workspace
(`panic = "abort"`) роняет процесс при ошибке из Rust-callback. Это прямо противоречит
§10.2 DESIGN_DOC («Lua-ошибка не роняет приложение») и §7 ТЗ («процесс жив»).

**Статус P1 — условно закрыт:** код готов, но до перехода к P3/P5 нужно зафиксировать
panic-стратегию (решение ниже, §3.4). В остальном v1.0 подтверждён.

## 3. Критическая находка: `panic = "abort"` роняет процесс на ошибке из Rust-callback

### 3.1 Симптом

В **release**-профиле (`[profile.release] panic = "abort"`, корневой `Cargo.toml`) любой
плагин, чья ошибка приходит из Rust-зарегистрированной функции, убивает процесс:

```
$ target/release/lua-proto.exe --plugin spin.lua        # while true do end + hook
thread 'main' panicked at core/src/panicking.rs:225:
panic in a function that cannot unwind
thread caused non-unwinding panic. aborting.        ← процесс мёртв (STATUS_ABORT)
```

### 3.2 Широта (важнее, чем в исходной находке владельца)

Аборт вызывает **не только hook**, а любая ошибка, поднятая из Rust-callback:

| Источник ошибки | release + `abort` | release + `unwind` |
|---|---|---|
| чистый Lua `error("boom")` | ловится, exit 1, процесс жив | ловится, exit 1 |
| ошибка из host-функции (`host.log("info")` без 2-го аргумента) | **abort** | ловится, exit 1 |
| ошибка из hook (`spin.lua`) | **abort** | ловится, exit 1 |

Это бьёт по H2/P5 напрямую: `apply_edit` без `document:write` должен вернуть
`permission_denied`, а по факту в релизе уронит приложение.

### 3.3 Механизм (первоисточник)

- `mlua` под `lua55` объявляет hook как `unsafe extern "C-unwind" fn hook_proc`
  (`mlua-0.12.2/src/state/raw.rs:466`), а при `Err` в callback вызывает
  `ffi::lua_error` (`raw.rs:174`).
- На MSVC `lua_error` разворачивает стек через SEH (`luaD_throw` → `RtlUnwindEx`).
  Когда ошибка рождается **внутри** Rust-фрейма (`hook_proc` или обёртка host-функции),
  разворачивание обязано пройти сквозь этот фрейм.
- Под `panic = "abort"` фрейм помечен как non-unwind, и разворачиватель упирается в
  `core::panicking::panic_cannot_unwind` → abort. `RUST_BACKTRACE=1` показывает
  `lua_error → luaG_errormsg → luaD_throw → RtlUnwindEx → panic_cannot_unwind`.
- Чистый Lua `error()` выбрасывается из C-кода VM, не пересекая Rust-фрейм, поэтому
  ловится даже под `abort` — отсюда ложное ощущение, что всё в порядке.

### 3.4 Исправление

| Вариант | Годится? | Комментарий |
|---|---|---|
| `[profile.release.package.lua-proto] panic = "unwind"` | **нет** | Cargo отвергает: “`panic` may not be specified in a `package` profile” |
| глобальный `[profile.release] panic = "unwind"` | да, но меняет продукт | влияет на релиз `mdedit` и его бюджет размера — решение владельца/ADR |
| **`[profile.proto] inherits = "release"; panic = "unwind"`** | **применено** | изолированно, не трогает релиз `mdedit`; проверено |

**Реализовано в этой правке** (корневой `Cargo.toml`):

```toml
[profile.proto]
inherits = "release"
panic = "unwind"
```

Замеры после правки:

```
target/release/lua-proto.exe  (abort)  = 438272 байт
target/proto/lua-proto.exe    (unwind) = 438272 байт   ← разница 0
```

Разницы нет: `catch_unwind` в mlua уже присутствует в бинарнике. `spin.lua` и `hosterr.lua`
под `--profile proto` дают `error` и exit 1, процесс жив.

Сборка для замеров P2/P3/P5 теперь: `cargo build --profile proto -p lua-proto`.

## 6. Уточнения к v1.0

### 6.1 `StdLib::BASE` не существует (v1.0 §4.3 — подтверждено по исходникам)

В mlua 0.12 флага `BASE` нет: есть `COROUTINE, TABLE, IO, OS, STRING, UTF8, BIT, MATH,
PACKAGE, BUFFER, VECTOR, INTEGER, JIT, FFI, DEBUG, NONE, ALL, ALL_SAFE`. Базовая библиотека
грузится всегда. Формулировку §6.1 DESIGN_DOC («`BASE` — да, с чисткой») стоит уточнить:
«base грузится неявно, чистка поверх».

### 6.2 Гейт P1 в ТЗ из корня падает (v1.0 §5.2 — усилено)

`cargo run -p lua-proto -- --plugin plugins/hello.lua` из **корня** не находит фикстуру:
Cargo не меняет CWD на каталог пакета. Гейт §4 P1 записан именно так. Варианты:
поправить формулировку в ТЗ (запуск из `crates/lua-proto`) **или** искать путь относительно
`env!("CARGO_MANIFEST_DIR")`. Решение — за владельцем.

### 6.3 Счётчик инструкций — баг, а не «неважно» (v1.0 §5.1 — усилено)

`limits::install_instruction_limit` держит один `AtomicUsize` на всё время жизни состояния.
В P3 это даст ложное срабатывание на втором вызове. Нужен сброс счётчика на каждый вызов.
Побочно: `INSTRUCTION_STEP = 10_000` при лимите 5 млн → до 500 срабатываний hook, точность
±10 тыс. инструкций (0.2%) — приемлемо, но оверхед M6 надо мерить.

### 6.4 `luajit-src` в дереве сборки

Это build-dependency `mlua-sys`, собирается всегда (все варианты Lua) и на бинарник не
влияет. Шум в логах, не проблема.

### 6.5 M7 проверен слабо

Изоляция глобалов проверялась на разных процессах. Корректная проверка M7 — два `Lua`
инстанса в одном процессе; остаётся на P3/P7.

## 7. Изменения в коде этой правки

- Корневой `Cargo.toml`: добавлен профиль `[profile.proto]` (`inherits = "release"`,
  `panic = "unwind"`). Релизный профиль `mdedit` не тронут.
- Код P1 (`main.rs`, `sandbox.rs`, `host.rs`, `limits.rs`, `plugins/hello.lua`) без изменений
  относительно v1.0.

---

## 8. Открытые решения

1. **Panic-стратегия продукта.** Оставить `mdedit` на `panic = "abort"` (тогда H2 обязан
   держать Lua в отдельном процессе/другом рантайме) или перевести на `unwind` (замерить
   размер `mdedit`). Это вход в ADR, не в прототип.
2. **Формулировка гейта.** Поправить ТЗ или реализовать поиск от `CARGO_MANIFEST_DIR`.
3. **Пробел: «Lua-ошибка не роняет приложение»** — §10.2 DESIGN_DOC требует правки
   независимо от выбора, т.к. под `abort` утверждение ложно.
