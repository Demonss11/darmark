## Вопрос 
Давай подумаем можем ли идти в историю: panic = "unwind" и Lua в том же процессе, но с важной оговоркой — использовать catch_unwind

## Вердикт

**Да, идти в историю можно — но это не бесплатный выбор, и он упирается не в панику, а в бюджет D6.**

Условия работоспособности (все проверены замером, не рассуждением):

1. профиль с `panic = "unwind"`;
2. `catch_unwind` вокруг **тела каждой** host-функции (иначе паника хоста = `exit 101` = смерть процесса);
3. `catch_unwind` вокруг внешнего вызова Lua — страховка на случай паники из hook или внутренностей mlua;
4. `LuaOptions::catch_rust_panics(false)` — дефолт, но его надо выставить **явно**, иначе плагин через `pcall` проглотит панику хоста и продолжит в неопределённом состоянии.

## Цена: +3.2 МБ на продукте

| Сборка | abort | unwind | Δ |
|---|---|---|---|
| `mdedit` (LTO, как в релизе) | 3 693 568 | **6 918 656** | **+3.22 МБ** |
| `mdedit` (без LTO — контроль) | 4 054 528 | 7 879 680 | +3.83 МБ |
| `lua-proto` | 438 272 | 438 272 | **0** |
| пустой exe | 114 176 | 114 176 | 0 |

Это **не** артефакт LTO (без LTO разрыв даже больше). Секции `mdedit`: `.text` 2.88→4.88 МБ, `.rdata` 0.70→1.73 МБ, `.pdata` 0.06→0.26 МБ.

Причина: под `abort` Rust вырезает весь landing-pad код и unwind-таблицы из **всей** графы зависимостей Tauri (tao, webview2-com, windows-rs — сотни крейтов). Под `unwind` всё это возвращается. `lua-proto` и пустой exe не раздуваются, потому что там нет такого объёма кода с drop-глю — эффект масштаба, а не свойство mlua.

**Следствие:** база 3.69 МБ → 6.92 МБ **до единого плагина**. D6 (≤ 6 МБ) нарушается сразу, а §14 «~4.2–4.6 МБ итого» становится недостижим. Для прототипа это неважно (`[profile.proto]` уже изолирован), для продукта — решающий фактор.

## Что подтвердилось и что уточнилось к v1.1

**Утечек нет.** 200 000 пойманных паник подряд: Lua-куча −0.039 Б/панику, Rust-куча −0.039 Б/панику (минус — шум и дефрагментация), после этого `ok_fn(21) = 42`, глобалы целы. Состояние не деградирует.

**Уточнение к v1.1 (существенное).** В отчёте покрыт только `Err`. Реальная Rust-*паника* — отдельный путь, и он опаснее:

| Место `catch_unwind` | Результат |
|---|---|
| нет | паника проходит насквозь → `exit 101`, процесс мёртв |
| вокруг внешнего вызова Lua | поймано, состояние живо — **но только если** паника не вырвалась из hook |
| **внутри тела host-функции** | паника → `Err(RuntimeError("host_panic_caught"))`; плагин видит `false, "runtime error: host_panic_caught"` через `pcall`. Процесс жив |

Вариант «внутри тела» — единственный, дающий плагину нормальный Lua-контракт. `catch_unwind` только снаружи оставляет дыру: паника из hook убьёт процесс мимо обработки.

**`catch_rust_panics` — новая находка.** Дефолт `true` позволяет плагину через `pcall(boom)` поглотить панику хоста (`ok=false`) и продолжить. При `false` паника всплывает до хоста через `resume_unwind` — плагин удержать её не может. Для песочницы нужен `false`, и это надо записать в ТЗ явно.

**`MemoryError` под abort работает** — проверено: `set_memory_limit(8 МБ)` → `Err(MemoryError("not enough memory"))`, процесс жив. Это ошибка из аллокатора внутри C, а не из Rust-фрейма, поэтому abort её не трогает.

## Третий путь, который меняет расклад

Под `abort` можно жить, если host-функции **никогда не возвращают `Err`**, а сигналят ошибку через Lua-значение. Проверил: `apply_edit` возвращает таблицу `{ok=false, code="permission_denied"}` — **процесс жив под abort**.

И это ровно то, что уже требует §8 DESIGN_DOC: «плагин без `document:write` получает `error { code = "permission_denied" }`, **а не исключение Lua**». То есть документ уже описывает паттерн, совместимый с `abort`.

**Блокер этого пути:** лимит инструкций. `Err` из hook под abort = аборт (воспроизведено). Свой C-hook тоже абортит — трансмутация `extern "C"` → `extern "C-unwind"` не помогла. Без лимита инструкций `while true do end` не убивает процесс, но **замораживает UI** — для редактора это неприемлемо.

Не проверял (нужен `cc`-крейт): hook, написанный на настоящем C вне Rust-фрейма. Это единственный способ вернуть лимит инструкций под abort, но он добавляет C-код в сборку — отдельная гипотеза, не факт.

## Развилка (вход в ADR)

| Вариант | Lua-ошибки | Лимит инструкций | Размер базы | Вердикт |
|---|---|---|---|---|
| **A.** `unwind` + `catch_unwind` в теле host-функций | работают, плагин видит `false, code` | есть | 6.9 МБ ❌ D6 | техника доказана, цена ломает бюджет |
| **B.** `abort` + Lua-значения вместо `Err` | работают | **нет** (hook абортит) | 3.7 МБ ✅ | требует C-hook или пересмотра §10.1 |
| **C.** `abort` + Lua в отдельном процессе | не касаются UI | есть | 3.7 МБ + процесс | panic-стратегия хоста неважна вообще |

Отдельный аргумент за `unwind`, не связанный с Lua: под `abort` **любая** паника в Rust-коде приложения — мгновенная смерть без шанса сохранить несохранённый текст. Под `unwind` панику можно поймать на границе команды Tauri и показать «внутренняя ошибка», не теряя документ. Для редактора это самостоятельная ценность.

## Дополнение (06.10.2026): результат C-hook-спайка

Гипотеза про нативный C-hook **проверена и подтверждена** — путь B становится реальным
кандидатом. Реализовано в прототипе (`crates/lua-proto/src/proto_hook.c`, `build.rs`, `cc`,
`limits.rs`, флаги `--c-hook`/`--hook-step`). Полная таблица — в `docs/proto/FINDINGS.md`.

### Ключевое

- **C-hook под `panic="abort"` работает:** `luaL_error` из чистого C-фрейма не пересекает
  Rust-фрейм, `spin.lua` прерван, `exit=1`, процесс жив. mlua-hook в тех же условиях абортит.
- **`pcall` закрыт RAII-гвардом.** «Голый» hook (и C, и mlua) проглатывается плагином через
  `pcall` (в т.ч. вложенный). Добавлена scoped safe-`pcall`/`xpcall` (C, поверх сохранённых
  оригиналов): лимит пробрасывается, обычные `pcall`/`xpcall` сохраняют семантику
  (`ok=false, err=…`). Установка/снятие — в том же `InstructionLimitGuard` (`Drop`).
- **RAII-гвард** снимает hook на любом выходе, сбрасывает счётчик на вызов (закрыт дефект
  накопления из v1.1 §5.1) и держит host вне оверхеда.

### Что этим НЕ закрыто

- **Host-функции с `Err` под `abort` по-прежнему абортят** (проверено). Это отдельная
  половина пути B: ошибки надо возвращать Lua-значением (как и требует §8 DESIGN_DOC).
- **Оверхед hook ~×2 и не зависит от шага** — посылка M6 «подобрать N так, чтобы ≤ +20%»
  не подтвердилась: `lvm.c:1192` вызывает `luaG_traceexec` каждую инструкцию, пока hook взведён.
  Нужно либо принять, либо пересмотреть механизм лимита (P3).
- Состояние C-модуля глобальное (одно `lua_State` на процесс) — для нескольких инстансов
  нужен per-state счётчик (P3/P5).

### Уточнение развилки

| Вариант | Лимит инструкций | Размер базы | Статус |
|---|---|---|---|
| A. `unwind` + `catch_unwind` | есть | 6.9 МБ | ломает D6 |
| B. `abort` + C-hook + safe-pcall + Lua-ошибки значениями | **есть** | ~3.7 МБ | **жизнеспособен**; остаётся host-`Err` |
| C. `abort` + Lua в отдельном процессе | есть | 3.7 МБ + процесс | тяжелее, но изоляция полная |

### Мелочи для API-референса 5.5

- В Lua 5.5 `LUA_REGISTRYINDEX = -(INT_MAX/2 + 1000)` = −1073742823 (не −1001000). Наш C-модуль
  сначала падал с `0xC0000005` из-за старого значения.
- `lua_insert`/`lua_remove`/`lua_pop`/`lua_pushcfunction` — макросы; реальные символы —
  `lua_rotate`/`lua_settop`/`lua_pushcclosure`.
