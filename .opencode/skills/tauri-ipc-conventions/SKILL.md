# Инварианты IPC и фронтенда darmark

Единый источник контрактов фронт↔Rust. Сегодня эти инварианты размазаны по `AGENTS.md`;
этот навык собирает их в месте, где живёт код. Дополняет `coding-discipline`, не
заменяя её: общая дисциплина изменений — там, контракты IPC/фронтенда — здесь.

## 1. Контракт фронт↔Rust

**Команды документов** (Tauri-шелл, `src-tauri`):

| Команда | Назначение |
|---------|------------|
| `new_document` | Создать новый документ |
| `open_document` | Открыть файл (путь выбирает пользователь в нативном диалоге на фронте) |
| `update_document` | Обновить текст на хосте |
| `render_document` | Запросить рендер (рендер и кэш — в сторе) |
| `save_document` | Сохранить на диск |
| `close_document` | Закрыть документ |

**CommandError { code, message }** — единственный тип ошибки команд. Фронт обязан
обрабатывать ошибки через эту пару, а не через исключения с произвольной формой.

**Рендер и кэш — в сторе (`state.rs`)**. `render_markdown` удалён: рендер идёт через
`render_document` + кэш стора, а не отдельной командой на каждый запрос. Не добавляй
новых команд рендера — используй существующий контракт.

**Зачем:** рендер Markdown — единственная ответственность Rust-ядра `md-core`; фронт
не парсит Markdown (см. §5). Любое расширение контракта — только через новый инвариант
здесь, а не через неявный сброс данных на фронте.

## 2. Брендированные id

Все DOM-id в приложении — брендированные (`ids.ts`, префикс §5.1 DESIGN_DOC).
Не используй случайные id.

**Зачем:** случайные id конфликтуют между панелями/плагинами и ломают E2E-селекторы;
брендированный префикс даёт предсказуемость и устойчивость тестов.

## 3. Защита от гонок

`docStore.ts` — проекция Rust-стора: текст/rev/path/dirty, дебаунс IPC, защита от гонок.

**Сверка rev:** ответы с устаревшим rev отбрасываются. Фронт не доверяет ответу,
если rev не совпал с запросившим состоянием.

**Зачем:** при дебаунсе и асинхронном IPC устаревший ответ перезаписал бы свежий контент
(гонка пользовательского ввода и ответа хоста). rev — дедупликатор и защита одновременно.

## 4. Дебаунс IPC

Не слать запросы на каждый кейстрок. Текст → дебаунс → пакетный `update_document`.

**зачем:** каждый запрос — IPC-круг и (при необходимости) рендер на хосте; дебаунс
превращает поток кейстрок в поток осмысленных изменений и снимает нагрузку со стора.

## 5. preview.innerHTML — единственная точка

`previewView.ts` — единственное место присваивания `preview.innerHTML`. Фронт не парсит
Markdown: он только присваивает готовый HTML от хоста.

**Состояние таблиц** — `WeakMap` по DOM-узлу (`tables.ts`): теряется при перерисовке.
Хост защищает флагом `RenderResult.changed`, но стабильного ключа на таблицу пока нет.

**зачем:** единая точка даёт один контракт «рендер → DOM» и один способ отладки;
WeakMap — осознанный компромисс (нет утечек, но состояние таблиц нужно пересоздавать).

## 6. Типы view/host

`viewRegistry.ts` — реестр тир-1/тир-2 + `ViewContext`:

- **HtmlView** — тир-1 (HTML-контент),
- **DomView** — тир-2 (DOM-контент),
- **ViewContext** — контекст view.

**Правила жизненного цикла:** у каждой панели `dispose`; подписки (например, на
`RenderResult`) закрываются при dispose. Не оставляй подписями после dispose — это
утечки и «воскрешённые» обновления мёртвой панели.

## 7. Строгий TS и CSP

**Строгий TS:** `strict`, `noUnusedLocals`, `noUnusedParameters`. Неиспользуемые
сущности ломают сборку (`tsc` валит `npm run build` на любой ошибке типов).

**Строгий CSP:** `default-src 'self'`. Никаких внешних скриптов/библиотек, никакого
`eval`. Inline-стили разрешены.

**Зачем:** TS-строгость — бесплатная статическая проверка без рантайм-цены; CSP держит
XSS-поверхность минимальной при доверии к рендеру от хоста.

## 8. Рендер на Rust-стороне

Рендер идёт на Rust-стороне (`md-core`, pulldown-cmark 0.13). Фронт только присваивает
`preview.innerHTML` (§5) — не парсит Markdown и не декоративно переписывает HTML.

**Зачем:** единый движок рендера (CLI/тесты/GUI дают идентичный результат), минимум
дублирующей логики и доверенный контур «Rust → санитайзер → DOM».
