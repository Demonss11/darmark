# Rust-тестирование

Цель — **быстро находить важные непокрытые места и закрывать их тестами**,
опираясь на конвенции конкретного Rust-проекта. Это не про погоню за процентом
покрытия: ценность дают тесты на рискованных участках (границы, ошибки,
парсинг, безопасность), а не на тривиальных ветках.

Инструкции самого репозитория (`AGENTS.md`/`CLAUDE.md`, манифесты) приоритетнее
этого навыка — если они расходятся, следуй репозиторию.

## 1. Сначала изучи репозиторий

Прежде чем писать тесты, выясни, как здесь принято их писать:

- **существующие тесты**: `#[cfg(test)] mod tests` в модулях, файлы `tests/`,
  примеры и doc-тесты. Придерживайся их стиля и структуры;
- **манифесты**: workspace и его члены, `[dev-dependencies]` (какие тестовые
  крейты уже доступны), включённые `features`, edition/toolchain;
- **инструкции и CI**: какие команды считаются проверкой, есть ли лимиты по
  размеру/зависимостям.

Не выдумывай новые тестовые крейты и структуру каталогов — используй то, что
уже есть.

## 2. Где искать пробелы

Приоритет — по риску и последствиям сбоя, а не по количеству кода:

- **Публичные функции и ветвления** — контракт, который видит вызывающая сторона.
- **Границы диапазонов** — off-by-one, пустые входы, максимумы/минимумы,
  срез по байтам против символов, границы буферов.
- **Обработка ошибок** — пути `Err`, `None`, некорректные/неполные данные,
  паника там, где ожидается `Result`.
- **Парсер и санитайзер** — разбор входа, экранирование/XSS, обход фильтров.
- **Регрессии** — ранее исправленные баги и код, ломающийся от рефакторинга.

Публичное поведение важнее приватных деталей. Выбирай **1–3 пробела** и
останавливайся; расширение scope — отдельный запрос.

## 3. Куда писать

- **Unit-тесты** — `#[cfg(test)] mod tests` в том же модуле. Видят приватные
  элементы, быстрые, компилируются вместе с модулем.
- **Integration-тесты** — `tests/*.rs`; используют только **публичный API**
  крейта, как внешний потребитель. Хороши для сквозных сценариев.
- **Doc-тесты** — примеры в `///`-комментариях; по необходимости, когда пример
  документации должен компилироваться и выполняться.

## 4. Команды

```bash
cargo test -p <crate>            # тесты конкретного крейта workspace
cargo test --workspace           # все тесты workspace
cargo test --no-run              # только скомпилировать тесты (быстрая проверка сборки)
cargo clippy --all-targets --all-features -- -D warnings   # линт, включая тест-таргеты
cargo fmt --check                # проверка форматирования
```

- Аргументы после `--` передаются тест-бинарнику, например
  `cargo test -p <crate> -- имя_теста` для запуска одного теста.
- Перед отчётом всегда **запусти** тесты и прочитай их вывод — рассуждение
  «по логике работает» доказательством не является.

## 5. Паттерны

- **Табличные/параметризованные тесты** — один цикл по наборам вход/ожидание
  вместо копипасты: дешевле добавлять новые случаи.
- **Граничные случаи** — пустой вход, один элемент, максимум, значения на
  границах диапазонов.
- **`#[should_panic(expected = "...")]`** — когда по контракту ожидается паника
  (в тестовой сборке; см. ограничения ниже).
- **Возврат `Result` из теста** — вместо `unwrap()` на каждом шаге:
  `fn t() -> Result<(), Box<dyn std::error::Error>>` и `?`.
- **Property-based** (`proptest`/`quickcheck`) — **только если такая
  dev-dependency уже есть** в проекте; не добавляй её без согласования.

## 6. Ограничения этого стека

- **Не добавляй зависимости** без явного согласования — следи за бюджетом
  размера и слоями проекта.
- **Релизный профиль `panic = "abort"`** — в релизе разворачивание стека
  недоступно; не строй тесты на `catch_unwind`/обработке паники как на
  production-механизме. Поведение на панике проверяй только в тестах.
- **clippy `-D warnings`** — тест-таргеты тоже должны проходить `clippy`
  (`--all-targets`); неиспользуемые импорты и переменные ломают CI.
- **Изоляция ядра**: если в проекте есть чистые библиотечные крейты без
  GUI/сетевых зависимостей, тестируй именно их изолированно — это быстро и
  детерминированно.

## 7. Scope-дисциплина и отчёт

- Выбери несколько **важных** пробелов и остановись; не гонись за покрытием.
- Отчёт — компактная таблица по каждому покрытому поведению:

  | Requirement | Evidence |
  | --- | --- |
  | Проверяемое поведение/сценарий | Имя теста; для запуска — команда и результат |

- Отдельно перечисли **найденные, но осознанно не покрытые** места с причиной,
  а также баги, вскрытые тестами (воспроизведение и расхождение).

## 8. Чего не делать

- **Не настраивать и не запускать coverage-инструменты** (tarpaulin, llvm-cov) —
  метрика покрытия не является целью.
- **Не менять production-код, чтобы «подогнать» тест**; тест вскрыл баг —
  сообщи о нём, а не глуши.
- **Не подменять запуск проверки рассуждением** — доказательство это вывод
  команды.

## Как это сочетается с другими навыками

- `test-driven-development` — как писать падающий тест **до** реализации; этот
  навык описывает механику тестов Rust, тот — порядок и смысл TDD.
- `verification-before-completion` — доказательство до заявления о готовности.
- `coding-discipline` — минимальный дифф и правки строго по месту.
- `code-testing-agent` — полный процесс выбора тестовых случаев.

Этот навык задаёт **механику Rust-тестов и поиск пробелов**, а не заменяет
перечисленные.
