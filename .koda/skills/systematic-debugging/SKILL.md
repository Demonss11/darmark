# Systematic Debugging

## Overview

**Core principle:** ALWAYS find root cause before attempting fixes. Symptom fixes are failure.

**Violating the letter of this process is violating the spirit of debugging.**

## The Iron Law

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

If you haven't completed Phase 1, you cannot propose fixes.

## When to Use

Для любой технической проблемы:
- падающие тесты (юнит, интеграционные, E2E) и сбои сборки;
- баги GUI: рассинхрон состояния, смещение подсветки, прокрутка, неверный вывод;
- ошибки ввода-вывода, лимиты, кодировки;
- сбои CSP/scope: стиль не применился, ресурс не резолвится, сработала XSS-защита.

**Особенно когда:**
- давит время и манит «быстрый фикс»;
- «очевидно, что не так» — до воспроизведения;
- уже пробовал несколько фиксов;
- предыдущий фикс не помог;
- баг воспроизводится нестабильно (плавающая синхронизация, границы кодировок, гонки).

**Не пропускай, когда:** баг кажется простым (у простых багов тоже есть root cause);
спешите (систематика быстрее перебора); нужно «прямо сейчас» (систематика — самый быстрый путь).

## The Four Phases

You MUST complete each phase before proceeding to the next.

### Phase 1: Root Cause Investigation

**BEFORE attempting ANY fix:**

1. **Read Error Messages Carefully**
   - тесты: имя теста, ожидаемое/фактическое, файл:строка;
   - компилятор: код ошибки — это контракт, а не «косметика»;
   - E2E: HTML-дамп страницы из отчёта + сам сценарий; в WebView без devtools дамп
     страницы и есть твой «консоль»;
   - читай стектрейс полностью, не пропускай warnings.

2. **Reproduce Consistently**
   - Точные шаги? Задокументируй: какой вход (размер, кодировка, содержимое), какое действие.
   - Плавающий баг (скролл, rAF, тайминги) → увеличь объём входа/число итераций, не угадывай.
   - Баг кодировок → минимальный пример: кириллица / эмодзи / CRLF по отдельности, затем вместе;
     сравни с ASCII-входом (там не проявляется?).
   - Не воспроизводится → собирай данные дальше, не предполагай.

3. **Check Recent Changes**
   - `git diff`, последние коммиты;
   - правки контракта между слоями (сигнатура функции ↔ обёртка ↔ вызывающий код);
   - правки постановки `tasks/TZ-*.md` (§3 «как в ТЗ» додумывать нельзя);
   - **пересобран ли артефакт**: E2E поверх собранного бинаря без пересборки после правок
     проверяют **старый код** — это не баг, а артефакт.

4. **Gather Evidence at Every Boundary**

   Если система состоит из нескольких компонентов — добавь инструментирование на **каждой**
   границе, а не только там, где заметил симптом. Иначе невозможно понять, какая граница ломает.

   ```
   Граница вызова:   аргументы и возврат (сними как есть)
   Граница слоя:     что передаётся внутрь, что вышло
   Граница вывода:   сними кусок результата рядом с подозрительным значением
   Граница потребления: как результат прочитан и применён
   ```

   Сравни с ожидаемым на каждой границе: где значение впервые расходится с ожиданием —
   там и корень.

5. **Trace Data Flow**

   Плохое значение — откуда родом? Тяни вверх по потоку данных до источника и чини у источника,
   а не у симптома. Типовые источники: функция-производитель значения, слой конвертации
   форматов, конфигурация (CSP/scope/лимиты).

### Phase 2: Pattern Analysis

1. **Find Working Examples** — похожий рабочий код в том же проекте. В чём разница обработки
   ввода/состояния/событий между рабочим и сломанным?
2. **Compare Against References** — если реализуешь по постановке, перечитай `tasks/TZ-*.md`
   **целиком** (особенно §3) и документацию библиотеки полностью, а не по диагонали.
3. **Identify Differences** — перечисли каждое отличие, каким бы мелким оно ни казалось.
   Не предполагай «это не может влиять»: для этого проекта «не может влиять» = CRLF в конце
   строки, BOM, trailing space, порядок атрибутов.
4. **Understand Dependencies** — обе стороны контракта согласованы? Конфигурация на месте?
   Артефакт пересобран? Заложена ли диагностика туда, где нет devtools?

### Phase 3: Hypothesis and Testing

1. **Form Single Hypothesis** — «Корень — X, потому что Y». Запиши. Конкретно, не расплывчато.
2. **Test Minimally** — наименьшее изменение для проверки гипотезы; одна переменная за раз.
   Фиксируй на одном слое: ядро / конвертация / GUI. Не меняй разные слои одновременно —
   иначе не понять, что сработало.
3. **Verify Before Continuing** — сработало → Phase 4. Не сработало → **новая** гипотеза,
   НЕ наслаивай фикс.
4. **When You Don't Know** — скажи «я не понимаю X». Не делай вид. Спроси или исследуй дальше.

### Phase 4: Implementation

1. **Create Failing Test Case** — падающий тест на конкретном значении, ДО фикса:
   ядро → юнит-тест; контракт кодировок → сценарий на Unicode-входе; GUI → feature-сценарий
   на пересобранном артефакте; шелл/IPC → тест команды.
   MUST have before fixing (red-green: сначала падающий тест, потом фикс).
2. **Implement Single Fix** — одно изменение за раз; никаких «заодно» улучшений и рефакторингов
   вперемешку. Правка контракта = синхронно обе стороны, но гипотеза по-прежнему одна.
3. **Verify Fix** — тесты затронутых слоёв зелёные; исходный симптом воспроизвести →
   он не проявляется; соседние сценарии не сломаны. Перед заявлением об успехе —
   скилл `verification-before-completion`.
4. **If Fix Doesn't Work** — STOP. Сосчитай, сколько фиксов попробовано.
   - < 3 → возвращайся в Phase 1 с новой информацией;
   - **≥ 3 → STOP, question architecture (шаг 5)**;
   - НЕ пытайся фикс №4 без обсуждения архитектуры.
5. **If 3+ Fixes Failed: Question Architecture**

   Паттерны архитектурной проблемы:
   - каждый фикс вскрывает ту же категорию ошибки в новом месте (например, конвертация
     единиц измерения между слоями) → возможно, её надо инкапсулировать в один модуль,
     а не латать по точкам;
   - каждый фикс порождает новую гонку между событием и тестом → возможно, нужен явный
     сигнал готовности вместо ожидания;
   - фиксы требуют «массивного рефакторинга» → вопрос, фундаментален ли сам паттерн.

   STOP и question fundamentals — обсуди с человеком **до** фикса №4.
   Это не неудачная гипотеза — это неправильная архитектура.

## Red Flags — STOP and Follow Process

- «Быстрый фикс сейчас, разберусь потом»
- «Просто поменяю X и посмотрю»
- «Заменю формат данных на другой и заработает» (не разобравшись, где ломается контракт)
- «Добавлю несколько правок, прогоню тесты» (разные слои разом)
- «Пропущу тест, проверю руками» (особенно для границ кодировок — руками не поймаешь)
- «Наверное дело в CSP, пофиксию»
- «Не понимаю до конца, но может сработать»
- «§3 ТЗ — сделаю как в ТЗ» без перечитывания раздела
- «E2E падают — увеличу timeout» (это маскирование, не фикс)
- Предложение решений до трассировки потока данных
- **«Ещё одна попытка фикса» (когда уже 2+)**
- **Каждый фикс вскрывает проблему в новом месте**

**Всё это значит: STOP. Возвращайся в Phase 1.**

## Signals You're Doing It Wrong

- «Это что, не происходит?» — ты предположил, не проверив (артефакт пересобран?)
- «Он покажет нам…?» — надо было добавить сбор доказательств на границах
- «Хватит гадать» — предлагаешь фиксы без понимания
- «Мы застряли?» (раздражение) — подход не работает

**When you see these:** STOP. Return to Phase 1.

## Common Rationalizations

| Excuse | Reality |
|--------|---------|
| «Баг простой, процесс не нужен» | У простых багов есть root cause. Процесс быстр для простых. |
| «Срочно, нет времени» | Систематика БЫСТРЕЕ гадания и перебора. |
| «Сначала попробую фикс, потом разберусь» | Первый фикс задаёт паттерн. Делай правильно с самого начала. |
| «Тест напишу после подтверждения» | Нетестированные фиксы не держатся. Тест сначала — и он же проверка. |
| «Несколько правок разом — экономия» | Не изолировать, что сработало. Порождает новые баги. |
| «Reference длинный, адаптирую» | Частичное понимание гарантирует баги. Читать целиком. |
| «Вижу проблему, сейчас пофикшу» | Видеть симптом ≠ понимать root cause. |
| «Ещё одна попытка» (после 2+ провалов) | 3+ провала = архитектурная проблема. Question pattern, не фиксь. |
| «E2E зелёные → всё ок» | На пересобранном ли артефакте? Иначе проверяли старый код. |

## Quick Reference

| Phase | Key Activities | Success Criteria |
|-------|---------------|------------------|
| **1. Root Cause** | Прочитать ошибки, воспроизвести (ASCII vs Unicode), `git diff`, инструментировать границы | Понять ЧТО и ПОЧЕМУ |
| **2. Pattern** | Найти рабочий пример, перечитать постановку/референс целиком, сравнить | Найти отличия |
| **3. Hypothesis** | Одна гипотеза, минимальная проверка на одном слое | Подтверждена или новая |
| **4. Implementation** | Падающий тест, один фикс, верификация | Баг решён, тесты зелёные |

## When Process Reveals "No Root Cause"

Если расследование показало, что сбой действительно средовой/тайминговый (плавающая
синхронизация, особенности рендера WebView):

1. Процесс завершён.
2. Задокументируй, что проверял (включая «артефакт пересобран», «воспроизводится ли на ASCII»).
3. Реализуй обработку: явный сигнал готовности вместо `setTimeout`, ожидание условия вместо
   фиксированного таймаута.
4. Добавь логирование для будущих расследований.

**But:** 95% «нет root cause» — это незавершённое расследование.
