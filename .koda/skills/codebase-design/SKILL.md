# Codebase Design

## Purpose

Методология проектирования модулей и разделения ответственности в кодовой базе.
Используется при разборе монолитных файлов, выделении чистых библиотек,
проектировании архитектуры новых фич и рефакторинге существующих слоёв.

## When to use

- Пользователь просит разобрать большой файл / модуль на части
- Требуется выделить чистую логику от UI/фреймворка
- Проектирование новой фичи с нуля (T-17 TZ-excel-tables)
- Рефакторинг с целью улучшения тестируемости
- Любая задача, где нужно "спроектировать модуль, а не писать код"

## Principles

### 1. Deep Module

Модуль должен быть "глубоким": маленький интерфейс, много функциональности внутри.
Проверка: публичные функции/типы ≤ 5 на модуль.
Если больше — разделить на подмодули.

### 2. Interface Is the Test Surface

Публичный API модуля = его контракт для тестов.
Если интерфейс невозможно протестировать без UI/фреймворка — модуль слишком поверхностный.

### 3. Layered Architecture

```
┌─────────────────────────────────────┐
│           UI / Presentation          │  (React, Tauri, CLI)
├─────────────────────────────────────┤
│         Application Logic            │  (IPC, orchestration)
├─────────────────────────────────────┤
│           Domain Core                │  (чистая логика, без зависимостей)
└─────────────────────────────────────┘
```

Каждый слой зависит только от нижележащих. Верхние слои "тонкие" — обёртки над ядром.

### 4. Separation of Concerns

Один модуль = одна ответственность. Не смешивать:
- парсинг данных и их отображение
- бизнес-логику и UI-состояние
- синхронную и асинхронную работу

## Instructions

### Шаг 1: Анализ текущего состояния

1. Определить текущий модуль/файл для разбора
2. Выписать все ответственности (что делает код)
3. Сгруппировать по семантике (парсинг, состояние, DOM, IPC…)

### Шаг 2: Проектирование границ

1. Для каждой группы ответственности определить модуль
2. Определить публичный интерфейс каждого модуля
3. Проверить: интерфейс тестобен без зависимостей верхнего слоя
4. Проверить: нет циклических зависимостей

### Шаг 3: Реализация слоёв

1. Сначала ядро (чистая логика)
2. Затем слой оркестрации (IPC, вызовы ядра)
3. В конце UI (отображение, пользовательские действия)

### Шаг 4: Проверка границ

- Rust: `cargo test -p <crate>` — ядро должно проходить без UI
- TypeScript: `tsc` — строгий типаж, `noUnusedLocals`, `noUnusedParameters`
- Каждый публичный API ядра покрыт unit-тестами

## Project Context (mdedit)

### Workspace структура

```
crates/
├── md-core/           # Ядро: markdown → HTML (pulldown-cmark)
│   └── src/lib.rs     #   to_html(), to_html_with(), DEFAULT_OPTIONS + тесты
└── app/               # Приложение: редактор + предпросмотр
    ├── src/main.ts    # Тулбар, debounce(120мс), renderSeq, lastRenderedHtml
    ├── src/tables.ts  # ~420 строк: парсинг, сортировка, фильтры, DOM
    ├── src/tauri.ts   # IPC: renderMarkdown, readFile, writeFile
    ├── src/style.css  # CSS-переменные, light/dark
    └── src-tauri/     # Tauri: read_file, write_file, render_markdown
        └── src/lib.rs #   ALLOWED_EXTS, invoke_handler
```

### Правила проекта

- `md-core` — **НИЧЕГО** не знает про Tauri/GUI, переиспользуется в CLI/TUI
- `src-tauri` — тонкая IPC-прослойка: `md_core::to_html()`, fs-операции, `ALLOWED_EXTS`
- `crates/app/src/*` — фронтенд, vanilla TS, строгий режим (`noUnusedLocals`, `noUnusedParameters`)
- `tables.ts` — WeakMap по DOM-узлу для состояния таблиц, экспорты: `enhanceTables()`, `attachMenuAutoClose()`
- `main.ts` — debounce 120мс, `renderSeq` для гонки запросов, `lastRenderedHtml`
- Зависимости: только с согласия пользователя
- CSP: `default-src 'self'; style-src 'self' 'unsafe-inline'`
- Команды сборки: `cargo test -p md-core`, `cd crates/app && npm run build` (tsc + vite build)

## Examples

### Разбор монолита

Файл `big-module.ts` (500 строк, 15 функций):
1. Выделить 3 группы ответственности
2. Создать 3 модуля с ≤5 публичных функций каждый
3. Оставить фасад-модуль для обратной совместимости
4. Протестировать каждый модуль отдельно

### Проектирование нового модуля

Новая фича "экспорт PDF":
1. Ядро: `pdf-core/` — конвертация HTML → структуры PDF (чистые функции)
2. Слой IPC: `src-tauri/` — вызов системного PDF-рендерера
3. UI: `src/export.ts` — кнопка экспорта, прогресс

### Проверка "глубины" модуля

```rust
// ✅ Глубокий модуль: 1 публичная функция, много логики внутри
pub fn to_html(markdown: &str) -> String { ... }

// ❌ Поверхностный модуль: 10 публичных функций, каждая 3 строки
pub fn a() { ... } // 3 строки
pub fn b() { ... } // 3 строки
// ...
```
