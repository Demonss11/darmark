# Codebase Design

Методология проектирования модулей и разделения ответственности. Применяется при разборе
монолитных файлов, выделении чистых библиотек, проектировании новых фич и рефакторинге слоёв.

## When to use

- Нужно разобрать большой файл / модуль на части.
- Требуется выделить чистую логику от UI/фреймворка.
- Проектирование новой фичи с нуля.
- Рефакторинг ради тестируемости.
- Любая задача «спроектировать модуль, а не писать код».

## Principles

### 1. Deep Module

Модуль «глубокий»: маленький интерфейс, много функциональности внутри.
Ориентир: ≤ 5 публичных функций/типов на модуль. Больше — дели на подмодули.

```rust
// Глубокий: 1 публичная функция, вся сложность внутри
pub fn to_html(markdown: &str) -> String { ... }

// Поверхностный: 10 публичных функций по 3 строки — интерфейс шире полезности
pub fn a() { ... }
pub fn b() { ... }
```

### 2. Interface Is the Test Surface

Публичный API модуля = его контракт для тестов. Если интерфейс нельзя протестировать
без UI/фреймворка — модуль спроектирован неправильно: чистая логика зашита в слой,
который её не принадлежит.

### 3. Layered Architecture

```
UI / Presentation        (обработчики, отображение)
Application Logic        (оркестрация, вызовы ядра, адаптация форматов)
Domain Core              (чистая логика, без зависимостей от окружения)
```

Каждый слой зависит только от нижележащих. Верхние слои тонкие — обёртки над ядром.
Циклических зависимостей нет; направление зависимостей фиксируется явно.

### 4. Separation of Concerns

Один модуль = одна ответственность. Не смешивать:
- парсинг данных и их отображение;
- бизнес-логику и состояние UI;
- синхронную и асинхронную работу в одном интерфейсе.

## Instructions

### Шаг 1: Анализ текущего состояния

1. Определи модуль/файл для разбора.
2. Выпиши все ответственности (что реально делает код).
3. Сгруппируй по семантике (парсинг, состояние, DOM, IPC…).

### Шаг 2: Проектирование границ

1. Для каждой группы ответственности — свой модуль.
2. Спроектируй публичный интерфейс каждого (≤ 5 сущностей).
3. Проверь: интерфейс тестируется без зависимостей верхнего слоя.
4. Проверь: нет циклов; направление зависимостей прежнее или улучшилось.

### Шаг 3: Реализация слоёв

1. Ядро (чистая логика) — первым, с тестами на публичный API.
2. Слой оркестрации — тонкие вызовы ядра.
3. UI — отображение и пользовательские действия.
При разборе существующего кода оставь фасад-модуль для обратной совместимости
и переводи потребителей поэтапно.

### Шаг 4: Проверка границ

Прогони проверки затронутых слоёв командами из `.kodarules` / `AGENTS.md`: ядро
тестируется без UI, типы компилируются, сборка проходит. Каждый публичный API ядра
покрыт юнит-тестами.

## Критерии переноса функции в ядро

Функция уходит в чистый модуль, если она:
- не трогает DOM/окружение (`document`, файловую систему, сеть);
- детерминирована по входным данным;
- не читает глобальное состояние.

Всё, что не проходит критерии, остаётся в слое-адаптере.

## Related Skills

- `verification-before-completion` — не заявлять о готовности модуля без свежих проверок.
- `systematic-debugging` — при отладке состояния и асинхронности разделённых модулей.
