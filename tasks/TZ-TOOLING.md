# TZ-TOOLING — расширение агентов и навыков OpenCode проекта

> **Статус:** к реализации.
> **Нормативный контекст:** `AGENTS.md` (границы, стек, конвенции), `docs/DESIGN_DOC.md`, `docs/adr/0021-plugin-isolation-process.md`, `docs/adr/0022-viewprovider-contract.md`, `.github/workflows/ci.yml`, `opencode.json`.
> **Методология:** навыки `skill-creator` (структура/описания навыков), `find-skills` (не изобретать готовое), `subagent-driven-development` (исполнение: план → свежий субагент на задачу → ревью → финальное сквозное ревью), при необходимости `code-testing-agent`.
> **Область:** `.opencode/agents/*`, `.opencode/skills/*`, правки `AGENTS.md`. Продуктовый код (`crates/`, `plugins/`) в рамках этого ТЗ **не меняется**.
> **Перед началом:** целиком прочитать `AGENTS.md`; для плагинных сущностей — `docs/DESIGN_DOC.md` §6–§12 и §14, ADR-0021, ADR-0022.

---

## 0. Цель и рамки

Расширить инструментарий OpenCode под реальные подсистемы darmark, **не дублируя** уже установленные глобальные скиллы. Цель — чтобы у типовых задач проекта (плагины, IPC/фронт, ядро Markdown, архитектурные решения, релиз) была подходящая роль с нужной дисциплиной и механикой.

**Делаем:** новых агентов и навыки из §3, правки `AGENTS.md` (разделы «Агенты проекта» и, при необходимости, «Команды»).

**Не делаем:**
- правки продуктового кода (`.rs`, `.ts`, `.lua`, конфиги сборки);
- дублирование того, что уже покрыто глобальными скиллами: планирование (`writing-plans`/`executing-plans`/`subagent-driven-development`), брейншторм, отладка (`systematic-debugging`), TDD, `verification-before-completion`, код-ревью (`review`/`caveman-review`), доки/AGENTS (`agents-md`), диаграммы (`design-doc-mermaid`), продукт/требования (`analyst`/`pm`);
- изменение схемы frontmatter существующих агентов (оставляем единый текущий стиль).

---

## 1. Инварианты инструментария (нельзя ломать)

1. **Агенты — без хардкода путей и имён файлов/крейтов проекта** в теле (структуру агент определяет сам). Исключение — `AGENTS.md`, где такие ссылки уместны.
2. **Навыки** (`.opencode/skills/<name>/SKILL.md`): frontmatter только `name` + `description` (русский, «настойчивый», отвечает «что + когда»).
3. **Единая схема frontmatter агентов** (как у `rust-developer`): `name, description(>)>, mode: subagent, model, temperature, permission` (ключ `permission` в единственном числе; без deprecated `tools`/`permissions`).
4. **Язык** — русский; в описаниях объясняем «зачем», а не «что».
5. **Ссылки** — только на существующие агенты/навыки. Никаких «висячих» имён.
6. **Без коммитов/пушей** без прямого запроса. Артефакты ревью — файлы, не git-диффы (`.opencode/` не отслеживается git).
7. **Не плодить сущности ради сущностей:** каждая новая роль/навык должна закрывать пробел, которого нет в глобальных скиллах (см. §0).

## 3. Область: новые сущности

### 3.1. Агенты

#### 3.1.1. `plugin-developer` (Lua-плагины) — Приоритет 1
- **Назначение:** писать и сопровождать плагины — `main.lua` + `plugin.json` — под песочницу darmark.
- **Делает:** использует предоставляемый API (`host.*`, `md.*`, `json.*`), объявляет permissions, укладывается в лимиты watchdog, следует каноническим формулировкам границы (`ISOLATION_NOTICE`/`DOCUMENT_ACCESS_NOTICE`).
- **Не делает:** не выходит за песочницу (нет сети/ФС напрямую), не тянет лишние зависимости, не правит `plugin-proto`/`plugin-host` (это Rust-задачи).
- **Опирается:** примеры `plugins/*`, `docs/DESIGN_DOC.md` §6–§12, ADR-0021; навык `plugin-sandbox`.
- **Связанные роли:** `rust-developer` (правки host/proto), `security-reviewer` (аудит плагина).

#### 3.1.2. `security-reviewer` — специализированный read-only
- **Назначение:** дополнять `code-reviewer` на security-чувствительных участках.
- **Фокус:** sandbox escape и обход permissions; согласие пользователя (consent); протокол host↔child (frame/envelope) на предмет подделок/переполнений; quarantine/watchdog (обход, дедлайн); XSS-санитайзер в ядре; строгий CSP и его обходы; обращение с внешними данными.
- **Не делает:** не заменяет общий код-ревью; не редактирует файлы.
- **Граница с `code-reviewer`:** общий ревью качества/логики — `code-reviewer`; угрозы модели, песочнице и границам доверия — `security-reviewer`.

#### 3.1.3. `architect` (ADR-keeper)
- **Назначение:** согласованность решений с `docs/DESIGN_DOC.md` и `docs/adr/*`.
- **Делает:** дизайн-ревью до кодинга; проверяет, что изменение не ломает замороженные контракты; предлагает/оформляет новый ADR по проектной конвенции.
- **Не делает:** не пишет продакшн-код.
- **Опирается:** `design-doc-mermaid`, `senior-system-analyst` (глобальные) — не дублировать, а делегировать.

#### 3.1.4. `release-engineer`
- **Назначение:** релизный процесс и бюджет размера.
- **Делает:** процедура `tauri build` (NSIS), контроль size-gate (release-exe ≤ 6 МБ, D6), проверка релизного профиля (LTO/strip/`panic=abort`), локальный прогон CI-шагов (`rustfmt`/`clippy`/`cargo test`/`npm run build`).
- **Не делает:** не меняет продуктовые контракты; не коммитит теги/релизы без запроса.

#### 3.1.5. `ui-designer`
- **Назначение:** придумывать визуальные направления и делать прототипы-референсы интерфейса, по которым затем пишется реальный UI.
- **Делает:** 2–3 варианта направления; самодостаточный HTML+CSS (+ минимум JS) в `ideas/` в стиле существующих `front_idea*.html` (CSS-токены, темы dark/light, `<html lang="ru">`); при необходимости обновляет бэклог `ideas/UI-IDEAS.md`; готовит хендофф (ТЗ/`DESIGN_DOC`).
- **Не делает:** не пишет продуктовый код (`crates/app/src`), не импортирует прототип в приложение; прототип — **выбрасываемый референс**, а не поставка.
- **Рамки (иначе референс бесполезен):** CSP-safe — без CDN/`eval`/фреймворков; десктопная эргономика Windows; где прототип ложится на реальное приложение/e2e — уважать замороженные контракты (`DESIGN_DOC` §13.2: DOM-id).
- **Опирается:** `ideas/*`, `docs/DESIGN_DOC.md` §5, глобальные `frontend-design`/`web-design-guidelines` (как ориентир, не дублировать); навык `ui-prototype`.
- **Связанные роли:** `frontend-developer` (реализация после согласования референса).

### 3.2. Навыки

#### 3.2.1. `plugin-sandbox` — Приоритет 1 (пара к `plugin-developer`)
- Схема `plugin.json` (id, `api_version`, contributes, permissions); условия валидации манифеста.
- Permissions и модель согласия пользователя; что доступно, что нет.
- Лимиты watchdog (прогресс + дедлайн), поведение при превышении, карантин N=3.
- Канонические формулировки границы изоляции (единый источник — не переписывать текст).
- Не дублирует `plugin-developer` (роль) — здесь механика/контракты.

#### 3.2.2. `tauri-ipc-conventions`
- Контракт фронт↔Rust: команды документов, `CommandError { code, message }`.
- Брендированные id; защита от гонок (сверка `rev`, отбрасывание устаревших ответов); дебаунс IPC.
- Единственная точка `preview.innerHTML`; тиры view/host (`HtmlView`/`DomView`, `ViewContext`); правила жизненного цикла (dispose/подписки).
- Собирает в один источник инварианты, сейчас размазанные по `AGENTS.md`; дополняет `coding-discipline`.

#### 3.2.3. `md-core-domain`
- pulldown-cmark 0.13, входы `to_html`/`to_html_with`/`to_html_mapped`.
- XSS-санитайзер (allowlist, `data-*`), YAML-шапка как «таблица таблиц».
- Mapping байты↔UTF-16; горячие пути рендера.
- Правило: ядро остаётся без GUI/Tauri-зависимостей.

#### 3.2.4. `release-checklist` (пара к `release-engineer`)
- Пошаговая релизная процедура; проверки бюджета размера; что гонять перед `tauri build`; артефакты (NSIS-путь).

#### 3.2.5. `ui-prototype` (пара к `ui-designer`)
- Механика прототипирования: где и как лежат прототипы (`ideas/front_ideaN.html`), структура CSS-токенов и тем, self-contained/CSP-safe, `lang="ru"`.
- Чек-лист «референс → ТЗ/`DESIGN_DOC` → реализация»; связь с `UI-IDEAS.md`/ADR; a11y-ориентиры (делегировать `web-design-guidelines`).
- Не описывает реализацию продукта (это `frontend-developer`).

## 4. С помощью чего делаем (инструменты и источники)

- **`skill-creator`** — проектирование навыков: «настойчивые» описания, прогрессивное раскрытие, черновик → оценка → доработка.
- **`find-skills`** — перед созданием каждого навыка проверить каталог (`npx skills find …`) и взять лучшее, **не копируя** и не устанавливая сомнительное.
- **`subagent-driven-development`** — исполнение: одна задача = свежий субагент-исполнитель + свежий ревьюер; фикс-цикл; финальное сквозное ревью. План — этот документ; леджер вести во временном файле (репозиторий не коммитим).
- **Существующие агенты:** `code-reviewer` — ревью; `rust-developer`/`frontend-developer` — если в ходе задачи правятся примеры/фикстуры (в рамках этого ТЗ продуктовый код не трогаем, но факты сверяем чтением).
- **Факт-ресёрч (чтение):** `crates/plugin-proto/src/*`, `crates/plugin-host`, `docs/DESIGN_DOC.md`, `docs/adr/0021`, `0022`, `.github/workflows/ci.yml`, `plugins/*/plugin.json`, `crates/app/src/tauri.ts`, `ids.ts`, `viewRegistry.ts`.
- **Делегировать, не дублировать:** `design-doc-mermaid`, `senior-system-analyst`, `systematic-debugging`, `verification-before-completion`, `test-driven-development`.

## 5. Критерии готовности (DoD)

1. Каждый агент/навык: валидный frontmatter по единой схеме (§1), русский язык, самодостаточность.
2. Нет дублей с глобальными скиллами и между новыми сущностями; ссылки только на существующее.
3. Агенты — без хардкода путей/имён файлов проекта.
4. `AGENTS.md` обновлён: новые агенты в «Агенты проекта» (и новые навыки — при наличии подходящего раздела), строго аддитивно.
5. Каждая задача прошла task-ревью (`code-reviewer`/`security-reviewer`), всё изменение — финальное сквозное ревью.
6. Навык `tooling-audit` (§10) прогоняется на итоговом `.opencode/` и не находит Critical-дефектов (Minor допустимы и перечислены в отчёте).

## 7. Проверка

- Каждая задача: ревью `code-reviewer` (для задач 1–2 — при участии `security-reviewer`) с вердиктами Spec и Quality.

## 8. Риски и открытые вопросы

- **Пересечение `security-reviewer` ↔ `code-reviewer`** — разграничить триггеры в обоих описаниях.
- **`code-testing-agent`** в описании ориентирован на .NET/MSTest — при ссылках из Rust-контекста оговаривать применимость или не ссылаться.
- **Legacy-поля схемы V2** (`temperature`/`permission`) — оставляем ради консистентности со всеми агентами (авто-трансляция).
- **Раздувание числа сущностей** — держать планку: добавляем только то, что реально не покрыто.
- **`architect`** может дублировать `senior-system-analyst` — решить на этапе задачи 5: тонкий специализированный агент или только навык ADR-конвенции.
- **`ui-designer`:** риск дрейфа прототипа от реальных ограничений (CSP/десктоп) — лечится жёсткими рамками в навыке `ui-prototype`; риск залезания в прод-код — граница с `frontend-developer` прописана явно; дублирование с `frontend-design` — использовать как ориентир, не копировать.

## 10. Аудит агентов и навыков

**Зачем.** Конфиги `.opencode/` дрейфуют при каждом добавлении сущности. За эту сессию вручную ловили: невалидную модель (`opencode/claude-sonnet-4.6`), несуществующие permission-ключи (`write`/`patch`), устаревшие `permissions:`/`tools:`, дубли блока «Профиль проекта», имя крейта проекта в `description`, пересечение ролей developer↔tester. Аудит делает эти проверки повторяемыми.

**Форма.** Навык `.opencode/skills/tooling-audit/SKILL.md` + bundled-скрипт `.opencode/skills/tooling-audit/scripts/audit.mjs` (Node). Отдельного агента **не** создаём — вызывается как навык (авто-срабатывание на «проверь агентов/навыки», «дрейф конфигов»). Вывод — advisory, не обязательный гейт.

**Механические проверки (скрипт, детерминированно; без сети и внешних зависимостей):**
- `frontmatter` агентов и `SKILL.md` валиден: блок `--- … ---`, минимальный разбор без внешнего YAML; набор ключей допустим; `permission` в единственном числе; нет `tools`/`permissions`.
- ключи `permission` входят в актуальный набор (`read`/`edit`/`glob`/`grep`/`list`/`bash`/`task`/`webfetch`/`websearch`/`lsp`/`skill`/`question`/`external_directory`/`todowrite`/`doom_loop`).
- `name` агента ↔ имя файла; `name` навыка ↔ имя каталога.
- «Висячие» ссылки: имена агентов/навыков, упомянутые в телах, против фактического списка `.opencode/` (+ пометка «глобальный навык» для известных встроенных).
- дубли абзацев между файлами (нормализованный хеш).
- отсутствие хардкода путей/имён крейтов проекта в телах агентов (эвристика по списку токенов из §2).

**Суждение (LLM по процедуре навыка):**
- качество описаний («что + когда», настойчивость);
- перекрытие ролей и границы (напр. developer↔tester, security-reviewer↔code-reviewer);
- дублирование с глобальными скиллами;
- ясность, «объясняет почему», русский язык, единообразие структуры;
- факт-точность относительно репозитория (команды, стек, ссылки).

**Выход.** Таблица «файл → проверка → OK / FAIL / ⚠️» + список находок с уровнями (Critical/Important/Minor). Скрипт печатает механическую часть; навык добавляет суждение и приоритеты.

**Ограничения и практика.**
- Аудит **не редактирует** файлы; исправления — отдельными задачами через `code-reviewer`.
- Проверка доступности `model` может требовать внешнего списка, которого нет у скрипта: если подтвердить нельзя — помечать `⚠️`, а не `FAIL`. Сужденческую сверку с доступными моделями делает LLM-часть.
- Сам навык/скрипт — тоже артефакт: держать в синхроне при изменении схемы агентов/навыков.
- Не превращать в блокирующий CI-гейт.

**DoD (задача 8).** Скрипт запускается на текущем `.opencode/` без падений и выдаёт осмысленный отчёт; навык авто-срабатывает на соответствующий запрос; артефакты прошли ревью; на момент сдачи Critical-находок нет.
