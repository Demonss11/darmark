# TASK-006 — Тиxое усечение документа в скиллах `{{doc}}` + неверная подсказка

> **Статус:** к исполнению (дефект, найден при анализе скилла «Переструктурировать»)
> **Дата создания:** 16.10.2026
> **Источник:** анализ `RESTRUCTURE_PROMPT` (сравнение скиллов ряда)
> **Независим от:** TASK-002/004/005 (правит фронт, не промты и не список скиллов)
> **Оценка:** ~30 строк фронта, ADR не требуется

---

## 1. Решение по кнопке «Переструктурировать»: ОСТАВИТЬ

`RESTRUCTURE_PROMPT` (`ai/skills/mod.rs:92-111`) — единственный **пишущий** скилл: план + переписанный
документ, применяется через «Применить как правку» (diff — `pluginCard.ts:223-231`).

| | Объяснить | Разбор разметки | Конспект | Переструктурировать |
|---|---|---|---|---|
| Вход | `{{doc}}` | `{{doc}}` | `{{doc}}` | `{{doc}}` |
| Выход | разбор | разбор по типам | сжатие | **новый документ** |
| Дублирует | — | секция «Разметка» | секция «О чём» | **ничего** |

Не дубль, замыкает цикл «спросил → применил», для длинных документов — самая частая задача.
Промт уходит только по нажатию, рантайм-стоимость нулевая. Удаление не обсуждается.

---

## 2. Дефект: тихое усечение документа = потеря данных

`skillBar.ts:28-34` — `truncateDoc` режет документ до `MAX_DOC_BYTES = 100 КБ`
(`constants.ts:3`). Единственное предупреждение — `state.log("warn", "system", …)`, то есть
**в лог-панель, не пользователю в чат**.

- Для `explain` / `explain-syntax` терпимо: разбор будет неполным, но ложных
  утверждений не появится. (`summarize` удалён как дубль — TASK-005; после TASK-004/005 боевых
  скиллов пять: `explain`, `create-plugin`, `restructure`, `explain-syntax`, `debug-plugin`.)
- Для `restructure` это **потеря данных**: модель физически не видела хвост документа, но
  промт требует «не выдумывай и не удаляй содержимое». Хвоста у неё нет — значит «Применить как
  правку» удалит его молча. Пользователь узнаёт по пропавшему тексту.

Второй, мелкий, дефект той же строки: `skillBar.ts:92` — захардкожено «для скилла «Создать
плагин» нужно описание в поле ввода». Этот текст показывается и для `debug-plugin` — он про
другое. (`add-view` удалён — TASK-004; после него `{{input}}`-скиллов ровно два:
`create-plugin`, `debug-plugin`.)

---

## 3. Решение

**Для пишущих скиллов не отправлять запрос вовсе и говорить об этом в чате.** Показывать усечение
в лог-панели недостаточно: пользователь её не смотрит, а цена ошибки — потерянный текст.
Набор пишущих скиллов задаётся списком, чтобы через полгода не искать по промту.

---

## 4. Шаги

### Шаг 1. `truncateDoc` возвращает признак усечения

`crates/app/src/panels/aiPanel/skillBar.ts:28-34` — вместо `string` вернуть
`{ text: string; truncated: boolean }`. Усечение считать по **байтам** (уже так) и запомнить
факт в возврате; само `state.log` оставить (для лог-панели).

### Шаг 2. Список пишущих скиллов

```ts
/** Скиллы, результат которых применяется к документу: при усечении документа запрос не отправляем —
 *  модель не видела хвост и «перепишет» документ без него (потеря текста). */
const DOCUMENT_MUTATING_SKILL_IDS: readonly string[] = ["restructure"];
```

Рядом с существующим `PLUGIN_SKILL_IDS` (`:14`). TASK-004/005 скиллы не добавляют, а удаляют
(`add-view`, `summarize`) — после них набор 7 → **5**, пишущий ровно один (`restructure`). Признак
«ответ применяется как правка» остаётся критерием, чтобы следующий пишущий скилл попал в список
по смыслу, а не по памяти.

### Шаг 3. Видимое предупреждение в чате

`chat.ts` — добавить `appendSystemNote(text: string)` по образцу `appendUser` (`:37-54`):
`div.msg.system` с `role="article"`, `aria-label="Предупреждение ассистента"`, текст через
`textContent`, затем `indicator.updateEmpty()`. **Не использовать `innerHTML`** (ADR-0038) —
правило применяется и к служебным узлам.

### Шаг 4. Поведение в `onSkillClick`

`skillBar.ts:78-100`:

- ветка `{{doc}}` (`:81-84`): получить `{ text, truncated }`; если `truncated` **и** скилл пишущий —
  не отправлять запрос, вместо этого `deps.appendSystemNote(...)` с текстом вида
  «Документ больше 100 КБ — «Переструктурировать» не запущен: ассистент перепишет только
  видимую часть и применение правки удалит остальное. Разбейте документ на части»
  и `dom.input.focus()`;
- если `truncated` и скилл **не** пишущий — отправлять как сейчас, но добавить в чат короткую
  заметку «Документ обрезан до 100 КБ — разбор неполный»;
- ветка `{{input}}` (`:85-97`): заменить захардкоженную строку на
  `` `AI: для скилла «${skill.title}» нужно описание в поле ввода` `` — сообщение станет верным
  для всех `{{input}}`-скиллов.

`ChatApi` (`chat.ts`) расширить на `appendSystemNote`; в `index.ts` пробросить зависимость в
`createSkillBar` (сейчас `deps` = `{ send }`).

---

## 5. Что НЕ делать

- Не увеличивать `MAX_DOC_BYTES`: лимит стоит из-за размера запроса, причина не в нём.
- Не помещать в промт «если текст обрезан — вставь маркер»: модель не может отличить
  «обрезано панелью» от «документа нет», маркер попадёт в документ при применении правки.
- Не переносить проверку в Rust: решение чисто фронтовое, лимит уже применяется во фронте.

## 6. Автоматическая приёмка: E2E-сценарий защиты от потери данных (конфликт C6)

Ручная приёмка (§7) регресс не ловит: удаление `DOCUMENT_MUTATING_SKILL_IDS` или перестановка
веток в `onSkillClick` пройдут `tsc`/`knip` молча. Сценарий ниже делает C6 («потеря текста при
усечении») проверяемым автоматически.

### 6.1. Где живёт

`crates/app/e2e/features/ai.feature`, новый сценарий **без** тега `@manual`: и усечение, и отказ
отправки офлайн-воспроизводимы. Ставится после сценария «Ряд скиллов AI…»; документ задаёт сам,
поэтому от порядка в файле не зависит.

### 6.2. Как получить документ > 100 КБ

**Рекомендуется генерация шагом** — без файла-фикстуры, детерминированно, `fixtures/` не тяжелеет:

```js
// crates/app/e2e/steps/ai.steps.js — рядом с шагами редактора.
Given("в редактор введён документ больше 100 КБ", async () => {
  // MAX_DOC_BYTES = 100*1024; усечение считает БАЙТЫ, а не символы (skillBar.ts:29).
  // Кириллическая строка даёт ~49 байт UTF-8 на повторение → 3000 повторов ≈ 143 КБ.
  await setMarkdown("Строка-проверка-усечения.\n".repeat(3000));
});
```

**Допустимая альтернатива** — фикстура `crates/app/e2e/fixtures/oversize-100k.md` и уже
существующий шаг `в редакторе документ из фикстуры "…"` (`steps/scrollsync.steps.js:106`).
Проще, но держит в репозитории ~140 КБ и менее наглядна по размеру; генерирующая версия
предпочтительнее.

### 6.3. Новые шаги (`crates/app/e2e/steps/ai.steps.js`)

- `When("я нажимаю скилл AI {string}")` — клик по `#ai-skills button.skill`, у которого
  `textContent` содержит название (тот же селектор, что у «боевого скилла», `:316-327`).
- `Then("в чате AI есть системное предупреждение {string}")` — среди `#ai-chat .msg.system` есть
  узел, чей `textContent` содержит фрагмент (класс задаёт `appendSystemNote`, шаг 3).
- `Then("в чате AI нет сообщения пользователя")` — `#ai-chat .msg.user` отсутствует. Это и есть
  «запрос не ушёл»: `send` дописывает пользовательское сообщение синхронно (`stream.ts:58`),
  до сети, поэтому проверка сразу после клика достаточна, без ручных таймаутов.

Обратный случай проверяет уже существующий `Then("в чате AI есть сообщение пользователя")`
(`:375-381`).

### 6.5. Границы покрытия (зафиксировать, а не закрывать костылём)

- **Бюджет сценария.** AGENTS.md: E2E > 5 с — повод для подозрения. Документ ~140 КБ проходит
  debounce-рендер и лишний рендер в `setMarkdown`; если сценарий устойчиво > 5 с, это сигнал к
  разбору, а не к снятию проверки (в частности — не добавлять второй большой документ).
- **Сетевой путь** мок-провайдера нужен лишь чтобы `send` дошёл до конца для непишущей ветки; сам
  ответ модели здесь не проверяется (он закрыт `@manual`-сценариями выше). Если мок недоступен,
  проверка «есть сообщение пользователя» остаётся валидной: `send` дописывает его до сети
  (`stream.ts:58`).
- **Достижимость усечения.** Воспроизводится без искривлений: ~140 КБ > `MAX_DOC_BYTES`, клик по
  скиллу — реальный путь `onSkillClick`. Ветка не недостижима — ограничений на автопрогон нет.
