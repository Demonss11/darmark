## 1. Целевая картина

MCP-сервер — **встроенная подсистема хоста** (как `DocumentStore` или `RenderCache`): сеть/логика
остаются в Rust (CSP `default-src 'self'`), сервер не выносится в отдельный процесс «на всякий
случай».

**Главное — не сам сервер, а результат:** у AI-агента появляется **чёткий, понятный перечень
команд и ресурсов** — что вызвать, что передать в вызов и какой результат ожидать. Контракт
формализован схемами и описаниями, доступен агенту для чтения (через реестр/`list`), а **каждый
вызов и его результат логируются в журнал** (`#logs-panel`), чтобы поток данных был наблюдаемым и
разбираемым.

Ключевой принцип: **MCP — это контракт и сужение поверхности, а не механизм принуждения.**
Валидация, права, `rev`-guard и безопасность путей остаются в существующих командах/песочнице
(та же развилка «объявляет — принуждает», что у манифеста плагина и хоста, ADR-0023/0027, §11.4).
MCP не создаёт второго источника правды для безопасности.

## 2. Рамка (что переопределено решением 12.10.2026)

- ADR-0034 §2.5 фиксировал MCP как **inbound** (внешние клиенты, auth/consent/аудит) и выводил
  его из MVP. Это решение **осознанно пересмотрено** — **ADR-0036** (in-memory, внутренний клиент).
- **Клиент — только внутренний** (встроенный AI darmark). **Внешних клиентов, inbound-auth и
  аудита внешних вызовов — нет.** Модель доверия простая: единственный клиент, доверенный, в
  процессе.
- Роли не смешиваются (ср. ADR-0034 §4.3): **MCP-сервер** — эта задача; **MCP-клиент** darmark к
  чужим MCP-серверам — **не входит**.

## 3. Scope

### 3.1. В scope

1. **Реальный MCP-сервер** (протокол по букве; `initialize`/`tools/list`/`tools/call`/
   `resources/list`/`resources/read`) — клиент внутренний.
2. **Первый срез — контракты плагинов, read-only** (§4). Мутаций нет.
3. **Контрактная ясность для агента** (§5, R1): реестр tools/resources со схемами и понятными
   описаниями; агент читает перечень и знает входы/выходы.
4. **Наблюдаемость в журнале** (§5, R2): логирование вызовов инструментов и результатов в
   `#logs-panel` под существующими правилами приватности.
5. **Внутренний tool-loop** у ассистента (сегодня его нет) — модель вызывает инструменты, а не
   только отдаёт текст.

### 3.2. Вне scope

| Задача | Обоснование |
|--------|-------------|
| **Внешние клиенты (inbound)** | Рамка 12.10.2026: клиент только внутренний; auth/consent/аудит внешних вызовов — отдельное решение при появлении кейса |
| **MCP-клиент darmark к чужим серверам** | Другое направление (outbound), не смешивать (§2) |
| **Мутации** (запись документа, install/init плагина) | Не в первом срезе; потребуют согласия/аудита — отдельный срез |
| **Discovery/адаптеры иных протоколов** | Вне scope |
| **Сайдкар MCP-сервера** | Состояние живёт в GUI-процессе; вынос — только по триггерам ADR-0034 §2.6 |
| **Сетевые вызовы из TS** | CSP `default-src 'self'`; всё — на Rust-стороне |

## 5. Требования

- **R1. Контракт для агента.** Реестр tools/resources со **схемами** (вход/выход) и **понятными
  описаниями**; перечень доступен агенту для чтения. Имена, параметры и формат результата —
  детерминированные. Критерий «понятно агенту»: по описанию и схеме однозначно ясно, что вызвать,
  что передать и что получить.
- **R2. Наблюдаемость.** Каждый вызов инструмента и его результат логируются в журнал
  (`#logs-panel`). **Поля записи:** инструмент, имя каталога/файла (последний компонент),
  длительность, итог/ошибка. **Приватность:** без секретов; полный `path` **исключается** из
  результата (в отчёте `plugin-cli` `path` → только имя, §4.6); содержимое документа не логируется.
- **R3. Принуждение вне MCP.** MCP — только маршрутизация (без бизнес-логики и своих проверок).
  Проверки выполняют команды: permissions, `rev`-guard, **безопасность путей**. `path` для
  `plugin_validate`/`plugin_test` разрешён **только** внутри `%APPDATA%/darmark/plugins/` и
  **системного временного каталога** (рабочая область валидации). Широта temp принимается
  осознанно: плагины валидируются из временных рабочих каталогов, поэтому сужение до префикса
  `darmark-ai-validate-*` сломало бы валидацию. Проверка — `canonicalize` + `starts_with` + отказ
  при reparse point (symlink/junction) — **в команде-обёртке `plugin_harness`, не в MCP**. `plugin_test` идёт
  **только через `plugin-cli`** (не напрямую `plugin-host`) — сохраняется «`mlua` вне GUI» (ADR-0021).
- **R4. Тонкие адаптеры.** Tool = обёртка над существующей командой/CLI; **никакой бизнес-логики в
  MCP**.
- **R5. Реальный протокол.** MCP-протокол реализуется по букве; **транспорт/размещение — in-memory,
  в процессе GUI (по ADR-0036)**.
- **R6. Tool-loop.** Встроенный ассистент вызывает инструменты в цикле. **Зависимость:** поддержка
  tool-calling (tools/function-calling) провайдером; при отсутствии — локальный разбор вызова
  отдельным дизайном.
- **R7. Изоляция tool-result от инструкций.** Результаты инструментов (манифест, лог `plugin_test`,
  рендер) попадают в контекст LLM — это **данные, не инструкции**; промт ассистента это размечает, а
  поля манифеста (`name`/`description`/…) подаются как потенциально враждебный текст (prompt-injection).

## 6. Критерии готовности

### 6.1. Функциональные

| # | Критерий | Проверка |
|---|----------|----------|
| AC-MCP-1 | MCP-сервер отвечает на `initialize`/`tools/list`/`tools/call`/`resources/list`/`resources/read` | Rust-тест протокола |
| AC-MCP-2 | Первый срез реализован: 6 resources + 4 tools (§4), все read-only | Rust-тест реестра/адаптеров |
| AC-MCP-3 | Агент по перечню понимает вход/выход: у каждого tool/resources есть описание и схема | Контракт-тест (схемы непусты и валидны) |
| AC-MCP-4 | Каждый вызов и результат логируются в журнал; формат наблюдаем | Тест/E2E: запись в журнале |
| AC-MCP-5 | Tool-loop: ассистент вызывает `plugin_validate`/`plugin_test` по своей инициативе | E2E: сценарий генерации плагина |
| AC-MCP-6 | Адаптеры не дублируют логику: результат совпадает с `plugin-cli`/`md-core` напрямую | Контракт-тест |

### 6.2. Инварианты и ограничения

| # | Критерий |
|---|----------|
| AC-MCP-7 | CSP не нарушен: всё на Rust-стороне; из TS — только IPC |
| AC-MCP-8 | Приватность журнала: без секретов и содержимого документа; пути — только имена (§4.6) |
| AC-MCP-9 | Принуждение не в MCP: права/`rev`-guard/пути проверяются существующими командами |
| AC-MCP-10 | Размер release-exe ≤6 МБ (D6); `npm run build` (tsc strict) и `cargo test -p darmark` зелёные |
| AC-MCP-11 | Инварианты ADR-0027: контракты §13.2 сохранены (аддитивность); `HOST_API_VERSION` не поднимается; `mlua` вне GUI |
| AC-MCP-12 | `plugin_validate`/`plugin_test` с путём вне белого списка, path traversal (`..`, абсолютный), symlink → ошибка (проверка в `plugin_harness`) |
| AC-MCP-13 | Журнал не содержит полных путей, секретов и содержимого документа (R2/§4.6) |
| AC-MCP-14 | Результаты инструментов размечаются как «данные, не инструкции» (R7) |

## 7. Риски

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Построить «сервер ради сервера» | Среднее | Главная цель — контракт для агента и наблюдаемость (§1), а не сам факт сервера; первый срез минимален |
| MCP сломает приватность журнала | Высокое | R2/AC-MCP-8: логирование по правилам §4.6, без секретов и содержимого |
| `plugin_test(path)` — ФС-поверхность | Высокое | R3/AC-MCP-12: белый список директорий, `canonicalize`+`starts_with`, отказ на reparse point; проверка в команде, не в MCP |
| Prompt-injection через tool-result | Среднее | R7/AC-MCP-14: «данные, не инструкции»; поля манифеста — как враждебные; в журнал — без содержимого |
| Утечка полного пути в журнал из отчёта CLI | Среднее | R2/AC-MCP-13: `path` → имя (последний компонент) перед записью в журнал |
| Провайдер не умеет tool-calling | Среднее | R6: локальный разбор вызова как отдельный дизайн |
| Раздувание AI-клиента транспортом | Среднее | Транспорт — по ADR-0036; контроль size-gate (AC-MCP-10) |
| «Соблазн втянуть внешних клиентов» | Среднее | Рамка §2: клиент только внутренний; inbound — отдельное решение |
| Дрейф схем MCP и реальных сигнатур | Среднее | AC-MCP-6: контракт-тест «схема == сигнатура» |
