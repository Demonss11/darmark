## 1. Целевая картина

Мониторинг ресурсов — **best-effort наблюдаемость** нагрузки на приложение и плагины прямо в
шапке панели «Журнал». Пользователь и разработчик плагинов видят, сколько ОЗУ (и, опционально,
CPU) потребляет главный процесс и каждый активный child `darmark-plugin-host.exe`, ловят утечки
и «болтливые»/зависшие плагины, не прибегая к внешним инструментам (Диспетчер задач, Process
Explorer).

**Гипотеза:** постоянное, малозатратное отображение рабочего набора процесса ловит утечку или
деградацию плагина в момент, когда она возникает, а не «по факту краша».

### Проблема

1. **Непрозрачность нагрузки.** Плагинная система использует модель «child на плагин» (ADR-0021,
   FINDINGS F30/F31). Ресурсы детей не видны в UI: утечка памяти одного плагина конкурирует с
   главным процессом, но обнаруживается только после замедления/падения редактора.
2. **Нет раннего сигнала.** Плагин, выходящий за бюджет Job Object (64 МБ), будет снят ОС, но
   пользователь узнаёт об этом по факту; тенденция к росту ОЗУ не видна.
3. **Диагностика требует внешних инструментов.** Чтобы понять, «кто ест память», нужно открыть
   сторонний монитор и сопоставить PID'ы — вручную и в реальном времени.

### Целевая аудитория

| Персона | Болевая точка |
|---------|---------------|
| **Разработчик плагинов** (основной) | Ловит утечку/лишний RSS в своём child'е по ходу отладки |
| **Продвинутый пользователь** | Хочет прозрачности: сколько памяти занимает редактор и его плагины |
| **Бета-тестировщик** | Сообщает о деградации с наблюдаемым числом, а не «тормозит» |

### Текущее состояние (после S11)

- Панель-консоль «Журнал» реализована (ADR-0029): сворачивающаяся панель над `#statusbar`,
  шапка `#logs-panel .logs-head`.
- Слот `#logs-resources` (`index.html:266`) **зарезервирован и пуст**: `role="note"`,
  `aria-label="Потребление памяти"`, стили `.logs-resources` — моно, `--fg-mute`,
  `tabular-nums`, `white-space: nowrap` (`style.css:1208`).
- В нижнем доке (ADR-0030) `#logs-resources` — **logs-режимный** слот: видим в режиме
  «Журнал», скрыт в режиме «AI-ассистент».
- Данных нет: ни сбора метрик на Rust-стороне, ни события, ни рендера в TS.

### Принципы (совместимость с архитектурой)

- **Best-effort:** потеря семпла метрик не критична (не журнал аудита); следующий тик через 2 с.
- **Рендер только `textContent`** (CSP/XSS), **без `innerHTML`** в строке ресурсов.
- **Источник данных — Rust-хост.** Фронт не читает ФС/процессы и не парсит `/proc` (на Windows его нет).
- **D6 (≤6 МБ):** межпроцессная статистика только через уже присутствующий `windows`-crate;
  тяжёлых зависимостей (`sysinfo` и т.п.) не добавляем без ADR.
- **Windows-only.** Как и вся плагинная подсистема (`plugins` включается под `#[cfg(windows)]`);
  на прочих платформах строка остаётся пустой.
- **Без авто-kill.** Мониторинг только наблюдает и подсвечивает; снятие child'а по бюджету —
  зона Job Object и watchdog (`DESIGN_DOC §10`), не этой задачи (§6.6).

## 2. Scope

### В scope

1. **Сбор метрик на Rust-стороне** (Windows-only): ОЗУ (working set) главного процесса и каждого
   активного child'а; CPU % (опционально по итогам спайка); число хендлов (только при превышении
   порога); время семпла.
2. **Поток событий `resource-metrics`** (текущий снимок) и `plugin-process-exited`
   (child завершился — для состояния `orphan`).
3. **Таймер опроса 2 с** в отдельном потоке Rust-хоста, не блокирующий UI/event-loop.
4. **Рендер строки `#logs-resources`** (`resourceMonitor.ts`): главный процесс + дети, числа +
   компактный прогресс-бар у плагинов (без спарклайна).
5. **Пороги и реакция:** янтарная/красная подсветка (`.warn`/`.crit`) + запись уровня
   `warn`/`error` в журнал (через существующий механизм `log-entry`). **Без авто-kill.**
6. **Состояние `orphan`:** завершённый child помечается «завершён» (opacity 0.5) и удаляется
   через 5 с, если плагин не перезапустился; запись в журнал о завершении процесса.
7. **Доступность:** `aria-label`/`role` для строки, скрытие декоративной графики от скринридеров.
8. **Учёт бюджета:** подтверждение размера release-exe в CI (size-gate ≤6 МБ, §14).

### Вне scope (отдельные задачи)

| Задача | Обоснование |
|--------|-------------|
| **Авто-kill по порогу** | Отдельный ADR: реакция «убить плагин» опасна и конфликтует с Job Object/watchdog. Здесь только подсветка + журнал. |
| **Панель «Производительность» со спарклайном/графиками (H3+)** | Графики истории — отдельная панель; в этой задаче строка + число + прогресс-бар. |
| **Мониторинг внуков/прочих процессов** | Не связаны с Job Object; см. §6.3. |
| **Настройки порога/частоты пользователем** | Отдельная задача настроек приложения; здесь фиксированные пороги (§6.5). |
| **Кроссплатформенность (Linux/macOS)** | Продукт — Windows (D15); на прочих платформах строка пуста. Альтернативный источник (`sysinfo`) — кандидат спайка, не гарантия. |
| **Персистентность метрик (история на диск)** | Best-effort снимок; история — часть панели «Производительность». |
| **Мониторинг диска/сети/handles главного процесса постоянно** | Расширение набора метрик после спайка (§4.2). |

### Предусловия (жёсткие, порядок обязателен)

> Порядок принятия решений проекта — `DESIGN_DOC §0`: **проверочный стенд (спайк) → ADR →
> реализация** (D11, ADR-18). Эта задача **не начинается** с кода.

1. **Спайк** — ✅ **выполнено** (`docs/proto/FINDINGS.md` §9, **F49–F54** + независимая проверка):
   WinAPI (`K32GetProcessMemoryInfo`/`GetProcessTimes`) ≥×100 дешевле `sysinfo`; CPU опроса 2 с
   в пределах AC-17; `windows` уже в дереве `darmark` (цена по размеру ≈0). Оговорка: WebView2/
   event-loop напрямую не тестировался — **AC-19 проверяется вручную в GUI при реализации**.
2. **ADR-0031** — ✅ **принят** (`docs/adr/0031-resource-monitoring-source.md`): источник данных и
   границы мониторинга (только главный + child'ы Job Object; без авто-kill; Windows-only; частота 2 с).
3. **Реализация** — после принятия ADR (Фазы 2+).

Зафиксированные решения (§6.2) взяты из уже согласованного видения IDEA-012 и не
пересматриваются; спайк уточняет **стоимость и технику**, а не продуктовые границы.

## 3. Пользовательские сценарии

### Сценарий 1: Прозрачность нагрузки (норма)

> **Как** пользователь, **я хочу** в шапке журнала видеть, сколько ОЗУ занимает редактор и каждый
> плагин, **чтобы** понимать профиль потребления.

**Приёмка:** Given запущены 2 плагина; When открыта панель «Журнал»; Then в `#logs-resources`
ровно одна строка главного процесса и по одной строке на каждый активный плагин; значения
обновляются каждые ~2 с без заметного усилия CPU.

### Сценарий 2: Ранний сигнал утечки/перегруза плагина

> **Как** разработчик плагина, **я хочу** видеть, что RSS моего child'а растёт или перевалил
> порог, **чтобы** поймать утечку до краша.

**Приёмка:** Given RSS плагина `word-count` превысил 500 МБ (предупреждение); When прошёл
очередной тик; Then строка плагина получает класс `.warn` (янтарная), прогресс-бар окрашивается,
в журнал добавлена запись уровня `warn`. Given RSS > 1 ГБ (критический); Then строка `.crit`
(красная) и запись `error`.

### Сценарий 3: Завершение/краш child'а

> **Как** пользователь, **я хочу**, чтобы строка исчезла корректно, а не «зависла» с устаревшим
> числом, **чтобы** не принимать мёртвый процесс за живой.

**Приёмка:** Given child плагина `export-html` завершился (краш/kill); When хост обнаружил
завершение; Then строка помечена состоянием `orphan` (`opacity 0.5`, пометка «завершён»), через
5 с удаляется (если плагин не перезапущен); в журнал добавлена запись
`[плагин] Плагин export-html: процесс завершён (PID N)`; метрики остальных плагинов не затронуты.

### Сценарий 4: Узкое окно

> **Как** пользователь на небольшом экране, **я хочу**, чтобы строка ресурсов не ломала шапку.

**Приёмка:** Given ширина панели уменьшена так, что строка не помещается в шапку; Then строка
переносится на отдельную строку (не обрезается и не вытесняет фильтр/кнопку очистки).

### Сценарий 5: Свернутая панель

> **Как** пользователь, **я хочу**, чтобы строка не мешала при свёрнутой панели-консоли.

**Приёмка:** Given панель свёрнута до полосы-шапки (28px); Then строка ресурсов остаётся
видимой и обновляется (шапка видна); при скрытой панели рендер не выполняется.

## 4. Архитектурные решения

### 4.1. Слои и размещение кода

```
┌─────────────────────────────────────────────────────────────┐
│ TS-оболочка (WebView)                                       │
│  resourceMonitor.ts — подписка на resource-metrics /        │
│  plugin-process-exited, рендер #logs-resources              │
│  logPanel.ts — слот #logs-resources в шапке (уже есть)      │
│  ❌ Нет доступа к процессам/ФС                              │
├─────────────────────────────────────────────────────────────┤
│ IPC-граница (Tauri events, только host→front)               │
│  resource-metrics{…}, plugin-process-exited{…}              │
├─────────────────────────────────────────────────────────────┤
│ Rust-хост (src-tauri/src/plugins/resource.rs)               │
│  ResourceMonitor — поток опроса 2 c → снимок метрик         │
│  WinAPI-провайдер (windows-crate): K32GetProcessMemoryInfo, │
│  GetProcessTimes / GetProcessHandleCount                    │
│  источник PID — PluginManager (active runtime → PID)        │
├─────────────────────────────────────────────────────────────┤
│ ОС (Windows)                                                │
│  главный процесс darmark.exe + child'ы darmark-plugin-host  │
└─────────────────────────────────────────────────────────────┘
```

**Размещение:**

- **Новый Rust-модуль** `crates/app/src-tauri/src/plugins/resource.rs` (Windows-only, как
  остальные `plugins/*`): тип снимка, WinAPI-провайдер, `ResourceMonitor` (поток + таймер).
- **Эмиттеры** — по образцу `services.rs`/`lib.rs`: канал `ResourceSink` (аналог `LogSink`,
  `DocumentSink`), подключаемый в `setup_plugins`; сам модуль не знает про Tauri.
- **Чтение PID:** `supervisor.rs` получает метод `pid()`, `PluginRuntime` — метод `pid()`
  (возвращает PID активного child'а), `PluginManager` — итератор активных плагинов с PID
  (`active_pids()`); монитор опрашивает хост через `PluginHost`.
- **Новый TS-модуль** `crates/app/src/resourceMonitor.ts`: держит последний снимок, состояния
  `orphan`, рендер строк, прогресс-бары, пороги подсветки. Добавляется в `DESIGN_DOC §5.5`.
- **Интеграция:** `main.ts` создаёт `resourceMonitor` и передаёт в `createShell`/`createLogPanel`;
  `logPanel.ts` (или `main.ts`) отдаёт `#logs-resources` dest'у монитора; `index.html` — только
  добавление контейнера `#mon-children` (см. §6.3), слот `#logs-resources` уже есть.
- **Стили** — `style.css`, в блоке `.logs-resources` (строки, прогресс-бар, `.warn`/`.crit`,
  `orphan`, перенос при узком окне).

### 4.2. Источник данных

**Решение: WinAPI через `windows`-crate (Windows-only).**

| Вариант | Плюсы | Минусы | Вердикт |
|---------|-------|--------|---------|
| **WinAPI (`windows`-crate)** | Крейт **уже в зависимостях** (`windows 0.62.2`, `windows-core 0.62`); точный working set главного процесса и child'ов; нет новых зависимостей → бюджет D6 не растёт | Windows-only; FFI-детали (`unsafe`) | **принято** (уточнение стоимости — спайк) |
| **`sysinfo`** | Кроссплатформенно; проще API | Новая зависимость (+сотни КБ к базе) — риск D6; даёт RSS, не обязательно working set | **отклонено как база**; кандидат спайка (§8) |

Провайдер для каждого процесса (главный `std::process::id()` и PID детей):

- **ОЗУ:** `K32GetProcessMemoryInfo` + `PROCESS_MEMORY_COUNTERS(_EX)` → `WorkingSetSize`
  (рабочий набор; «ОЗУ» в UI). `PeakWorkingSetSize` — опционально в detail.
- **CPU %:** `GetProcessTimes` (kernel+user `FILETIME`) на каждом тике; процент =
  `Δ(CPU) / (2 c вала) × 100`, с поправкой на число логических ядер (уточняется спайком, §8).
- **Хендлы:** `GetProcessHandleCount` (и/или `GetGuiResources` — GDI/USER); отображаются **только
  при превышении порога** (§6.5).
- **Ошибки доступа:** `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) —` при отказе метрика
  пропускается (процесс мог завершиться между тиками); `Opened`-handle закрывается сразу.

**Открытые параметры техники** (спайк): точный набор метрик (ОЗУ обязательно; CPU/хендлы —
опционально), «working set ± private bytes» в тултипе, стоимость вызова на процесс и в сумме.

### 4.3. Источник списка процессов

**Решение: только главный процесс + child'ы Job Object (плагинные `darmark-plugin-host.exe`).**

- Список PID берётся из `PluginManager` — только **активные** плагины (`PluginStatus::Active`),
  у которых есть живой `Supervisor` с PID. Это соответствует модели «child на плагин»
  (FINDINGS F30/F31) и семантике Job Object (`DESIGN_DOC §10`).
- **Не мониторим:** внуков плагина, процессы `darmark-plugin.exe` (CLI), процессы вне Job Object.
  Обоснование: они не связаны с runtime-инвариантами изоляции; учёт «всех подпроцессов» размывает
  ответственность и усложняет привязку к `plugin_id`.
- Плагины в `failed`/`quarantined`/`stopped` не имеют живого child'а → строки нет (только запись
  в журнал о завершении, §6.6).

### 4.4. Поток событий

Двунаправленного канала нет: **только host → front** (push, Tauri `emit`), аналог `log-entry`.

| Событие | Payload | Когда |
|---------|---------|-------|
| `resource-metrics` | см. §4.5 | Каждый тик (2 с), если есть что показать (главный процесс — всегда) |
| `plugin-process-exited` | `{plugin_id, pid, reason?}` | Хост обнаружил завершение child'а (crash/kill) — до следующего тика |

**Контракт `resource-metrics`:**

```json
{
  "ts": 1760000000000,
  "main": { "mem_bytes": 163577856, "cpu_percent": 3.1, "handles": 412 },
  "children": [
    { "plugin_id": "word-count",  "pid": 12345, "mem_bytes": 25165824, "cpu_percent": 0.4, "handles": 96 },
    { "plugin_id": "export-html", "pid": 12346, "mem_bytes": 18874368, "cpu_percent": 0.0, "handles": 88 }
  ]
}
```

- `ts` — `Date.now()` на Rust-стороне (для «N сек назад», §6.4).
- `mem_bytes` — рабочий набор (байты); формат «156 МБ» делает фронт.
- `cpu_percent` и `handles` — опциональны (могут отсутствовать; фронт рендерит, если есть).
- Дети без метрики (процесс завершился между тиками) в `children` не попадают — фронт помечает
  `orphan` по `plugin-process-exited`, а отсутствие в следующем снимке подтверждает удаление.

### 4.5. Порядок и защита от гонок

- Монитор **никогда** не держит `Mutex<PluginManager>`/`Mutex<DocumentStore>` во время вызова
  WinAPI: сначала снимок `(plugin_id, pid)` под коротким локом, затем замеры без лока, затем
  эмит. (Ср. инвариант дедлок-безопасности `PluginHost::pump`.)
- PID мог умереть между снимком и замером — ошибка доступа → метрика пропускается, не паника
  (аналог «host трактует кадры child'а как hostile», F36).
- Порядок событий `plugin-process-exited` и `resource-metrics` не гарантирован по времени
  (разные тики); фронт идемпотентен: `exited` переводит строку в `orphan`, отсутствие в снимке
  через 5 с — удаление; перезапуск (та же `plugin_id`, новый PID) отменяет удаление.

### 4.6. Таймер и завершение

- Отдельный поток `std::thread` со циклом `sleep(2 c)` + проверка флага остановки
  (`Arc<AtomicBool>`): не занимает event-loop и не блокирует IPC.
- Поток завершается при закрытии окна/остановке приложения (флаг взводится в `Drop`/`on_window_event`);
  незавершённый поток не должен мешать выходу. (Точный хук закрытия — уточнить при реализации.)
- При **свёрнутой** панели строка остаётся в шапке и обновляется; при **скрытой** панели фронт
  не рендерит (снимок продолжает идти, чтобы при открытии число было свежим) — оптимизация
  «останавливать опрос при скрытой панели» — открытый вопрос спайка (§8).

## 5. Модель данных (TS)

```ts
/** Метрика одного процесса в снимке (§4.4). */
export interface ProcessMetrics {
  mem_bytes: number;            // рабочий набор, байты
  cpu_percent?: number;         // 0..100·cores (см. §4.2)
  handles?: number;             // число хендлов (только при превышении порога — §6.5)
}

export interface MainMetrics extends ProcessMetrics {
  // main-процесс: pid известен фронту из снимка детей не нужен
}

export interface ChildMetrics extends ProcessMetrics {
  plugin_id: string;
  pid: number;
}

export interface ResourceSnapshot {
  ts: number;                   // Date.now() на Rust-стороне
  main: MainMetrics;
  children: ChildMetrics[];
}

/** Состояние строки (рендер §6.2). */
export type MonState = "ok" | "warn" | "crit" | "orphan";
```

Строка монитора — **проекция** снимка: `ResourceMonitor` держит последний `ResourceSnapshot`,
набор «осиротевших» `plugin_id` с дедлайном удаления (5 с) и пересобирает DOM при каждом
событии (без `innerHTML`).

## 6. UI-спецификация

### 6.1. Место и поведение

- Строка живёт в **шапке панели «Журнал»** — слот `#logs-resources` (`index.html:266`),
  `role="note"`, `aria-label="Мониторинг ресурсов"` (уточняется в §6.7).
- **При узком окне** — перенос на отдельную строку под шапкой (flex-wrap или вторая строка
  контейнера); строка не обрезается и не вытесняет фильтр/кнопку очистки.
- Строка **не яркая**: базовый цвет `--fg-mute`, моно, `tabular-nums` (стили `.logs-resources`
  уже заданы).
- **Числа + компактный прогресс-бар 4px у плагинов** (главный — без бара), **без спарклайна**.

### 6.2. DOM (ориентир — расширение зарезервированного слота)

```html
<div class="logs-resources" id="logs-resources" role="note" aria-label="Мониторинг ресурсов">
  <div class="mon-row mon-main" data-pid="main">
    <span class="mon-name">darmark</span>
    <span class="mon-val" id="mon-main-mem">156 МБ</span>
    <span class="mon-cpu" id="mon-main-cpu">CPU 3%</span>
    <span class="mon-age" id="mon-age">2 сек назад</span>
  </div>
  <div class="mon-children" id="mon-children">
    <!-- .mon-row.mon-child[data-plugin-id] — генерируется на фронте (textContent) -->
    <!-- <div class="mon-row mon-child" data-plugin-id="word-count">
           <span class="mon-dot" aria-hidden="true"></span>  <!-- цвет --pc -->
           <span class="mon-name">word-count</span>
           <span class="mon-val">24 МБ</span>
           <span class="mon-bar"><i style="--fill: 12%"></i></span>  <!-- 4px, inline-ширина -->
         </div> -->
  </div>
</div>
```

- `#logs-resources` и `.logs-resources` — **уже в разметке/стилях** (S11 §6.8), не переименовываем.
- Добавляется контейнер `#mon-children` и строки `.mon-row`; **все** тексты — через `textContent`.
- Точка `--pc` — цвет плагина (детерминированный из id; `pluginColor.ts`, `--pc` уже токен).

### 6.3. Строка главного процесса и детей

- **Главный процесс:** `darmark <ОЗУ> · CPU <n>%` (+ «N сек назад» в конце строки).
- **Дети:** `● <plugin_id> <ОЗУ> [CPU <n>%]`, где `●` — цвет `--pc`; прогресс-бар — доля от
  критического порога (`--fill`, §6.5).
- Порядок детей — детерминированный (по `plugin_id`), как в `PluginManager::list_plugins`.
- Итог по плагинам (необязательный элемент «суммарно») — по итогам спайка (§8).

Формат-образец: `darmark 156 МБ · CPU 3% | ● word-count 24 МБ · ● export-html 18 МБ`.

### 6.4. Обновление и возраст снимка

- «N сек назад» считается фронтом от `ts` относительно `Date.now()`; обновляется локально
  (по rAF/интервалу) между тиками, чтобы возраст не «замирал».
- Если снимков не было > ~6 с (3 пропущенных тика) — строка показывает «нет данных»
  (`--fg-dim`), не устаревшее число без пометки.

### 6.5. Пороги и реакция

| Ресурс | Предупреждение (`.warn`, янтарь) | Критический (`.crit`, красный) |
|--------|----------------------------------|-------------------------------|
| ОЗУ плагина | > 500 МБ | > 1 ГБ |
| ОЗУ главного | > 800 МБ | > 1.5 ГБ |
| CPU плагина | > 50% | > 80% |
| CPU главного | > 70% | > 90% |

- Предупреждение → подсветка `.warn` + запись `[warn]` в журнал; критический → `.crit` + `[error]`.
- **Записи в журнал дедуплицируются по фронту** (на `logEntry` уходит событие через существующий
  `log-entry`; одинаковые подряд по одному `plugin_id`+ресурсу не спамят): не более одной
  записи на переход через порог (снять/поставить порог), а не на каждый тик.
- Прогресс-бар плагина: `fill = min(1, mem_bytes / 1 ГБ) × 100%` (критический порог — 100%);
  цвет бара — `.warn`/`.crit` при превышении, иначе `--pc`.
- **Без авто-kill** (§6.6).

### 6.6. Состояние `orphan` и завершение child'а

- `plugin-process-exited{plugin_id, pid}` → строка `plugin_id` переходит в `orphan`:
  `opacity 0.5`, пометка «завершён», прогресс-бар погашен.
- Через **5 с** строка удаляется, если плагин не перезапущен (нет нового PID того же `plugin_id`
  в свежем снимке).
- Запись в журнал: `[плагин] Плагин <id>: процесс завершён (PID <n>)` (уровень `info`, категория
  `plugin`; при известной причине — в `detail`).
- Перезапуск плагина (reload/enable) даёт новый PID — `orphan`-состояние снимается, строка
  возвращается к обычному рендеру.
- **Авто-kill запрещён:** мониторинг ничего не завершает; ограничение ресурсов — Job Object и
  watchdog (`DESIGN_DOC §10`), реакция UI — только подсветка и журнал.

### 6.7. Доступность (a11y)

- Контейнер: `role="note"` (пометка) с `aria-label="Мониторинг ресурсов"`; либо `role="status"` +
  `aria-live="off"` — **лишний live-регион не нужен**: частые обновления раздражали бы скринридер.
  Значения доступны по запросу, без автоозвучивания (уточнить на этапе реализации).
- Каждый числовой элемент имеет текстовое значение («156 МБ», «CPU 3%») — доступно скринридеру.
- Прогресс-бар и точка-цвет — `aria-hidden="true"` (декор); семантику несёт число.
- `.warn`/`.crit` — не только цвет: пометка «перегруз» в `title`/тексте (WCAG: цвет не
  единственный носитель информации).
- При `prefers-reduced-motion` — анимации ширины бара отключены.

### 6.8. Токены и размеры

- Цвета: `--fg-mute` (норма), `--amber`/`--warning` (`.warn`), `--error`/`--red` (`.crit`),
  `--pc` (точка/бар плагина). Токены уже есть (`style.css:23,29,30,61`).
- Типографика: 10.5px, моно, `tabular-nums` (как в зарезервированном `.logs-resources`).
- Прогресс-бар: высота 4px, ширина строки-плагина фиксированная/клампованная, `--r-sm`.

## 7. Критерии готовности

### Функциональные

| # | Критерий | Проверка |
|---|----------|----------|
| AC-1 | В `#logs-resources` видны ОЗУ главного процесса и по строке на каждый активный плагин | E2E (фикстура с 1–2 плагинами) |
| AC-2 | Значения обновляются каждые ~2 с без действий пользователя | E2E/ручная |
| AC-3 | Строка плагина привязана к `plugin_id` и его PID; завершившийся child → `orphan` (opacity 0.5, «завершён») | E2E |
| AC-4 | `orphan`-строка удаляется через 5 с, если плагин не перезапущен; перезапуск возвращает обычный рендер | E2E/ручная |

| AC-6 | Прогресс-бар плагина отражает долю ОЗУ; при превышении окрашивается в `warn`/`crit` | ручная |

| AC-9 | Мониторинг **не завершает** процессы (авто-kill отсутствует) | ревью кода |

## 9. Риски

| Риск | Влияние | Митигация |
|------|---------|-----------|
| `windows`-crate тянет лишние фичи и растёт exe | Среднее | Только нужные фичи (`Win32_System_ProcessStatus`/`Threading`); size-gate в CI; спайк размера |
| Опрос 2 с заметно нагружает CPU на многих плагинах | Среднее | Замер в спайке; при необходимости — опрос только видимых/активных панелью (§8) |
| Гонка PID (процесс умер между снимком и замером) | Среднее | Ошибку `OpenProcess`/замера пропускаем, не паникуем (§4.5) |
| Дедлок при сборе метрик под блокировкой менеджера | Высокое | Снимок PID — под коротким локом; замеры/эмит — вне локи (§4.5) |
| Журнал спамит записями при каждом тике выше порога | Среднее | Дедуп по переходу через порог (§6.5) |
| `orphan` «залипает» или мигает при быстром рестарте | Низкое | Удаление через 5 с + снятие по новому PID; идемпотентный фронт (§4.5) |
| Поток опроса мешает выходу из приложения | Низкое | Флаг остановки + `Drop`/`on_window_event` (§4.6) |
| Кроссплатформенная сборка ломается | Среднее | Весь модуль под `#[cfg(windows)]`; не-Windows — пустая строка (AC-14) |
