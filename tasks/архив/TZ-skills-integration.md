# TZ-skills-integration — интеграция навыков и субагентов Koda в проект mdedit

## 0. Что изменилось относительно первой редакции

Первая редакция ТЗ строилась на гипотезе «взять 9 полезных скиллов из каталога GitVerse и
встроить их в `.kodarules`». Изучение документации Koda
(`docs.kodacode.ru/cli/features/skills.html`, `.../subagents.html`,
`.../desktop/settings/config-files.html`) показало два расхождения:

1. **Скилл — это устанавливаемый каталог с `SKILL.md`**, а не текст в `.kodarules`. Тело
   скилла грузится в контекст **только после активации** (`activate_skill`), в системный промпт
   попадают лишь `name` + `description`. «Встраивание тела в `.kodarules`» — прямой путь к шуму
   в контексте (нарушение принципа `.kodarules` «не читай лишнее»).
2. **Сторонние скиллы GitVerse не подтверждены**: не наш стек (React/Go/.NET/CI/медиа), а доступ
   к содержимому ранее отдавал 404. Полезнее и дешевле **написать собственные узкие скиллы под
   mdedit**, чем импортировать каталог наугад.

Итог: приоритет меняется на **собственные скиллы проекта** (workspace-scope, в git) плюс
**роли субагентов**; сторонние кандидаты S1–S9 понижены до «проверить доступ → оценить».

## 1. Контекст (зачем)

Цель — повысить качество и повторяемость работы агента на задачах проекта
(`TZ-excel-tables.md`, `TZ-inspect-mode.md`, `TZ-fixes.md`), не раздувая контекст.
Скиллы дают процедурное знание «под задачу», субагенты — изоляцию исследования/ревью.

Дисциплина та же, что и в первой редакции: **не «наставить скиллов наугад», а пройти цикл**
изучение → оценка применимости → пилот на реальной задаче → обоснованное решение.

## 2. Механика Koda (факты, на которые опираемся)

### 2.1. Навыки (skills)
- Формат: каталог `skill-name/SKILL.md` с frontmatter `name` + `description`; опционально
  `scripts/`, `references/`, `assets/`.
- Источники (приоритет от низкого к высокому): встроенные (bundle CLI) → расширения →
  `~/.kodacli/skills` → `~/.agents/skills` → `<ws>/.kodacli/skills` → `<ws>/.agents/skills`.
  Workspace-навыки грузятся только для доверенной рабочей области.
- Установка: `koda skills install <git|dir|*.skill> [--path <subdir>] [--scope user|project|workspace]`.
  `project` и `workspace` → один и тот же каталог `<ws>/.kodacli/skills`.
- Управление: `koda skills list|enable|disable|uninstall <name>`; в интерактиве —
  `/skills list|enable|disable|reload`. `/skills reload` выполняет **пользователь вручную**.
- Отключённые навыки хранятся в `~/.kodacli/settings.json` → `skills.disabled`.
- Жизненный цикл: обнаружение → активация моделью (`activate_skill`) → подтверждение (кроме
  встроенных) → внедрение тела + путь каталога в контекст → выполнение.

### 2.2. Субагенты-роли (subagents)
- Роль — файл `<ws>/.koda/agents/<name>.md` или `~/.kodacli/agents/<name>.md`
  (workspace перекрывает глобальную).
- Frontmatter: `name` (совпадает с именем файла), `description`, опц. `model`, `reasoningEffort`,
  `tools` (заменяет общий набор — роль может разрешать пишущие инструменты).
- Требуется `subagents.enabled = true`; применяется без перезапуска.
- Запуск моделью через `run_subagent` или явно: `@agent:<имя>` в начале абзаца.
- Управление: `/subagents roles [enable|disable|create|delete <имя>]`.
- По умолчанию субагенту доступны только «читающие» инструменты.

### 2.3. Конфиги проекта
- `.kodaignore`, `.kodarules` (целиком в системный промпт), `.koda-prompts/` — уже действуют.
- **Важно:** `.kodacli/` уже в `.kodaignore` → скиллы в `<ws>/.kodacli/skills` не засоряют
  чтение проекта агентом, но механизм скиллов их видит. В `.gitignore` `.kodacli/` нет →
  workspace-скиллы попадают в git (плюс: версионируются вместе с проектом).

## 5. Критерии приёмки (AC)

- **AC-1.** Для Класса B получено и сохранено реальное содержимое всех доступных скиллов;
  недоступные помечены `BLOCKED` с причиной.
- **AC-2.** Заполнена карточка статической оценки по каждому скиллу (§7).
- **AC-3.** По каждому скиллу, дошедшему до пилота, есть измеримый результат (время, итерации,
  покрытие AC) с/без скилла.
- **AC-4.** По каждому кандидату — обоснованный вердикт (`интегрировать`/`доработать`/`отклонить`/`BLOCKED`).
- **AC-5.** Интегрированные скиллы добавлены в `.kodarules`/`KODA.md` **только** как краткая
  ссылка+правило, не полным телом.
- **AC-6.** Ни один скилл/роль не нарушает CSP (`default-src 'self'`), TS strict (`tsc` проходит)
  и не влечёт правок `md-core`/`src-tauri` вне рамок выбранной подзадачи.
- **AC-7.** Отклонённые кандидаты задокументированы в §9.
- **AC-8.** После интеграции `npm run build` (tsc) и `cargo test -p md-core` проходят без новых ошибок.
- **AC-9.** Workspace-скиллы лежат в `<ws>/.kodacli/skills`, роли — в `<ws>/.koda/agents`;
  их подключение воспроизводимо (команда установки зафиксирована в `tasks/skills-eval.md`).

## 6. Ограничения (жёсткие)

1. **Не расширять область.** Только S1–S9 из Класса B. Новое — отдельной правкой ТЗ.
2. **Не интегрировать без пилота** (Этап C обязателен).
3. **Не дублировать тело скилла в `.kodarules`.** Только ссылка+правило.
4. **Зависимости** (npm/crate) — только с явного согласия пользователя и после проверки CSP/размера
   (см. `.kodarules`).
5. **Область правок:** пилоты S5/S1/S2/S8 — только `crates/app/src/*`; S7 — только `md-core`
   по согласованной подзадаче. `src-tauri` не трогать без нужды.
6. **Русские комментарии/строки** сохраняются; скилл не тащит англоязычные UI-строки.
7. **Не менять `.gitignore`** без прямого запроса (в т.ч. не добавлять `.kodacli/`).
8. **`/skills reload` и правку `settings.json`** выполняет пользователь; агент не делает это сам.
