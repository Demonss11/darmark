## 1. Целевая картина

Панель «Журнал» — инструмент **наблюдаемости** (best-effort observability) для пользователя
и разработчика плагинов. Закрывает пробел: ошибки плагинов, карантины, сообщения и действия
с документами происходят незаметно, причины отказов не диагностируются без внешних инструментов.

**Ключевая гипотеза:** персистентная, читаемая история событий сокращает время диагностики
с «угадывания по статусбару» до «прочтения последних записей журнала» и повышает доверие
к продукту через прозрачность.

**Целевая аудитория:**
- **Плагин-разработчик** (основной) — правит `.lua`, перезагружает, отлаживает; ошибки всплывают и исчезают.
- **Продвинутый пользователь** — замечает деградацию, хочет понять причину.
- **Бета-тестировщик** — может приложить контекст к баг-репорту.

### Текущее состояние

- `#sb-logs` — кнопка в статусбаре (`index.html:244`), по клику показывает флеш «Журнал — скоро» (`shell.ts:81`).
- Бейдж `#log-badge` предусмотрен ADR-0024 (`index.html:250`, `hidden`), не используется.
- Слот H3: полноценная панель журнала запланирована как отдельная панель (ADR-0024 §3: «вне scope» H2).
- Система уже генерирует события: `plugins-changed`, `plugin-views-changed`, `plugin-message`, `document-updated` — но с пустым payload (недостаточно деталей для журнала).

### Принцип

Best-effort observability: потеря записей журнала не критична (это не audit log), но падение
плагина или ошибка команды обязаны быть видны. Рендер записей — только `textContent` (CSP/XSS).

## 2. Scope S11

### В scope

1. **Панель-консоль «Журнал»** — сворачивающаяся панель на всю ширину над `#statusbar`, **внутри layout** (сжимает рабочую область, не перекрывает контент). Развёрнутое/свёрнутое состояние, resize по высоте.
2. **Лента событий** — ring buffer на фронте, последние 200 записей, автопрокрутка с заморозкой.
3. **Источники событий** — существующие Tauri-события + новые события Rust (обогащение payload).
4. **Бейдж `#log-badge`** — счётчик непрочитанных событий, цвет по уровню.
5. **Фильтр по категориям** — 5 вкладок (Все/Плагины/Документы/Ошибки/Система).
6. **Кнопка «Очистить журнал»** — очистка ленты без подтверждения.
7. **Группировка по дате** — разделители «Сегодня»/«Вчера»/«11 октября».
8. **Доступность** — ARIA, клавиатурная навигация, `aria-live`.

### Вне scope (отдельные задачи)

| Задача | Обоснование |
|--------|-------------|
| **IDEA-012** — мониторинг ресурсов (ОЗУ/CPU) | Отдельный источник данных (WinAPI), спайк, ADR. Другой продуктовый сценарий. **UX-видение согласовано** (см. §6.8): строка `#logs-resources` в шапке панели, Windows-only, 2 сек опроса, без авто-kill. |
| **Персистентность на диск** | Требует дизайна формата (JSON lines?), ретеншена по дате/размеру, приватности. Для беты достаточно in-memory истории сессии. |
| **Экспорт лога в файл** | Удобно, но не критично для беты. |
| **Поиск по журналу** | Для 200 записей не критично. |
| **Настройки уровня логирования** | Отдельная задача (настройки приложения). |
| **Полноценная панель журнала (H3)** | ADR-0024 §3 относит полноценную панель к H3. S11 — только наполнение слота `#sb-logs`. |

## 3. Пользовательские сценарии

### Сценарий 1: Диагностика отказа плагина
> **Как** пользователь, у которого перестал работать плагин, **я хочу** открыть журнал и увидеть последние события по нему, **чтобы** понять, на каком шаге что пошло не так.

**Приёмка:**
- Given плагин `word-count` в статусе `failed`
- When пользователь кликает `#sb-logs`
- Then в ленте есть запись `[ошибка] Плагин word-count: <текст ошибки>`

### Сценарий 2: Отслеживание карантина
> **Как** пользователь, у которого плагин попал в карантин, **я хочу** увидеть историю падений, **чтобы** понять, сколько раз плагин падал подряд.

**Приёмка:**
- Given плагин `X` в статусе `quarantined`
- When пользователь открывает журнал
- Then в ленте есть серия записей с ошибками и финальной записью `[система] Плагин X: карантин (3 падения подряд)`

### Сценарий 3: Проверка перезагрузки после правки `.lua`
> **Как** плагин-разработчик, который сохранил изменённый `.lua` и нажал Ctrl+R, **я хочу** убедиться, что перезагрузка прошла успешно, **чтобы** продолжить работу.

**Приёмка:**
- Given пользователь нажал Ctrl+R
- When открывается журнал
- Then в ленте есть запись `[плагин] Плагин Y: перезагружен`

### Сценарий 4: Отслеживание действий с документом
> **Как** пользователь, который заметил, что документ изменился плагином, **я хочу** увидеть, какие операции выполнялись с документом.

**Приёмка:**
- Given плагин вызвал `apply_edit`
- When открывается журнал
- Then в ленте есть запись `[документ] Документ обновлён (rev=N)`

### Сценарий 5: Использование бейджа как сигнала
> **Как** пользователь, который не следит за статусбаром, **я хочу** видеть бейдж на кнопке «Журнал» при новых событиях, **чтобы** знать, что есть что посмотреть.

**Приёмка:**
- Given панель журнала закрыта
- When произошло 5 новых событий
- Then бейдж `#log-badge` показывает «5»
- When пользователь открывает панель
- Then бейдж сбрасывается

## 4. Архитектурные решения

### 4.1. Размещение кода

- **Новый файл:** `crates/app/src/logPanel.ts` — контроллер панели журнала (буфер + подписка + рендер).
- **Изменения в `shell.ts`:** заменить заглушку `commands.flash("Журнал — скоро")` на вызов `logPanel.toggle()`.
- **Изменения в `main.ts`:** создать экземпляр `logPanel`, передать в `createShell`.
- **Изменения в `index.html`:** добавить разметку панели журнала **между рабочей областью и `#statusbar`** (`#logs-panel`, `#logs-resize`, `#logs-head`, `#logs-collapse`, `#logs-filter`, `#logs-list`, `#logs-clear`).
- **Изменения в `style.css`:** стили панели журнала (токены, записи, фильтры, бейдж).

### 4.2. Модель данных

```ts
interface LogEntry {
  id: number;          // монотонный счётчик на фронте
  ts: number;          // Date.now()
  level: "debug" | "info" | "warn" | "error";
  source: "core" | `plugin:${string}`;
  message: string;     // человекочитаемый текст (не HTML)
}

type LogCategory = "plugin" | "document" | "error" | "system";
```

Рендер — только `textContent`, без `innerHTML` (CSP). Цвет/иконка уровня — через CSS-классы.

### 4.3. Ring buffer

- Массив `LogEntry[]`, лимит **200 записей** (FIFO, сброс старших).
- Перерисовка — по throttle/raf, не на каждое событие.
- Коалесинг частых событий (`document-event` saved): не чаще 1 раза в N секунд.

### 4.4. Доставка событий

- **Push:** Rust-хост эмитит события через `app.emit(...)` → фронт подписывается через `listen(...)` → добавляет записи в ring buffer.
- **Pull при открытии:** не требуется (буфер копится с запуска приложения).
- **Гарантии:** best-effort; порядок FIFO в пределах источника; потеря при закрытии окна допустима.

### 4.5. Размещение и состояния панели

- Панель — **внутри layout**, в flex-колонке между рабочей областью и `#statusbar` (не `position:fixed`, не overlay). Раскрытие **сжимает** рабочую область.
- **Состояния:** развёрнута (высота по умолчанию `--h-logs: 220px`), свёрнута (полоса-шапка `--h-logs-bar: 28px`), скрыта.
- **Resize:** drag-handle сверху панели, высота клампится (мин ~28px, макс ~520px / ≤50% окна).
- Триггер `#sb-logs` в статусбаре: клик — развернуть/свернуть; получает `aria-expanded` и `.active` при раскрытой панели.
- Свёртывание: клик по `#sb-logs`, шеврон `#logs-collapse` в шапке, Esc (когда фокус в панели).
- Взаимоисключение с дровером плагинов и палитрой **не требуется** — панель не перекрывает контент.

### 4.6. Приватность и безопасность

- В журнал не писать содержимние документов, пути к файлам (только имена), секреты.
- Сообщения об ошибках — без стектрейсов.
- Рендер записей только через `textContent`.

## 5. Источники событий

### 5.1. Уже существующие (переиспользуем)

| Событие | Эмиттер | Payload | Интерпретация в журнале |
|---------|---------|---------|------------------------|
| `plugins-changed` | `host.rs: notify_plugins()` | `()` | «Плагины: обновлён список/статус» |
| `plugin-views-changed` | `services.rs: set_view_content` | `()` | «Представления обновлены» |
| `plugin-message` | `services.rs: show_message` | `{plugin_id, text}` | «Плагин «X»: <text>» |
| `document-updated` | `services.rs: apply_edit` | `{doc_id, rev}` | «Документ обновлён (rev=N)» |

### 5.2. Добавляем (Rust)

| Новое событие | Эмиттер | Payload | Зачем |
|---------------|---------|---------|-------|
| `plugin-status-changed` | `host.rs` в точках смены статуса (`set_enabled`, `reload`, `remove`, `set_permissions`, `pump` при ошибке, `start_enabled` при ошибке старта) | `{plugin_id, old_state, new_state, message?}` | Журнал: «плагин X: active → failed (…)», «плагин X: карантин (N=3)» |
| `document-event` | `lib.rs` в `new_document`, `open_document`, `save_document`, `close_document` | `{type: "opened"\|"saved"\|"closed"\|"created", path?, rev?}` | Журнал: «Открыт файл …», «Сохранён …» |
| `log-entry` | Новый `LogSink` в `services.rs`, подключаемый в `setup_plugins` (аналогично `StatusSink`/`DocumentSink`) | `{level: "debug"\|"info"\|"warn"\|"error", source: "plugin:<id>"\|"core", message}` | Журнал: сообщения от `host.log` плагинов + системные ошибки IPC |

**Примечание:** `plugins-changed` оставить как есть (пустой payload) для обратной совместимости — фронт и так делает `list_plugins`. Детали для журнала нести отдельным событием `plugin-status-changed` (принцип S2 — разделение сигналов).

## 6. UI-спецификация

### 6.1. Размещение

- Сворачивающаяся панель на **всю ширину** приложения, **внутри layout** между рабочей областью и `#statusbar` (не `position:fixed`, не overlay).
- **Развёрнута:** высота по умолчанию `--h-logs: 220px`; рабочая область сжимается.
- **Свёрнута:** полоса-шапка `--h-logs-bar: 28px` (тело скрыто).

- **Resize:** drag-handle `#logs-resize` сверху; высота клампится (~28–520px / ≤50% окна).
- Анимация: плавная смена высоты (`transition: height 0.18s`).

### 6.3. Запись журнала

```html
<div class="log-item" data-type="plugin" data-read="false" tabindex="0">
  <span class="log-dot" aria-hidden="true"></span>
  <span class="log-time">12:34:56</span>
  <span class="log-msg">Плагин «word-count» включён</span>
  <span class="log-detail">версия 1.0.0</span>
</div>
```

- **Точка-индикатор** (`.log-dot`): 6px, цвет типа события.
- **Время** (`.log-time`): моноширинный шрифт, `--fg-mute`, `font-variant-numeric: tabular-nums`.
- **Сообщение** (`.log-msg`): `--fg`, основной текст.
- **Детали** (`.log-detail`): `--fg-dim`, второй строкой.

### 6.4. Типы записей

| Тип | Цвет | Примеры |
|-----|------|---------|
| **Плагин** | `--accent` | Включён, отключён, перезагружен, упал, карантин |
| **Документ** | `--accent-2` | Открыт, сохранён, обновлён, закрыт |
| **Ошибка** | `--error` | Падение плагина, ошибка ФС, ошибка рендеринга |
| **Система** | `--fg-mute` | Запуск, закрытие, обновление |
| **Предупреждение** | `--warning` | Превышение лимита, медленный плагин, карантин N=3 |

### 6.5. Бейдж `#log-badge`

- Показывается при непрочитанных > 0, скрывается (`hidden`) при 0.
- Сбрасывается при открытии панели.
- Цвет: `--bg-3` (серый, по умолчанию), `--error` (красный, при ошибках), `--warning` (янтарный, при предупреждениях без ошибок).
- `aria-label="Непрочитанных событий: N"`.

### 6.6. Состояния

| Состояние | Визуализация |
|-----------|--------------|
| **Пустой журнал** | `.log-empty`: «Событий пока нет», подсказка «События появятся при работе плагинов и документов» |
| **Фильтр без результатов** | `.log-empty`: «Нет событий по фильтру «Плагины»» |
| **Переполнение** | Лимит 200 записей: старые удаляются, в шапке появляется предупреждение «Журнал очищен (лимит 200 записей)» |

### 6.7. Группировка по дате

- `.log-date-separator`: липкая шапка группы, текст «Сегодня», «Вчера», «11 октября».
- Разделитель — `border-bottom: 1px solid var(--line-soft)`.

### 6.8. Секция мониторинга ресурсов (IDEA-012)

> **Статус:** UX-видение согласовано. Реализация — отдельная задача (спайк + ADR + TZ).
> **Место:** компактная строка `#logs-resources` **в шапке панели** журнала (правая часть, §6.2); при узком окне может переноситься в отдельную строку.

#### Что показываем

- **ОЗУ (working set)** — обязательно, на процесс + итого.
- **CPU %** — опционально, на процесс.
- **Хендлы** — только при превышении порога.
- **Время обновления** — «N сек назад» в заголовке.

#### Частота опроса

2 секунды. Источник — Rust-хост (WinAPI `K32GetProcessMemoryInfo` через `windows`-crate, уже в зависимостях). Фронт получает готовые метрики по событию `resource-metrics`.

#### Пороги и реакция

| Ресурс | Предупреждение | Критический |
|--------|---------------|-------------|
| ОЗУ плагин | > 500 МБ | > 1 ГБ |
| ОЗУ главный | > 800 МБ | > 1.5 ГБ |
| CPU плагин | > 50% | > 80% |
| CPU главный | > 70% | > 90% |

- Предупреждation: янтарная подсветка (`.warn`) + запись `[warn]` в журнал.
- Критический: красная подсветка (`.crit`) + запись `[error]` в журнал.
- **Без авто-kill** (MVP). Авто-kill — отдельный ADR.

#### Crash/kill child

- Child завершается → статус `orphan` (opacity 0.5, пометка «завершён»).
- Через 5 секунд строка удаляется (если плагин не перезапущен).
- Запись в журнал: `[плагин] Плагин X: процесс завершён (PID N)`.

#### Визуальная структура

- Компактная строка `.logs-resources` в правой части шапки панели (высота шапки `--h-logs-bar`).
- Формат: `darmark 156 МБ · CPU 3% | ● word-count 24 МБ · ● export-html 18 МБ` (точки плагинов — цвет `--pc`).
- Число + компактный прогресс-бар (4px) у плагинов; при узком окне — перенос в отдельную строку.
- Без спарклайна (MVP). Спарклайн — отдельная панель «Производительность» (H3+).

#### DOM

```html
<div class="logs-resources" id="logs-resources" aria-label="Мониторинг ресурсов">
  <div class="mon-row mon-main" data-pid="main">
    <span class="mon-name">darmark</span>
    <span class="mon-val" id="mon-main-mem">156 МБ</span>
    <span class="mon-cpu" id="mon-main-cpu">CPU 3%</span>
  </div>
  <div class="mon-children" id="mon-children">
    <!-- .mon-row.mon-child[data-plugin-id] с точкой --pc -->
  </div>
</div>
```

#### ARIA

- `#logs-resources`: `role="group"`, `aria-label="Мониторинг ресурсов"`.
- Строка процесса: `aria-label="<имя>: <ОЗУ>, CPU <N>%"`.
- При превышении порога: запись в журнал (скринридер слышит через `aria-live="polite"` ленты).

## 7. Доступность (a11y)

- Панель: `role="region"`, `aria-label="Журнал событий"`, `aria-labelledby="logs-title"`.
- Список: `role="log"`, `aria-live="polite"`, `aria-relevant="additions"`.
- Фильтры: `role="tablist"`, `role="tab"`, `aria-selected="true/false"`, `tabindex="0/-1"`.
- Бейдж: `aria-label="Непрочитанных событий: N"`.
- Клавиатура: `Tab`, `Enter`/`Пробел`, `Esc`, `↑`/`↓`, `Home`/`End`.
- Фокус: при открытии — на первый фильтр; при закрытии — возврат на `#sb-logs`.
- `prefers-reduced-motion`: анимация открытия/закрытия отключается.

## 10. Риски

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Централизация подписки на события может сломать существующие контроллеры | Среднее | Сохранить существующие `listen()` в `pluginManager.ts` / `pluginViews.ts` и продублировать в `logPanel.ts` (события idempotent) |
| Панель занимает вертикаль у пользователя, работающего на маленьком экране | Низкое | Сворачивание до полосы-шапки, resize, дефолт 220px |
| XSS через сообщения плагинов | Высокое | Только `textContent`, без `innerHTML` |
| Раздувание памяти при интенсивных событиях | Низкое | Лимит 200 записей |
| Drag-resize конфликтует с выделением текста | Низкое | `user-select: none` на время драга, pointer capture |
