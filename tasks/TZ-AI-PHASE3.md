## 1. Целевая картина и статус

AI-ассистент — **встроенная подсистема хоста** (как `DocumentStore` или `RenderCache`): снижает порог
входа в Markdown и в создание Lua-плагинов. Пользователь описывает задачу на естественном языке,
ассистент предлагает правки документа или генерирует код плагина, пользователь проверяет и применяет.
Ключевой принцип — **AI помощник, а не замена**: пользователь контролирует, что применить, а что
отклонить; все действия проходят через существующие механизмы (DocumentStore, песочница плагинов,
permissions).

### 1.1. Что уже реализовано (Фазы 1–2 — вход в Ф3)

**Фаза 1 (AI-модуль Rust + режим AI нижнего дока) — реализована:**

- режим `AI` нижнего дока `#logs-panel` (ADR-0030), триггеры `#sb-ai`/`#tb-ai`, порядок
  «Журнал | Мониторинг | AI-ассистент»; включаемость `ai.enabled` (default `false`, opt-in),
  состояния `#ai-dot` («выкл / нет ключа / нет согласия / офлайн / готов»);
- провайдер MVP — OpenAI-совместимый API (точка `routerai.ru`, модель
  `deepseek/deepseek-v4.1-flash`) — **ADR-0032**; ключ локально в `%APPDATA%/darmark/config.json`
  (секция `ai`, SettingsStore D11), наружу — только `has_key`;
- сетевой слой — Rust-сторона: `reqwest` (`native-tls`/SChannel) + **SSE**-стриминг —
  **ADR-0033**; события `ai:chunk`/`ai:done`/`ai:error`; AI-рантайм — **в процессе GUI** за швом
  `AiBackend`/`AiTransport` — **ADR-0034**;
- 2 скилла MVP: `explain` и `create-plugin`; согласие `consent_document_send` (диалог при первой
  отправке, именует `routerai.ru`); ответ AI рендерится через `textContent`.

**Фаза 2 (harness документа и плагинов) — реализована:**

- harness документа: `ai_diff` (минимальный дифф) + `ai_apply_edit` (rev-guard `ai_stale_edit`,
  атомарная проверка `ops`), предпросмотр диффа, отмена через undo-стек;
- harness плагинов: `ai_validate_plugin` / `ai_create_plugin` / `ai_update_plugin` /
  `ai_delete_plugin`; делегирование `plugin-cli` (`init` / `test <dir> --json`,
  версионированный отчёт `schema_version: 1`) с fallback на `plugin_core::manifest` +
  `plugin-host --self-test`.

> Реализация Ф1/Ф2 зафиксирована в ADR-0030/0032/0033/0034 и в коде
> (`crates/app/src-tauri/src/ai/`, `crates/app/src/aiPanel.ts`). Здесь она **не повторяется** —
> настоящее ТЗ описывает только то, что осталось на Ф3.

### 1.2. Предмет Ф3

Ф3 развивает ассистента по четырём направлениям:

1. **Полнота скиллов** — остальные документные/плагинные скиллы и **пользовательские скиллы**;
2. **Зрелость UX** — **персистентность истории чата** и **Rust-санитайзер** ответа AI
   (рендер Markdown ответа через `md-core` вместо `textContent`);
3. **Универсальная конфигурация провайдеров** (ADR-0035) — несколько провайдеров, `provider/model`,
   произвольные заголовки/тело, ключ на провайдера, миграция текущей секции `ai`;
4. **MCP (inbound)** — отдельная граница доверия (внешние клиенты вызывают darmark); вносится в
   это ТЗ, но **вне текущего MVP** и под отдельный ADR.

## 2. Scope Фазы 3

### 2.1. В scope

1. **Остальные готовые скиллы** (за рамками `explain`/`create-plugin`):
   - документные: **переструктурировать**, **конспект** (сжатое изложение), **объяснить синтаксис**
     (отдельным скиллом — разбор разметки Markdown);
   - плагинные: **отладить плагин** (диагностика/исправление ошибок песочницы), **добавить view**
     (генерация команды представления по контракту `ViewProvider`).
2. **Пользовательские скиллы и редактор скиллов** — расширяемость промтов пользователем и
   (позже) плагинами; UI создания/редактирования/удаления скиллов поверх формата JSON
   (`%APPDATA%/darmark/ai-skills.json`).
3. **Персистентность истории чата** — сохранение диалога между запусками (сейчас — только в памяти
   на сессию).
4. **Rust-санитайзер ответа AI** — рендер Markdown ответа через `md-core` (`to_html` +
   `sanitize_html`, D7/§11) вместо `textContent`; **единственная** точка вставки HTML ответа LLM —
   в теле режима AI (`aiPanel.ts`), и только **санитизированный** HTML; сырой вывод LLM в
   `innerHTML` не попадает.
5. **Универсальная конфигурация провайдеров** (ADR-0035) — см. §3 (детально).
6. **MCP (inbound)** — внесено в это ТЗ как отдельное направление; **вне текущего MVP**,
   реализуется по отдельному ADR (§4).
7. **Прочие провайдеры** (Anthropic-compatible и др.) — в рамках универсальной конфигурации (§5),
   без отдельного кода клиента (пока протокол OpenAI-совместимый).

### 2.2. Вне scope

| Задача | Обоснование |
|--------|-------------|
| **MCP (inbound) — реализация** | Внесено в ТЗ, но **вне MVP Ф3**; отдельная граница доверия, свой consent/permissions/auth и **отдельный ADR** (§4) |
| **Локальная LLM (Ollama/llama.cpp)** | Отложена на неопределённый срок (ADR-0032); при возврате — отдельный ADR/спайк |
| **AI как плагин** | Противоречит архитектуре: нужен Rust-сетевой слой (ADR-0021) |
| **Мультимодальность** (изображения/аудио) | Не в scope |
| **Телеметрия/аналитика** | Вне scope (ADR-0032 §2.9) |
| **Сайдкар `darmark-ai.exe`** | Отложен (ADR-0034); пересмотр — по триггерам ADR-0034 §2.6 |
| **Сетевые вызовы из TS** | Запрещены CSP `default-src 'self'`; сеть — только Rust |

## 3. Универсальная конфигурация провайдеров (ADR-0035)

> Нормативное решение — **ADR-0035** (`docs/adr/0035-ai-provider-config.md`, **принят**). Этот раздел —
> ТЗ-уровня: что именно требуется от продукта; детали схемы/валидации — по ADR-0035 (синхронизированы).

### 3.1. Проблема

Текущая секция `ai` описывает **ровно один** провайдер плоскими полями
(`provider`/`base_url`/`model`/`api_key`). Это не позволяет: держать несколько провайдеров
(например, `routerai.ru` и корпоративный шлюз), задавать произвольные заголовки/поля тела,
менять точку без потери прежней, хранить ключ на провайдера, выбирать модель как `provider/model`.

### 3.2. Идея (заимствована из раздела **Custom** доки OpenCode)

Конфигурация провайдеров строится как **map провайдеров** (ключ — id провайдера) плюс выбор
активной пары `active_provider`/`active_model` — по образцу `providers` в `opencode.json`
(дока: https://opencode.ai/v2/docs/providers/#custom, раздел **Custom**). Оттуда переносим
**имена полей** записи провайдера: `name`, `env` (упорядоченные env-переменные ключа),
`package` (runtime/протокол), `settings` (`baseURL`, `apiKey`, `timeout`), `headers`, `body`,
`models` (`name`, опц. `modelID`, опц. `disabled`). Ссылка на модель — **`provider/model`**.

Отличия от `opencode.json` (осознанные, адаптация под darmark):

- `canonical` **не переносим** — у darmark нет каталога `models.dev`, наследовать нечего;
- `package` переносим **как строковый id протокола** (`openai-compatible`), а не как путь к
  npm-пакету: в darmark нет JS-runtime; поле зарезервировано под `anthropic-compatible`
  (адаптер — отдельным решением, §5);
- `variants`/`capabilities`/`cost`/`limit`/`family`/`compatibility` и раздельные
  `settings.headerTimeout`/`chunkTimeout` **не вводим** в MVP;
- секрет хранится **локально** (`settings.apiKey`) с приоритетом над `env` (см. §3.5), а не
  только в переменной окружения.

### 3.3. Схема конфигурации (секция `ai`, `config.json`, D11)

```jsonc
{
  "ai": {
    "enabled": false,
    "active_provider": "routerai",
    "active_model": "deepseek/deepseek-v4.1-flash",
    "consent_document_send": false,
    "max_tokens": 4096,
    "temperature": 0.7,
    "providers": {
      "routerai": {
        "name": "RouterAI",
        "env": ["ROUTERAI_API_KEY"],              // упорядоченные env-переменные ключа
        "package": "openai-compatible",           // runtime/протокол
        "settings": {
          "baseURL": "https://routerai.ru/api/v1",
          "apiKey": "",                           // локальный секрет; приоритет над env
          "timeout": 30000
        },
        "headers": {},
        "body": {},
        "models": {
          "deepseek/deepseek-v4.1-flash": { "name": "DeepSeek V4.1 Flash" }
        }
      }
    }
  }
}
```

**Поля провайдера** (имена — из раздела **Custom** доки OpenCode, §3.2):

| Поле | Тип | Назначение |
|------|-----|------------|
| `name` | string | Отображаемое имя (UI) |
| `env` | string[] | **Упорядоченный** список env-переменных с ключом; берётся первая непустая (§3.5) |
| `package` | string | Runtime/протокол провайдера: пока `openai-compatible`; зарезервировано под `anthropic-compatible` (§5) |
| `settings.baseURL` | string | Базовая точка OpenAI-совместимого API; валидация — §3.6 |
| `settings.apiKey` | string | Локальный секрет; приоритет над `env` (§3.5); наружу — только `has_key` |
| `settings.timeout` | number \| null | Таймаут запроса для этого провайдера (мс); `null`/отсутствие → дефолт (ориентир 30 с) |
| `headers` | map<string,string> | Доп. HTTP-заголовки, добавляются к каждому запросу; `Authorization` ими не задаётся (§3.5) |
| `body` | object | JSON-поля, **сливаемые** в тело каждого запроса (например `metadata`) |
| `models` | map<string,{name, modelID?, disabled?}> | Модели провайдера: ключ — id (используется в `provider/model` и в `active_model`), значение — `name` (отображаемое), опц. `modelID` (id, отправляемый провайдеру), опц. `disabled` (исключить из выбора) |

**Верхний уровень `ai`:** `enabled` (opt-in, ADR-0034), `active_provider` + `active_model`
(активная пара — аналог корневого `model` в `opencode.json`), `consent_document_send` (согласие,
§3.7), `max_tokens`/`temperature` (дефолты), `providers` (map).

### 3.4. Ссылка `provider/model`

- Канонически активная пара хранится **раздельно** (`active_provider`, `active_model`) и
  резолвится **по полям**: id — ключ в `providers`, `active_model` — ключ в
  `providers[active_provider].models`.
- В UI/строках отображения модель показывается как **`provider/model`** (например
  `routerai/deepseek/deepseek-v4.1-flash`), но строка **не разбирается** по `/`: id модели **сам
  может содержать `/`** (`deepseek/deepseek-v4.1-flash`), поэтому резолв — только по полям
  (ADR-0035 §2.2 п. 5).
- Если провайдер или модель не найдены в `providers` → понятная ошибка (`ai_bad_settings`),
  запрос не уходит.

### 3.5. Ключ и секреты

- **Ключ на провайдера** — `settings.apiKey` внутри записи провайдера (а не общее поле). Команда
  `ai_set_api_key` получает **id провайдера**; пустая строка (после `trim`) очищает ключ
  **этого** провайдера (`settings.apiKey = ""`).
- **`env`** — альтернативный путь: **упорядоченный** список имён env-переменных; берётся первая
  непустая (значение читается в момент запроса). **Приоритет (ADR-0035 §2.3 п. 7):** если заданы
  оба источника — `settings.apiKey` (значение из конфига **перекрывает** `env`). Env-путь удобен,
  когда пользователь не хочет держать секрет на диске.
- **`Authorization: Bearer <key>`** формируется **из ключа** (конфиг либо `env`), а **не** из
  `headers`: источник авторизации однозначен, пользовательские `headers` не могут его подменить.
- **Инварианты (сохраняются из Ф1):** ключ **не** попадает в TS-код, логи, снапшоты и события;
  наружу — только `has_key`; в UI — маска; в `{:?}` — `<redacted>`.
- **Миграция ключа** (§3.8): старый `ai.api_key` переносится в `settings.apiKey` первого провайдера.

### 3.6. Валидация `settings.baseURL`

- `https://` — разрешено всегда.
- `http://` — **только loopback** (`127.0.0.1`/`localhost`/`[::1]`) — для локальных рантаймов.
- Иначе — ошибка **`ai_bad_settings`** (запрос не уходит). Логика уже реализована в Ф1-hardening;
  распространяется на каждый провайдер.

### 3.7. Согласие именует активный хост

- Диалог согласия при первой отправке именует **активного провайдера**: `name` + **хост его
  `settings.baseURL`** — а не жёстко `routerai.ru`.
- Согласие остаётся полем **`consent_document_send`** (секция `ai`, как в Ф1). При смене
  `active_provider` (или `settings.baseURL` активного провайдера) на **другой хост** значение
  **сбрасывается** и согласие **запрашивается заново** (отправка на новый хост без согласия не
  происходит) — ADR-0035 §2.7 п. 17–18.
- Отдельных команд согласия **не вводится** (как в Ф1): поля читаются/пишутся через
  `ai_get_settings`/`ai_set_settings`.

### 3.8. Миграция текущей секции `ai`

При загрузке настроек (SettingsStore, D11):

- если `providers` **отсутствует**, а есть legacy-поля (`provider`/`base_url`/`model`/`api_key`) —
  синтезируется **первый провайдер**: id — из `provider` (дефолт `routerai`), `base_url` →
  `settings.baseURL`, `api_key` → `settings.apiKey`, `package = "openai-compatible"`, `env = []`,
  `model` добавляется в `models`; `active_provider`/`active_model` выставляются на него;
  `consent_document_send` сохраняется (хост тот же);
- после миграции конфиг **переписывается** в новый вид (idempotent, обратной миграции нет);
- чтение legacy-полей сохраняется для совместимости (если новый вид ещё не записан).

Пример: legacy `{ "provider": "openai-compatible", "base_url": "https://routerai.ru/api/v1",
"model": "deepseek/deepseek-v4.1-flash", "api_key": "…" }` → провайдер `routerai` (§3.3) с
`settings.baseURL`/`settings.apiKey` и `active_model = "deepseek/deepseek-v4.1-flash"`.

### 3.9. UI настроек

Поповер `#ai-settings-pop` расширяется до **менеджера провайдеров** (аддитивные id):

| Элемент | id (предлагаемые) | Назначение |
|---------|-------------------|------------|
| Список провайдеров | `#ai-providers` | Выбор провайдера (источник для правки) |
| Добавить / править / удалить | `#ai-provider-add`, `#ai-provider-edit`, `#ai-provider-remove` | CRUD записей |
| Активный провайдер | `#ai-provider-active` | Переключатель активного |
| Имя | `#ai-provider-name` | `name` |
| Протокол | `#ai-provider-package` | `package` (в MVP фиксирован `openai-compatible`) |
| Базовая точка | `#ai-provider-base-url` | `settings.baseURL` (+ валидация §3.6) |
| Ключ | `#ai-provider-key` (`type="password"`) | `settings.apiKey` (маска) |
| Env-переменные ключа | `#ai-provider-env` | `env` (упорядоченный список) |
| Заголовки | `#ai-provider-headers` | `headers` (JSON-редактор) |
| Тело запроса | `#ai-provider-body` | `body` (JSON-редактор) |
| Таймаут | `#ai-provider-timeout` | `settings.timeout` |
| Активная модель | `#ai-model-select` (существует) | Выбор `active_model` из `models` (`disabled` скрываются) |

Правила: **нельзя удалить провайдера, который активен** (сначала переключить) либо удаление
сбрасывает активного на первого доступного; изменения применяются к активному провайдеру
**лениво** (без перезапуска). Существующие id `#ai-model`, `#ai-settings`, `#ai-key`,
`#ai-enabled` сохраняются (аддитивность; §13.2 не ломается).

### 3.10. Discovery моделей (опционально)

- Опционально: `GET {settings.baseURL}/models` с ключом провайдера → список моделей для `#ai-model-select`.
- Discovery **не** отправляет содержимое документа и **не** требует согласия (согласие относится к
  отправке содержимого, не к проверке ключа) — проверяются `ai.enabled` и наличие ключа.
- При недоступности discovery — fallback на `models` из конфига; ошибка не блокирует чат.

## 4. MCP (inbound) — внесено, вне текущего MVP

> Источник — IDEA-016. Нормативная граница зафиксирована в ADR-0034 §2.5 (MCP — вне MVP);
> для реализации потребуется **отдельный ADR**.

### 4.1. Суть

darmark выступает **MCP-сервером** (inbound): **внешние AI-клиенты** (другие агенты/редакторы)
вызывают инструменты/ресурсы darmark по открытому протоколу. Сервер строится **над существующими
CLI/командами** (документные команды, harness, каталог плагинов) — не дублирует их, а оборачивает.

### 4.2. Отделённая граница доверия (ключевое)

MCP — **качественно иная граница**, чем outbound-запрос AI к провайдеру:

- **входящий канал**: не мы инициируем вызов, а внешний клиент — ему нужно **аутентифицироваться**;
- **свой consent/permissions**: отдельное согласие на доступ внешних клиентов, отдельный набор
  разрешённых инструментов, **аудит** вызовов;
- **не повторять «инверсию привилегий»** (ср. разбор сайдкара в ADR-0034 §4): не открывать
  больше, чем нужно; минимизировать поверхность.

### 4.3. Роли (не смешивать)

- **MCP-сервер** (inbound, эта задача) — внешние клиенты вызывают нас;
- **MCP-клиент** внутри darmark (outbound к внешним MCP-серверам) — **другое направление**,
  в это ТЗ не входит.

### 4.4. Статус и следующий шаг

- **В текущий MVP (Ф3) не входит** — не раздувать объём; включается только при появлении кейса
  внешних клиентов.
- Следующий шаг при появлении кейса: **отдельный ADR** (граница доверия, набор инструментов,
  транспорт, аутентификация) + при необходимости спайк.

---

## 5. Прочие провайдеры (Anthropic-compatible и др.)

- Реализуются **в рамках универсальной конфигурации** (§3): провайдер описывается той же записью
  `providers.<id>`, отличается только `settings.baseURL`/`headers`/`body`.
- **Ограничение:** в Ф3 код клиента остаётся **OpenAI-совместимым** (`POST /chat/completions`,
  `messages`/`choices[].message.content`). Провайдеры с иным протоколом (например,
  Anthropic Messages) требуют **адаптера** — это расширение за тем же интерфейсом провайдера
  (ADR-0032 §2.2), вводится отдельным решением, если понадобится.
- Локальные OpenAI-совместимые рантаймы (LM Studio/vLLM/Ollama с `/v1`) уже покрываются
  универсальной конфигурацией через `settings.baseURL` = loopback (`http://127.0.0.1:…`), без
  отдельного кода — но **автоподъём** локального сервера и загрузка моделей остаются вне scope
  (ADR-0032).

## 6. Критерии готовности

### 6.1. Функциональные

| # | Критерий | Проверка |
|---|----------|----------|
| AC-P3-1 | Доступны остальные скиллы: переструктурировать, конспект, объяснить синтаксис, отладить плагин, добавить view | E2E: выбор и отправка скилла |
| AC-P3-2 | Пользователь может **создать/править/удалить** скилл (JSON `ai-skills.json`); пользовательский скилл выбирается и отправляется | E2E/тест: CRUD скиллов |

| AC-P3-7 | Ключ хранится **на провайдера** (`settings.apiKey`); `ai_set_api_key(provider_id, "")` очищает ключ именно провайдера; приоритет `settings.apiKey` > `env` | Тест: чтение настроек |
| AC-P3-8 | Согласие именует **активного провайдера** (`name` + хост `settings.baseURL`); смена активного хоста **сбрасывает** `consent_document_send`, согласие запрашивается заново | E2E: смена провайдера |
| AC-P3-9 | Валидация `settings.baseURL`: `https` — всегда, `http` — только loopback; иначе `ai_bad_settings` | Тест: валидация |
| AC-P3-10 | Миграция: legacy-секция `ai` превращается в первый провайдер, конфиг переписывается | Тест: миграция |
| AC-P3-11 | UI: список/добавить/править/удалить провайдера; выбор активной модели | E2E: менеджер провайдеров |
| AC-P3-12 | Discovery `GET /models` (опц.) не шлёт содержимое документа и не требует согласия; при сбое — fallback на конфиг | Тест: discovery |

## 7. План реализации

Порядок — по возрастанию риска; каждый блок завершается проверками (`cargo test -p darmark`,
`npm run build`, E2E).

1. **Остальные скиллы** (AC-P3-1): добавить готовые промты в `ai-skills.json` и карточки в UI;
   документные скиллы подключаются к существующему harness `ai_diff`/`ai_apply_edit`.
2. **Пользовательские скиллы + редактор** (AC-P3-2): CRUD поверх JSON, валидация схемы скилла.
3. **Персистентность истории чата** (AC-P3-3): хранение диалога (файл в `%APPDATA%/darmark/`),
   восстановление при старте, лимиты объёма.
4. **Rust-санитайзер ответа AI** (AC-P3-4): рендер Markdown ответа через `md-core`
   (`to_html` + `sanitize_html`); единственная точка вставки HTML.
5. **Универсальная конфигурация провайдеров** (AC-P3-5…12) — по ADR-0035:
   схема `providers` + `active_provider`/`active_model`; поля провайдера; ключ на провайдера;
   валидация `settings.baseURL`; согласие по активному хосту; **миграция** legacy-секции; UI менеджера;
   discovery моделей (опц.).
6. **Прочие провайдеры** (AC-P3-5…6, §5): проверка на OpenAI-совместимом шлюзе; адаптеры иного
   протокола — отдельным решением.
7. **MCP (inbound)** — **не в этом релизе**: при появлении кейса — отдельный ADR + спайк, затем
   реализация (§4).

## 8. Риски

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Универсальная конфигурация усложнит онбординг | Среднее | Дефолт — один провайдер (`routerai`) как сейчас; менеджер — опционален, «из коробки» не требуется |
| Произвольные `headers`/`body` могут сломать запрос | Среднее | JSON-валидация в UI; понятная ошибка сборки запроса; слияние `body` — поверх дефолтных полей, не вместо |
| Ключ на диск в открытом виде (несколько провайдеров) | Среднее | Принятый компромисс (ADR-0032 §2.4); `env` как альтернатива; маскирование, запрет логирования |
| Смена хоста провайдера без согласия | Высокое | Согласие `consent_document_send` **сбрасывается** при смене активного хоста и запрашивается заново (§3.7) |
| Миграция конфига повредит настройки пользователя | Среднее | Idempotent-миграция с перезаписью; чтение legacy сохранено; покрытие тестом (AC-P3-10) |
| Рендер Markdown ответа AI — XSS | Высокое | Единый Rust-санитайзер `md-core::sanitize_html` (D7/§11); сырой вывод LLM в `innerHTML` запрещён (AC-P3-4) |
| Персистентность истории раздуёт диск/утечёт данные | Среднее | Лимит объёма истории, локальное хранение, отсутствие логирования содержимого; очистка по действию пользователя |
| Соблазн втянуть MCP в текущий релиз | Среднее | MCP — **вне MVP** (§4): отдельная граница доверия, отдельный ADR |
| Новые поля/модели увеличивают AI-клиент | Низкое | Изменения — в основном данные/UI; контроль size-gate (AC-P3-15) |
| Пользовательские скиллы с небезопасным промтом | Низкое | Скилл — только текст промта; исполнение/сеть не даёт; действия проходят через harness/permissions |
