## 1. Контекст

IDEA-002 — архитектурная идея продуктового pivot: от «Markdown-редактора» к универсальному
редактору с подключаемыми движками. **Host работает с файлом, не зная про Markdown.**

**Ключевой факт текущего состояния:** понятия «Engine» в проекте **нет**. Нет трейта, нет
реестра, нет типа результата — есть вызов функции. `docs/DESIGN_DOC.md` слово «движок» не
употребляет вовсе: §3 описывает «контракт ядра `md-core`» как набор функций над Markdown. То
есть граница Host ↔ Engine сегодня **не зафиксирована нигде**, и именно её предстоит
зафиксировать — в этом и состоит спайк.

Продуктовая цель: перестать быть приложением, «умеющим Markdown», и стать редактором, умеющим
подключать движки.

## 2. Текущее состояние системы (As-Is)

### 2.1 Архитектура рендера

```
TS-редактор (#editor, textarea)
  │ debounce 120 мс (DEBOUNCE_MS)
  │ invoke("update_document" | "render_document")
  ▼
Rust-хост: DocumentStore → Document::render
  │ кэш по (mapped, rev); при попадании — рендер не запускается
  │ md_core::to_html_mapped(&text) | md_core::to_html(&text)
  ▼
md-core (pulldown-cmark, GFM+сноски+шапка)
  │ парсинг → html::push_html → санитайзер белых списков
  │ опционально: инъекция data-md="start,end" (байты UTF-8) ПОСЛЕ санитайзера
  ▼
RenderResult { html, rev, changed }
  │ changed:false → TS не трогает DOM
  ▼
TS: preview.innerHTML (HTML уже санитизирован на хосте)
  │ renderIndex.set(text, rev, root) — снимок на ревизию
  ▼
inspector (подсветка блока) + scrollsync (вертикальная синхронизация)
```

### 2.2 Точки вызова движка — 7 вызовов в 4 файлах, все хардкодом

| Файл:строка | Вызов | Назначение | Горячий путь |
|---|---|---|---|
| `src-tauri/src/state/store.rs:51` | `to_html_mapped` | рендер документа в предпросмотр (mapped) | **да** — debounce 120 мс |
| `src-tauri/src/state/store.rs:53` | `to_html` | рендер документа в предпросмотр (plain) | **да** |
| `src-tauri/src/ai/commands/mod.rs:335` | `to_html` | `ai_render_markdown` — рендер ответа модели | нет |
| `src-tauri/src/mcp/adapters/tools.rs:210` | `to_html_mapped` | MCP-tool `markdown_render` (mapped) | нет |
| `src-tauri/src/mcp/adapters/tools.rs:212` | `to_html` | MCP-tool `markdown_render` (plain) | нет |
| `plugin-host/src/bindings.rs:263` | `to_html` | Lua-функция `md.render` в child | нет |
| `plugin-host/src/bindings.rs:269` | `to_html_mapped` | Lua-функция `md.render_mapped` в child | нет |

**Наблюдение.** Точки не выглядят как «список мест, куда вставлен движок» — они выглядят как
разные фичи, каждая из которых сама решила, что ей нужен Markdown. Это и есть признак
отсутствия границы: подмена движка означала бы правку всех семи мест, а не одной точки.

**Отдельное ограничение (важно для спайка).** `md-core` линкуется **в child-процесс**
(`plugin-host/src/bindings.rs:5`), то есть `md.*` для плагина рендерит **внутри** child. Движок,
живущий в процессе GUI, из child недостижим без IPC. Значит «подключаемость движка» для
плагинов и для хоста — это две разные задачи, и их нельзя закрыть одним реестром.

### 2.3 Контракт выхода, который сегодня есть

| Элемент | Фактический вид | Комментарий |
|---|---|---|
| Вход | `&str` (текст) | плюс неявные флаги выбора `mapped`/опций на стороне вызова |
| Выход | `String` (HTML) | уже прогнан через санитайзер белых списков |
| Разметка блоков | атрибут `data-md="start,end"` | **байтовые** смещения UTF-8; границы — char-boundary |
| Санитайзация | `sanitize_fragment` — отдельный публичный вход | та же политика, что у `to_html` (для плагинных view) |

Публичный API `md-core`: `DEFAULT_OPTIONS`, `to_html`, `to_html_with(markdown, Options)`,
`to_html_mapped`, `sanitize_fragment`. Модули: `lib.rs` (~1900 строк), `frontmatter.rs`.

### 2.4 Что уже вшито в формат выхода — ограничения для любого движка

1. **`data-md` — контракт инспектора** (§13.2). Любой движок обязан уметь отдавать сопоставление
   «блок → диапазон байт в исходнике», иначе теряются inspector и scrollsync. Это не
   Markdown-специфичное требование, а требование к абракции движка.
2. **Единицы.** `data-md` — байты UTF-8; TS строит карты байты↔UTF-16 (`mapping.ts`:
   `b2u`/`u2b` как `Int32Array`) и начала строк. Если движок отдаст смещения в кодовых
   единицах, расхождение будет молчаливым — инвариант стоит зафиксировать в контракте явно.
3. **Индексация привязана к тексту, ушедшему в рендер.** `renderIndex` хранит `source` — тот
   самый текст, по которому считались `data-md`; до следующего рендера индекс считается
   устаревшим (потребители видят `null`). Это защита от «двойной истины о тексте» и должна
   пережить появление второго движка.
4. **Дебаунс 120 мс** (`docStore/helpers.ts`) — бюджет горячего пути. D2 прямо запрещает гнать
   его через интерпретатор.
5. **`innerHTML` — ровно три точки**, список исчерпывающий (ADR-0038 §2.1): `previewView.ts`,
   `pluginViews.ts`, `safeHtml.ts`. Новая точка — ревью-блокер.

## 3. Целевое состояние (To-Be)

### 3.1 Концепция

```
Сейчас:  TS editor → IPC → DocumentStore::render → md_core::to_html   (вызов вшит в 7 мест)
Целевое: TS editor → IPC → EngineRegistry → Engine::render(text) → RenderOutput
                                 ├── MarkdownEngine (md-core, сегодня)
                                 ├── WasmEngine    (кандидат, под вопросом D6/D2)
                                 ├── IpcEngine     (движок в child/плагине — §2.2)
                                 └── … будущие форматы
```

### 3.2 Что обязано войти в контракт движка — гипотезы

- **Вход:** текст + ревизия (+ явный флаг «нужна разметка блоков» вместо пары функций
  `to_html`/`to_html_mapped`).
- **Выход:** `RenderOutput { html, blocks? }` — здесь развилка: **HTML-строка** (как сегодня) или
  **структурные данные** (AST/токены/патчи), из которых хост сам собирает разметку и DOM.
  Структура даёт инкрементальность и независимость от синтаксиса; строка — простоту и
  совместимость с плагинным тиром.
- **Кто владеет сопоставлением** (байты↔UTF-16, `data-md`): хост или движок. Если движок — то
  нужен формальный контракт границ блоков (char-boundary, вложенность, таблицы).

### 3.3 Точка стыковки с `tasks/IDEA-004-SPIKE-DISCUSSION.md`

В §3.1 того документа «будущие engines» перечислены среди провайдеров реестра адаптеров. То
есть движок может оказаться либо отдельной абстракцией рядом с реестром, либо одним из видов
провайдеров. **Это общий вопрос двух спайков.** Закрыть его нужно один раз: иначе границы
Host ↔ Engine и host ↔ адаптеры будут зафиксированы несовместимо, и один из спайков придётся
переделывать.

## 5. Конечная цель спайка

**Спайк должен доказать, что Host перестал знать про Markdown** — второй движок подключается
через реестр, без правок ядра хоста и без правок точек вызова из §2.2.

| Критерий | Целевое состояние |
|---|---|
| **Подключаемость** (главный) | Второй движок (не-Markdown) включается в предпросмотр без изменения кода хоста |
| **Точки расширения** | Сколько мест в хосте должны измениться, чтобы добавить движок; цель — одна (регистрация) |
| **Совместимость** | `md-core` остаётся дефолтным; поведение предпросмотра, инспектора и scrollsync не меняется |
| **Форма выхода** | Решение по §4 п.1, оформленное как формальный контракт |
| **Метрики** | Латентность рендера (в т.ч. в пределах debounce 120 мс), стоимость сериализации render-data, размер и старт WASM-движка, число точек расширения |
| **Ограничения** | D2/D6/D16, §13.2 и e2e зелёные; три точки `innerHTML` не расширяются |

**Где живут числа:** `docs/FINDINGS.md`, форма «гипотеза → замер → вывод» (D15). Использованные
факты — `F1–F63`, следующий свободный номер — **F64**. Стенд (`crates/engine-spike`) в продукт не
входит и удаляется после реализации — как предыдущие `crates/*-spike`.

**Минимальный объём стенда** (чтобы не раздувать спайк, по образцу Q10 IDEA-004-СПАЙК):
реестр с одним регистрируемым движком + один второй движок-заглушка, отдающий не-Markdown,
плюс замеры по четырём метрикам. Без этого «доказать подключаемость» нельзя.
